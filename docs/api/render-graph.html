API reference

Render graph and custom passes

A render graph is a list of passes. Each pass says what it reads and writes, and records its commands in a callback. The graph puts the passes in an order that respects those reads and writes, then runs them every frame between beginFrame and endFrame. Use it when one render call is not enough: offscreen targets, post effects, compute work.

CPU work GPU work GPU buffer or texture your callback

In short

  • Create targets and buffers in the setup callback, and declare them with read / write. Only these declarations order the passes.
  • A graphics pass draws into exactly one target: the render target it writes, or the swapchain with writeSwapchain(). The first pass that draws a target clears it; later passes on the same target draw on top.
  • For last frame's image (accumulation, trails, temporal effects), create the target with history = true and declare readPrevious(rt).
  • Any other target from builder.createRenderTarget is transient: targets that are never used at the same time share memory. Set swapchainScale = 1.0f to make a target follow the window size.
  • The graph records the barriers and layout changes from what the passes declare. Declare every buffer and texture a pass uses: an undeclared one gets no barrier.
  • A compute pass runs outside any render pass, so it can dispatch.
  • Inside a callback, record with the RenderContext and the frame's command buffer: engine.getCurrentFrameResources().commandBuffer.
  • Pipelines for your own shaders come from createPipeline and createComputePipeline, compiled from Slang source at run time.

1The graph

RenderGraph createRenderGraph();

Returns an empty graph tied to this engine. Keep it alive for as long as you call execute, and keep everything its callbacks capture by reference alive too.

class RenderGraph
{
public:
         RenderGraph(Engine* owner);
    void addPass(std::string name,
             const std::function<void(PassBuilder&)>& setup,
             std::function<void(RenderContext&)> execute);
    void addComputePass(std::string name,
             const std::function<void(PassBuilder&)>& setup,
             std::function<void(RenderContext&)> execute);
    void compile();
    void execute(CameraHandle camera);
};

The pass list and its order. Make one with createRenderGraph rather than with the constructor. Passes cannot be removed; build a new graph to change the frame.

void addPass(std::string name,
         const std::function<void(PassBuilder&)>& setup,
         std::function<void(RenderContext&)> execute);

Adds a graphics pass. setup is called right away, before addPass returns, so handles it creates are ready on the next line. The graph must be compiled again (execute does it if you don't).

name
A label. It names the pass's GPU timer in the frame stats.
setup
Gets a PassBuilder. Create resources and declare reads and writes here.
execute
Called every frame between beginPass and endPass, so draws are allowed and dispatches and barriers are not. The viewport and scissor cover the whole target, and the cull mode is NONE.

target The target is the render target the pass writes, or the swapchain image after writeSwapchain(). A graphics pass must declare exactly one of them, or compile fails. The first pass in the frame that draws a target clears it: color to the target's clearColor (the swapchain uses a dark gray), depth to 0. A later pass on the same target keeps color and depth and draws on top (see Load and store).

void addComputePass(std::string name,
         const std::function<void(PassBuilder&)>& setup,
         std::function<void(RenderContext&)> execute);

Adds a compute pass. It is sorted like any other pass. execute runs outside any render pass, so dispatch and memoryBarrier are allowed and draws are not. There is no target, no clear and no layout transition.

errors A render target or swapchain write declared in setup logs Compute pass '…' cannot write a render target or the swapchain; the write is ignored. and is dropped. A compute pass must write at least one buffer, since compute writes only buffers: without one, compile fails with Compute pass '…' declares no buffer write; declare every buffer it uses.

The graph adds a barrier before the pass only for a buffer it declares that another pass (or the previous frame) wrote or read; see Barriers. A pass with several dependent dispatches records ctx.memoryBarrier(commandBuffer, PipelineStage::COMPUTE, PipelineStage::COMPUTE) between them itself.

2Declaring reads and writes

class PassBuilder
{
public:
                       PassBuilder(RenderGraph& g, uint32_t passIdx);
    TextureHandle      createTexture(const TextureDesc& desc);
    BufferHandle       createBuffer(const BufferDesc& desc);
    RenderTargetHandle createRenderTarget(const RenderTargetDesc& desc);
    void               read(TextureHandle handle);
    void               read(BufferHandle handle);
    void               read(RenderTargetHandle handle);
    void               readPrevious(RenderTargetHandle handle);
    void               write(TextureHandle handle);
    void               write(BufferHandle handle);
    void               write(RenderTargetHandle rt);
    void               writeSwapchain();
};

Given to your setup callback. It records what one pass uses. The graph makes it; you do not construct one.

TextureHandle      createTexture(const TextureDesc& desc);
BufferHandle       createBuffer(const BufferDesc& desc);
RenderTargetHandle createRenderTarget(const RenderTargetDesc& desc);

The same as Engine::createTexture, Engine::createBuffer and Engine::createRenderTarget. They do not declare a read or write: call read or write too. A render target without history is transient: the graph owns its memory and shares it with other transient targets. Textures, buffers and history targets live until the engine shuts down (D4); transient targets are freed with the graph.

void read(TextureHandle handle);
void read(BufferHandle handle);
void read(RenderTargetHandle handle);

This pass reads the resource. If another pass writes it, that pass runs first. A read of something no pass writes adds no order. Declaring a read does not bind anything: the pass still finds the data itself (a bindless index, a device address). It does decide the barriers: a texture or render target read is moved to SAMPLED before the pass, and a buffer read waits for the last write (see Barriers).

void readPrevious(RenderTargetHandle handle);

This pass reads the color the previous frame drew into handle. Fetch it with getPreviousRenderTargetTexture. The target must be created with history = true (see History). The read adds no edge, because nothing this frame writes that copy, so a pass may read the previous copy of the target it draws to: that is how accumulation works. The copy is always ready to sample: the frame before drew it, or it is new and was cleared to clearColor at the start of the frame.

errors A target without history logs Pass '…' reads the previous frame of a render target created without history; the read is ignored. during addPass.

void write(TextureHandle handle);
void write(BufferHandle handle);

This pass writes the resource, so passes that read it run after this one. If several passes write the same resource, the last one added is the one readers wait for. Writing a buffer makes the pass wait for every earlier use of it. Writing a texture does not make it an attachment, and records no barrier, since no shader can write a texture yet; only a render target is drawn into.

void write(RenderTargetHandle rt);

This graphics pass draws into rt. A pass has one output target: a second call replaces the first. Passes that draw into the same rt run in the order they were added, and a pass that reads rt runs after the last of them.

void writeSwapchain();

This graphics pass draws into this frame's swapchain image: the window. Passes that draw into the swapchain run in the order they were added. A pass that declares neither write(rt) nor writeSwapchain(), or both, makes compile fail with Pass '…' must write either one render target or the swapchain.

struct Pass
{
    std::string                         name;
    std::vector<TextureHandle>          inputTextures;
    std::vector<BufferHandle>           inputBuffers;
    std::vector<RenderTargetHandle>     inputRenderTargets;
    std::vector<RenderTargetHandle>     previousRenderTargets;
    std::vector<TextureHandle>          outputTextures;
    std::vector<BufferHandle>           outputBuffers;
    RenderTargetHandle                  outputRenderTarget;
    std::function<void(RenderContext&)> execute;
    AttachmentOps                       attachmentOps;
    bool                                compute         = false;
    bool                                writesSwapchain = false;

    uint32_t                inDegree = 0;
    std::vector<uint32_t>   successors;
};

What the graph stores per pass. read and write fill the input and output lists, readPrevious fills previousRenderTargets, and writeSwapchain sets writesSwapchain. compile fills attachmentOps (see Load and store). inDegree and successors are filled by compile: the number of passes that must run first, and the passes that wait for this one. You never build a Pass yourself.

struct ResourceMetadata
{
    uint32_t producerIdx = static_cast<uint32_t>(-1);
};

Declared in rasm/render/renderGraph.h, but nothing uses it: compile keeps its producer maps locally.

struct BufferAccess
{
    PipelineStage   writeStages = {};
    PipelineStage   readStages  = {};
};

A protected type inside RenderGraph: what the graph remembers about each buffer a pass declares. writeStages is the stage of the last write (none before the first), and readStages the stages that have read it since, behind a barrier. It is kept across frames, and only execute changes it. You never build one yourself.

3Compile and execute

void compile();

Builds one edge from the writer of each resource to every pass that reads it, and one from each pass that draws into a target to the next pass added that draws into the same target. Then it sorts the passes (Kahn's algorithm). Does nothing if the graph is already compiled. execute calls it when a pass was added since the last compile, so calling it yourself only moves the work (and its log line) to start-up.

errors A cycle (A reads what B writes and B reads what A writes) logs Frame Graph contains a cycle! and leaves no pass to run. The graph stays uncompiled, so each execute tries again and logs again. Frames still run and present a cleared image, so the window keeps responding.

void execute(CameraHandle camera);

Runs one whole frame: beginFrame(camera), every pass in order, endFrame. Call it once per loop instead of render. The results show on screen when the frame is presented.

camera
Gets this frame's mouse and keyboard input (through pollEvents). It is not given to the passes: a pass that calls drawScene names its own camera.

When beginFrame returns false (window minimized, swapchain being re-created, failed wait), no pass runs that frame. If no pass draws into the swapchain, endFrame clears it so it can be presented. If the transient targets cannot be placed (out of memory), no pass runs either, and the graph tries again the next frame.

Barriers

Before each pass begins, execute records what its reads and writes need. A pass is COMPUTE or GRAPHICS as a whole.

All of a pass's buffers share one global barrier. A buffer or texture the pass uses without declaring it gets nothing, so declare everything it touches. The graph knows only its own passes: a buffer shared with another graph, or with work outside the graph, is not ordered.

errors compile fails, like on a cycle, for declarations that cannot be right: a pass that reads the render target it draws to (Pass '…' reads the render target it draws to.), a compute pass with no buffer write, a graphics pass that does not write exactly one render target or the swapchain, and a read of a transient target that no earlier pass draws. The frames then draw no passes until the graph changes.

RenderTargetHandle createRenderTarget(const RenderTargetDesc& desc);

Creates an offscreen color + depth target and makes its color bindless: one pair that every frame draws, or one pair per frame slot when desc.history is set. Ready at once. With swapchainScale it is rebuilt at the new size when the window resizes; the handle stays the same. A pass draws into it after builder.write(rt), or after setRenderTarget(rt) in a hand-written frame.

errors If a texture cannot be created or the bindless set is full, it logs an error, destroys what it created, and returns an invalid handle.

struct RenderTargetDesc
{
    std::string name;
    uint32_t    width          = 0;
    uint32_t    height         = 0;
    float       swapchainScale = 0.0f;
    Format      colorFormats[MAX_COLOR_ATTACHMENTS] = {};
    Format      depthFormat    = Format::UNKNOWN;
    glm::vec4   clearColor     = glm::vec4(0.0f);
    bool        history        = false;

    bool operator==(const RenderTargetDesc&) const = default;
};
name
A label. The textures are named "<name> Color Texture" (then "<name> Color Texture 1", …) and "<name> Depth Texture" in debug tools.
width, height
Pixels. Used when swapchainScale is 0.
swapchainScale
Above 0: the size is the window's (the swapchain's, in pixels) times this, at least 1 × 1, and follows each resize. 1.0f for full size, 0.5f for half. A rebuilt history target loses last frame's image, and its first read after the resize sees clearColor.
colorFormats
One format per color attachment, up to MAX_COLOR_ATTACHMENTS (4); the list ends at the first UNKNOWN, so .colorFormats = {format} makes one. At least one is needed. For drawScene, or a pipeline from the two-argument createPipeline, use one attachment in the swapchain format: engine.getRenderContext().getSwapchainImageFormat(). For several, make the pipeline with createPipeline(name, source, renderTarget).
depthFormat
Needed: every pass binds a depth attachment. Use Format::D32_SFLOAT for the same reason. Only a D32_SFLOAT depth can be sampled, which occlusion culling needs.
clearColor
Linear color, the same for every color attachment. The first pass that writes the target clears to it, and each new history copy is cleared to it before the next frame's passes.
history
true keeps one copy per frame slot, so a pass can read last frame's color with readPrevious. It costs twice the memory. Leave it false for a target that is drawn and read in the same frame.

The full target, with its per-slot textures, is the RenderTarget that RenderContext::getRenderTarget returns.

TextureHandle getRenderTargetTexture(const RenderTargetHandle& renderTarget, uint32_t attachment = 0);

The color texture this frame draws, of color attachment attachment (invalid past the target's last one). For a history target it changes every frame, so fetch it every frame, inside the pass that reads it. Pass it to getBindlessTextureIndex to get the index a shader samples with. endPass leaves it in the sampled layout. In a graph, declare read(rt) so the pass sorts after the one that draws it. An unknown handle logs Render target handle not found. and returns an invalid handle.

TextureHandle getPreviousRenderTargetTexture(const RenderTargetHandle& renderTarget, uint32_t attachment = 0);

The color texture of attachment attachment that the previous frame drew, for a pass that declared readPrevious(renderTarget). Fetch it every frame and pass it to getBindlessTextureIndex. Returns an invalid handle for a target created without history. A copy that no frame drew yet holds clearColor, also outside a graph.

History

Transient render targets

A render target made with builder.createRenderTarget and no history is transient. It belongs to the graph and lives only from the first pass that uses it to the last. After each compile, the graph places all transient targets in shared heaps: two targets whose lifetimes do not overlap get the same memory.

  • The handle is ready at once, but the textures exist only from the first execute after a compile. Fetch them inside a pass that declares the target.
  • A transient target's contents are gone after its last pass. Read it in a later frame, or before a pass draws it, and you read another target's data. compile fails when the first pass that uses one reads it: Pass '…' reads a transient render target that no pass before it draws.
  • For a target that must keep its contents between frames, use history = true, or Engine::createRenderTarget.
  • Before the first pass of each transient target, the graph records an aliasingBarrier, so its writes wait for the target that used the memory before, last frame's included.
  • A compile that changes when the targets are used lays the memory out again: it waits for the GPU to be idle first, so add passes before the loop.
  • The transient targets and their memory are freed when the graph is destroyed, after the GPU is idle. A RenderGraph can be moved, not copied.
void setRenderTarget(const RenderTargetHandle& renderTarget);

The next beginPass draws into this target instead of the swapchain. For frames you write by hand with beginFrame / beginPass; RenderGraph::execute calls it for each pass from the pass's write.

void resetRenderTarget();

The next beginPass draws into the swapchain again.

// A hand-written frame with an offscreen pass (what the graph does for you)
if (engine.beginFrame(camera))
{
    engine.setRenderTarget(rt);
    engine.beginPass("Offscreen");
    engine.drawScene(scene, camera);
    engine.endPass();
    engine.resetRenderTarget(); // endPass left rt's color ready to sample

    engine.beginPass("Present"); // swapchain; sample rt here
    // ... bind a pipeline and draw
    engine.endPass();
    engine.endFrame();
}

PipelineHandle createPipeline(const std::string& name,
                              const std::string& shaderSource);

Compiles shaderSource (Slang) twice, for vertMain and fragMain, and makes a graphics pipeline from them. It compiles at once, on the calling thread, which can take a moment: create pipelines before the loop, not every frame.

name
A label for logs and debug tools. Two pipelines may share one name.
shaderSource
The full Slang source, as a string (a raw string literal works well, see below). The same name and source give back the same pipeline.

errors A compile error is logged with Slang's message and the call returns an invalid handle. Binding the pipeline in a pass whose attachments have other formats logs an error and skips the pass's draws.

PipelineHandle createPipeline(const std::string& name,
                              const std::string& shaderSource,
                              const RenderTargetHandle& renderTarget);

The same, but the pipeline draws into targets with renderTarget's formats: its color formats, in order, and its depth format. Use it for a target with several color attachments, or with formats other than the swapchain's. The target's textures need not exist yet: a transient target's handle is enough. In the shader, fragMain returns a struct with one output per attachment, in the target's order:

struct Targets
{
    float4 color : SV_TARGET0;
    float4 mask : SV_TARGET1;
};

errors A target with no color formats (or an unknown handle) logs Pipeline '…' needs a render target with color formats. and returns an invalid handle.

PipelineHandle createComputePipeline(
    const std::string& name,
    const std::string& shaderSource,
    const std::string& entryPoint = "compMain");

Compiles one compute entry point of shaderSource and makes a compute pipeline. Bind it in a compute pass, push constants with ShaderType::COMPUTE, then dispatch.

entryPoint
The [shader("compute")] function to use. One source can hold several, as shaders/passes/cull.slang does.

errors A compile error, or a missing entry point, logs an error and returns an invalid handle.

6Timing your own GPU work

uint32_t beginGpuTimer(const CommandBufferHandle& commandBuffer,
                       const std::string& name);

Writes a start timestamp into the frame's command buffer and returns a timer id. Call it between beginFrame and endFrame, with getCurrentFrameResources().commandBuffer. The graph already times every pass by its name, so use this for a part of a pass.

Returns UINT32_MAX (which endGpuTimer ignores) when nothing is measured: the stats overlay is off and getFrameStats was never called, the GPU has no timestamps, or the frame already used all timers. A frame has MAX_GPU_TIMERS (16) timers: one for the whole frame, one kept for culling, and 14 for the passes and your timers together. The first time they run out, a warning is logged.

void endGpuTimer(const CommandBufferHandle& commandBuffer, uint32_t timer);

Writes the end timestamp of timer. The time appears in FrameStats::gpuTimers under the timer's name MAX_FRAMES_IN_FLIGHT frames later, when that frame slot is reused. See getFrameStats.

7Complete examples

Offscreen scene, trail and full-screen passes (examples/01_render_graph)

// Shortened from examples/01_render_graph/main.cpp
rasm::RenderGraph graph = engine.createRenderGraph();
const rasm::Format colorFormat = engine.getRenderContext().getSwapchainImageFormat();

// No history: transient. It lives from "Forward" to "Trail".
rasm::RenderTargetHandle rtHandle{};
graph.addPass(
    "Forward",
    [&](rasm::PassBuilder &builder)
    {
        rtHandle = builder.createRenderTarget({
            .name = "offscreen_rt",
            .swapchainScale = 1.0f,
            .colorFormats = {colorFormat},
            .depthFormat = rasm::Format::D32_SFLOAT,
            .clearColor = glm::vec4(0.0f),
        });
        builder.write(rtHandle);
    },

    [&](rasm::RenderContext &)
    {
        engine.drawScene(scene, camera);
    });

// fullScreenTriangle is Slang source: a vertMain that covers the screen, the bindless
// array, and push constants with two texture indices. Each pipeline adds its fragMain.
auto trailPipeline = engine.createPipeline("trail", fullScreenTriangle + trailFragment);
auto presentPipeline = engine.createPipeline("present", fullScreenTriangle + presentFragment);

auto drawFullScreen = [&engine](rasm::RenderContext &ctx, rasm::PipelineHandle pipeline, uint32_t first, uint32_t second)
{
    auto commandBuffer = engine.getCurrentFrameResources().commandBuffer;
    const uint32_t indices[2] = {first, second};
    ctx.bindPipeline(commandBuffer, pipeline);
    ctx.bindDescriptorSet(commandBuffer, pipeline, engine.getBindlessDescriptorSet(), 0);
    ctx.pushConstants(commandBuffer, pipeline, rasm::ShaderType::VERTEX_FRAGMENT, indices, sizeof(indices), 0);
    ctx.draw(commandBuffer, 3);
};

// History: one copy per frame slot, so the pass reads last frame's trail.
rasm::RenderTargetHandle trailHandle{};
graph.addPass(
    "Trail",
    [&](rasm::PassBuilder &builder)
    {
        trailHandle = builder.createRenderTarget({
            .name = "trail_rt",
            .swapchainScale = 1.0f,
            .colorFormats = {colorFormat},
            .depthFormat = rasm::Format::D32_SFLOAT,
            .clearColor = glm::vec4(0.0f),
            .history = true,
        });
        builder.read(rtHandle);            // runs after "Forward"
        builder.readPrevious(trailHandle); // last frame's trail
        builder.write(trailHandle);        // this frame's trail
    },

    [&](rasm::RenderContext &ctx)
    {
        drawFullScreen(ctx, trailPipeline, engine.getBindlessTextureIndex(engine.getRenderTargetTexture(rtHandle)),
                       engine.getBindlessTextureIndex(engine.getPreviousRenderTargetTexture(trailHandle)));
    });

// Transient. It starts after offscreen_rt's last pass, so the two share memory.
// Two color attachments: the trail's color, and a mask of where the bunny is.
rasm::RenderTargetHandle compositeHandle{};
rasm::PipelineHandle backgroundPipeline{};
graph.addPass(
    "Background",
    [&](rasm::PassBuilder &builder)
    {
        compositeHandle = builder.createRenderTarget({
            .name = "composite_rt",
            .swapchainScale = 1.0f,
            .colorFormats = {colorFormat, rasm::Format::R8G8B8A8_UNORM},
            .depthFormat = rasm::Format::D32_SFLOAT,
        });
        builder.read(trailHandle);
        builder.write(compositeHandle);
    },

    [&](rasm::RenderContext &ctx)
    {
        drawFullScreen(ctx, backgroundPipeline, engine.getBindlessTextureIndex(engine.getRenderTargetTexture(trailHandle)), 0);
    });

// The pipeline takes both formats from the target. Its fragMain writes SV_TARGET0 and SV_TARGET1.
backgroundPipeline = engine.createPipeline("background", fullScreenTriangle + backgroundFragment, compositeHandle);

graph.addPass(
    "Present",
    [&](rasm::PassBuilder &builder)
    {
        builder.read(compositeHandle);
        builder.writeSwapchain();
    },

    [&](rasm::RenderContext &ctx)
    {
        // Green where the mask is 0
        drawFullScreen(ctx, presentPipeline, engine.getBindlessTextureIndex(engine.getRenderTargetTexture(compositeHandle, 0)),
                       engine.getBindlessTextureIndex(engine.getRenderTargetTexture(compositeHandle, 1)));
    });

graph.compile();
while (engine.running())
    graph.execute(camera);

Compute then draw (examples/04_compute)

// Shortened from examples/04_compute/main.cpp
rasm::BufferHandle particles = engine.createBuffer({.name = "Particle Positions",
                                                    .usage = rasm::BufferUsage::STORAGE,
                                                    .size = PARTICLE_COUNT * 2 * sizeof(float)});
const uint64_t particlesAddress = engine.getRenderContext().getBufferDeviceAddress(particles);

graph.addComputePass(
    "Animate",
    [&](rasm::PassBuilder &builder)
    {
        builder.write(particles);
    },

    [&](rasm::RenderContext &ctx)
    {
        auto commandBuffer = engine.getCurrentFrameResources().commandBuffer;
        const AnimatePushConstants pushConstants = {
            .positions = particlesAddress, // 8 bytes
            .count = PARTICLE_COUNT,       // 4 bytes
            .time = frame * FRAME_TIME};   // 4 bytes: 16 in all
        ctx.bindPipeline(commandBuffer, animatePipeline);
        ctx.pushConstants(commandBuffer, animatePipeline,
                          rasm::ShaderType::COMPUTE,
                          &pushConstants, sizeof(pushConstants));
        const uint32_t groups = (PARTICLE_COUNT + GROUP_SIZE - 1) / GROUP_SIZE;
        ctx.dispatch(commandBuffer, groups);
    });

graph.addPass(
    "Draw",
    [&](rasm::PassBuilder &builder)
    {
        builder.read(particles); // this pass runs after "Animate"
        builder.writeSwapchain();
    },

    [&](rasm::RenderContext &ctx)
    {
        auto commandBuffer = engine.getCurrentFrameResources().commandBuffer;
        // ... push the address, then three vertices per particle
        ctx.bindPipeline(commandBuffer, drawPipeline);
        ctx.pushConstants(commandBuffer, drawPipeline,
                          rasm::ShaderType::VERTEX_FRAGMENT,
                          &pushConstants, sizeof(pushConstants));
        ctx.draw(commandBuffer, PARTICLE_COUNT * 3);
    });

In the shader the address arrives as a pointer: float2* positions; in the push constant struct. See getBufferDeviceAddress.

8What the graph does not do

Known limits
  • Only render targets are transient. Textures and buffers from the builder, and history targets, live until shutdown (D4).
  • Depth is not kept between passes.
  • The early scene culling, which drawScene needs, runs on the GPU before every pass of the frame, including your compute passes (D18). The late culling runs inside the pass that calls drawScene.
  • Nothing can be destroyed: render targets, buffers and pipelines live until shutdown (D4).

How the graph works inside, with the barriers and layouts step by step: the guide Render graphs. To add a pass to the engine itself, see the new-pass skill in .claude/skills/.
