API reference

Engine

rasm::Engine is the one object your program creates. It opens the window, owns every scene object and GPU resource, and runs the frame. This page covers how to create it, the frame functions, loading, frame stats, paths and the window. The table below lists every method and the page that documents it.

2Create and shut down

engine setup GPU buffers and descriptor sets 
Engine(const EngineConfig& config);

Opens the main window and sets up the whole renderer. It also resolves shaderDir and assetRoot (see paths) and creates the default material. On any failure it logs an error and returns early, and running() stays false. A window width or height of 0 or less fails at once with "Window dimensions must be positive.".

config
Copied into the engine. Fields are in the EngineConfig table below (also on types.html).
rasm::Engine engine(config);
if (!engine.running())
    return 1;
~Engine();

Waits for background loads that are still running, frees every GPU resource, destroys the window and shuts SDL down. Scene objects cannot be destroyed earlier: there is no destroy function for scenes, entities, meshes, materials, cameras or lights yet (D4).

bool running() const;

True while the engine works. It becomes false when the window is closed or Esc is pressed (both handled in pollEvents, inside beginFrame), and it is false from the start when the constructor failed. Use it as the main loop condition.

struct EngineConfig   // include/rasm/types.h

All settings of the engine. Pass it to the constructor; later changes to your copy have no effect. Use designated initializers and leave out what you do not need.

Geometry and instance rows are never freed (D4). When a pool is full, the next mesh or entity fails with an error that names the EngineConfig field to raise. Size the pools for everything your program will ever load.

3Run a frame

A frame is beginFrame, then one or more passes, then endFrame. render does all of it for one scene, through a render graph with the scene's passes. Here is what each part does inside:

engine work on the CPU uploads to GPU buffers 
void render(SceneHandle scene, CameraHandle camera);

One whole frame of the scene, drawn into the window. The engine keeps a render graph with the scene's passes (addScenePasses into the swapchain) and runs it with RenderGraph::execute: beginFrame(camera), the passes, endFrame. It builds the graph again only when scene or camera is not the same as in the last call. When beginFrame returns false, no pass runs.

scene
The scene to draw. Invalid: an error is logged once, and the window is only cleared.
camera
Gets this frame's input (mouse, keys) and is the view. It does not need to be in the scene.
while (engine.running())
    engine.render(scene, camera);
[[nodiscard]] bool beginFrame(CameraHandle camera);

Starts a frame (steps in the diagram above). It handles window events and moves camera with the input, finishes background loads for up to 4 ms, waits until this frame slot is free, uploads changed scene data, acquires a window image and starts the frame's command buffer.

camera
The camera that the mouse and keyboard move. Invalid: "Invalid camera handle." is logged every frame, and the frame still runs.
returns
false when the frame must be skipped: window minimized or 0 pixels wide, swapchain rebuild failed, fence wait failed, or the image could not be acquired. Then record nothing and do not call endFrame.

may block It waits for the GPU when the CPU is 2 frames ahead.

void endFrame();

Ends the frame's command buffer and sends the frame to the GPU, then shows it in the window. If no pass drew to the window this frame (for example, all passes drew to render targets), it adds a pass that clears the window first. With the stats overlay shown, it draws the overlay in a pass of its own on top. The frame is one command buffer: culling is recorded in it as ordinary scene passes.

Call it only after a beginFrame that returned true, and after the last endPass.

void beginPass(const std::string& name = "Pass", const AttachmentOps& ops = {});

Starts rendering into the current target: the window, or the render target set with setRenderTarget. By default it clears color and depth (their old contents are dropped), sets the viewport and scissor to the whole target, and sets cull mode to none. Only between beginFrame and endFrame.

name
Label of the pass. It names the pass's GPU timer in getFrameStats and the stats overlay.
ops
Which attachments to keep instead of clearing, and whether to keep depth at the end. See AttachmentOps. A render graph sets them for you.

The window is cleared to a dark gray. A render target is cleared to its own clearColor.

struct AttachmentOps
{
    bool loadColor  = false;
    bool loadDepth  = false;
    bool storeDepth = false;
};

What a pass does with its attachments. The defaults clear both and throw depth away at the end.

loadColor, loadDepth
true: keep what the attachment holds, and draw on top. false: clear it (color to the target's clear color, depth to 0).
storeDepth
true: keep depth at the end of the pass, for a later pass that loads it or samples it. Color is always kept. A render graph sets it on the pass before one that loads the target or reads its depth (readDepth).
// A hand-written frame: two passes on the window, the second on top of the first
engine.beginPass("Background", {.storeDepth = true});
// ... draw the background
engine.endPass();
engine.beginPass("UI", {.loadColor = true, .loadDepth = true});
// ... draw the UI
engine.endPass();
void endPass();

Ends the pass. On a render target, it moves the color image to the sampled layout, so later passes can sample it (see getRenderTargetTexture). The depth image stays a depth attachment; in a graph, a later pass that declares readDepth gets it moved to the sampled layout. endFrame moves the swapchain image to the present layout.

bool addScenePasses(RenderGraph& graph, SceneHandle scene, CameraHandle camera, const RenderTargetHandle& renderTarget = {});

Adds the passes that draw scene from camera to graph. They are ordinary graph passes: the graph sorts them with your passes, records their barriers from what they declare, and times each one under its name. render calls it for you; call it yourself when you build your own graph.

graph
The graph to add to, before its compile. Add your own passes before or after.
scene
Invalid: logs addScenePasses needs a valid scene handle., adds nothing and returns false.
camera
The view. Its projection is fitted to the target's aspect ratio every frame; the camera itself does not change. Invalid: logs an error, adds nothing and returns false.
renderTarget
Where the scene is drawn. Invalid (the default): the window, through the swapchain. A target needs one color in the swapchain's format and D32_SFLOAT depth, the formats of the scene's pipeline. Make it with RenderGraph::createRenderTarget before this call.
returns
true when the passes were added. On false nothing was added.
scene passes, run on the GPU the target 
// From examples/01_render_graph/main.cpp: the scene into an offscreen target
const rasm::RenderTargetHandle rtHandle = graph.createRenderTarget({
    .name = "offscreen_rt",
    .swapchainScale = 1.0f,
    .colorFormats = {colorFormat},
    .depthFormat = rasm::Format::D32_SFLOAT,
    .clearColor = glm::vec4(0.0f), // alpha 0 marks the background
});

// The scene's culling and draw passes, into offscreen_rt. The passes below read what they drew.
if (!engine.addScenePasses(graph, scene, camera, rtHandle))
{
    return 1;
}

Scene views. Each (scene, camera, target) is a scene view, with its own culling buffers on the GPU. A view lives while a graph holds it: graphs built for the same three share it, and when the last of them is destroyed or replaced, the view's buffers are freed. Views let one frame draw several scenes, cameras or targets. The scene's lights are read every frame. Nothing is drawn, with no error, while the scene is empty or all its entities still load: the target keeps its clear color.

Culling also picks each visible draw's level of detail from its distance to the camera and EngineConfig::lodErrorPixels. A view drawn without culling draws LOD 0.

RuleWhat happens otherwise
At most MAX_SCENE_VIEWS (8) scene views held by graphs at onceAn error ("At most 8 views (scene, camera, target) can be held by render graphs at once."), nothing added, false
One graph adds each scene view onceAn error, nothing added, false
A render target has one color in the window's format and D32_SFLOAT depthAn error, nothing added, false
The scene shader passes/rasm.slang must compileAn error is logged; the engine tries again next frame, so a fixed shader file is picked up while the program runs
The culling shader passes/cull.slang should compileThe scene is still drawn, only without culling. Without passes/hiz.slang, or when the view's occlusion buffers cannot be made, it is frustum culled only.
const FrameResources& getCurrentFrameResources();

The current frame slot's FrameResources: commandBuffer (record your own draws and dispatches into it), depthTexture (the window pass's depth) and fenceValue. Fetch it every frame, because the slot changes every frame. The depth textures are replaced on resize.

auto commandBuffer = engine.getCurrentFrameResources().commandBuffer;
ctx.bindPipeline(commandBuffer, pipeline);
ctx.draw(commandBuffer, 3);
bool recreateSwapchain();

Rebuilds the swapchain, the depth textures, and the aspect ratio of every camera, from the window's current pixel size. beginFrame already calls it after a resize or an out-of-date swapchain, so a program does not need to.

returns
false while the window has 0 pixels, or when the rebuild failed. beginFrame then tries again next frame.

4Loading and waiting

void waitForLoads();

Finishes every pending mesh and texture load now: it waits for the worker threads and uploads the results, with no time limit. After it returns, isLoaded is true for every successful load. Entities that use them join their scenes' draw lists at the next beginFrame, so the first frame after it shows everything.

blocks the main thread Use it before the main loop to avoid objects popping in, or in tests. Do not call it every frame.

auto mesh = engine.loadGLTF("models/gltf/coffee-room/scene.gltf");
engine.waitForLoads();
bool ok = engine.isLoaded(mesh); // false if the file failed to parse

5Frame stats

GPU work CPU work 
const FrameStats& getFrameStats() const;

The latest measured frame. The first call turns measuring on for every later frame, so the values fill in a few frames later. The reference stays valid; read it every frame.

const rasm::FrameStats &stats = engine.getFrameStats();
for (uint32_t i = 0; i < stats.gpuTimerCount; ++i)
    std::printf("%s: %.2f ms\n", stats.gpuTimers[i].name.c_str(), stats.gpuTimers[i].milliseconds);
struct FrameStats
cpuFrameMs
Time between the last two frames on the CPU, in ms. Capped at 100 ms. Updated every frame, even when not measuring.
gpuFrameMs
GPU time of the whole frame (all passes), in ms. 0 on a GPU without timestamps.
gpuTimers
One GpuTimer per pass (graphics or compute, the scene passes included) and per timer of your own, in GPU start order. Room for MAX_GPU_TIMERS - 1 (15).
gpuTimerCount
How many entries of gpuTimers are filled.
draws
Draws of all scene views the frame drew, before culling (one per sub-mesh of each entity).
drawsVisible
Draws that passed culling: inside the view, and with occlusion culling also not hidden. Draws of a view drawn without culling all count.
triangles
Triangles before culling, at LOD 0.
trianglesVisible
Triangles of the visible draws, at the LOD culling picked for each.
trianglesVisibleLod0
Triangles of the same visible draws at LOD 0. trianglesVisibleLod0 - trianglesVisible is what LODs saved this frame.
drawsPerLod
Visible draws at each LOD, from LOD 0 to MAX_MESH_LODS - 1. They add up to drawsVisible.
memory
VRAMStats of that frame (see queryMemoryStats).
struct GpuTimer
name
The pass name (for the scene passes: "Cull 1", "Scene 1", "Hi-Z", "Cull 2", "Scene 2", or "Cull" and "Scene"), or the name you gave beginGpuTimer.
milliseconds
GPU time between the timer's start and end, in ms.
uint32_t beginGpuTimer(const CommandBufferHandle& commandBuffer, const std::string& name);

Writes a start timestamp into the frame's command buffer. The GPU time until the matching endGpuTimer appears in getFrameStats and the overlay. Passes and render graph compute passes are already timed for you.

commandBuffer
The frame's command buffer, from getCurrentFrameResources.
name
Label in the stats.
returns
The timer id, or UINT32_MAX when nothing is measured: measuring is off, the GPU has no timestamps, or the frame used all its timers (a warning is logged once).

A frame has MAX_GPU_TIMERS (16) timers: one for the whole frame, and 15 for passes and your timers together.

void endGpuTimer(const CommandBufferHandle& commandBuffer, uint32_t timer);

Writes the end timestamp of timer. It does nothing for UINT32_MAX, so you can always pass what beginGpuTimer returned.

const uint32_t timer = engine.beginGpuTimer(commandBuffer, "Particles");
ctx.dispatch(commandBuffer, groupCount);
engine.endGpuTimer(commandBuffer, timer);
VRAMStats queryMemoryStats();

Asks the GPU memory allocator now. Returns vramBudget and vramUsage (device-local memory) and hostBudget and hostUsage (host-visible memory), all in bytes. See VRAMStats.

shaderDir follows the same rule against the executable's folder, with the build-time default when empty. Paths are UTF-8, so folders with non-Latin names work.

std::string resolveAssetPath(const std::string& path) const;

Joins path to the resolved assetRoot, as every loader does, and returns it as UTF-8 with forward slashes. Useful to check where a file is looked for, or to open your own files from the same folder.

EngineConfig getConfig() const;

A copy of the engine's config. shaderDir and assetRoot are the resolved paths (an empty assetRoot stays empty), and showStats is its current value (F1 changes it). Changing the copy changes nothing in the engine.

7The window

Built-in keys

Esc or closing the window: running() becomes false.
F1: shows or hides the stats overlay.
F2: cycles forcedLod: by distance, LOD 0, 1, … 7, by distance.
Mouse and WASD: move the camera passed to beginFrame (see camera.html).

Two sizes

width, height: logical size, the unit of mouse positions.
pixelWidth, pixelHeight: the drawable size. They differ on HiDPI screens. The swapchain, depth and viewports use the pixel size.

The engine owns the window and the input

Events are read inside beginFrame, and your program does not see them. You cannot render into a window you made yourself, or run without a window (D7).

const Window& getMainWindow() const;

The window the engine renders to, with its current sizes and state (minimized, resized, mouse drag). It updates in beginFrame. Use the pixel size for viewports, like examples/01_render_graph/main.cpp does. Fields are in types.html.

const auto &window = engine.getMainWindow();
const float width = static_cast<float>(window.pixelWidth);
const float height = static_cast<float>(window.pixelHeight);
const float aspect = width / height;
Window createWindow(uint32_t width, uint32_t height);

Starts SDL and opens a resizable Vulkan window titled "RASM Engine". The constructor calls it for the main window. A program has no use for it: a second window gets no rendering. Returns a Window with an invalid handle on failure (logged).

void destroyWindow(const Window& window);

Closes the window and shuts SDL down. The destructor calls it for the main window; do not call it on the main window yourself. docs/code_review.md lists both window functions among the calls that should leave the public API for a platform layer (D2, D7).

8Raw GPU resources

For your own passes you may need buffers and textures that are not part of a scene. These two functions forward to RenderContext. The descriptors (BufferDesc, TextureDesc) and how to fill, read and bind the resources are on RenderContext and resources.

BufferHandle createBuffer(const BufferDesc& desc);

Creates a new GPU buffer, every call (two equal descriptors give two buffers). Returns an invalid handle and logs an error on failure. It is device-local unless hostVisible is set. RenderContext::destroyBuffer frees it.

rasm::BufferHandle particles = engine.createBuffer({.name = "Particle Positions",
                                                    .usage = rasm::BufferUsage::STORAGE,
                                                    .size = PARTICLE_COUNT * 2 * sizeof(float)});
const uint64_t address = engine.getRenderContext().getBufferDeviceAddress(particles);

From examples/04_compute/main.cpp: a shader reads and writes the buffer through its device address.

TextureHandle createTexture(const TextureDesc& desc);

Creates a new, empty texture. Fill it with RenderContext::fillTexture, and add it to the bindless set (addBindlessTexture) to sample it in a shader. For image files use loadTexture instead. Returns an invalid handle on failure.
