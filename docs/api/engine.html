2Create and shut down

engine setup GPU buffers and descriptor sets 
Engine(const EngineConfig& config);

Opens the main window and sets up the whole renderer. It also resolves shaderDir, assetRoot and cacheDir (see paths) and creates the default material. On any failure it logs an error and returns early, and running() stays false. A window width or height of 0 or less fails at once with "Window dimensions must be positive.".

config
Copied into the engine. Fields are in the EngineConfig table below (also on types.html).
rasm::Engine engine(config);
if (!engine.running())
    return 1;
~Engine();

Waits for background loads that are still running, frees every GPU resource, destroys the window and shuts SDL down. Objects can be destroyed earlier, one by one: see destroyEntity, destroyMesh and the other destroy* calls in the table above.

bool running() const;

True while the engine works. With the SDL platform it becomes false when the window is closed or Esc is pressed (both handled in pollEvents, which beginFrame calls unless you did); with NATIVE or HEADLESS the application decides when to stop, and it stays true. It is false from the start when the constructor failed. Use it as the main loop condition.

The pools never shrink

A destroyed mesh gives its geometry ranges back, and a destroyed entity its instance rows (deferred destruction). When a pool is full, the next mesh or entity fails with an error that names the EngineConfig field to raise and the largest free range. Size the pools for what is alive at once, with room for fragmentation.

3Run a frame

A frame is beginFrame, then one or more passes, then endFrame. render does all of it for one scene, through a render graph with the scene's passes. Here is what each part does inside:

engine work on the CPU uploads to GPU buffers 
void render(SceneHandle scene, CameraHandle camera);

One whole frame of the scene, drawn into the window. The engine keeps a render graph with the scene's passes (addScenePasses into a 16-bit float target, with EngineConfig::bloom addBloomPasses, then addToneMapPass into the swapchain, and with EngineConfig::ui addUiPass over it) and runs it with RenderGraph::execute: beginFrame(camera), the passes, endFrame. It builds the graph again only when scene or camera is not the same as in the last call, also after a failure: a view whose passes could not be added is not tried again until one of them changes. When beginFrame returns false, no pass runs.

scene
The scene to draw. Invalid: an error is logged once, and the window is only cleared.
camera
Gets this frame's input (mouse, keys) and is the view. It does not need to be in the scene.
while (engine.running())
    engine.render(scene, camera);
[[nodiscard]] bool beginFrame(CameraHandle camera);

Starts a frame (steps in the diagram above). It handles window events and moves camera with the input, finishes background loads for up to 4 ms, waits until this frame slot is free, uploads changed scene data, acquires a window image and starts the frame's command buffer.

camera
The camera that the mouse and keyboard move. Invalid: "Invalid camera handle." is logged every frame, and the frame still runs.
returns
false when the frame must be skipped: window minimized or 0 pixels wide, swapchain rebuild failed, fence wait failed, or the image could not be acquired. Then record nothing and do not call endFrame.

may block It waits for the GPU when the CPU is 2 frames ahead.

void endFrame();

Ends the frame's command buffers and sends the frame to the GPU, then shows it in the window. If no pass drew to the window this frame (for example, all passes drew to render targets), it adds a pass that clears the window first. With the stats overlay shown, it draws the overlay in a pass of its own on top. Without async compute the frame is one command buffer: culling is recorded in it as ordinary scene passes. With EngineConfig::asyncCompute it is a few batches, each one command buffer and one submit on one queue. They are all submitted here, in the order they were closed. The last graphics batch waits for all of the frame's compute work, and presents.

Call it only after a beginFrame that returned true, and after the last endPass.

void beginPass(const std::string& name = "Pass", const AttachmentOps& ops = {});

Starts rendering into the current target: the window, or the render target set with setRenderTarget. By default it clears color and depth (their old contents are dropped), sets the viewport and scissor to the whole target, and sets cull mode to none. Only between beginFrame and endFrame.

name
Label of the pass. It names the pass's GPU timer in getFrameStats and the stats overlay.
ops
Which attachments to keep instead of clearing, and whether to keep depth at the end. See AttachmentOps. A render graph sets them for you.

The window is cleared to a dark gray and has no depth: draw anything that needs a depth test into a render target. A render target is cleared to its own clearColor.

struct AttachmentOps
{
    bool loadColor      = false;
    bool loadDepth      = false;
    bool storeDepth     = false;
    bool firstWrite     = false;
    bool encodedColor   = false;
};

What a pass does with its attachments. The defaults clear both and throw depth away at the end.

loadColor, loadDepth
true: keep what the attachment holds, and draw on top. false: clear it (color to the target's clear color, depth to 0).
storeDepth
true: keep depth at the end of the pass, for a later pass that loads it or samples it. Color is always kept. A render graph sets it on the pass before one that loads the target or reads its depth (readDepth).
firstWrite
true: no earlier pass drew into the target this frame. For a cube target (RenderTargetDesc::cube) a pass draws one face, but the layout change before it covers all six. Only with this set does beginPass let a clearing pass drop the whole cube's old contents; otherwise it keeps the other faces. A render graph sets it on a target's first pass of the frame. Leave it false when you draw a cube's faces by hand: every face you draw stays.
encodedColor
true: draw the swapchain through its UNORM view, where the device has one (getSwapchainEncodedFormat). The pass then writes and blends the stored sRGB numbers as they are, and its pipelines must be made for that view's format. A render graph sets it for the UI pass. It has no effect on render targets or on a swapchain without the view.
// A hand-written frame: two passes on the window, the second on top of the first
engine.beginPass("Background");
// ... draw the background
engine.endPass();
engine.beginPass("UI", {.loadColor = true});
// ... draw the UI
engine.endPass();
void endPass();

Ends the pass. On a render target, it moves the color image to the sampled layout, so later passes can sample it (see getRenderTargetTexture). The depth image stays a depth attachment; in a graph, a later pass that declares readDepth gets it moved to the sampled layout. endFrame moves the swapchain image to the present layout.

bool addScenePasses(RenderGraph& graph, SceneHandle scene, CameraHandle camera, const RenderTargetHandle& renderTarget, const SceneShadow* shadows = nullptr, uint32_t shadowCount = 0);

Adds the passes that draw scene from camera to graph. They are ordinary graph passes: the graph sorts them with your passes, records their barriers from what they declare, and times each one under its name. render calls it for you; call it yourself when you build your own graph. The culling passes and Hi-Z are async compute passes: with EngineConfig::asyncCompute they run on the compute queue.

graph
The graph to add to, before its compile. Add your own passes before or after.
scene
Invalid: logs addScenePasses needs a valid scene handle., adds nothing and returns false.
camera
The view. Its projection is fitted to the target's aspect ratio every frame; the camera itself does not change. Invalid: logs an error, adds nothing and returns false.
renderTarget
Where the scene is drawn. A target needs one color in SCENE_COLOR_FORMAT and D32_SFLOAT depth, the formats of the scene's pipeline. The color is linear light with no upper limit: draw it to the window with addToneMapPass. A second color of MOTION_FORMAT (one sample only) takes each pixel's motion, for addTaaPass. The target may have several samples per pixel (samples, MSAA): the scene's pipelines are made for its count, cut-out materials use alpha-to-coverage, and the Hi-Z reads every depth sample; resolve it with addMsaaResolvePass. Invalid: logs an error, adds nothing and returns false. A target with D32_SFLOAT depth and no color is depth-only: the scene's depth is drawn and nothing else, in passes named Shadow 1, Shadow 2, … (a depth pre-pass, for example; shadows come from addShadowPasses). Make it with RenderGraph::createRenderTarget before this call.
shadows, shadowCount
Up to MAX_VIEW_SHADOWS (4) shadows (SceneShadow), of different lights, that addShadowPasses returned for the same scene and camera in this graph. Each darkens its own light. The draw passes read every map's depth, so the graph runs them after the map passes. nullptr and 0 (the default): no shadow. More than 4, two of one light, a shadow that addShadowPasses did not make for this scene and camera in this graph, a shadow that another view in the graph already reads (cascades are fitted to one view's aspect ratio), or shadows on a depth-only view, log an error, add nothing and return false. A cube render target (RenderTargetDesc::cube) is not a valid renderTarget.
returns
true when the passes were added. On false nothing was added.
scene passes, run on the GPU the target 
// From examples/01_render_graph/main.cpp: the scene into an offscreen target
const rasm::RenderTargetHandle rtHandle = graph.createRenderTarget({
    .name = "offscreen_rt",
    .swapchainScale = 1.0f,
    .colorFormats = {rasm::SCENE_COLOR_FORMAT},
    .depthFormat = rasm::Format::D32_SFLOAT,
    .clearColor = glm::vec4(0.0f), // alpha 0 marks the background
});

// The scene's culling and draw passes, into offscreen_rt. The passes below read what they drew.
if (!engine.addScenePasses(graph, scene, camera, rtHandle))
{
    return 1;
}
SceneShadow addShadowPasses(RenderGraph& graph, SceneHandle scene, CameraHandle camera, const ShadowDesc& desc);

Adds a light's shadow to graph: depth-only maps of the scene, each drawn by a scene view of camera. Give the returned SceneShadow to addScenePasses for the same scene and camera. The maps depend on the light's type:

LightMapsScene viewsGuide
DIRECTIONALcascadeCount cascades, shadow_cascade_0, …, each covering a slice of the camera's view out to distance, fitted every framecascadeCountCascaded shadow maps
SPOTone perspective map at the light along its cone, shadow_spot_<light index>1Spot and point light shadows
POINTone cube map, shadow_cube_<light index>6 (one per face)
graph
The graph to add to, before its compile. It owns the maps' targets, so they live as long as the graph.
scene
The scene whose depth the maps hold. Invalid: logs an error and returns an empty shadow.
camera
The camera you then give addScenePasses. A directional light's cascades follow its view. Every map's view takes its level of detail from this camera, so a mesh is drawn at the same level in both. Invalid: logs an error and returns an empty shadow.
desc
The light and its maps (ShadowDesc). An invalid light or a size of 0 logs an error and returns an empty shadow. So does, for a directional light, 0 or more than MAX_SHADOW_CASCADES (4) cascades, a distance not beyond the camera's near plane or a splitLambda outside 0 to 1, and for a spot or point light a distance that is not finite and above 0. So do fewer free scene views than the shadow needs: nothing is added then.
returns
The shadow, with mapCount 0 on failure. Each map's depth is maps[i], which a pass of yours can read with readDepth.

Shadows. Call addShadowPasses for each light, then addScenePasses with the shadows it returned. The order of the passes does not matter: the graph sorts them by the depth reads. Each cascade, spot map and cube face is one scene view: a sun with 4 cascades, a spot light, a point light and the shaded view take 12 of the MAX_SCENE_VIEWS (16).

    return 1;

    engine.addShadowPasses(graph, scene, camera, rasm::ShadowDesc{.light = moon, .cascadeCount = 4, .size = 2048, .distance = 40.0f}),
    engine.addShadowPasses(graph, scene, camera, rasm::ShadowDesc{.light = lamp, .size = 2048, .distance = 40.0f}),
    engine.addShadowPasses(graph, scene, camera, rasm::ShadowDesc{.light = lantern, .size = 1024, .distance = 14.0f}),
};
if (!engine.addScenePasses(graph, scene, camera, sceneTarget, shadows, 3))
    return 1;

A light taken out of the scene casts no shadow, and its maps draw nothing; so does a directional light's shadow when the camera's near plane is moved to distance or beyond. Points farther than distance from the camera are lit; a directional shadow fades out over the last tenth of it. Casters up to distance toward the sun from a slice are in its map. A spot or point light shadows up to distance from the light. Every shadow uses 3x3 PCF. Each shadow darkens only its own light; lights without one and the ambient term are not shadowed. How it works: Shadow mapping, Cascaded shadow maps and Spot and point light shadows.

Scene views. Each (scene, camera, target, face, shadows) is a scene view, with its own culling buffers on the GPU; the face is a cube's, for a point light's map. A view lives while a graph holds it: graphs built for the same five share it, and when the last of them is destroyed or replaced, the view's buffers are freed. Views let one frame draw several scenes, cameras or targets. The scene's lights are read every frame. Nothing is drawn, with no error, while the scene is empty or all its entities still load: the target keeps its clear color.

Culling also picks each visible draw's level of detail from its distance to the camera and EngineConfig::lodErrorPixels. A view drawn without culling draws LOD 0.

RenderTargetHandle addMsaaResolvePass(RenderGraph& graph, const RenderTargetHandle& source, CameraHandle camera);

Adds a compute pass named MSAA Resolve that turns the samples of each pixel of source's color 0 into one color, in a new single-sample target. Each sample is weighted by 1 / (1 + its brightness × the camera's exposure), so an edge between a bright sky and a dark roof keeps its in-between shade after tone mapping, where a plain mean would look almost like the sky. Give the target it returns to addBloomPasses and addToneMapPass. render adds it when EngineConfig::antiAliasing is an MSAA mode. How it works: MSAA and alpha-to-coverage.

graph
The graph to add to, before its compile. The pass reads source, so the graph runs it after the passes that draw it.
source
A target with samples above 1 and a color, usually the one addScenePasses drew. Invalid, single-sample or depth-only: logs an error, adds nothing and returns an invalid handle.
camera
Its exposure is read each time the pass runs. Invalid: logs an error, adds nothing and returns an invalid handle.
returns
The resolved target, <source name>_resolved: a transient storage target of SCENE_COLOR_FORMAT, the source's size, one sample. Invalid when the target can't be made (no free storage slot, for example; the error says why). The pipeline is made the first time the pass runs; if passes/msaaResolve.slang does not compile, it logs an error and tries again next frame.

At 1920 × 1080 on an RTX 3060 it takes 0.12 ms at 2 samples, 0.14 ms at 4 and 0.38 ms at 8.

RenderTargetHandle addTaaPass(RenderGraph& graph, const RenderTargetHandle& source, CameraHandle camera);

Temporal anti-aliasing. The scene view that draws source in this graph is jittered by a sub-pixel offset each frame, reads its textures one mip sharper, and writes each pixel's motion into source's second color. The compute pass TAA then blends each frame into a history: it reads the history where each pixel was last frame, clips it to the colors around the pixel, and keeps about 10 frames. Give the target it returns to addBloomPasses and addToneMapPass. render adds it with EngineConfig::antiAliasing = AntiAliasing::TAA. How it works: Temporal anti-aliasing.

graph
The graph to add to, after addScenePasses drew source in it, before its compile.
source
A single-sample target with colors {SCENE_COLOR_FORMAT, MOTION_FORMAT} and D32_SFLOAT depth. A multisampled one logs that TAA and MSAA exclude each other; any other, or one no scene view of this graph draws, logs an error. Then it adds nothing and returns an invalid handle.
camera
Its exposure weighs bright pixels down; its moves decide when the history is dropped. Invalid: logs an error, adds nothing and returns an invalid handle.
returns
The history target, <source name>_taa: a storage target with history (two copies of SCENE_COLOR_FORMAT, the source's size), owned by the graph. Invalid when it can't be made. The pipeline is made the first time the pass runs; if passes/taa.slang does not compile, it logs an error and tries again next frame.

The history is dropped in the first frame, after a resize, after resetCameraHistory, and when the camera turns more than 30° or moves more than 100 near planes (half its width, for an orthographic camera) in one frame. The same frames give the same pixels. At 1920 × 1080 on an RTX 3060 the pass takes 0.37 ms, and writing the motion adds about 0.13 ms to the draw passes.

RenderTargetHandle addBloomPasses(RenderGraph& graph, const RenderTargetHandle& source, CameraHandle camera);

Adds the bloom of source: 11 compute passes, Bloom Down 1 to Bloom Down 6 and Bloom Up 5 to Bloom Up 1, that blur its light at six sizes, from half the source down to 1/64. Give the target it returns to addToneMapPass, which mixes it into the image. render adds it when EngineConfig::bloom is on (off by default). How it works: Bloom.

graph
The graph to add to, before its compile. The passes read source, so the graph runs them after the passes that draw it. They make 11 transient storage targets in the graph, which share memory with the graph's other transient targets.
source
Color 0 is read, as linear light: the target addScenePasses drew. The levels are sized from it: a target sized from the window gives levels that follow the window. A small source runs fewer levels: the chain stops at the last level of at least 2 × 2. Invalid, a depth-only target, or a multisampled one (resolve it first with addMsaaResolvePass): logs an error, adds nothing and returns an invalid handle.
camera
Its bloom strength is read each time the passes run. At 0 they dispatch nothing (the graph still records their barriers). Invalid: logs an error, adds nothing and returns an invalid handle.
returns
The bloom target, half the size of source, or an invalid handle when the passes could not be added, for example when the storage slots ran out (the error names the limit). The pipelines are made the first time the passes run. If passes/bloom.slang does not compile, they log an error, the frame has no bloom, and they try again next frame.

The passes share one GPU timer, Bloom. In examples/09_gltf_materials (RTX 3060, Release) it takes about 0.2 ms at 1280 × 720 (0.10 to 0.27 ms from run to run), 0.37 ms at 1920 × 1080 and 0.75 ms at 3840 × 2160.

4Loading and waiting

void waitForLoads();

Finishes every pending mesh and texture load now: it uploads each result as soon as its workers are done, which frees its part of EngineConfig::loadMemoryBudget for the loads that wait for it, with no time limit. After it returns, isLoaded is true for every successful load. Entities that use them join their scenes' draw lists at the next beginFrame, so the first frame after it shows everything.

blocks the main thread Use it before the main loop to avoid objects popping in, or in tests. Do not call it every frame.

auto mesh = engine.loadGLTF("models/gltf/coffee-room/scene.gltf");
engine.waitForLoads();
bool ok = engine.isLoaded(mesh); // false if the file failed to parse

rasm links Dear ImGui PUBLIC, as a static library (vcpkg's plain imgui port, with no backend: RASM feeds it input and draws it), and owns the context. find_package(rasm) finds it for you and links it into your program, so your code includes imgui.h and calls ImGui:: functions on that same library. void setUiCallback(std::function<void()> callback);

Your UI. The engine calls callback once per frame between ImGui::NewFrame and ImGui::Render, inside beginFrame: after the input was read and the frame slot's fence was waited for, before the scene is uploaded. So a light or a transform you change in it shows in the same frame. Call ImGui:: functions in it; do not render or begin a frame from it. An empty function removes the callback.

Without EngineConfig::ui: logs a warning and the callback never runs. Draw callbacks of ImGui (ImDrawList::AddCallback) run while the UI is built, not while it is drawn.

ImGui saves no imgui.ini: ImGuiIO::IniFilename is nullptr, so nothing is written into the working directory and every run starts the same. To keep window positions between runs, set your own path in the callback's first frame (ImGui::GetIO().IniFilename = path;, with a string that lives as long as the engine).

bool addUiPass(RenderGraph& graph);

Adds a graphics pass named UI that draws the frame's ImGui windows into the swapchain, over what the passes before it drew. It keeps the image and has no depth. render adds it after the tone map; in your own graph, add it after addToneMapPass (or after your last pass on the swapchain).

graph
The graph to add to, before its compile.
returns
true when the pass was added; false, with nothing added, when the UI is off.

A frame whose graph has no UI pass still shows the UI: endFrame draws it in a render pass of its own, so F1 works in every program. That costs one more load and store of the swapchain image, only on frames that have something to draw; the first time, a debug-level log line says so. addUiPass draws in a pass the graph already orders, so it is the cheaper way.

The pass draws through the swapchain's UNORM view where the device has one (getSwapchainEncodedFormat), so ImGui's colors blend as the sRGB numbers ImGui is designed for; elsewhere they blend in linear light (D31).

void setCullingFrozen(bool frozen);

While frozen is true, each shaded scene view culls as in the frame it froze in: with that frame's frustum, LOD camera and occlusion results. The camera still moves and draws, so you can fly out and look at what was kept. With the UI on, the frozen frustum is drawn as orange lines. Best seen with DebugView::CULLING.

  • Only the early culling pass runs. The Hi-Z and the late pass record nothing.
  • See-through (BLEND) draws are culled in the early pass too, and drawn in list order, not sorted.
  • Shadow maps are not frozen: they follow the camera, with the frozen LOD camera.
  • What the frozen visibility never saw stays hidden until you unfreeze: an entity added after the freeze, or a mesh that finished loading after it.
  • Freeze after a few frames of normal culling: a view's first frame has seen nothing yet.

The RASM window has two more sections. Two sizes

pixelWidth, pixelHeight: the drawable size. They differ on HiDPI screens. The swapchain, the render targets sized from it and the viewports use the pixel size.

Three platforms (EngineConfig::platform): SDL opens a window and reads its events for you; NATIVE draws into your window, and your program runs the event loop and sends the input; HEADLESS has no window. In all three, the input goes through the same InputEvents, to the camera, Dear ImGui and the keys above, and getInputEvents gives them back after pollEvents. How it works: The platform layer.

Your own window

Give the engine your window's native handles, its size in points and pixels, and the display's scale. Each frame, send it your window's events and size changes before render (or beginFrame). Your window must live longer than the engine. examples/19_embedding does this with an SDL3 window of its own; its --headless run opens the window hidden and plays a scripted input.

rasm::EngineConfig config = {
    .appName = "editor",
    .platform = rasm::PlatformType::NATIVE,
    .windowWidth = 1280,
    .windowHeight = 720,
    .nativeWindow = {.type = rasm::NativeWindowType::WINDOWS, .window = hwnd, .pixelWidth = 1920, .pixelHeight = 1080, .contentScale = 1.5f},
    .ui = true};
rasm::Engine engine(config);
while (editorRunning)
{
    // Your loop: turn each of your window's events into an InputEvent.
    engine.addInputEvent({.type = rasm::InputEventType::MOUSE_MOVE, .x = 640.0f, .y = 360.0f});
    engine.render(scene, camera);
}
void addInputEvent(const InputEvent& event);

Queues one input event (InputEvent). The next pollEvents (first thing in beginFrame, unless you called it) applies the queue in order, before the platform's own events: to Dear ImGui while it builds frames, to the built-in keys, and to the input of the camera passed to beginFrame, without what the last UI frame took. An event added after this frame's poll goes into the next frame. Use it with NATIVE, or to script the input of a headless engine. The queue keeps its capacity, so a steady frame makes no heap allocation.

main thread Mouse positions are in window points from the top-left corner, like windowWidth. Escape does not stop a NATIVE or headless engine.

void setWindowSize(uint32_t width, uint32_t height, uint32_t pixelWidth, uint32_t pixelHeight);

The main window's new size, in points and in pixels, for NATIVE and HEADLESS. A new pixel size rebuilds the swapchain and everything sized from it in the next beginFrame; the points place the mouse and the UI. A pixel size of 0 skips frames, as for a minimized window: send it while your window is minimized. Headless, it changes the size of the offscreen images. With SDL it logs a warning and does nothing, since the SDL platform reads its window's size itself.

void setWindowContentScale(float scale);

The display's scale setting (1.5 at 150 % in Windows' settings), without the pixel density, for NATIVE and HEADLESS. The UI's sizes and fonts follow it from the next UI frame. Call it when your window moves to a display of another scale. A scale of 0 or less is refused with an error; with SDL it logs a warning and does nothing.

Headless: no window

With EngineConfig::platform = PlatformType::HEADLESS the engine opens no window, starts no SDL and reads no events of its own. The device has no surface. Each frame renders into one of two offscreen images of windowWidth × windowHeight pixels, which take the place of the swapchain: the tone map and every pass that writes "the swapchain" write there, and readFrame copies one back. With EngineConfig::ui the UI runs with no input unless you send some with addInputEvent: the RASM window and the windows of setUiCallback are drawn as with a window, and readFrame copies them. running() stays true until the engine is destroyed, so the program decides how many frames to render. examples/16_headless renders a scene and writes a PNG, and every example takes --headless --frames N --out file.png (examples/exampleArgs.h): it renders N frames with no window, writes frame N and exits.

rasm::EngineConfig config = {
    .appName = "thumbnails",
    .platform = rasm::PlatformType::HEADLESS,
    .windowWidth = 512,
    .windowHeight = 288,
    .assetRoot = "assets"};
rasm::Engine engine(config);
const Window& getMainWindow() const;

The window the engine renders to, with its current sizes, content scale and state (minimized, resized). It updates in beginFrame. Use the pixel size for viewports, like examples/01_render_graph/main.cpp does. Fields are in types.html.

const auto &window = engine.getMainWindow();
const float width = static_cast<float>(window.pixelWidth);
const float height = static_cast<float>(window.pixelHeight);
const float aspect = width / height;
Window createWindow(uint32_t width, uint32_t height);

Asks the platform for a window. With SDL it starts SDL and opens a resizable window titled "RASM Engine"; with NATIVE it returns your window from EngineConfig::nativeWindow; headless it returns a Window with no handle and a pixel size of width × height. The constructor calls it for the main window. A program has no use for it: a second window gets no rendering. With SDL it returns a Window with an invalid handle on failure (logged).

void destroyWindow(const Window& window);

Closes the window and shuts SDL down (nothing when headless). The destructor calls it for the main window; do not call it on the main window yourself. docs/code_review.md lists both window functions among the calls that should leave the public API for a platform layer (D2, D7).

10Reading images back

A readback copies an image from the GPU to the CPU, for a screenshot, a thumbnail or an image test. The copy is recorded at the end of a frame and is done when the GPU has finished that frame, so asking never stalls the frame. With two frames in flight the pixels are ready about two frames later. The idea, with pictures of the frames: Headless rendering and readback.

ReadbackHandle readFrame(ReadbackFormat format = ReadbackFormat::RGBA8_SRGB);

Asks for a copy of the image the frame shows, with the UI and the overlay: the offscreen image of a headless engine, or the window's swapchain image. Call it before render or graph.execute (or inside the frame, from the UI callback): the copy goes into the next endFrame. Returns an invalid handle when the window's surface does not allow copies from its images (logged); a headless engine can always be read.

const rasm::ReadbackHandle shot = engine.readFrame();
engine.render(scene, camera);
ReadbackHandle readTexture(const TextureHandle& texture, ReadbackFormat format = ReadbackFormat::RGBA8_SRGB, uint32_t layer = 0, uint32_t mip = 0);

The same for one layer (a cube face) and mip of a readable texture, as it is at the end of the frame. A render target is readable when it is made with RenderTargetDesc::readable; take its texture for the frame with getRenderTargetTexture. Returns an invalid handle, with an error that names the reason, for a texture that is not readable, a multisampled one (read its resolve), a block-compressed or 3-channel format, a depth asked for as RGBA8_SRGB, or a layer it does not have. A mip it does not have makes the copy fail at the end of the frame, and takeReadback returns false.

// The HDR scene color as floats, e.g. for its average brightness.
const rasm::ReadbackHandle hdr = engine.readTexture(engine.getRenderTargetTexture(sceneTarget), rasm::ReadbackFormat::RGBA32_FLOAT);
bool isReadbackReady(ReadbackHandle readback);

True once takeReadback would not wait: the GPU has finished the frame that copied it, or the copy failed. Poll it each frame so the program never stalls. False for a readback no frame has copied yet, and for an unknown handle.

bool takeReadback(ReadbackHandle readback, ReadbackImage& image);

Converts the copy into image and frees it; the handle is then used up. may block When the copy is recorded but the GPU has not finished it, it waits for that frame's fence. Returns false when the copy failed, or when no frame has copied it yet: then it does not wait, and the readback stays pending for the next frame.

if (engine.isReadbackReady(shot))
{
    rasm::ReadbackImage image;
    if (engine.takeReadback(shot, image))
        rasm::writePng("frame.png", image);
}

11Raw GPU resources

For your own passes you may need buffers and textures that are not part of a scene. These functions forward to RenderContext. The descriptors (BufferDesc, TextureDesc) and how to fill, read and bind the resources are on RenderContext and resources.

BufferHandle createBuffer(const BufferDesc& desc);

Creates a new GPU buffer, every call (two equal descriptors give two buffers). Returns an invalid handle and logs an error on failure. It is device-local unless hostVisible is set. destroyBuffer frees it.

rasm::BufferHandle particles = engine.createBuffer({.name = "Particle Positions",
                                                    .usage = rasm::BufferUsage::STORAGE,
                                                    .size = PARTICLE_COUNT * 2 * sizeof(float)});
const uint64_t address = engine.getRenderContext().getBufferDeviceAddress(particles);

From examples/04_compute/main.cpp: a shader reads and writes the buffer through its device address.

TextureHandle createTexture(const TextureDesc& desc);

Creates a new, empty texture. Fill it with RenderContext::fillTexture, and add it to the bindless set (addBindlessTexture) to sample it in a shader, or give it to a material. For image files use loadTexture instead. Returns an invalid handle on failure. destroyTexture frees it.

void destroyTexture(const TextureHandle& texture);

Destroys a texture from loadTexture or createTexture. The handle is invalid at once: a later call with it logs an error, even when a new texture took its index. The texture and its bindless slot are freed once the GPU has finished every frame that may sample them, so the call never waits, and a new texture then reuses the slot.

  • Every material that uses the texture loses it: that texture slot of the material samples nothing from the next frame on (the material's factor alone, as with no texture). An entity that waited for it to load is drawn.
  • A load that has not finished is dropped at once: a decode still in the queue never runs, and a running one gives its result up. loadTexture of the same path then loads it again.
  • Swapchain images and render target textures are refused: they belong to the swapchain and to their render target.
// A tile's material gets a new texture; the old one goes once no frame in flight samples it.
rasm::Material values = engine.getMaterial(tile.material);
values.textures[static_cast<uint32_t>(rasm::PbrSlot::ALBEDO)] = texture;
engine.updateMaterial(tile.material, values);
engine.destroyTexture(tile.texture);

From examples/17_streaming/main.cpp, which pushes far more textures through the bindless set than it has slots. How the wait works: Deferred destruction.

PoolStats getPoolStats() const;

The live objects and the used part of each engine-wide pool (PoolStats). It walks no object: every number is kept as things are made and destroyed, except the bindless slot count (1024 slots). examples/17_streaming prints it every 120 frames.

LoadStats getLoadStats() const;

The load workers now (LoadStats): how many there are, the jobs that wait and run, and the decoded bytes held now and at most since the start. The RASM window (F1) shows it on its Loads line. examples/17_streaming --burst and examples/10_ktx2_textures --measure print the workers and the peak. See Job systems.

void destroyBuffer(const BufferHandle& buffer);

Destroys a buffer from createBuffer: the handle at once, the buffer and any upload still queued for it once the GPU has finished every frame that may use it. Calls RenderContext::destroyBuffer.

void destroyRenderTarget(const RenderTargetHandle& renderTarget);

Destroys a render target from createRenderTarget: the handle at once, its textures and bindless slots once the GPU is done with them. A render graph destroys the targets it made itself. Calls RenderContext::destroyRenderTarget.
