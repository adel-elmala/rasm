# RASM Code Review — October 2026

This review covers the whole repository as of `feat/pbr` @ `61d8028`. Every finding has an ID that the [development plan](development_plan.md) refers to.

| Prefix | Meaning |
|---|---|
| **B** | Bug: wrong behaviour, a crash, or undefined behaviour |
| **D** | Design or architecture issue |
| **P** | Performance |
| **C** | Code health and refactoring |

**Confidence.** *Confirmed* means the failure follows deterministically from the code as read. *Likely* means it follows from the code plus an assumption about driver or library behaviour; verify it at runtime before fixing.

### Problems

1. **Public headers expose implementation details (`D2`).** *Fixed 2026-11-01:* public headers include nothing from `src/` and no third-party header except glm. `RenderContext` keeps its Vulkan state in a private `Impl`, and `Engine` holds `ShaderCompiler` through a forward declaration. `src/`, the backend libraries and the tinygltf/stb include paths are PRIVATE. The original finding follows.
   - `engine.h` includes the private `renderer/shaderCompiler.h` and `renderer/uberMaterialTypes.h`; `render/renderContext.h` includes `rhi/vulkan/vulkanTypes.h` and `rhi/vulkan/vulkanContext.h` (→ vk-bootstrap, VMA).
   - `types.h` and `mesh.h` include `tiny_gltf.h`, `window.h` includes `vulkan/vulkan.h`, and `render/renderGraph.h` includes `spdlog/spdlog.h`.
   - Because of this, `src/` is temporarily a PUBLIC include directory, and Vulkan, VMA, vk-bootstrap, Slang, glm, Tracy, spdlog and the tinygltf/stb include paths are all linked PUBLIC. Applications still compile against the whole backend.
   - This keeps compiles slow, makes the backend impossible to swap, and blocks a stable API/ABI.
2. **Some files still mix concerns.** *Partly fixed 2026-11-04:* `prepareScene` and `drawScene` moved to `renderer/gpuScene.cpp`, glTF/OBJ parsing to `assets/meshImport.cpp`, texture loading to `assets/texture.cpp`, and `VulkanQueue` to its own pair. Still open:
   - `assets/material.cpp` holds both the material API and glTF material import;
   - `engine.cpp` (frame loop and pipeline creation) still sits at the root of `src/`.
3. **Shaders are found through the working directory (`D11`).** *Fixed 2026-11-01:* shaders load from `EngineConfig::shaderDir`, by default a `shaders/` folder beside the executable, and `EngineConfig::assetRoot` locates assets. The original finding follows. Paths are cwd-relative (`./shaders/passes/...` in `material.cpp`/`scene.cpp`, `cwd/shaders/lib` in `shaderCompiler.cpp`), so the examples only work when run from the repo root (not from the build directory, an IDE, or an installed app).
4. **No install/export.** *Fixed 2026-11-01:* `cmake/RasmInstall.cmake` installs the library, public headers and shaders and exports `rasm::rasm`, so `find_package(rasm)` works from an install tree or a build tree. The original finding follows. There is no `install()`/`export()`, so `find_package(rasm)` does not work.
5. **No `tests/` and no CI** (plan phase 1.5). *Partly resolved 2026-11-01:* `tests/` has a doctest target run through CTest. CI is still missing.
6. **Binary assets live in plain git.** The glTF/OBJ sample models are committed directly, so the clone grows with every asset added.

- Keep moving code incrementally: move a file only while you are working on it, and change the CMake lists in the same commit.
- Add CI that builds the presets and runs `rasm_tests` (phase 1.5).

## 2. Bugs

### High severity

**B1 — Creation dedup aliases resources that must be distinct.** *Fixed 2026-10-26:* buffer, texture, descriptor-pool and descriptor-set dedup has been removed. Shader and pipeline dedup is now keyed on full state; shader equality used to compare the SPIR-V *pointer*. glTF images are cached per model by image index and color space. Resize destroys the old depth textures. The original finding follows.
`RenderContext::create{Buffer,Texture,…}` returns an existing handle when it has seen an equal `ResourceDesc` before ([renderContext.cpp:137-141](../src/rhi/renderContext.cpp#L137-L141), [renderContext.cpp:175-179](../src/rhi/renderContext.cpp#L175-L179)). This bites in several places:
- `prepareScene` creates `megaModelDataBuffer[i]` and `sceneDataBuffer[i]` in a loop with an identical desc ([scene.cpp:204-208](../src/scene/scene.cpp#L204-L208), [:229-233](../src/scene/scene.cpp#L229-L233)). Both frame slots get the **same** buffer, so the CPU rewrites `SceneData`/`Modeldata` while the GPU may still be reading them for the previous frame. That undoes the frames-in-flight fix in `27bb89a`.
- Render-target attachments per frame slot alias each other ([renderContext.cpp:590-593](../src/rhi/renderContext.cpp#L590-L593)).
- Two OBJ meshes with the same vertex and index counts share one buffer, and the second upload overwrites the first ([mesh.cpp:183-195](../src/assets/mesh.cpp#L183-L195)).
- glTF textures are named by `image.uri`, which is empty for images embedded in `.glb` files ([material.cpp:183](../src/assets/material.cpp#L183)). Two embedded images of the same size and format therefore become one texture, and the last upload wins.
- Even a "correct" cache hit re-uploads the texture and takes a new bindless slot (see B7).

*Fix:* remove desc-based dedup from buffer and texture creation. Keep dedup only for immutable objects (samplers, pipeline layouts, pipelines), keyed on their *complete* state. Asset-level caching (by path, or by model + image index) belongs in the asset layer.

**B2 — The projection uses the OpenGL depth range [-1, 1].** *Fixed 2026-10-26:* `GLM_FORCE_DEPTH_ZERO_TO_ONE` is now a PUBLIC compile definition of the `rasm` target in [src/CMakeLists.txt](../src/CMakeLists.txt), and the define in `engine.cpp` was removed. Reversed-Z with an infinite far plane followed on 2026-11-04 (plan 1.4, architecture.md §8 and §11), so the step suggested at the end of the fix is done. The original finding follows.
- `#define GLM_FORCE_DEPTH_ZERO_TO_ONE` sits at [engine.cpp:9](../src/engine.cpp#L9), *after* `engine.h` has already included glm through `rasm/types.h`, so it has no effect. `camera.cpp` never sees it either.
- `glm::perspective`/`glm::ortho` therefore emit z in [-1, 1]. Vulkan clips z < 0, which moves the effective near plane to ≈ 2·n·f/(n+f) (≈ 0.2 for n = 0.1, f = 32) and wastes half the depth range.

*Fix:* set `GLM_FORCE_DEPTH_ZERO_TO_ONE` (and `GLM_FORCE_RADIANS` if wanted) with `target_compile_definitions(rasm PUBLIC ...)`, or call `glm::perspectiveRH_ZO` explicitly. After that, move to reversed-Z (see the plan, phase 1).

**B3 — Debug-name calls without the debug-utils extension.** *Fixed 2026-10-27:* `initInstance` now enables `VK_EXT_debug_utils` whenever the instance reports it, independent of validation, and all naming goes through `VulkanContext::setObjectName`, which does nothing when the extension is not enabled. The original finding follows.
- `setDebugUtilsObjectNameEXT` is called for every buffer, image, view, shader and pipeline ([vulkanContext.cpp:232](../src/rhi/vulkan/vulkanContext.cpp#L232), [:425-426](../src/rhi/vulkan/vulkanContext.cpp#L425-L426), [:456](../src/rhi/vulkan/vulkanContext.cpp#L456), [:644](../src/rhi/vulkan/vulkanContext.cpp#L644)).
- `VK_EXT_debug_utils` is enabled only when validation is requested *and* available ([vulkanContext.cpp:1374-1380](../src/rhi/vulkan/vulkanContext.cpp#L1374-L1380)).
- With `enableValidation = false`, or on a machine without the SDK layers, the dispatch-table entry is most likely null, so the first `createBuffer` crashes. Every release build is affected.

*Fix:* always enable `VK_EXT_debug_utils` when it is available (it is cheap), and skip naming when it is not.

**B4 — Swapchain acquire and present results are ignored; the fence is reset before acquire.** *Fixed 2026-10-27:* acquire, present and recreation return `SwapchainStatus`. `beginFrame` waits on the fence, acquires, and resets the fence only after a successful acquire. It returns `false` to skip the frame on `OUT_OF_DATE`. `SUBOPTIMAL` from acquire and `SUBOPTIMAL`/`OUT_OF_DATE` from present set `swapchainOutOfDate`, and the swapchain is recreated at the start of the next frame. The original finding follows.
- `beginFrame` waits on and resets `inFlightFence`, then ignores the result of `acquireNextImage` ([engine.cpp:310-326](../src/engine.cpp#L310-L326)). `present` failures are only logged ([vulkanContext.cpp:1162-1168](../src/rhi/vulkan/vulkanContext.cpp#L1162-L1168)).
- On `VK_ERROR_OUT_OF_DATE_KHR` the image-acquired semaphore is never signaled, yet the frame still submits work that waits on it. That is invalid usage and can hang.
- `VK_SUBOPTIMAL_KHR` is treated as an error.

*Fix:* acquire first. On `OUT_OF_DATE`, recreate the swapchain and skip the frame. Reset the fence only after a successful acquire. Recreate on `SUBOPTIMAL` or `OUT_OF_DATE` from present.

**B5 — Resize and minimize can destroy the swapchain, and leak.** *Fixed 2026-10-27:* frames are skipped while the window is minimized or 0×0, and `pollEvents` blocks for events instead of spinning. `VulkanContext::recreateSwapchain` keeps the old swapchain when the surface extent is 0 (`OUT_OF_DATE`). When creation fails it destroys the retired swapchain and leaves none, so acquire reports `OUT_OF_DATE` and the engine retries. `get_images`/`get_image_views` are checked. `RenderContext::recreateSwapchain` drops the old swapchain image handles from `textureCache`. The depth textures were already destroyed on resize (`B1`). The original finding follows.
- Minimizing gives a 0×0 extent, so swapchain creation fails. `_recreate_swapchain` destroys the old swapchain anyway ([vulkanContext.cpp:1561-1568](../src/rhi/vulkan/vulkanContext.cpp#L1561-L1568)), `Engine::recreateSwapchain` ignores the failure ([engine.cpp:454](../src/engine.cpp#L454)), and the next acquire uses a destroyed swapchain.
- `get_images().value()` is called unchecked ([vulkanContext.cpp:862-863](../src/rhi/vulkan/vulkanContext.cpp#L862-L863)).
- Every resize leaks the previous depth textures ([engine.cpp:471-482](../src/engine.cpp#L471-L482)) and leaves stale swapchain `TextureVKHandle`s in `textureCache` ([renderContext.cpp:658-664](../src/rhi/renderContext.cpp#L658-L664)).

*Fix:* skip rendering while the extent is 0. Recreate only on success. Destroy the old depth textures and drop the old swapchain image handles.

### Medium severity

**B6 — Gaps in glTF geometry import.** *Fixed 2026-10-27:* `extractGLTFRaws` reads every attribute and index buffer through one accessor reader. It handles byte strides, accessors without a buffer view, sparse accessors, and normalized or integer components (`KHR_mesh_quantization`). It bounds-checks the accessor against its buffer view and the buffer view against its buffer. Non-indexed primitives get generated indices, which the smooth-normal path now shares. Triangle strips and fans become triangle lists. Points and lines are skipped with a warning. Primitives with a missing or invalid `POSITION`, invalid indices, or indices out of range are also skipped with a warning. An invalid optional attribute is ignored with a warning. `TANGENT` is imported and used for normal mapping (see `B19`). The original finding follows.
- Primitives without indices get an empty index list and are never drawn. Indices are filled only when `primitive.indices > -1` ([mesh.cpp:336-362](../src/assets/mesh.cpp#L336-L362)), and the smooth-normal path generates indices but does not keep them.
- `primitive.mode` is ignored, so lines, points and strips are drawn as triangle lists.
- Accessors are assumed to be tightly typed `float`. This breaks `KHR_mesh_quantization`, normalized integer UVs, and sparse accessors.
- `ByteStride()` returning -1 and `bufferView == -1` are not checked.
- The tangent attribute is ignored. That is acceptable for now because tangents are reconstructed in the shader.

**B7 — glTF materials and textures are duplicated for every primitive.** *Fixed 2026-10-27:* `loadMaterial` caches materials per model by material index, next to the per-model image cache from `B1`. Both live in a `GltfImportCache` that `processGLTF` creates for each import. A global texture cache is still open. The original finding follows.
- `extractGLTFRaws` calls `loadMaterial` for each primitive ([mesh.cpp:365-366](../src/assets/mesh.cpp#L365-L366)). Each call creates a new material and uploads every one of its textures again, taking new bindless slots ([material.cpp:155-194](../src/assets/material.cpp#L155-L194)).
- A model whose 50 primitives share one material consumes 50 materials and up to 250 bindless slots. The limits are 256 materials and 1024 slots, so medium-sized scenes fail.

*Fix:* add a per-model cache from material index to `MaterialHandle` and from image index to `TextureHandle` (and later a global texture cache).

**B8 — Missing materials crash or render black.** *Fixed 2026-10-27:* the engine creates `defaultMaterial` (the glTF default material) at startup, and `getMaterial` resolves invalid handles to it instead of throwing. Primitives without a material still prefer their entity's material. The original finding follows.
- `getMaterial` checks only `index >= size()` and throws ([material.cpp:241-247](../src/assets/material.cpp#L241-L247)). An OBJ entity without a material, in a program that never created a material, throws an uncaught `std::runtime_error` from `prepareScene` ([scene.cpp:282](../src/scene/scene.cpp#L282)).
- If other materials do exist, an invalid handle (index 0) returns the zeroed slot 0. A glTF primitive without a material then renders with base color 0 (black) instead of the glTF default material (white, metallic 1, roughness 1).

*Fix:* create a default material at startup and resolve invalid handles to it.

**B9 — `MaterialType::UNLIT` references a missing shader.** *Fixed 2026-10-31:* `gfx::Modeldata` now carries a `MaterialId` that `fragMain` branches on, so `UNLIT` is a path in the uber shader (`Unlit()` in `unlit.slang`). The legacy path uses `basic.slang` for it, which multiplies the first texture by the base color factor and handles a missing texture. glTF materials with `KHR_materials_unlit` import as `UNLIT` and upload only their base color texture. The original finding follows.
`createMaterial(UNLIT)` reads `./shaders/passes/unlit.slang` ([material.cpp:65](../src/assets/material.cpp#L65)), which does not exist. The file read fails and later compilation fails.

**B10 — The render-target path is broken.** *Fixed 2026-11-01:* `endPass` moves the color attachment to `SHADER_READ_ONLY_OPTIMAL` behind a barrier that waits for its color writes, depth attachments are no longer sampled or in the bindless array, and `beginPass` sizes the viewport from the render target. `B1` had already removed the aliasing. In `01_render_graph` the overlay reads the render target through this flow. `transitionImageLayout` now takes its source scope from the old usage instead of assuming render-target writes, so a target rendered again after being sampled waits for those reads, and usages it has no scope for are rejected. Validation does not guard the fix: on SDK 1.4.363, GPU-assisted validation with `VK_LAYER_GPUAV_IMAGE_LAYOUT=1` did not report the old layout either. The original finding follows.
- The attachments for each frame slot alias each other (B1).
- After rendering, the color attachment is never transitioned to `SHADER_READ_ONLY_OPTIMAL`: the barrier is commented out ([engine.cpp:416-423](../src/engine.cpp#L416-L423)). The bindless descriptor promises that layout ([vulkanContext.cpp:898](../src/rhi/vulkan/vulkanContext.cpp#L898)), so `01_render_graph` samples an image that is still in `COLOR_ATTACHMENT_OPTIMAL`. The default validation layers do not report this, because bindless (partially bound, update-after-bind) descriptors are only layout-checked with GPU-assisted validation.
- `beginPass` sets the viewport and scissor from the *window* size, not the render-target size ([engine.cpp:407-408](../src/engine.cpp#L407-L408)).
- The depth attachment of each RT also goes into the bindless array as a combined depth/stencil image.

**B18 — `ResourceDesc` is not zero-initialized.** *Fixed 2026-10-26:* the constructor now zeroes the whole union and `type` has a default initializer. The original finding follows.
- `ResourceDesc() {}` is a user-provided constructor ([resource.h:213](../include/rasm/render/resource.h#L213)), so `ResourceDesc desc{}` does **not** zero the union.
- Fields that a caller doesn't set (`buffer.offset`, `vertexIndexBuffer.*`, and texture fields when you use the buffer variant) are indeterminate. `operator==` and `ResourceDescHash` read them, so dedup (B1) also depends on stack garbage.

*Fix:* zero the storage in the constructor (`std::memset` the union, or give each variant default member initializers). Better, replace the union with `std::variant` or separate desc types (D5).

**B19 — The reconstructed tangent frame inverted the normal-map green channel.** *Fixed 2026-10-27:* `getNormalFromMap` now points the bitangent toward decreasing v (−dP/dv). glTF puts the UV origin at the image's top-left and normal maps store +Y as up in the image, so that is the direction of `cross(N, T) · w` for authored tangents. Before the fix, the derivative path aligned B with +dP/dv, so every normal map without `TANGENT` data was lit with Y flipped. This came to light when `TANGENT` import landed. On a test mesh with standard UVs, mirrored UVs and a mirroring node, and on the authored tangents of `coffee-room`, the two frames now agree (dot > 0.999). Before the fix they disagreed everywhere.

**B20 — Shader dedup keys pointed at freed SPIR-V.** *Fixed 2026-11-01:* `RenderContext::createShader` now keeps its own copy of the SPIR-V in `shaderSources`, and the cache key points at that copy. The bug came from `B1`, which made shader equality compare the code instead of the pointer. `shaderDescCache` still stored the caller's pointer into a temporary blob, so every later lookup that reached `operator==` ran `memcmp` on freed memory. This crashed intermittently with an access violation in any application that compiled the same shader twice, such as one that prepared a second scene. In a debug build, 5 of 30 runs crashed before the fix and 0 of 60 after it.

**B21 — Non-FIFO present modes crash `vkDestroyDevice` on NVIDIA.** *Worked around 2026-11-01; root cause unknown:* both swapchain builders now request `VK_PRESENT_MODE_FIFO_KHR`, so the frame rate is capped at the display's refresh rate. With vk-bootstrap's default of MAILBOX, closing a window that fills the screen raised an access violation inside `nvoglv64.dll` (driver 610.296, RTX 3060) during `vkDestroyDevice`. It depends on the window size, not on the example or on render targets: `00_hello_scene` crashes at 1920x1080 on a 1920x1080 display, and `01_render_graph` does not crash at 720x480. IMMEDIATE crashes too, and so does MAILBOX capped to about 60 fps, so it is not a frame-rate problem. Waiting 500 ms before teardown, destroying the swapchain before the semaphores, skipping the startup swapchain recreation and disabling validation do not help, and validation reports nothing. FIFO gave 0 crashes in 30 runs, against 40–100% per batch with the others. `vkcube` does not crash in any present mode at the same size, so the engine does something it does not, and that difference has not been found. The trigger is NVIDIA's overlay: with it turned off in the NVIDIA App, MAILBOX at 1920x1080 gave 0 crashes in 16 runs. `nvspcap64.dll` (NVIDIA's capture hook) stays loaded either way, but the overlay processes do not run. Keep FIFO while the overlay can be on, because it is on by default for many users, and revisit this before adding a way to turn vsync off.

**B22 — `Transform::rotate` did nothing on a default transform.** *Fixed 2026-11-01:* `Transform::rotation` now defaults to `glm::identity<glm::quat>()`. It used `glm::quat()`, which value-initializes to all zeros, not to identity. A zero quaternion passes for identity in `q * v` and `mat4_cast`, so nothing looked wrong, but any composition stays zero. Every entity or camera that didn't set a rotation was affected: the spin calls in `00_hello_scene` and `02_gltf` were no-ops, and the first trackball drag of such a camera was lost. Those objects now spin.

**B25 — Destroying a texture leaves its bindless slot behind.** *Fixed 2026-11-22 (`D4`):* a texture holds its slot in `TextureTable::slots`, and `RenderContext::destroyTexture` gives the texture and its slot to the release queue ([renderContext.cpp:1222](../src/rhi/renderContext.cpp#L1222)), which frees them once the frame fences and the upload fence pass the frames that may sample them; `updateBindlessDescriptorSet` takes freed slots first ([renderContext.cpp:1436](../src/rhi/renderContext.cpp#L1436)). `Engine::destroyTexture` removes the texture from every material and rewrites their rows first ([texture.cpp:137](../src/assets/texture.cpp#L137)). `bindlessTextureIndexMap` is gone. `examples/17_streaming` pushes 1584 textures through the 1024 slots in 60 frames, with GPU-assisted validation clean. The original finding follows. `RenderContext::destroyTexture` ([renderContext.cpp:1040-1054](../src/rhi/renderContext.cpp#L1040-L1054)) destroys the image and forgets its layout, but does not touch the texture's bindless slot or its entry in `bindlessTextureIndexMap`. A material row that still holds that slot samples a descriptor whose image view is destroyed, which is undefined behaviour and can be a device lost. The engine's own calls are safe: on resize it rewrites the depth texture's slot right away, and `destroyAttachments` erases a render target's map entries, so nothing samples the old slots again (they are lost, not reused). An application that calls `destroyTexture` on a texture a material still uses hits it. Part of the slot lifetime that `D4` asks for. *Confirmed.*

**B33 — Samples after a cut-out's `discard` had undefined derivatives.** *Fixed 2026-11-22:* the Slang session adds the `spvDemoteToHelperInvocation` capability ([shaderCompiler.cpp](../src/renderer/shaderCompiler.cpp), `getTargetDesc`), so every `discard` compiles to `OpDemoteToHelperInvocation`, and the device enables `shaderDemoteToHelperInvocation` (core in Vulkan 1.3). A demoted lane writes nothing but stays in its 2x2 quad as a helper. The original finding follows. Slang compiled `discard` to `OpKill` for profile `spirv_1_4`. The 1-sample MASK `fragMain` ([rasm.slang:185](../shaders/passes/rasm.slang#L185)) discards below the cutoff and then samples the material's other textures with implicit LOD; a killed lane leaves its quad, so those samples' derivatives, and their mip, were undefined at the cut-out's edges. The RTX 3060 drew the same image either way (max diff 0 at 1920x1080 in `sponza` and `alpha_modes`), so it was invisible there. lavapipe (Mesa 25.3.6, 26.2.7, 26.3.0) crashes on it: the golden-image tests `alpha_modes` and `sponza` stopped with an access violation in its JIT code, a null texture handle for a lane while sampling the bindless array (`get_sample_function` in `lp_texture_handle.c`). A kill that never runs did not crash, nor did the same model with alpha-to-coverage (`msaa4`), which has no `discard`. The demote costs nothing measurable: `Scene 1` of `sponza` at 1920x1080 on the RTX 3060, Release, 1.342 ms with kill and 1.336 to 1.346 ms with demote. *Confirmed* by the lavapipe crash and its fix. The crash itself is a Mesa bug: a kill followed by a descriptor-indexed sample should give a wrong mip, not a null handle; the issue text is in the image-tests pull request.

### Low severity

**B11** — *Fixed 2026-10-31:* `submit` builds one wait stage per wait semaphore. The original finding follows. `VulkanContext::submit` passes one `waitStages` entry while `waitSemaphoreCount = waitSemaphores.size()` ([vulkanContext.cpp:1120-1138](../src/rhi/vulkan/vulkanContext.cpp#L1120-L1138)). Waiting on more than one semaphore reads past the array. The bug is latent today, because callers pass 0 or 1 semaphores.

**B12** — *Fixed 2026-10-31:* the SPIR-V options are now a static array. The original finding follows. `ShaderCompiler::getTargetDesc` allocates `new slang::CompilerOptionEntry[1]` and never frees it ([shaderCompiler.cpp:456-458](../src/renderer/shaderCompiler.cpp#L456-L458)).

**B13** — Handle indices are consumed before validation and are never reused. *Fixed 2026-11-22 (`D4`):* every index comes back when its object is destroyed. `loadMesh` still needs its handle before the file is parsed, since it returns at once and parses on a worker; a mesh that fails keeps its index until `destroyMesh` ([mesh.cpp:386](../src/assets/mesh.cpp#L386)) frees it, and a path whose mesh was destroyed loads again as a new mesh.
- `loadMesh` takes a handle before parsing the file ([mesh.cpp:116](../src/assets/mesh.cpp#L116)), so failed loads burn slots. A retry of the same path reuses its handle.
- *Partly fixed 2026-11-22 (`D4`):* every registry hands out indices from a `HandlePool`, so a released index comes back with a new generation; only textures, buffers and render targets can be released so far.

**B24 — A camera at rest moved by float noise that depended on the frame time.** *Fixed 2026-11-07:* `easeCamera` snaps the rendered transform to the target once position, rotation and scale are within 1e-6 of it (relative for the position). *Extended 2026-11-25:* the position is a `glm::dvec3` now, so the threshold is an absolute 1e-6 (`ease` in `cameraController.cpp`), which double rounding stays far below anywhere on a planet. The original finding follows. `easeCamera` ([camera.cpp:121-156](../src/scene/camera.cpp#L121-L156)) ran `slerp`, `normalize` and `mix` toward the target every frame, even when the camera was already there. **B26 — A glTF primitive without normals gets smooth normals.** `meshImport.cpp` ([meshImport.cpp:282](../src/assets/meshImport.cpp#L282)) averages face normals per vertex when `NORMAL` is missing. The glTF 2.0 spec says a client must compute **flat** normals in that case, so faceted models (low-poly art, CAD exports) look rounded. Flat normals need one vertex per face corner, so unweld the vertices of such primitives before computing them. *Confirmed.*

**B27 — Nothing checks the swapchain format that was really chosen.** The swapchain asks vk-bootstrap for `VK_FORMAT_B8G8R8A8_SRGB` with `VK_COLOR_SPACE_SRGB_NONLINEAR_KHR` ([vulkanSwapchain.cpp:59](../src/rhi/vulkan/vulkanSwapchain.cpp#L59)), and then uses whatever `image_format` comes back. `set_desired_format` is a preference, so on a surface without that format the swapchain can be UNORM. The shaders write linear color and rely on the sRGB format to encode it, so the whole image would come out too dark, with no log line. Log an error or warning when the chosen format is not sRGB. *Likely.*

**B28 — A render graph that fails to compile logs the same error every frame.** When the up-front checks fail or the graph has a cycle, `RenderGraph::compile` leaves `compiled` false ([renderGraph.cpp:402-406](../src/renderer/renderGraph.cpp#L402-L406)), and `execute` calls `compile` again whenever `compiled` is false ([renderGraph.cpp:545-546](../src/renderer/renderGraph.cpp#L545-L546)). The graph cannot change between frames, so it fails the same way and floods the log once per frame. Remember the failure until a pass is added. *Confirmed.*

**B29 — glTF samplers ignore `wrapT` and `minFilter`.** `toSamplerType` ([materialImport.cpp:15-31](../src/assets/materialImport.cpp#L15-L31)) picks the sampler from `wrapS` and `magFilter` alone. A texture that repeats in u but clamps in v, or that asks for nearest minification, is sampled with the wrong mode. The six shared samplers have one wrap mode for both axes, so a fix needs either more samplers or a nearest match with a warning. *Confirmed.*

**B30 — A frame that fails partway through its submits cannot put its texture states back.** *Fixed 2026-11-15:* `TextureStates` keeps every change with its command buffer, and a successful submit forgets only the changes of its own command buffers ([renderContext.cpp:1322](../src/rhi/renderContext.cpp#L1322)); `discardRecording` puts the rest back, last first. A history clear is forgotten only when the command buffer it was recorded into goes out. Tested in `tests/textureStatesTests.cpp`. The original finding follows. With async compute a frame is several submits ([engine.cpp:496-541](../src/engine.cpp#L496-L541)). Each successful `RenderContext::submit` forgets the states from before the recording and the recorded history clears ([renderContext.cpp:1334-1335](../src/rhi/renderContext.cpp#L1334-L1335)), including those of batches that are not submitted yet. If a later batch then fails, `discardRecording` has nothing to put back, so the next frame transitions from layouts the GPU never reached, and a history clear in that batch is lost. A submit fails only on device loss or out of memory, so this is rare. Fix by keeping the states per batch and committing each when its batch goes out. *Likely.*

**B31 — `getMaterial` returns a reference into a vector that grows.** `Engine::getMaterial` returns `const Material &` into `registry.materials` ([material.cpp:151](../src/assets/material.cpp#L151)), and `createMaterial` and every glTF load resize that vector. An application that keeps the reference, for example `const Material &m = engine.getMaterial(a); engine.createMaterial(...); use(m);`, reads freed memory. The examples copy the result (`auto values = engine.getMaterial(material)`), so none does today. Return it by value, as `getLight` does. *Confirmed* by reading.

**B32 — A morphed primitive without normals is lit with the normals of its base shape.** A primitive with no `NORMAL` gets smooth normals once, from its base positions ([meshImport.cpp:282](../src/assets/meshImport.cpp#L282)), and its targets then have no `NORMAL` deltas, so the `Skin` pass moves the positions and keeps those normals ([skin.slang](../shaders/passes/skin.slang)). A POSITION-only target that bends the surface out of its plane is drawn bent but lit flat; glTF asks a viewer to compute the normals of the morphed shape. Rebuild the normals from the morphed positions for such primitives (a pass over the triangles after the `Skin` pass), or warn at import. *Confirmed* by reading, from the morph targets review.

## 3. Design and architecture

**D1 — The backend abstraction does not scale.** *Fixed 2026-11-02:* `src/rhi/device.h` defines a virtual interface (`Device`, `CommandBuffer`, `Queue`, `Swapchain`, and the `Buffer`, `Texture`, `Sampler`, `Shader`, `Pipeline`, descriptor and `Fence` objects), and `src/rhi/vulkan/` implements it. `RenderContext` has no `switch (backend)` left: it maps handles to `rhi::` objects and keeps the dedup caches and render targets. Fences are timelines, and the swapchain owns its acquire and present semaphores, so no binary semaphore or command pool crosses the interface. `vulkanContext.*` is gone, and the only `Vk*` type outside `src/rhi/` was the `createWindowSurface` hook in `src/platform/`, which `D7` removed (2026-11-24): a window reaches the device as a `NativeWindow`, and `createVulkanSurface` in `src/rhi/vulkan/` makes the surface. The generational pools in the last bullet are left to `D4`, as the development plan schedules them. See [architecture.md §12](architecture.md#12-rhi). The original finding follows. Every `RenderContext` method is a `switch (backend)` with empty DX12/Metal branches (≈1,300 lines, mostly boilerplate). Replace it with an RHI interface:
- a small set of objects (`Device`, `Buffer`, `Texture`, `Sampler`, `Pipeline`, `CommandBuffer`, `Queue`, `Swapchain`, `Fence`/timeline),
- either a virtual interface or a compile-time backend selection,
- a pool per object type with generational handles.

**D2 — The public API leaks its implementation.** *Mostly fixed 2026-11-01:* the header split is done (see §1.1). `createSurfaceVk` became the private `createWindowSurface` in `src/platform/`, so the backend does not depend on SDL (since `D7`, 2026-11-24, the surface comes from a `NativeWindow` in `createVulkanSurface`), `convertToGfxMaterial` is a helper in `gpuScene.cpp`, and the glTF import functions are private. Still open:
- `Engine` keeps a large public surface that mixes the high-level API with lower-level calls such as `addBindlessTexture`, `getCurrentFrameResources`, `createWindow` and `pollEvents`.
- `RenderContext` is a friend of `Engine`: it reads `Engine`'s handle manager and bindless map, and calls `addBindlessTexture` for render targets. (*Fixed 2026-11-24*: `RenderContext` is made from a `RenderContextDesc`, owns the bindless set and fills it for render targets itself, and takes each window's `Window` for its swapchain, so it has no `Engine` or `Renderer` pointer.) (*Fixed 2026-11-07* for `RenderGraph`: `execute(camera)` takes the camera, so it no longer reads the registry.)
- Import and renderer internals are public types: `ObjRaw`, `SubGLTFRaw`, `GLTFRaw` (with its `tinygltf::Model`) and `GltfImportCache` in [mesh.h](../include/rasm/mesh.h). Applications never use them, but `Engine` holds them by value (`std::future<GLTFRaw>` in `PendingMeshLoad`), so `engine.h` needs their full definitions. (The scene-preparation types left `scene.h` on 2026-11-07: the GPU scene state is a private `GpuScene` behind a `unique_ptr`.) Moving them to private headers needs the private-`Impl` approach `RenderContext` uses, which is part of `D3`. (*Fixed 2026-11-24*: they are in the private `src/assets/meshData.h`; the loader's state is the private `AssetLoader::Impl`, so no public header names a tinygltf type.)

**D3 — `Engine` is a god object.** *Fixed 2026-11-24:* `Engine` is built from subsystems with one job each, and an integrator uses only the ones it needs.
- `rasm::Renderer` (`rasm/renderer.h`, `src/renderer/renderer.cpp`): the scene objects, the GPU scene, the frame, the windows' swapchains and the UI. It draws into the application's window (`RendererConfig::nativeWindow`, `addWindow` with `WindowDesc::native`) or offscreen images, opens no window and needs no SDL (`examples/21_renderer`). `Renderer` has no virtual function but its destructor.
- `rasm::AssetLoader(Renderer&, AssetLoaderConfig)` (`rasm/assetLoader.h`, `src/assets/assetLoader.cpp`): the worker pool, the load budget, the path caches and the glTF, OBJ, KTX2 and HDR loads. The renderer finishes its loads at the start of each frame and tells it of destroyed objects through `LoadHooks` (`src/renderer/loadHooks.h`), and keeps its own state of a load's result (`MeshState`, `loadingTextures`), so it never reads the loader. The renderer must outlive the loader; the other order logs an error, drops the loads and makes the loader refuse every call (`tests/rendererConfigTests.cpp`). `examples/19_embedding` uses a Renderer with an AssetLoader.
- `Platform` (`src/platform/platform.h`): SDL, the application's window, or none, given to the `Renderer`.
- `RenderContext` over `rhi::Device`: made from a `RenderContextDesc`, it owns the bindless set and knows no `Renderer` (`D2`).
- `Engine` is a `final` `Renderer` that picks its `Platform` (`EngineConfig::platform`) and owns an `AssetLoader`; it overrides nothing, and its own non-virtual `loadMesh`, `loadGLTF`, `loadTexture`, `loadEnvironment`, `resolveAssetPath` and `getConfig` (the whole `EngineConfig`, `toEngineConfig`) keep its API. `RendererConfig` and `AssetLoaderConfig` are its config's parts (`toRendererConfig`, `toAssetLoaderConfig`), checked field by field both ways.
- Two libraries: `rasm::renderer` links no SDL3, tinygltf, tinyobjloader or libktx; `rasm::rasm` adds the Engine, the SDL platform and the loader. Both are installed and exported, and `find_package(rasm COMPONENTS renderer)` needs only the renderer's dependencies. `examples/21_renderer` links only `rasm::renderer`.
- `Scene` stays part of the `Renderer` by decision: the GPU tables mirror the scene objects row by row, and a separate `Scene` would only add change lists without a use case.

The original finding follows. It owns the window, input, assets, scene registry, cameras, the frame loop and the renderer. Split it into subsystems that `Engine` composes: `Platform`, `AssetManager`, `Scene`, `Renderer`, `rhi::Device`. Then integrators can use only the pieces they need, for example the renderer with their own window and asset pipeline.

**D4 — There is no resource lifetime.** *Extended 2026-11-22 (`P21`):* destroying a mesh, texture or environment while it loads drops its load at once: a queued job never runs, and a running one gives its result up when it ends. *Fixed 2026-11-22:* every object the public API creates can be destroyed: `destroyEntity` ([entity.cpp:68](../src/scene/entity.cpp#L68)), `removeEntityFromScene`, `destroyMesh` ([mesh.cpp:386](../src/assets/mesh.cpp#L386)), `destroyMaterial` ([material.cpp:134](../src/assets/material.cpp#L134)), `destroyLight`, `removeLightFromScene`, `destroyEnvironment` (`D22`), `destroyCamera` and `destroyScene` (refused while a render graph draws a view of them, [scene.cpp:116](../src/scene/scene.cpp#L116)). Pools hand out ranges with `RangeAllocator` (first fit, neighbours joined): the five geometry streams and the geometry table rows ([geometryPool.cpp:84](../src/renderer/geometryPool.cpp#L84)) and the animation pool come back through the release queue after the frames in flight; instance rows ([gpuScene.cpp:598](../src/renderer/gpuScene.cpp#L598)), material and light rows and the animated entity rows and ranges are reused at once, since each frame slot has its own copy and a freed animated row is written stopped. A glTF import's materials and textures belong to its mesh and go with it; users of a destroyed mesh or material fall back, found through user counts so the usual order searches nothing. `examples/17_streaming` streams 795 tiles in 1500 frames through pools sized for about two windows of them, with `getPoolStats` flat, sync and GPU-assisted validation clean, and ASan clean. The material table's size is `EngineConfig::maxMaterials` (`D34`). Remaining waits on the GPU are `D35`; pools are not defragmented. *Partly fixed 2026-11-22:* handles come from generational pools (`HandlePool`, [handle.cpp:7](../src/core/handle.cpp#L7)): a free list of indices, a generation bump on release, and `isAlive`, which every `RenderContext` lookup ([renderContext.cpp:253](../src/rhi/renderContext.cpp#L253)) and every `Engine` public call (`isLive`) checks, so a stale handle logs an error instead of reaching another object. `RenderContext` keeps its objects in vectors indexed by handle (`P4`). Destruction is deferred: `destroyTexture`, `destroyBuffer` (and `resizeBuffer`'s old buffer) and `destroyRenderTargets` release the handle at once and give the free to `rhi::ReleaseQueue`, which `endFrame` tags with the graphics, compute and upload fence values signaled last (`tagReleases`, [renderContext.cpp:1502](../src/rhi/renderContext.cpp#L1502)) and `beginFrame` collects without waiting; bindless slots are reused through it (`B25`), and `destroyRenderTargets` no longer waits for the device. Applications get `Engine::destroyTexture`, `destroyBuffer` and `destroyRenderTarget`; Dear ImGui's texture releases use the same queue. Tests: `tests/handleTests.cpp`, `tests/releaseQueueTests.cpp`; example `17_streaming`. Still open: destroying meshes (with their geometry pool ranges and the materials and textures a glTF import made), materials (with `D34`), entities and removing them from a scene, cameras, lights, scenes and environments (`D22`), and reusing instance rows and animation ranges. The original finding follows.
- Applications cannot destroy anything before shutdown: there is no `destroyMesh`, `destroyMaterial`, `destroyEntity` or `removeEntityFromScene`. The low-level `RenderContext::destroyBuffer` and `RenderContext::destroyTexture` exist, and the engine uses them for buffers that grow, for render-target attachments and for the depth texture on resize, but they free no bindless slot (`B25`).
- Handles are never invalidated (`generation` is always 1, [handle.cpp](../src/core/handle.cpp)), so use-after-free can't be detected.
- Streaming (map tiles, game levels) needs generational handles, deferred destruction tied to frame fences, and free-list reuse of registry slots and bindless slots. The material table needs the same row reuse, and a size from `EngineConfig` (`D34`). The [generational handles](guides/generational-handles.html) and [bindless](guides/bindless.html) guides describe the usual design.

**D5 — `ResourceDesc` is fragile.** *Fixed 2026-11-02:* `ResourceDesc` and `ResourceType` are gone. `rasm/render/resource.h` has one aggregate per resource (`BufferDesc`, `TextureDesc`, `ShaderDesc`, `PipelineDesc`, `RenderTargetDesc`, `BindlessDescriptorSetLayoutDesc`, `DescriptorPoolDesc`), each with a defaulted `operator==`. `ShaderDesc` owns its SPIR-V, so the pointer-pinning `shaderSources` deque in `RenderContext` is gone. The dedup hashes and `HandleHash` combine fields with `hashCombine`. See [architecture.md](architecture.md). The original finding follows.
- It is a hand-maintained tagged union with a `std::string`, plus manual `==`/hash.
- Equality ignores fields that matter: pipeline equality ignores vertex layout, attachment formats and the descriptor layout, so two pipelines that differ only in color format alias each other.
- The hash XORs component hashes, so collisions are common (`a^b == b^a`, `x^x == 0`).
- Prefer distinct `BufferDesc`, `TextureDesc`, `PipelineDesc`, … structs with defaulted `operator==` and a proper hash combine.

**D6 — Scene preparation is all-or-nothing.** *Fixed 2026-11-22 (`D4`):* entities, meshes, materials and lights can be removed and destroyed, and their rows and pool ranges are reused. *Mostly fixed 2026-11-07:* `prepareScene` is gone. Engine-wide GPU tables (instances, materials, geometry) live for the engine's lifetime, and `syncGpuScene` uploads only the rows that changed. Each scene keeps a draw list that is rebuilt when an entity is added, an asset finishes loading, or a cull mode changes. Entities and materials can be added and edited at runtime (`updateMaterial`). Still open: nothing can be removed, since there is no destroy API and the tables are append-only (`D4`). The original finding follows. `prepareScene` is cached forever ([gpuScene.cpp:121-124](../src/renderer/gpuScene.cpp#L121-L124)). Entities, meshes and materials added, removed or edited after the first frame are ignored; only transforms update. A GPU scene needs incremental updates:
- slot allocation inside persistent mega buffers,
- dirty tracking with per-frame upload of the changed ranges,
- material and instance tables separate from geometry.

**D7 — The engine owns the event loop and input.** *Extended 2026-11-24:* more than one window: `Engine::addWindow(WindowDesc)` opens an SDL window, wraps an application's (`NATIVE`) or makes an offscreen one (`HEADLESS`), each with its own swapchain and surface; one submit waits for and presents every window's image; `InputEvent::window` tags each event, closing a window other than the main one is a `WINDOW_CLOSE` event, and only the main window's events reach the UI and the engine's camera (`examples/19_embedding`, `examples/20_views`). Still open: `D38`, `D39`. *Mostly fixed 2026-11-24:* `PlatformType::NATIVE` draws into the application's window: `EngineConfig::nativeWindow` is a `NativeWindow` (`NativeWindowType` `WINDOWS`, `X11`, `XCB`, `WAYLAND` or `METAL`, two `void*`, the first pixel size and the content scale), which `DeviceDesc::window` carries to `createVulkanSurface` (`src/rhi/vulkan/vulkanSurface.cpp`), the only file with window-system types. The SDL platform fills the same struct from SDL's window properties (a Metal view's `CAMetalLayer` on macOS), so every window takes the embedder's path, and SDL no longer loads Vulkan (`windowSurface.h` is gone). All input is a stream of `InputEvent`s (`rasm/input.h`: a key's meaning and its position, mouse, wheel, text, focus): the SDL platform makes them from its events, the application sends them with `Engine::addInputEvent`, and `pollEvents` applies them in `beginFrame` to Dear ImGui (no ImGui platform backend any more, so the `sdl3-binding` feature is dropped) and to `InputState` (`src/platform/input.cpp`), which gives the camera its input. `setWindowSize` and `setWindowContentScale` are the application's resize and display-scale events; the SDL platform reports a display-scale change itself, and the UI rescales its style. Cursor shapes, the clipboard and starting text input go through `Platform` hooks, which SDL fills. Escape quits only with SDL. Example `19_embedding` opens its own SDL3 window, and its `--headless` run uses a hidden window with a scripted drag, click and typing, so `verify-change` checks the native surface, the swapchain and the input path with nothing on screen. Camera controllers are helpers the application drives (2026-11-24): `CameraRig`, `createCameraRig` and `updateCameraRig` (`rasm/cameraController.h`) and `CameraInputState`, `addCameraInputEvent`, `takeCameraInput` with an `InputArea` per view (`rasm/cameraInput.h`) are plain structs and free functions with no `Engine`, which the engine's own path also calls; `CameraController::Type::NONE` keeps `beginFrame` off a camera, and `pollEvents()` (once per frame, callable before `render`), `getInputEvents`, `getCameraInput`, `getUiInputCapture` and `getDeltaTime` give the application the frame's input on every platform (`examples/05_city`, `examples/19_embedding`). Still open: more than one window (plan item "Multiple views and windows"), the IME candidate window's position (`D38`), and SDL video drivers without a native window handle (`D39`). *Partly fixed 2026-11-22:* the window and its events are behind a private `Platform` interface (`src/platform/platform.h`): `sdlPlatform.cpp` opens the SDL3 window and turns its events into `PlatformEvents`, which `Engine::pollEvents` applies, and `headlessPlatform.cpp` has neither. `EngineConfig::platform = PlatformType::HEADLESS` runs the engine with no window and no SDL: the device has no surface, and the frames render into an `OffscreenSwapchain` that `Engine::readFrame` copies back. A headless engine runs the UI with no input (`uiPlatform.cpp` uses no SDL for a window without a handle). Still open: creating the engine from a native window or surface handle (`PlatformType::NATIVE`), input fed by the application, the UI in a window the application owns, and camera controllers as helpers the application drives. The original finding follows.
- `pollEvents` runs inside `beginFrame`. Escape quits. The camera controller is driven internally and the caller must pass a camera.
- Applications never see input events.
- With `EngineConfig::ui` the SDL events also feed Dear ImGui, through ImGui's SDL3 backend in `src/platform/uiPlatform.cpp` only. An application that owns the loop either passes its SDL events on, or feeds ImGui with its own platform backend and tells RASM not to.
- You can't embed RASM in a host window (Qt, editor, map application) or run it headless.

Needed: a platform layer the application can replace, creation from a native surface or window handle, an offscreen/headless mode, and camera controllers as optional helpers driven by the application.

**D8 — Coordinate handedness is achieved by mirroring the world.** *Fixed 2026-11-04:* the world is right-handed Y-up. Import no longer mirrors glTF or OBJ geometry, and the Vulkan backend flips Y with a negative-height viewport in `setViewport`. Front faces are counter-clockwise. Cull mode is dynamic pipeline state (`RenderContext::setCullMode`), so the uber pipeline stays one pipeline. `prepareScene` groups the draws by cull mode, and `drawScene` issues one indirect draw per run of equal modes taken from the current transforms: `NONE` for double-sided materials (glTF `doubleSided`, or `createMaterial(..., doubleSided)`), `BACK` otherwise, and `FRONT` under a mirroring transform. Double-sided back faces are lit with the reversed normal. The original finding follows.
- glTF geometry gets a `scale(1,-1,1)` root ([meshImport.cpp:545](../src/assets/meshImport.cpp#L545)), and OBJ vertices are negated per vertex ([meshImport.cpp:687-689](../src/assets/meshImport.cpp#L687-L689)).
- That mirrors the world: the determinant is negative and the triangle winding flips. Back-face culling is disabled to hide this ([vulkanDevice.cpp:651-652](../src/rhi/vulkan/vulkanDevice.cpp#L651-L652)).
- User-specified positions and directions live in a Y-down world.

Use a right-handed Y-up world (glTF's convention) and do the Vulkan flip with a negative-height viewport (core since 1.1) or in the projection. Then enable culling and honor glTF `doubleSided`.

**D9 — The render graph only sorts.** *Resolved 2026-11-13:* all four bullets below are fixed; the steps follow. *Partly resolved 2026-11-07:* the graph now records barriers from what passes declare. `RenderContext` keeps each texture's state, so `transitionImageLayout` takes only the new usage, and the graph moves the textures a pass reads to `SAMPLED`. For buffers it keeps the last write and the reads since, across frames, and records one `memoryBarrier` per pass only for a read after a write, a write after a read or two writes. Before, it put a barrier on every change between compute and graphics and missed two graphics passes sharing a buffer. `endPass` still moves a render target's color to `SAMPLED` (`B10`), and `endFrame` moves the swapchain image to `PRESENT_SRC`. **D28 — An entity cannot hang on a node of an animated entity.** The pose lives only on the GPU: the `Animate` pass writes each animated sub-mesh's matrices ([animate.slang](../shaders/passes/animate.slang)), and the CPU never learns where a node is. **D32 — The Buffers section finds a target by its name, and names repeat.** *Extended 2026-11-24:* with several views (`Engine::render(views, count)`) each view's HDR target has its own name (`scene_hdr`, `scene_hdr_1`, ...), but the bloom levels of every view are named alike (`bloom_down_1`, ...), so only the first view's can be picked. `Inspection::target` is a `RenderTargetDesc::name`, and `updateInspectPass` takes the first entry whose name, kind and attachment match ([inspector.cpp:268](../src/renderer/inspector.cpp#L268)). Names are not unique: every directional light's shadow names its maps `shadow_cascade_0`, `shadow_cascade_1`, ... ([gpuScene.cpp:822](../src/renderer/gpuScene.cpp#L822)), so with two shadowed suns the list shows two `shadow_cascade_0 depth` entries and picking the second one shows the first. The same holds for two targets an application names alike. Name the maps after their light (as the spot and point maps are), or let an entry carry its handle and match by it. *Confirmed* by reading.

**D33 — An engine holds at most 7 meshes in its lifetime.** *Fixed 2026-11-22:* `MAX_MESHES` is gone, and an engine creates and loads meshes until its geometry pool is full. A mesh needs one row of the geometry table per sub-mesh (`EngineConfig::geometryPoolSubMeshes`) and ranges of the vertex, index, color, skin and morph pools; `GeometryPool::fits` checks all of them for the whole mesh before anything is created and logs what it needs, what is in use and the `EngineConfig` field to raise ([geometryPool.cpp:82](../src/renderer/geometryPool.cpp#L82)). The animation pool has its own check (`EngineConfig::animationPoolBytes`). `createMesh` takes its handle only after the upload, so a mesh that does not fit uses no index. The golden-image runner uses one engine for its 15 tests, and the goldens did not move. Handle reuse stays with `D4`. The original finding follows. `MAX_MESHES` is 8 ([mesh.h:19](../include/rasm/mesh.h#L19)) and `createMesh` and `loadGLTF` / `loadMesh` refuse a handle index at or above it ([mesh.cpp:70](../src/assets/mesh.cpp#L70), [mesh.cpp:122](../src/assets/mesh.cpp#L122)). Indices start at 1 and are never reused (`B13`, `D4`), and a glTF file is one mesh, so an application can create or load only 7 meshes in an engine's life, failed loads and meshes it no longer uses included. Nothing else is sized by it: the registry is a `std::vector`, and the GPU side lives in the geometry pool and its sub-mesh table (`EngineConfig::geometryPoolSubMeshes`). The golden-image runner needs 3 engines for its 13 models because of it (`tests/image/imageTests.cpp`). Raise the limit or drop it (an `EngineConfig` field like `maxLights`), and reuse handles with `D4`. *Confirmed* by reading and by the runner.

**D34 — An engine creates at most 255 materials in its lifetime.** *Fixed 2026-11-22 (`D4`):* `MAX_MATERIALS` is gone; `EngineConfig::maxMaterials` (4096 by default) sets how many materials are alive at once, the material table has one more row, and a full table logs an error that names the field ([material.cpp:71](../src/assets/material.cpp#L71)). `destroyMaterial` frees the row and the handle index for the next material. The original finding follows. `MAX_MATERIALS` is 256 ([engine.h:47](../include/rasm/engine.h#L47)), and it sizes the material table, one row per handle index ([gpuScene.cpp:324](../src/renderer/gpuScene.cpp#L324)). `createMaterial` and the glTF importer's `loadMaterial` refuse an index at or above it ([material.cpp:74](../src/assets/material.cpp#L74), [material.cpp:168](../src/assets/material.cpp#L168)). Indices start at 1 and are never reused (`B13`, `D4`), and every glTF material is a new one, so a streaming application runs out: Sponza alone has 25. Past the limit a glTF primitive falls back to its entity's material, or the default one, with only a warning, and `createMaterial` returns an invalid handle. Size the table from `EngineConfig` (like `maxLights`) and reuse its rows with `D4`'s destroy APIs. *Confirmed* by reading.

**D35 — Some lifetime paths still wait for the GPU.** *Extended 2026-11-24:* `Engine::resizeRenderTarget` waits for the frames in flight (the last values of both fences) when a size changes, because the new textures take the old ones' bindless slots, which those frames may read; `Engine::render(views, count)` calls it when a view's rect or texture changes size, so dragging an editor's splitter waits each frame of the drag. New slots for the new textures, with the old ones through the release queue (as below), would remove the wait; the material rows that name the slots would then be written again. Deferred destruction (`D4`) frees textures, buffers and render targets without a wait, but three paths still block the CPU: the last graph that lets go of a scene view waits for the frame and compute fences before it frees the view's buffers ([gpuScene.cpp:1096](../src/renderer/gpuScene.cpp#L1096)); placing transient render targets again waits for the device to be idle, because the new textures are written into the old ones' bindless slots at once ([renderContext.cpp:909](../src/rhi/renderContext.cpp#L909)); and growing the animation buffers waits for both fences ([animation.cpp:708](../src/renderer/animation.cpp#L708)). Each happens on a graph rebuild or a new animated entity, not every frame, so a streaming application that only creates and destroys meshes and textures does not hit them, but one that rebuilds graphs or starts many animations stalls a frame each time. Give the view buffers and the old animation buffers to the release queue, and let a re-placed target take new slots and release the old ones through it. *Confirmed* by reading.

**D37 — Skinned and morphed meshes have no meshlets.** `buildMeshlets` skips a sub-mesh with a skin or morph targets ([meshlets.cpp](../src/assets/meshlets.cpp)): its vertices move every frame, so meshlet spheres and normal cones made from the bind pose would cull visible pieces. Such a mesh is culled per draw with the posed sphere of the `Animate` pass, and drawn whole. Meshlets for them need bounds that move: per meshlet and frame from the `Skin` pass's posed vertices (its cost grows with the vertices, like `P18`), or per joint like the posed sphere (cones would then have to widen by the joints' rotation). Like `D29`, a LOD and its meshlets are built in the bind pose. *Confirmed* by reading.

**D38 — The IME window does not follow the text field.** Dear ImGui reports where the text cursor is through `ImGuiPlatformIO::Platform_SetImeDataFn`, and RASM sets no handler, so an input method (Japanese, Chinese, Korean) opens its candidate window where the window system puts it, not under the field being typed in. Typing works; only the candidate window's place is wrong. Fix: a `Platform` hook that takes the rectangle (`SDL_SetTextInputArea` for SDL), set from `updateUiPlatform`, and a way to read it for `NATIVE` applications.

**D39 — The SDL platform needs a native window handle.** Since `D7` the SDL platform makes no surface through SDL: `getNativeWindow` in [sdlPlatform.cpp](../src/platform/sdlPlatform.cpp) reads the Win32, Cocoa, X11 or Wayland handle from SDL's window properties, and the device makes the surface from it. SDL's other video drivers have no such handle, so the engine no longer starts on them; the one that matters is `kmsdrm` (a Linux console with no X11 or Wayland), where `SDL_Vulkan_CreateSurface` used `VK_KHR_display`. The error names the driver. Fix, if a target needs it: a `NativeWindowType` for a display plane (`VK_KHR_display`, picked by the device), or an opt-in fallback that lets SDL make the surface. *Confirmed* by reading.

**D40 — A view texture has no mips.** A view texture (`ViewOutput::target`) is a color target with one mip, drawn every frame by the tone-map pass ([toneMap.cpp](../src/renderer/toneMap.cpp)). A material that samples it on a far or slanted surface (a TV across a room) reads one texel per pixel from a much larger image, so the picture shimmers as the camera moves, as an unmipmapped texture does (`docs/guides/mipmaps-sampling.html`). Build its mips after the tone map (a compute pass that halves level by level, like the bloom chain) when a view texture is sampled smaller than its size. *Confirmed* by reading; the TV of `examples/20_views` is seen near its size, so it does not show there.

**D41 — The C API's last error hears every spdlog user on the thread.** The C layer adds its sink to spdlog's default logger ([cApi.cpp](../src/c/cApi.cpp), `initialize`), and RASM logs through that logger. With the vcpkg `x64-windows` triplet spdlog is a DLL, so the default logger is shared with every module of the process that uses the same spdlog DLL. An error that such a host module logs on a thread becomes that thread's `rasm_get_last_error`, reaches the C API's log callback, and, when it happens during a C call (only through the log callback today), turns that call's result into `RASM_ERROR_FAILED`. Fix direction: RASM logs through a logger of its own (`spdlog::get("rasm")`), and the C layer adds its sink to that one. *Likely.*

**D42 — The environment and the free-fly camera assume the world's +Y is up.** *Fixed 2026-11-25:* `SceneEnvironment::orientation` (a quaternion, identity by default) places the environment in any frame after its `rotation` around +Y, through `SceneData::environmentOrientation` and `toEnvironment`; `CameraController::FreeFly::up` (zero or +Y: as before) makes the free-fly controller yaw around it. Both are in the C API 1.2 (`rasm_scene_environment::orientation`, `rasm_camera_controller::free_fly_up`), and `examples/23_large_world` uses both. The original finding follows. A map engine on a globe places a scene in a local frame whose up is the ellipsoid's normal (`examples/23_large_world`: east, up and south at Paris, 48° from +Y). `SceneEnvironment::rotation` turns the environment only around +Y ([scene.h:26](../include/rasm/scene.h#L26)), so its sky and image-based light are tilted there, and the example draws without an environment; the free-fly controller yaws around world +Y ([cameraController.cpp:47](../src/scene/cameraController.cpp#L47)), so it rolls the horizon in such a frame. Fix: a full rotation (a quaternion) for the environment, and an up vector for the free-fly controller. *Confirmed* by reading, from the large-world work.

**D43 — A scene has one drawn set of tiles, whatever views draw it.** A `TileStreamer` adds the drawn tiles' entities to its scene ([tileStreamer.cpp](../src/scene/tileStreamer.cpp), `show`), and every view of the scene draws that one set; a tile's screen error is the largest over the views (`getTileScreenError`, [tileResidency.cpp](../src/scene/tileResidency.cpp)). A main view and a map of the same scene therefore share one cut: the map draws the main view's fine tiles near the camera, which is right but costs it triangles it does not need, and two views far apart (split screen over two cities) both draw the union of their cuts. Two scenes with a streamer each give each view its own cut, but load a tile both need twice. A per-view cut needs the entity's visibility per scene view (a view mask in `InstanceData`, culled in `countMain`) instead of scene membership, and the stand-in rule per view. *Confirmed* by reading.

**D36 — A 16-bit image loads as 8 bits.** stb_image gives 8 bits per channel: `loadTexture` decodes with `stbi_load` ([textureLoad.cpp:36](../src/assets/textureLoad.cpp#L36)), and a glTF's PNG with `stbi_load_from_memory` in its image job, which logs one info line for a 16-bit image ([meshImport.cpp:545](../src/assets/meshImport.cpp#L545)). Before `P14` such a glTF image was refused. Data that needs the precision loses it: a height map shows steps, and a 16-bit normal map bands on smooth curves. Decode with `stbi_load_16` and keep `R16G16B16A16_UNORM` (or BC5 / BC6H through KTX2) for data slots. *Confirmed* by reading.

## 4. Performance

**P1 — Every buffer is host-visible and mapped.** *Fixed 2026-11-04:* only buffers with `BufferDesc::hostVisible` (the per-frame model and scene data) are forced into host-visible memory. Other buffers are device-local, use `ALLOW_TRANSFER_INSTEAD` so they stay mapped where device-local memory is host-visible, and are otherwise filled through `rhi::UploadManager`: a staging ring with batched copies and timeline-fence completion ([architecture.md §12](architecture.md#12-rhi)). The original finding follows. (`HOST_ACCESS_SEQUENTIAL_WRITE | MAPPED`, [vulkanContext.cpp:205-208](../src/rhi/vulkan/vulkanContext.cpp#L205-L208)). On discrete GPUs without ReBAR, the mega vertex and index buffers end up in system RAM and every vertex fetch crosses PCIe. Static data should go to device-local memory through staging (or `ALLOW_TRANSFER_INSTEAD`). Keep host-visible memory for per-frame data only.

**P2 — Texture path.** *Fixed 2026-11-22:* host image copy is optional and used only where it costs the GPU nothing, mips are made on the worker, a model's texture copies spread over frames, and sampled textures are sub-allocated (`P22`) ([architecture.md §5](architecture.md#5-materials-and-textures), the guide `docs/guides/texture-uploads.html`). The `hostImageCopy` feature is enabled only when present ([vulkanDevice.cpp:588](../src/rhi/vulkan/vulkanDevice.cpp#L588)); a format is copied on the host only with `HOST_IMAGE_TRANSFER`, `optimalDeviceAccess`, `SHADER_READ_ONLY_OPTIMAL` among the copy layouts and a device-local memory type that a copied image may use too (`getHostCopyMemoryTypes`, [vulkanUtils.cpp:188](../src/rhi/vulkan/vulkanUtils.cpp#L188)), and its images are allocated only from those types, with no host-access flags. On the RTX 3060 the driver allows `HOST_TRANSFER` images only in host-visible types; host-copied into the BAR type, the GPU stalled 50 to 185 ms while a model's textures loaded, so host copy is off there and every texture comes through the staging ring; lavapipe copies 13 formats on the host. PNG and JPEG mips are made on the worker (`buildTextureLevels`, [mipChain.cpp:89](../src/rhi/mipChain.cpp#L89)), sRGB in linear light with alpha weighting, data as stored, glTF normal maps renormalized (the `sponza` golden moved for it). A glTF's textures are filled one at a time under `LOAD_BUDGET` (`PendingTextureLoad::levels`), and `isLoaded(mesh)` waits for them. `examples/10_ktx2_textures --measure` (Release, headless, RTX 3060), longest frame while loading: Flight Helmet PNG 206 → 10 ms, Sponza 280 → 6 ms, Flight Helmet KTX2 28 → 5 ms; whole load 0.92 → 1.00 s and 0.97 → 1.06 s, since the mips now follow the decode on the model's one worker (`P14`, fixed since: 191 and 200 ms). `VRAMStats::vramAllocated` counts the bytes in VMA's blocks. The original findings follow.
- Sampled images are created with `HOST_ACCESS_*` allocation flags for host image copy ([vulkanDevice.cpp:633-637](../src/rhi/vulkan/vulkanDevice.cpp#L633-L637)), which can push them into host-visible memory.
- Each image gets a dedicated allocation, and an image's (PNG, JPEG) mips are generated on the CPU on the main thread: 200 ms for the Flight Helmet's 15 PNG textures in a Release build. KTX2 files bring their mips.
- *Fixed 2026-11-02 (`D1`), 2026-11-04:* bindless textures share a fixed set of six samplers (`SamplerType`), picked per slot; glTF textures map their sampler onto it. Originally each texture created its own `VkSampler` and called `vkGetPhysicalDeviceProperties`. Drivers often cap samplers at about 4000, so use a handful of shared samplers.
- Host image copy also requires the `hostImageCopy` feature, which narrows hardware support. *Partly fixed 2026-11-21:* `HOST_IMAGE_TRANSFER` is checked per format (`VulkanDevice::queryFormatSupport`), and a format without it, or every format with `EngineConfig::hostImageCopy` false, is filled through the staging ring (`UploadManager::uploadTexture`). Still open: the device still requires the `hostImageCopy` feature, so a GPU without it can't start, though the staging path would serve it. The original finding: it also needs `HOST_IMAGE_TRANSFER` support per format, which nothing checked, so a driver that offers it for RGBA8 only failed every environment's `R16G16B16A16_SFLOAT` image.
- *Fixed 2026-11-21:* GPU-compressed textures. KTX2 files (`loadTexture`, glTF `KHR_texture_basisu`) are transcoded on the worker to BC7/BC5/BC4, ASTC or ETC2, whichever the device samples, with RGBA8 as the fallback, and keep the file's mips ([architecture.md §6](architecture.md#6-asset-import)). The Flight Helmet takes 68.6 MiB of video memory instead of 272.6 MiB as PNG. Images (PNG, JPEG) still become RGBA8 with mips made on the main thread.

**P3 — No instancing.** *Fixed 2026-11-07:* geometry is uploaded once per mesh into the geometry pool (since `P6`, 2026-11-04), and each draw now names an instance row (transform, geometry index, material index) through `DrawInfo::firstInstance`. Materials live once in the material table instead of being copied into every draw's `Modeldata`. Several instances of one sub-mesh are still separate draws, not one draw with `instanceCount > 1`. The original finding follows. Each entity copies its mesh into the mega buffer. `00_hello_scene` uploads the bunny three times ([gpuScene.cpp:134-157](../src/renderer/gpuScene.cpp#L134-L157)). Separate *geometry* (uploaded once per mesh) from *instances* (transform + material + mesh-range index).

**P4 — Per-call overhead in `RenderContext`.** *Fixed 2026-11-22 (`D4`):* each object type is a table of a `HandlePool` and a vector of `rhi::` pointers indexed by handle, so a lookup is a generation compare and an array access, with no hash; a texture's bindless slot is stored beside it, so `getBindlessTextureIndex` (called per pass) is no hash either. *Partly fixed 2026-11-02 (`D1`):* the tables hold pointers to `rhi::` objects, so a lookup copies nothing and device addresses are stored on `rhi::Buffer`. Every call still hashes its handles, until the index-based pools of `D4`. The original finding follows. Every call hashes a handle and **copies** the backend struct, including a `ResourceDesc` with a `std::string` (e.g. `fillBuffer`, [renderContext.cpp:675](../src/rhi/renderContext.cpp#L675); `getBufferDeviceAddress`, [renderContext.cpp:750](../src/rhi/renderContext.cpp#L750)). Use index-based pools, return references, and cache device addresses.

**P5 — Large by-value copies in the scene code.**
- *Fixed:* scene preparation no longer copies meshes (`processMesh` is gone), and `drawScene` copies nothing. Since 2026-11-07 the draw list is built from the GPU scene tables (`D6`).
- *Fixed 2026-11-04:* `getMeshByteSize` copied a whole `Mesh`; it now sums the sub-mesh ranges by reference.
- *Fixed 2026-11-07:* `RenderGraph::execute` copied `Scene`, which held 1,040 handles ([renderGraph.cpp:148](../src/renderer/renderGraph.cpp#L148)). It now reads only the camera handle; `Scene::entities` became a vector of up to 65,536 handles, which would have made the copy far worse.

**P6 — CPU memory retention.** *Fixed 2026-11-04:* meshes live in an engine-wide geometry pool (one vertex and one index buffer), uploaded when their load finishes, and keep only their pool ranges. The CPU vertex and index arrays, the `tinygltf::Model` and the `stbi` pixels are freed right after upload. Files are read and decoded on worker threads (`std::async`), and the main thread uploads the results at the start of a frame. A scene is prepared once all its assets are loaded. *Partly fixed 2026-11-01:* `GLTFRaw` no longer kept a copy of the `tinygltf::Model`. The original finding: CPU vertex and index arrays and the `stbi` pixel data for every `loadTexture` stayed resident for the engine's lifetime.

**P7 — Per-frame CPU work grows with draw count.** *Partly fixed 2026-11-07:* `updateTransform` rewrites only that entity's instance rows, and `syncGpuScene` uploads only the dirty row ranges of each frame slot. `drawScene` no longer loops over draws: it issues the cull-mode runs stored with the draw list. In `03_instances`, CPU frame time is the same with 1k and 10k static cubes. Still open: GPU-side transforms, and the draw-list rebuild. Only the scenes that hold a changed entity rebuild, and an entity triggers it once, when it becomes drawable, not once per finished texture. The rebuild itself is still O(entities in the scene) when the scene changes. The original finding follows. `updateUniforms` recomputes and uploads every model and normal matrix every frame, with no dirty tracking. That is fine now, but it becomes the bottleneck at 10⁴–10⁵ instances. Plan for dirty ranges and, later, GPU-side transform computation.

**P8 — Shader and pipeline creation.** *Fixed 2026-11-22:* `EngineConfig::cacheDir` ("cache" beside the executable, else the user's local cache folder; "" for none) holds a SPIR-V cache and a `VkPipelineCache`. A shader's entry, `shaders/<key>.shader`, is found by a 128-bit FNV-1a key of every input (the Slang build tag, the target and every compiler option, every file of `shaders/lib`, the source with its defines, the module name and entry point) and holds the struct layouts too, which `validateRasmStructs` checks on every hit; the folder is kept under 256 MiB. The pipeline cache, one file per GPU, is checked (vendor, device, driver version, UUID, Vulkan's own header, checksum) before use, merged with what another run saved and written through a temporary file and a rename. Every pipeline shares the bindless set layout's pipeline layout, with one push-constant range for every stage, and `RenderContext::pushConstants` lost its stage. `09_gltf_materials` (Release, headless): 2.43 s to the first frame without caches, 1.02 s warm. The vertex and fragment shaders of a pipeline are still compiled from two modules (`P23`). The original finding follows. Shaders are compiled from source on every launch. There is no `VkPipelineCache` and no SPIR-V cache. A pipeline layout is created per pipeline even though all pipelines share the same set layout and push-constant range.

**P9 — Shader detail.** *Partly fixed 2026-11-21:* the lights are read through `SceneData::lightsPtr`, one at a time in `shadePBR`'s loops, and `PBRInfo` holds no lights. `fragMain` still copies the material into `PBRInfo`. The original finding follows. `fragMain` copies all 8 lights and the material into a `PBRInfo` local ([rasm.slang:127-158](../shaders/passes/rasm.slang#L127-L158)). Read through the pointer, or pass indices, to keep register pressure down.

**P10 — The upload staging ring may be placed in video memory.** *Fixed 2026-11-22:* a staging buffer has `BufferUsage::TRANSFER`, which has no device-address bit ([vulkanDevice.cpp:276](../src/rhi/vulkan/vulkanDevice.cpp#L276)), so the rings go to system memory, unless all of video memory is host-visible (resizable BAR, or memory shared with the CPU, `VulkanDevice::wholeVramMapped`): there they ask for video memory ([vulkanDevice.cpp:757](../src/rhi/vulkan/vulkanDevice.cpp#L757)), since the GPU then copies within video memory and no small BAR heap is used up. Measured on the RTX 3060 with resizable BAR: the rings in system memory made the copies take 2.6 times as long on the GPU (the `17_streaming` burst 80 against 30 ms) and the burst load 486 to 507 ms against 432 to 441 ms. The original finding follows. Every buffer gets `VK_BUFFER_USAGE_SHADER_DEVICE_ADDRESS_BIT` ([vulkanDevice.cpp:277](../src/rhi/vulkan/vulkanDevice.cpp#L277)), and VMA counts any usage other than transfer as GPU access. With `VMA_MEMORY_USAGE_AUTO` and `HOST_ACCESS_SEQUENTIAL_WRITE`, `hostVisible` buffers, including the 64 MiB staging ring, then prefer device-local host-visible memory (ReBAR) over system RAM. That wastes the small BAR heap on systems without full ReBAR, and a staging buffer gains nothing from being in video memory. Leave the device-address bit off buffers that shaders never read through a pointer, starting with the staging ring. *Likely.*

**P11 — Async compute does not pay off for the scene passes yet.** *Extended 2026-11-22 (`D13`):* the loads' copies now run on the transfer queue where there is one, so only the frames' own fills are flushed before a compute submit; a texture filled from the ring is shared by the graphics, compute and transfer families when there is a compute queue, and the other images by the first two, still with no ownership transfers between them. With `EngineConfig::asyncCompute` the culling and Hi-Z passes run on the compute queue ([gpuScene.cpp:909-985](../src/renderer/gpuScene.cpp#L909-L985)), but the scene passes form a chain (cull, draw, Hi-Z, cull, draw), so each step waits for the other queue, and only the first cull of a frame can run next to the previous frame's last draw. Measured on `05_city` (RTX 3060, Release, present mode switched to IMMEDIATE for the test, two runs each): 1.68 / 1.69 ms per frame without, 1.71 / 1.72 ms with, so the handoffs cost a little more than the overlap saves. Uploads also stop the overlap: a frame with pending copies flushes them on the graphics queue before its first compute submit ([renderContext.cpp:1947](../src/rhi/renderContext.cpp#L1947)), and the compute queue waits for them while `copyBuffers` waits for all earlier graphics work ([uploadManager.cpp:209](../src/rhi/uploadManager.cpp#L209)). And with a compute queue every buffer and image is shared by both families (`VK_SHARING_MODE_CONCURRENT`, [vulkanDevice.cpp:470](../src/rhi/vulkan/vulkanDevice.cpp#L470)), which some GPUs compress less. So the option is off by default. It should pay off once a frame has graphics work that does not depend on culling (shadow maps, several views); measure again then. Ownership transfers for the images only compute reads would avoid the concurrent sharing. *Confirmed* (the measurement).

**P12 — Every fragment reads every shadow, even where its light adds nothing.** *Fixed 2026-11-21:* `shadePBR` shades each shadowed light first without its shadow and calls `sampleShadow` only when that light adds something to the pixel ([pbr.slang:213](../shaders/lib/pbr.slang#L213)); the texture indices still come from `SceneData`, so they stay uniform. The original finding follows. `fragMain` samples the shadow of each light before shading ([rasm.slang:156](../shaders/passes/rasm.slang#L156)), and `shadePBR` multiplies it in only afterwards. In `examples/07_lights` a fragment outside the spot light's cone, past the lantern's `range` or facing away from a light still runs the spot map's 4 gathers, the cube's 4 gathers and the cascade loop, then multiplies the results by 0. Sample a light's shadow inside the light loop of `shadePBR`, only when its attenuation, cone and n·l are above 0 (the texture indices stay uniform: they come from `SceneData`). *Confirmed* by reading; not measured.

**P13 — Every shaded view has a Transparent pass, also without see-through draws.** `addSceneViewPasses` adds the `Transparent` pass to each shaded view because the graph is fixed and the scene may gain `BLEND` materials later ([gpuScene.cpp:1148](../src/renderer/gpuScene.cpp#L1148)). In a scene without them the pass still begins and ends rendering, and the draw pass before it must store its depth for it. On a desktop GPU that is noise (0.001 ms for the pass in `05_city`, RTX 3060), but a tiled GPU loads and stores color and depth for it. Skip the attachments when the view has no blend run (the graph would need a pass that can be empty), or draw the blend run at the end of the last draw pass instead, which loses its GPU timer. *Confirmed* by reading; measured on desktop only.

**P14 — A glTF's KTX2 images are transcoded one after another on one thread, and its PNG and JPEG images get their mips the same way.** *Fixed 2026-11-22 (with `P21`):* the import job only parses the file and plans the images: tinygltf keeps every image's file bytes (`loadImage`), and each image a material reads becomes a child job on the worker pool that decodes it once (or transcodes it once per format) and makes the levels of each slot that reads it (`runImageWork`, [meshImport.cpp:714](../src/assets/meshImport.cpp#L714)); each sub-mesh's LODs are a child job too. No job waits: the last child to end runs `finishImageWork` (a failed KTX2 transcode falls back to the PNG or JPEG source there) and finishes the load ([mesh.cpp:79](../src/assets/mesh.cpp#L79)). Each job reads only its own image and writes only its own levels, so the result is the same in any order. `examples/10_ktx2_textures --measure` (Release, headless, RTX 3060, 24 hardware threads, median of 3): Flight Helmet KTX2 535 → 110 ms, Flight Helmet PNG 931 → 191 ms, Sponza 1052 → 200 ms. The longest frame while a model loads stays about the same, but Sponza's grows a little (`P25`). The original finding follows. Since `P2`, `buildImageLevels` makes each image's mips after the import on the same worker, one image after another: 223 ms for the PNG Flight Helmet's 15 images and 300 ms for Sponza's 69 (Release), and the whole loads went from 0.92 to 1.00 s and from 0.97 to 1.06 s. The fix is the same for both, and belongs with `P21`: a job per image (transcode or mips) on a bounded worker pool, with the import job waiting for its image jobs without holding a worker the pool needs. The mesh load's single worker transcodes every `KHR_texture_basisu` image in turn after the import ([meshImport.cpp:421](../src/assets/meshImport.cpp#L421)), while the other cores wait. The Flight Helmet's 15 textures (12 at 2048²) take most of its 540 ms load in `10_ktx2_textures` (Release, RTX 3060), so the load time grows with the texture count. Transcode the images on several workers (a job per image, once the engine has a thread pool, `P6`), or let Basis transcode a level on several threads. *Confirmed* by reading; the share of the load is estimated, not profiled.

**P15 — Far light clusters are big, so short-range lights crowd them.** A shaded view has 16 × 9 tiles at any resolution and slices that grow with depth ([lightClusters.slang:9](../shaders/lib/lightClusters.slang#L9)), so a far cluster covers much more of the world than a near one. In `examples/11_many_lights --bench --lights 16384` (lights of 0.9 m range, 1920x1080, RTX 3060) the clusters near the horizon fill up: 10 light and cluster pairs are dropped, and their pixels loop over up to `MAX_CLUSTER_LIGHTS` lights that mostly do not reach them. The draw passes take 10.8 ms, against 4.5 ms with 4096 lights of 1.75 m that cover the ground as densely; the example's marker cube per light adds to that, not measured apart. Shrink each cluster to the depths its pixels hold (needs the depth of a pre-pass), cut far tiles finer, or bin lights by depth (z-binning, Drobot 2017). *Confirmed* by measurement.

**P16 — One workgroup prepares every light of a view.** `lightsMain` runs as a single group of 256 threads over all of a view's local lights ([lightClusters.slang:50](../shaders/passes/lightClusters.slang#L50)), so it finds the slices' depth range with workgroup atomics and needs no clearing pass, but its time grows with the light count and the rest of the GPU waits for it. At the default `EngineConfig::maxLights` (16384) each thread prepares 64 lights in a row; the whole `Light Clusters` timer is 0.69 ms there (`examples/11_many_lights --bench --lights 16384`, RTX 3060), and a larger `maxLights` makes it longer. Dispatch a group per 256 lights and reduce the depth range with buffer atomics (cleared by the previous step, or by a fill), keeping the order of the lists. *Confirmed* by reading; not measured apart.

**P17 — A glTF mesh that several nodes use is uploaded once per node.** `traverseNodes` calls `extractGLTFRaws` for every node with a mesh ([meshImport.cpp:366](../src/assets/meshImport.cpp#L366)), so each use becomes its own sub-meshes, with its own copy of the vertices, indices and LODs in the geometry pool. A scene that places one tree mesh on 200 nodes stores the tree 200 times. Extract each glTF mesh once, and give each node's sub-meshes the same `MeshGeometry` with their own transform; the geometry table already allows rows that share geometry. *Confirmed* by reading.

**P18 — The Animate pass poses every playing entity in every frame, and the Skin pass skins it.** `recordAnimation` dispatches one group per row of the animated entity table ([animation.cpp](../src/renderer/animation.cpp)), and `recordSkinning` one group per row and 64 of its skinned vertices, also for an entity whose clip stands still (`speed` 0, or a clip that does not loop and has ended), and for one that no view sees. Its time grows with the playing entities, their nodes and their skinned vertices (numbers in `docs/development_plan.md`, phase 4). Skip an entity whose clip time and matrix are the same as in the frame two before (its slot still holds the result), and one that no view drew in the frame before (the views' visibility flags), keeping its previous transform and its previous skinned vertices for motion (the Skin pass then copies them, or the two slots swap per entity). Since `D30` is fixed, a skinned entity that plays nothing is posed at rest and skinned every frame too, until this is done; so is a morphed one, whose weights stand still, and a group of the Skin pass lists its targets again each frame. A graph that draws two scenes poses all playing entities, also those of other scenes, and two graphs in one frame pose them twice. *Confirmed* by reading.

**P19 — The Skin dispatch is sized by every animated row and the largest skinned mesh.** `recordSkinning` dispatches `entityRows` × ceil(`maxSkinnedVertices` / 64) groups ([animation.cpp](../src/renderer/animation.cpp)), so rows of rigid-only or stopped entities and every row past its own mesh's vertices launch groups that read the row and return, and each group walks its mesh's sub-meshes to find its own ([skin.slang](../shaders/passes/skin.slang)). 10000 entities with rigid clips beside one 50k-vertex character launch about 7.8 million groups to skin 50k vertices. Dispatch over a compact list of (skinned row, 64 vertices) jobs that the CPU appends at an entity's first play, with the sub-mesh in the job. Since morph targets, every posed sub-mesh starts on a multiple of 64 among its entity's skinned vertices (`alignToSkinGroup`, [animation.cpp:391](../src/renderer/animation.cpp#L391)), so a group holds one sub-mesh's weights; a skinned mesh of many small sub-meshes pays for the padding: 30 sub-meshes of 20 vertices take 1920 vertex slots instead of 600 per entity (128 B each, both slots) and three times the groups. The job list would remove the padding too. *Confirmed* by reading, from the skinning review; the padding from the morph targets review.

**P20 — A clip's morph weights take about five times the animation pool they need.** `readWeightSamplers` gives each target its own sampler with its own copy of the key times ([animationImport.cpp:93](../src/assets/animationImport.cpp#L93)), and `buildAnimationPoolData` stores each scalar weight as a 16-byte value with 3 unused floats ([animation.cpp:268](../src/renderer/animation.cpp#L268)). A 52-target face with a 60 s clip at 30 keys per second takes about 1.9 MB instead of 0.4 MB, so a few such clips fill the default 16 MiB `EngineConfig::animationPoolBytes`, and the next mesh fails to load. Share the key times of one weights channel and pack its values per key (all targets in a row), with a sampler kind that the `Animate` pass reads with a stride. *Confirmed* by reading, from the morph targets review.

**P21 — Every load starts its own thread, and nothing bounds how many run at once.** *Fixed 2026-11-22:* loads run on one `WorkerPool` ([workerPool.cpp:150](../src/core/workerPool.cpp#L150)) of `EngineConfig::loadThreads` threads (0: the hardware threads minus one), with two FIFO queues: the child jobs of a running load first, then the loads. A load starts only when its bytes fit `EngineConfig::loadMemoryBudget` (512 MiB) next to what started loads and results waiting for upload hold, or when nothing is held ([workerPool.cpp:181](../src/core/workerPool.cpp#L181)); its bytes are estimated from the header (a mesh: its file size until it is parsed, then its geometry and image files, with its decoded images as a next step that waits for the budget too) and set to the real size when it ends, and the main thread gives them back once it has used the result (a glTF texture's levels when that texture is filled). A waiting load waits as a path in the queue, not as pixels. Each load has a `LoadTicket`: `destroyMesh`, `destroyTexture` and `destroyEnvironment` drop its pending entry and the ticket (`dropLoad`, [workerPool.cpp:85](../src/core/workerPool.cpp#L85)), so a queued job is skipped and a running one gives its result up; `~Engine` drops every load and joins the workers. `waitForLoads` finishes what is ready before it waits for the next load, so a load behind the budget always starts. `Engine::getLoadStats`, a Loads line in the RASM window; tests in `tests/workerPoolTests.cpp`. `examples/17_streaming --burst` (300 Sponza images in one frame, 75 of them destroyed a frame later; Release, headless, RTX 3060, median of 3): peak private memory 3519 → 2964 MiB with at most 512 MiB decoded at once, the longest frame 37.2 → 22.2 ms, all loaded in 501 → 453 ms. On Windows `std::async` went through the MSVC thread pool, so the process had 44 threads at most, not 300 (libc++ on macOS starts one per call); now 23 workers and 39 threads in all. The original finding follows. `loadMesh`, `loadTexture` and `loadEnvironment` each call `std::async(std::launch::async, ...)` ([mesh.cpp:155](../src/assets/mesh.cpp#L155), [texture.cpp:135](../src/assets/texture.cpp#L135), [environment.cpp:63](../src/assets/environment.cpp#L63)), and the result (a whole decoded glTF with its buffers, or a decoded image) stays in memory until `finishLoads` uploads it, under its per-frame budget. An application that asks for 300 map tiles in one frame starts 300 threads, and its peak memory is the size of all 300 decoded files. Before `D33` the mesh cap kept mesh imports at 7 for an engine's life; textures never had a cap. Run the imports on a small pool of workers (the hardware thread count) with a queue, and keep the decoded results that wait for upload under a byte budget. The same pool should run a glTF's per-image work as jobs of their own (`P14`: KTX2 transcodes, and since `P2` the mips of PNG and JPEG images), so an import job must wait for its image jobs without blocking the workers they need. *Confirmed* by reading, from the `D33` review.

**P22 — Freeing a texture costs a dedicated allocation's free, and a frame frees all it may.** *Fixed 2026-11-22 (`P2`):* sampled textures are sub-allocated from VMA's blocks; attachments and storage textures keep a dedicated allocation ([vulkanDevice.cpp:746](../src/rhi/vulkan/vulkanDevice.cpp#L746)). In `17_streaming` (Release, headless, RTX 3060) `collectReleases` takes 0.020 ms per frame on average and 0.15 ms at most (Tracy), against 0.61 and 1.42 ms before, and the longest frame after the first second went from 9.4 to 1.2 ms, so the release queue needs no time budget. The original finding follows. Every texture has a dedicated allocation (`VMA_ALLOCATION_CREATE_DEDICATED_MEMORY_BIT`, [vulkanDevice.cpp:740](../src/rhi/vulkan/vulkanDevice.cpp#L740)), so `destroyTexture` is a `vkFreeMemory`. In `17_streaming` (Release, RTX 3060) the release queue itself costs 0.035 ms per frame that has something to free, but the texture frees inside it take 0.16 ms each on average and up to 13 ms for the fox's texture, and `collectReleases` runs every free that is due in one frame, so destroying a mesh with big textures makes one long frame. Suballocate sampled textures (with `P2`), or give `collectReleases` a time budget and leave the rest for the next frame. *Confirmed* by measurement.

**P23 — A graphics pipeline's source is compiled twice.** `Renderer::createGraphicsPipeline` calls `compileFromString` once for `vertMain` and once for `fragMain`, with the module names `<name>.vert.slang` and `<name>.frag.slang`, so Slang loads, parses and checks the same source (`rasm.slang` with `pbr.slang` and the rest of `lib/`) twice before it links each stage ([renderer.cpp:588-589](../src/renderer/renderer.cpp#L588-L589)). It costs only when the shader cache (`P8`) misses, but then Slang takes 1389 ms of the 1449 ms `09_gltf_materials` spends making pipelines (Release), and the second load's share of it is not measured yet. Load the module once and link both entry points from it, or ask Slang for both stages' code from one composite. *Confirmed* by reading and measurement, from the `P8` work.

**P24 — A load's steps on the main thread are never split.** *Partly fixed 2026-11-22:* a load's texture is filled in parts of `TEXTURE_FILL_PART` (4 MiB) with `LOAD_BUDGET` checked between them (`RenderContext::fillTexturePart`, `TextureFillProgress`), the ones begun first, and a part stops where the staging ring is full instead of waiting for the GPU; the texture counts as loaded once its last part is on the GPU. The longest frame while the PNG Flight Helmet loads went from 9.2 to 5.0 ms, and the `17_streaming` burst's from 25.8 to 18 to 21 ms, the first frame's pipelines (Release, headless, RTX 3060). Still open: a model's geometry and materials are made in one step, `finishMeshLoad` ([mesh.cpp:272](../src/assets/mesh.cpp#L272)), which is now the longest frame while Sponza loads (7.0 to 7.7 ms, 6.2 ms of it there, Tracy). The original finding follows. `finishReadyLoads` checks `LOAD_BUDGET` only between steps ([engine.cpp:320](../src/engine.cpp#L320)), and two steps can be long. `finishMeshLoad` ([mesh.cpp:272](../src/assets/mesh.cpp#L272)) copies a model's whole geometry into the pool and creates all its materials and textures in one go: 5.6 ms for Sponza (Release, RTX 3060), more for a bigger model. And one texture's fill copies every level in one go: 1.6 ms on average and up to 5.2 ms for a 2048² RGBA8 texture with its mips through the staging ring (the PNG Flight Helmet, Tracy), so about 16 times that for an 8192² one. Since `P2` a model's textures are separate steps, so these are the long frames left while loading. Split a texture's fill by mip level (or rows) across frames, keeping the texture unsampled until its last part, and append a model's sub-meshes to the pool a few per frame. *Confirmed* by measurement, from the `P2` work.

**P25 — The load workers compete with the main thread for the CPU.** `AssetLoaderConfig::loadThreads` (`EngineConfig::loadThreads`) defaults to the hardware threads minus one ([assetLoader.cpp:30](../src/assets/assetLoader.cpp#L30)), and the workers run at the same OS priority as the main thread. While a model's image jobs fill every worker, the driver's threads and the workers share the cores with the main thread, so its frames take longer: in `examples/10_ktx2_textures --measure --model Sponza.gltf` (Release, headless, RTX 3060, 23 workers) the longest frame while loading is 7 to 10 ms and sometimes 16 ms, against 6.5 ms with one `std::async` task per load. Run the workers at a lower priority (`SetThreadPriority`, `pthread_setschedparam` or a QoS class on macOS), or leave one more hardware thread free by default. *Confirmed* by measurement, from the `P21` work.

**P26 — A finished load's decoded data is freed on the main thread.** *Fixed 2026-11-23:* `AssetLoader::Impl::freeOnWorker` ([assetLoader.cpp:201](../src/assets/assetLoader.cpp#L201)) hands the last reference of a finished load's result (`MeshLoadJob`, `TextureLoadJob`, a glTF texture's levels, `EnvironmentLoadJob`) to a child job of the worker pool, which frees it and only then gives its bytes back to the load budget, so the budget does not count a result as gone while it is still in memory (`dropLoad` returns a finished load's bytes for that, also when it finished just as it was dropped); `dropPendingLoad` does the same for a finished load that is dropped, and a pool that is stopping frees on the caller. Measured (Release, headless, RTX 3060, 23 workers, `tools/load_bench.py`, median of 5): the main thread spent 70.5 ms in `new` and `delete` during the 300-image burst of `17_streaming` and 3.5 ms after; `beginFrame`'s self time in a burst frame fell from 1.1 to 0.05 ms, and the `LOAD_BUDGET` copies more in that time instead, so the burst loads in 335 ms instead of 413, Sponza in 176 ms instead of 184. Still open: a glTF image that several textures share counts its bytes with the first of them (`GltfImportCache::movedBytes`), which gives them back when it is filled while the others still hold the levels, so for a while the budget counts less than what is in memory. The original finding follows. After a texture is filled, `finishReadyLoads` destroyed its `PendingTextureLoad`, which freed the decoded levels on the main thread: a block of several MiB comes from the operating system, and its free gives the pages back (0.15 to 0.3 ms each, 1.2 ms per burst frame). `finishMeshLoad` freed the mesh's CPU geometry the same way (1 ms in one Sponza frame).

**P28 — Meshlet culling on the vertex-pulling path costs more than it saves with LODs.** *Partly fixed 2026-11-23:* the mesh-shader path (`MeshletPath::MESH_SHADERS`, `VK_EXT_mesh_shader`) culls the same chunks in a task shader inside the draw pass (`taskMain` in `shaders/lib/meshletTask.slang`), with no meshlet passes, no meshlet draw list and no budget. Measured the same way (off / vertex pulling / mesh shaders, 600 frames after 120): `18_meshlets` 1.97 / 2.18 / 1.99 ms; `--no-shadows` 0.58 / 0.61 / 0.54; `--lod-error 0` 5.81 / 5.59 / 5.15 (13.1 M triangles, vertex pulling 15.9 M as it hits its budget); `--lod-error 0 --no-shadows` 1.71 / 1.17 / 1.19; `--async-compute` 1.96 / 2.22 / 1.97; `05_city` 1.91 / 1.92 / 1.93. So the default is now `MeshletPath::AUTO`: mesh shaders where the GPU has them (about 1% more with LODs, up to 30% less on dense meshes), off elsewhere (MoltenVK). What stays open is the vertex-pulling path's cost, below. The original finding follows. With `MeshletPath::VERTEX_PULLING` every culling phase of every view that draws meshlets adds two indirect dispatches and two barriers (`recordMeshletCulling`, [gpuScene.cpp](../src/renderer/gpuScene.cpp)), and `writeMain` writes chunks. In `examples/18_meshlets --bench` (Release, headless, 1920x1080, RTX 3060, the camera and 4 cascades) that is 0.24 ms for 21k meshlets drawn and 10k culled, while the 1M triangles it drops cost little: the frame goes from 1.96 to 2.22 ms. Only where LODs leave many triangles does it win (every mesh at LOD 0: 1.69 → 1.19 ms without shadows, 5.79 → 5.59 ms with them). So `EngineConfig::meshletPath` is `OFF` by default. A task shader that culls the same chunks inside the draw (the mesh-shader path) has no extra passes and no meshlet draw list; on the vertex-pulling path, async compute (`EngineConfig::asyncCompute`: 2.08 → 2.16 ms) and fewer views with meshlets help. *Confirmed* by measurement.

**P29 — Debug builds allocate in steady frames.** `rasm_image_tests` built with `x64-debug` reports 4 to 5 heap allocations of 16 bytes per steady frame (`local_shadows`, `skinning`, on `main` too), where the Release build has none (`P27`). They are likely the debug iterators' proxy objects of the Microsoft STL (`_ITERATOR_DEBUG_LEVEL` 2), made when a container is created or moved. Only the Release numbers matter for `P27`; finding the site would let Debug runs check it too. *Confirmed* by measurement.

**P27 — Steady frames allocate on the heap.** *Fixed 2026-11-23:* every example's steady frame makes no heap allocation on the main thread, and `rasm_image_tests` fails a test whose steady frames do (`tests/image/allocationCounter.cpp`, Windows only). Measured with a counting `operator new` (Release, frames 500 to 1500): `05_city` made 24 allocations and 259 KB per frame, `11_many_lights` 18, `07_lights` 6, the others 0 to 7. The sites: `syncGpuScene` moved `movedEntities` into `settlingEntities`, so the list grew again from empty every frame (now a swap, [gpuScene.cpp:383](../src/renderer/gpuScene.cpp#L383)); `drawCullingSection` built its "LOD draws" line in a `std::string` (now a stack buffer); `RenderContext::getTextureDesc` returned a copy with its name string, which `beginPass` and `getUiTexture` called every frame (it returns a `const TextureDesc&` now); `prepareSceneView` built a debug view's defines string every frame (now only while a pipeline is missing). The time was small (5.4 µs of a 1.36 ms frame in `05_city`), so the frame times did not change. A per-frame arena and pool allocators for the registries were not built: nothing in a steady frame needs them. Still allocating, on purpose: Dear ImGui when it bakes a new glyph or grows its buffers, and creating or destroying objects (about 7 allocations a frame of `RangeAllocator` free lists while `17_streaming` streams, a few µs).

**P30 — `createMesh` builds a large mesh's meshlets on the main thread.** `Renderer::createMesh` ([mesh.cpp](../src/assets/mesh.cpp)) calls `buildMeshlets` (and `buildMeshLods` with `RendererConfig::meshLods`) before it writes the pool, on the calling thread, for every sub-mesh of 1024 triangles or more. An application that makes its own tiles, as a map engine does from height maps or vector tiles, pays it in the frame: a 33 × 33 height grid with its skirt (2560 triangles) took about 1 ms of the main thread in `examples/24_map_tiles` (Release, RTX 3060), so 4 tiles a frame made 5.6 ms frames, and the example uses a 17 × 17 grid (768 triangles) to stay under the threshold. Let an application build the meshlets on its own thread (a `buildMeshlets`-like step on plain arrays, then a `createMesh` that takes them), or let `createMesh` hand the work to the loader's worker pool and return a `LOADING` mesh. *Confirmed* by measurement, from the tile streaming work.

The overlay's text is rebuilt every 250 ms of wall-clock time ([statsOverlay.cpp:21](../src/renderer/statsOverlay.cpp#L21), [statsOverlay.cpp:146](../src/renderer/statsOverlay.cpp#L146)), so the frame whose numbers show at frame N depends on how fast the frames before it ran. `03_instances` and `05_city` show it, and `verify-change` reports a DIFF in its top-left corner whenever start-up gets faster or slower: on the spot and point shadow branch, slower shader compiles moved the shown frame past one more spawned row of `03_instances` (draws 7856 / 10.2K became 7956 / 10.3K) with the scene's pixels unchanged. Rebuild the text every N frames under `--fixed-step`, or hide the overlay in verification runs. With `EngineConfig::ui`, which every example sets, the RASM window renews its numbers every 250 ms the same way (`STATS_REFRESH` in [engineUi.cpp](../src/renderer/engineUi.cpp)), so `03_instances`, `05_city` and `10_ktx2_textures` (which show the stats from the start) and `15_debug_ui` have it too. *Confirmed.*
- **C16 — Verify images depend on how far the asynchronous loads got.** *Fixed 2026-11-22:* every example that loads takes `--wait-for-loads` (`examples/exampleArgs.h`) and then calls `Engine::waitForLoads` before its first frame, and `verify-change` passes it with `--fixed-step`. The original finding follows. `verify-change` screenshots frame N, but an example that does not wait for its loads draws a mesh only from the frame its load (and its textures) finished, which depends on wall-clock time, not on N. Under the gfxreconstruct capture, `02_gltf` on `main` (cc790ed) spends about 7 s (Release) to 9 s (Debug) in its first 4 frames and has the coffee room loaded by frame 4; on the node animation branch those frames are fast, the room loads at frame 18 to 22 (Release, 0.95 s) or 167 to 240 (Debug, 2.4 to 3.8 s), so frame 60 shows the room on one and not on the other. The import itself takes the same time on both (183 to 186 ms in Release without capture). Fix with the headless/golden-image item: the examples (or the verify script, through a flag) wait until every load is done (`isLoaded` of each mesh and texture, or `waitForLoads`) before they count frames. *Confirmed* by measurement.
- **C17 — The `--bench` averages of `12_animation` count one frame too many.** It adds the GPU timers of frames 300 to 600, 301 frames, and divides by 300 ([main.cpp](../examples/12_animation/main.cpp)), so every printed time is about 0.3% high. `13_skinning` sums frames 300 to 599. Stop at frame 599 there too. *Confirmed*, from the skinning review.

- **C18 — A copied runtime DLL goes stale when only the library changes.** `rasm_copy_runtime_dlls` copies a program's DLLs next to it in a `POST_BUILD` step ([RasmRuntimeDlls.cmake:6](../cmake/RasmRuntimeDlls.cmake#L6)), which runs only when the program links again. A change inside `rasm_c` that keeps its exports leaves the import library the same, so Ninja does not link `22_c_api` again, and it runs with the old `rasm_cd.dll` beside it: after a GPU struct change it failed the struct check with the old sizes. CI builds from scratch, so it does not show there. Fix: copy with a custom command that depends on the DLLs (`$<TARGET_RUNTIME_DLLS>` as a dependency), or set the examples' output folder to the libraries'. *Confirmed*.

## 6. What is already good

These are worth keeping as the engine evolves:
- **Modern Vulkan baseline:** dynamic rendering, synchronization2, per-image render-finished semaphores (the correct modern pattern), VMA with budget tracking, vk-bootstrap.
- **A GPU-driven core:** one pipeline and a few indirect draws per scene, vertex pulling, bindless textures, and BDA through a single 16-byte push constant.
- **A careful CPU/GPU layout contract:** scalar layout with `static_assert`s and comments explaining the failure mode.
- **Correct color handling:** sRGB versus linear texture formats, sRGB-aware mip generation, and linear shading with sRGB output.
- **A solid PBR core:** a Filament-style BRDF, UV-derivative tangent frames that handle mirrored UVs, and per-texture UV sets.
- **A thoughtful camera:** frame-rate-independent easing, and a trackball that eases along the orbit sphere.
- **A clean layering intent:** handles everywhere and a single creation descriptor. The ideas are right; the implementation needs to catch up (D1, D5).
