Color spaces: sRGB and linear

A color value can mean two different things: an amount of light, or a code chosen to look even to the eye. Images are stored as codes (sRGB). Light must be computed as amounts (linear). This page explains the sRGB curve, why the math must happen in linear, which textures are colors and which are data, and how the GPU converts between the two for free. The last part shows how RASM does it.

In short

  • A linear value is proportional to the light: 0.5 is half as much light as 1.0.
  • An sRGB value is a code on a curve that spends more of the 256 steps on dark tones, where eyes are sensitive. Linear 0.5 is sRGB 0.735 (byte 188); sRGB 0.5 is only 21% of the light.
  • Lighting, blending, filtering and averaging must use linear values. Doing them on sRGB codes gives wrong, usually too dark, results.
  • Color textures (base color, emissive) are sRGB. Data textures (normals, roughness, metalness, occlusion) are plain numbers and must not be converted.
  • Formats ending in _SRGB make the GPU decode on read and encode on write, in hardware. The shader sees and writes linear values only.
  • Light can be brighter than 1.0. Tone mapping squeezes it into 0 to 1 before the final encode.

1Two kinds of numbers

Light is made of photons. Twice the photons is twice the light, and two lamps together give the sum of both. A number that works like that is linear: it is proportional to the physical amount of light. All of physics, and so all lighting math, works on linear numbers.

Eyes do not work like that. They notice ratios: going from 1% to 2% of the light looks like a big step, going from 50% to 51% looks like nothing. If an 8-bit image stored linear values, most of its 256 steps would be spent on bright tones that look the same, and the dark tones would show visible bands.

So images are stored as codes on a curve that roughly matches the eye. The curve used by almost every screen, photo and web page is sRGB. A program that wants to do math on light must first decode the code to a linear value, do the math, and encode the result for the screen.

2The sRGB curve

The sRGB standard (IEC 61966-2-1) defines the curve exactly. It is a power curve with a short straight piece near black, so that the slope at 0 is not infinite. Values are between 0 and 1 (divide a byte by 255).

decode (sRGB code s → linear light L):
    L = s / 12.92                          if s ≤ 0.04045
    L = ((s + 0.055) / 1.055) ^ 2.4        otherwise

encode (linear light L → sRGB code s):
    s = 12.92 · L                          if L ≤ 0.0031308
    s = 1.055 · L ^ (1 / 2.4) − 0.055      otherwise

The value people find surprising: a pixel stored as byte 128, "half" of 255, shows only 21% of full light. And half of full light is byte 188.

3Why the math must be linear

Lighting is adding and scaling amounts of light: a surface under two lamps gets the sum of both, a surface turned away gets a fraction. That is only true for linear values. On sRGB codes, "half" and "plus" mean something else, and every result comes out wrong.

Follow one texel from the texture to the screen. The texture says the surface is gray, stored as byte 128. Two lamps each give it half of full light.

1. The texel: byte 128, an sRGB code

This is what the artist's image file holds: a code chosen so that it looks like a mid gray on screen.

2. Decode to linear

Now the number means something physical: the fraction of light the surface reflects (its albedo).

3. Light it: two lamps, half light each

Adding and scaling linear values is just physics. This is the part the shader does.

4. Encode for the screen

The screen's own curve then turns the code back into light. The round trip is exact.

Now the same with one lamp, done right and done wrong:

Math on codes makes every shadow and every falloff too dark, and makes light sources add up wrongly: two lamps that each give a mid gray do not add to the brightness one lamp twice as strong would give. The look is harsh, with sudden dark edges. Linear lighting gives soft, physically plausible falloff.

4Color textures and data textures

Only textures that hold colors meant to be seen are stored as sRGB. Many textures hold numbers: a direction, a roughness, a mask. Those are already linear, and decoding them as sRGB changes the numbers.

5The GPU converts for free

Modern GPUs do the sRGB curve in hardware. The format of an image says whether its bytes are sRGB codes. A format ending in _SRGB (for example R8G8B8A8_SRGB) means: decode when read, encode when written. The same bytes in a _UNORM format are read as plain numbers divided by 255.

StepWhat the hardware does with an _SRGB format
SampleDecodes each texel it reads to linear, then filters (bilinear, trilinear) the linear values. Alpha is not decoded.
WriteEncodes the shader's linear output to sRGB codes as it stores them.
BlendReads the stored code, decodes it, blends in linear, encodes the result.
Copy, clearA copy moves bytes unchanged. A clear color is given in linear and encoded.

Converting in the shader instead (reading a UNORM texture and calling pow) works for a single read but is wrong with filtering: the GPU then filters the codes, before the shader can decode them. Use the _SRGB format and let the sampler do it.

6Filtering and blending are math too

Any operation that mixes colors must mix linear values. The same black-and-white example comes up again and again:

OperationMixing white and black 50/50On codesIn linear
Bilinear filteringa sample between a black and a white texel128 (21% light)188 (50% light)
Mipmap generationa 2×2 block of black and white (see mipmaps)128188
Alpha blendingwhite at 50% opacity over black128188
Anti-aliasing (MSAA resolve)an edge pixel half covered128188

On codes, every mix is too dark. Thin bright lines (text, wires, stars) look thinner and darker than they should, and edges look jagged even with anti-aliasing.

7Light above 1.0: tone mapping

Linear light has no upper limit. A lamp-lit white wall can be 4.0, a spot of sunlight 20.0. The screen's codes stop at 1.0. Simply clipping everything above 1 turns all bright areas into the same flat white. Tone mapping is a curve that squeezes the whole range into 0 to 1, keeping the order of brightness. It runs on linear values, before the sRGB encode.

To have values above 1 to map, the scene must be rendered into a target that can store them: a 16-bit float format, not an 8-bit one. A typical frame renders the scene in linear float, applies exposure and tone mapping in one full-screen pass, and writes the result to the sRGB swapchain.

sRGB is also a set of colors

This page is about the transfer function: the curve between light and code. A color space also fixes its primaries: which exact red, green and blue the channels mean. sRGB shares its primaries with Rec. 709 (HDTV). Wide-gamut and HDR displays use other primaries (Display P3, Rec. 2020) and other curves (PQ for HDR10). The rule stays the same: decode to linear, compute, encode for the display.

9In RASM

RASM follows the textbook pipeline with 8-bit textures and an 8-bit sRGB swapchain. The GPU decodes color textures and encodes the output. Shaders work in linear only, and the PBR shader tone maps each pixel itself.

Keep these true
  • Normal, metallic-roughness and occlusion textures are R8G8B8A8_UNORM; color and emissive textures are R8G8B8A8_SRGB.
  • Shaders output linear color. Never apply the sRGB curve in a shader: the swapchain format encodes.
  • The swapchain and any render target that drawScene draws into must be an sRGB format; with a UNORM one, the image comes out too dark.
  • Material factors are linear. Convert a color from an sRGB color picker before storing it.
