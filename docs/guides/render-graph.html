Rendering

The render graph

A render graph is a list of passes. Each pass says what it reads and what it writes. The graph sorts the passes so every writer runs before its readers, then records them into one frame, with the barriers and layout changes that the reads and writes need.

CPU work GPU work (a pass) GPU buffer or texture

In short

  • addPass / addComputePass take a name, a setup function (runs once, at once) and an execute function (runs every frame).
  • In setup, PassBuilder::read and PassBuilder::write record the textures, buffers and render targets the pass uses.
  • compile turns "B reads what A writes" into an edge A → B and sorts with Kahn's algorithm. A cycle logs an error and the graph draws nothing.
  • execute(camera) runs beginFrame, every pass in order, then endFrame.
  • Before each pass the graph records what its declarations need: textures and render targets it reads go to SAMPLED, and a buffer gets a memoryBarrier only after another pass wrote it, or before a write when another pass used it. The buffer state carries over to the next frame.
  • A render target has one color and one depth texture per frame slot. Later passes read the color through the bindless set.

2Adding a pass

setup: runs once, inside addPass

It gets a PassBuilder. It can create resources (they are created at once, through the engine) and must declare what the pass reads and writes. Nothing is recorded on the GPU.

execute: runs every frame

It gets the RenderContext and records commands: drawScene, or its own pipeline, binds and draws or dispatches. It takes the frame's command buffer from getCurrentFrameResources.

graph.addPass(
    "Forward",
    [&](rasm::PassBuilder &builder) // setup: once
    {
        rtHandle = builder.createRenderTarget({...});
        builder.write(rtHandle);
    },
    [&](rasm::RenderContext &) // execute: every frame
    {
        engine.drawScene(scene, camera);
    });

3compile: edges and Kahn's sort

First compile maps every written resource to its writer. There is one map per kind: textures, buffers and render targets.

ResourceWriterReadersEdges
particles (buffer)SimulateForwardSimulate → Forward
scene RTForwardComposite, BloomForward → Composite, Forward → Bloom
bloom RTBloomCompositeBloom → Composite

Each edge adds the reader to the writer's successors and adds 1 to the reader's inDegree. Then Kahn's algorithm runs. Click through it.

1. Count the incoming edges

Passes with no incoming edge can run first. They go into a FIFO queue in pass-index order.

2. Take Simulate

Each successor of the taken pass loses one incoming edge. A pass that reaches 0 joins the queue.

3. Take Forward

Composite still waits for one writer, Bloom. It cannot run yet.

4. Take Bloom, then Composite

4 sorted of 4 passes: the sort worked. The result goes into executionOrder and compiled becomes true.

5. When there is a cycle

No pass can start. execute still runs beginFrame and endFrame, so the window keeps handling events, but no pass is drawn. Because compiled stays false, the next execute tries to compile again.

Edge cases the sort handles

CaseResult
Passes with no edge between themThey keep the order they were added in (the queue is FIFO).
A read of something no pass writes (a loaded texture)No edge.
A pass reads its own outputNo edge, so no cycle.
A pass reads the same resource twiceTwo edges, removed twice. The sort still works.
Two passes write the same resourceThe one added last is the writer. Readers wait only for it.
addPass after compilecompiled becomes false; the next execute sorts again.

4execute: one frame

beginPass starts a rendering scope that clears the target: the render target's clearColor, or the swapchain clear color, and depth 0. It also sets the viewport and scissor to the target's size and the cull mode to NONE. A pass that draws to the swapchain also gets the stats overlay drawn at the end of it.

5Barriers from reads and writes

Before a pass begins, execute looks at what it declared and records only what that needs. Barriers are not allowed inside a render pass, so they all go before beginPass.

Buffers: what the graph remembers

Shaders reach buffers through device addresses, so the graph cannot see them. It trusts the declarations. For each declared buffer it keeps a BufferAccess: the stage of the last write, and the stages that have read it since, behind a barrier. A pass is COMPUTE or GRAPHICS as a whole. A barrier's first scope includes earlier submissions on the queue, so a wait for the previous frame needs no fence. A buffer a pass uses without declaring it gets nothing, and the graph knows only its own passes: a buffer shared with another graph, or with work outside the graph, is not ordered.

What one barrier covers

It is a global memory barrier, for every buffer at once. The source side makes the earlier stage's writes available. The destination side covers reads and writes of the later stage. GRAPHICS means indirect, index, vertex and fragment stages.

Inside one compute pass

The graph adds barriers only between passes. A pass with two dispatches where the second reads the first's output records ctx.memoryBarrier(cmd, PipelineStage::COMPUTE, PipelineStage::COMPUTE) between them itself. memoryBarrier and dispatch refuse to record inside a render pass.

6Render targets: one set per frame slot

RenderContext::createRenderTarget creates both slots and adds both color textures to the bindless set. If any step fails, it destroys what it made and returns an invalid handle.

A D32_SFLOAT depth texture is created SAMPLED_DEPTH_ATTACHMENT. drawScene adds it to the bindless set (NEAREST_CLAMP) the first time it occlusion-culls into the target, and builds its Hi-Z from it. Other depth formats are DEPTH_STENCIL_ATTACHMENT only, because a depth/stencil view cannot be sampled; drawScene does not draw into those targets anyway. See occlusion culling.

The life of one color attachment in a frame

Reading an earlier target

The reading pass declares builder.read(rtHandle), so it sorts after the writer, and the graph moves the current slot's color to SAMPLED before it. In execute it finds the current slot's texture and its bindless index, and gives the index to the shader in a push constant. This is the overlay pass of examples/01_render_graph:

auto commandBuffer = engine.getCurrentFrameResources().commandBuffer;
// Each frame slot renders to its own attachment.
auto textureIndex = engine.getBindlessTextureIndex(
    engine.getRenderTargetTexture(rtHandle));

ctx.bindPipeline(commandBuffer, overlayPipeline);
ctx.bindDescriptorSet(commandBuffer, overlayPipeline,
                      engine.getBindlessDescriptorSet(), 0);
ctx.pushConstants(commandBuffer, overlayPipeline,
                  rasm::ShaderType::VERTEX_FRAGMENT,
                  &textureIndex, sizeof(textureIndex), 0);
ctx.draw(commandBuffer, 3); // one triangle covers the screen

The shader reads it with gTextures[pc.textureIndex].Sample(input.UV). Every shader stage can sample: the bindless set is created for ShaderType::ALL. A compute pass binds it with bindDescriptorSet on its compute pipeline.

7The two examples

Both examples call graph.compile() once after adding the passes, then graph.execute(camera) in the main loop. Example 04 has no scene, but still passes a camera, because beginFrame needs one for input.

8What the graph does not do

Not doneWhat it means for a pass
See undeclared useA buffer or texture a pass uses without read or write gets no barrier and no order.
Order work across graphsEach graph keeps its own buffer state. A buffer used by two graphs, or by code outside the graph, is not ordered between them.
Load or keep a target's contentsEvery graphics pass clears its target: beginPass never asks beginRendering to load. Two passes that draw to the swapchain: the second wipes the first (D9).
Transient resources and memory aliasingPassBuilder::createRenderTarget makes a normal, permanent resource.

Own the cullingCulling is not a graph pass. The early culling runs before all the frame's work, compute passes included (D18). The Hi-Z build and the late culling run inside the pass that calls drawScene.

10Rules when you change it

Keep these true
  • Declare every resource a pass reads or writes with PassBuilder. An undeclared use is not sorted and gets no barrier.
  • Look up getRenderTargetTexture and its bindless index inside execute, every frame. They differ per frame slot.
  • Do not record a dispatch or a memoryBarrier inside a graphics pass. Use addComputePass; RenderContext refuses both inside a render pass.
  • A pass that draws with drawScene into a render target needs the swapchain's color format and D32_SFLOAT depth; otherwise it logs an error and draws nothing.
  • Push constants are 16 bytes at most (PUSH_CONSTANTS_SIZE).
  • Change a texture's layout only through transitionImageLayout, which keeps the remembered state right.
  • Sorting and buffer barriers are CPU-only and covered by tests/renderGraphTests.cpp. Add a test there when you change compile or bufferBarrier.
