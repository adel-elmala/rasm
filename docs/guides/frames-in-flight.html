Foundations

Frames in flight

The CPU and the GPU are two processors. If each waits for the other, each sits idle half the time. With frames in flight, the CPU prepares the next frame while the GPU still draws the last one. That needs a few copies of the data that changes every frame, and a fence that says when a copy is free again. The last part shows how RASM does it.

In short

  • The CPU records a frame, the GPU runs it later. They can work on different frames at the same time.
  • Data the CPU writes every frame gets one copy per frame slot. Frame n uses slot n mod N.
  • Before the CPU reuses a slot, it waits on a fence until the GPU has finished the last frame that used it.
  • A timeline fence is one growing counter. Each submit signals the next value; each slot remembers its value.
  • More slots hide more spikes, but add latency. When the GPU is the slow side, a third slot adds latency and no speed.
  • Data that never changes, or that only the GPU writes and reads within a frame, needs no copies.

1Two workers, one frame at a time

The CPU builds a frame: it reads input, moves objects, and records commands. Then it submits them, and the GPU runs them. If the CPU then waits for the GPU before it starts the next frame, the two never work at the same time:

With overlap, the frame time is set by the slower side alone: max(CPU, GPU) instead of CPU + GPU. Here the speed goes from 62.5 to 100 frames per second, with no change to the work.

2The problem: shared data

Overlap has a price. A frame's commands do not run when they are recorded; they read their data later, while the GPU runs them. Take the camera matrix. The CPU writes it into a buffer, and the GPU reads it during the frame. If there is one buffer, the CPU writes frame 1's camera while the GPU still draws frame 0 with it:

There are only two ways out: wait until the GPU is done before writing (the "one slot" picture, slow), or write somewhere else. Frames in flight do the second, and wait only when the other place is still in use.

3Frame slots

Pick a number N, usually 2 or 3. Give every per-frame resource N copies, and call copy i slot i. Frame n uses slot n mod N. So with N = 2, frames 0, 2, 4 use slot 0 and frames 1, 3, 5 use slot 1.

With N slots, the CPU can be at most N − 1 frames ahead of the GPU: frame n must wait for frame n − N, which used the same slot. That wait is the only one the CPU needs.

4Fences: how the CPU knows

A fence is a sync object the GPU signals and the CPU can wait on. The submit names it; when the GPU has finished everything in that submit, it signals the fence. There are two kinds.

Do not confuse a fence with a semaphore in the binary sense. A binary semaphore orders work between GPU submissions (for example, "draw only after the swapchain image is free"); the CPU cannot wait on it. See the swapchain and GPU synchronization.

5Worked example: the fence, frame by frame

Two slots and one timeline fence that starts at 0. Each slot starts with the value 0, so the first wait on each slot returns at once. Click through the steps (or use the arrow keys).

1. Frame 0, slot 0

The submit names the value it will signal. The slot stores it, so the next frame that uses slot 0 knows what to wait for.

2. Frame 1, slot 1

The CPU is now one frame ahead. Slot 0 is still in use by the GPU, but the CPU did not touch it.

3. Frame 2, slot 0: the CPU waits

This is the wait that keeps the race away. It sits at the start of the frame, right before the slot is touched, so the CPU did as much work as possible before it.

4. Frame 3, slot 1

With a timeline, the bookkeeping is one number per slot and one counter. Nothing is ever reset.

6What gets a copy per slot, and what does not

The rule is simple: a resource needs one copy per slot when the CPU changes it every frame (or the CPU reads it back), and the GPU may still be using the old contents.

ResourcePer slot?Why
Command buffers and their memory (pools, allocators)yesRe-recording resets their memory, which the GPU reads while it runs them.
Per-frame constants: camera, time, lightsyesThe CPU rewrites them every frame.
Per-object data the CPU updates (transforms)yesSame. A change must reach every copy, each in its own frame.
Readback buffers, timer queriesyesThe GPU writes them, the CPU reads them after the fence. A second frame must not overwrite them first.
Meshes, textures, pipelines, samplersnoWritten once, then only read. If they change, write new data elsewhere, or wait.
GPU-only scratch: a depth buffer, a culling list made and used in one frameusually noThe queue runs frames in order, and a barrier covers earlier submissions. One copy is enough, unless frames may overlap on the GPU or the data must survive to the next frame.
Swapchain imagesno, the swapchain owns themTheir count is not N. See the swapchain.

Changing a resource that has only one copy is still possible. Either write only to parts no running frame reads (a new row, a new descriptor slot), or defer the change: remember the fence value of the current frame, and apply the change once the counter has passed it. Deleting works the same way: a destroyed object is put in a queue with the current value, and really freed later.

7How many slots: throughput against latency

Latency here means the time from the start of a frame on the CPU (when input is read) to the end of its GPU work. A simple model, with fixed costs per frame, shows the trade-off. The numbers come from stepping the rule "frame n may start when the CPU is free and frame n − N is done on the GPU":

GPU-bound

The CPU runs ahead until it hits the fence. Each extra slot is one more finished frame waiting in the queue, so latency grows by one GPU frame, and speed does not change.

CPU-bound

The GPU waits for the CPU, never the other way. The queue stays empty, so more slots change nothing. They do help when costs vary: a slow CPU frame can then hide behind a fast one.

That is why 2 is the common default, and 3 is used when frame costs jump around. Games that care about input lag go further: they limit how far the CPU may run ahead, or delay the start of the CPU frame so it finishes just in time.

8Where to wait, and other pitfalls

PitfallWhat happensInstead
Waiting right after submitBack to "one slot": no overlap.Wait at the start of the frame that reuses the slot.
Writing the slot before the waitThe race from section 2 comes back, but only sometimes.Everything that writes a slot's resources runs after its wait.
Remembering a value nothing signalsA submit failed, but the slot stored its value anyway. The next wait on that slot never returns.Store the value only after the submit succeeded.
Mixing up frame number and slotTwo frames in flight share one slot.Keep both, and index per-frame resources by the slot.
Readback "now"The CPU reads a result the GPU has not written yet.Read a slot's results after its wait: they are N frames old, and that is fine for statistics.
Waiting foreverA GPU hang (device lost) freezes the program.A timeout, or at least an error on a failed wait.
Resize or shutdown with frames in flightResources are freed while the GPU still uses them.Wait for the device to go idle first; it is rare, so the cost does not matter.

9In RASM

RASM uses two slots (MAX_FRAMES_IN_FLIGHT = 2) and one timeline fence, Engine::frameFence. frameCount is the slot, 0 or 1, not a frame counter. Everything that writes a slot's resources runs right after the wait in beginFrame.

A changed table row is marked dirty in every slot (GpuTable::setRow). Each slot then uploads it once, in its own frame, after its own wait. That is why EngineConfig::maxInstances costs its memory twice.

One GPU-only buffer is shared on purpose: GpuScene::visibility, what the last frame's occlusion culling saw. The next frame reads it, so it must survive the frame. The queue runs frames in order, and recordCulling starts with a compute-to-compute barrier, so one copy is safe (see occlusion culling).

A render target without history also has one copy that both slots share. Each frame draws it before it reads it, and the queue runs the frames in order, so the next frame's draw waits behind the barriers of this one (see temporal history).

The geometry pool, textures, pipelines and the one bindless descriptor set have a single copy. They are only added to: new ranges, new textures, new bindless slots, never a change to something a running frame reads. The bindless set's layout uses update-after-bind, which allows writing new slots while earlier frames still run. Nothing is freed while frames are in flight, because nothing can be destroyed yet (D4). Resize is the exception: it waits for the device to go idle, then replaces the depth textures and rebuilds the render targets sized from the window (RenderContext::resizeRenderTargets).

Keep these true
  • Per-frame mutable buffers are indexed by frameCount, and written only after beginFrame's wait for that slot.
  • GPU scene tables are written only in syncGpuScene. Change rows through GpuTable::setRow, never by writing a slot's buffer.
  • A slot takes a fence value only after a submit that signals it succeeded.
  • A resource with one copy is only added to while frames are in flight. Replacing or freeing one needs the device idle (as resize does) until deferred destruction exists (D4).
