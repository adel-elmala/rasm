Engine tour

One frame, step by step

A frame is beginFrame, some passes, and endFrame. All passes go into one command buffer, and the frame has one submit. The CPU records the next frame while the GPU still runs the last one, so there are two frame slots. One timeline fence tells the CPU when a slot is free again.

This is stop 2 of the engine tour, after the big picture. It walks one frame of RASM and shows where each job runs. The ideas under it have their own guides: frames in flight, the swapchain, barriers and layouts, and indirect draws.

CPU work GPU work GPU buffer shader entry point

In short

  • Engine::render runs a render graph (Renderer::render): beginFrame, the scene passes from addScenePasses, endFrame.
  • The scene passes are Cull 1, Scene 1, Hi-Z, Cull 2, Scene 2 (only Cull and Scene without occlusion culling). The graph puts the barriers between them.
  • frameCount is the slot (0 or 1), not a frame counter. MAX_FRAMES_IN_FLIGHT = 2.
  • Each submit signals the next value of frameFence. Before a slot is reused, beginFrame waits for the value its last submit signaled.
  • Everything that rewrites a slot's buffers runs right after that wait: frame stats, overlay text, syncGpuScene.
  • beginFrame returns false to skip a frame (minimized, swapchain out of date). Then record nothing and do not call endFrame.

1Three ways to run a frame

2One frame, step by step

This is frame 7 of an app that calls render(scene, camera) with occlusion culling on (the default). Frame 7 uses slot 0. Click through the steps (or use the arrow keys). The strip at the top of each picture shows where we are.

1. Input and finished loads

F1 shows the stats overlay (showStats), and F2 steps forcedLod through the LODs and back to the automatic choice (-1). Loads that end together spread over several frames. finishLoads runs before anything binds the bindless set or the geometry pool, so what it writes is ready for this frame's draws. See Streaming assets in the background.

2. Skip checks and resize

While the window is minimized, pollEvents waits up to 100 ms for an event (SDL_WaitEventTimeout), so skipped frames do not spin the CPU. A failed recreation keeps swapchainOutOfDate set, so the next frame tries again.

3. Wait until the slot is free

beginFrame waits for frameResources[frameCount].fenceValue. Then the GPU is done with everything slot 0 used: its command buffer, its per-slot buffers, its timestamp queries. At start both slots hold 0 and the fence starts at 0, so the first waits return at once. How a timeline fence works is in Frames in flight.

4. Rewrite the slot: stats, overlay, scene

A change made after beginFrame (for example updateTransform during the passes) reaches the GPU in the next frame. See the GPU scene tables (stop 3), GPU timing for the stats and bitmap text for the overlay.

5. Acquire a swapchain image

Acquire comes after the scene sync, so a skip here wastes nothing: the uploads it queued go out with the next submit. The swapchain picks its own acquire semaphore; see The swapchain and presenting.

6. Start recording, then Cull 1

beginFrame sets swapchainRendered to false and begins the slot's command buffer. Each command buffer has its own pool, and begin resets it. That is safe because of the wait in step 3. Then RenderGraph::execute runs the passes in its order. Before each pass it records the barriers that the pass's declared reads and writes need, outside any render pass.

Cull 1 is a compute pass, so its dispatches sit between render passes, in the same command buffer. countMain tests each draw against the frustum and last frame's visibility flags, and writeMain packs the visible ones into the view's visible-draw list. The COMPUTE → COMPUTE barrier between them is inside the pass. What they do is in Frustum culling, LOD selection and Stream compaction.

7. Scene 1: the early draws

A barrier call names only the new usage: RenderContext remembers the layout each texture is in (TextureStates). With discard set, as here, the old contents are dropped and the barrier starts from UNKNOWN. acquireNextImage marks the acquired image UNKNOWN too, and the image barrier waits at color output, after the acquire. Barriers must be recorded outside a render pass. See GPU synchronization.

The draw lists and runs drawSceneView uses are in stop 3. The ideas: indirect draws, device addresses for the push constant, vertex pulling and the uber shader for what each draw runs.

8. Hi-Z, Cull 2, Scene 2: occlusion culling

Each step is a pass of its own, so no dispatch ever sits inside a render pass. The late culling rewrites the same visible-draw list and counts that Scene 1 read, so the graph's barrier before Cull 2 waits for the early draws. Cull 1 reads the visibility flags that this pass wrote last frame (readPrevious). Without occlusionCulling, addScenePasses adds only Cull and Scene, and this step is not there. Why two passes, and how a Hi-Z works, is in Occlusion culling with Hi-Z.

9. endFrame closes the command buffer

Present needs the image in PRESENT_SRC. A frame that only draws into render targets gets the empty "Clear" pass, so it presents the clear color (there is no offscreen-only frame yet, D7). A render target pass instead leaves its color textures SAMPLED in endPass, for later passes.

10. Submit and present

The upload copies go out first on the same queue, so the frame sees their data (GPU memory and uploads). A slot takes the new fence value only after a successful submit: waiting for a value that nothing signals would block forever.

11. Move to the other slot

Frame 8 can start at once if the GPU already reached 6. Otherwise the CPU waits in step 3 of frame 8.

3Two slots over time

With two slots, the CPU can record frame N+1 while the GPU runs frame N. It cannot get further ahead: frame N+2 uses the same slot as frame N, so step 3 waits for frame N's fence value. Frames in flight draws this on a timeline and explains why one timeline fence is enough.

"Recreate next frame" means swapchainOutOfDate is set, and step 2 of the next frame recreates the swapchain. What these results mean in Vulkan is in The swapchain and presenting.

A skipped frame (beginFrame returns false)

Nothing is recorded or submitted. frameCount does not move, and there is no Tracy frame mark. What ran before the skip still counts: input, finished loads, and (when acquire skips) the scene sync, whose uploads go out with the next submit.

A frame that fails to submit

It was recorded, but the slot keeps its old fence value, so the next wait on it passes at once. frameCount still moves. The image stays acquired, and the next acquire returns it again. Its timestamps are not read, because the slot's value did not change. endFrame calls discardRecording, so the textures it moved go back to the layouts they still have on the GPU.

5Resize

  1. SDL reports a new pixel size. SDL_EVENT_WINDOW_PIXEL_SIZE_CHANGED sets resized and the new pixelWidth and pixelHeight in pollEvents.
  2. The next beginFrame recreates. It calls Engine::recreateSwapchain, which calls RenderContext::recreateSwapchain.
  3. The swapchain is rebuilt. A 0 × 0 surface returns OUT_OF_DATE and keeps the old swapchain. Otherwise it releases pending semaphores, waits until the device is idle, and builds the new swapchain.
  4. Image handles change. The old swapchain image handles are dropped and new ones are registered. Handles from an earlier getSwapchainImages are no longer valid.
  5. Sizes follow. createSwapchainResources recreates both depth textures at the new size and calls updateCameraAspectRatio. The device is idle, so the old depth textures can be destroyed at once. With occlusion culling, it puts each new depth texture into the bindless slot of the old one, where the Hi-Z pass samples it.

Everything swapchain-sized uses the swapchain extent in pixels. Window::width and height are the logical size, used only for the mouse. They differ on HiDPI screens.

Known issues

D7: the engine owns the event loop: pollEvents runs inside beginFrame, and there is no offscreen-only frame.

B21: the swapchain always uses VK_PRESENT_MODE_FIFO_KHR, so the frame rate is capped at the display refresh rate.

8Rules when you change it

Keep these true
  • frameCount is the frame-in-flight slot (0 or 1). Per-frame mutable buffers are indexed by it.
  • A slot's buffers are written only after that slot's fence wait. GPU scene tables are written only in syncGpuScene.
  • A slot takes a new fence value only when a submit that signals it succeeded.
  • The frame has one command buffer and one submit. GPU work goes in as a graph pass that declares every buffer and target it uses: the graph records barriers only for what is declared.
  • When beginFrame returns false, record nothing and do not call endFrame.
  • Every swapchain call handles SUBOPTIMAL and OUT_OF_DATE explicitly.
  • Swapchain-sized resources use the swapchain extent in pixels, not the window's logical size.
  • Run the examples with enableValidation on after a frame-loop change. A change that adds validation messages is not done.
