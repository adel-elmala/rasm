Foundations

The swapchain and presenting

A program never draws straight onto the screen. It draws into an image, and hands the image to the system, which shows it at the next refresh. The swapchain is the small set of images that goes round between the two. This page explains the loop (acquire, render, present), the sync it needs, the present modes behind "vsync", and what to do when the window changes size. The last part shows how RASM does it.

In short

  • A swapchain is a ring of 2 to 4 images owned by the presentation engine (the OS compositor or display).
  • Each frame: acquire an image, render into it, present it.
  • Acquire returns before the image is really free. An acquire semaphore makes the GPU wait; a present semaphore makes the present wait for the rendering.
  • The present mode decides what happens at the refresh: wait for it (FIFO, vsync), replace the waiting image (MAILBOX), or show at once and tear (IMMEDIATE).
  • When the window changes, the swapchain becomes out of date or suboptimal. The program then builds a new one, and everything sized like it.
  • A minimized window has size 0 × 0: no swapchain can exist for it, so frames are skipped.

1Why not draw onto the screen

The display reads its picture from memory, line by line, about 60 to 240 times per second. If the program drew into that same memory, the display would show half-drawn frames. So there are several images. The display shows one, while the program draws into another. When the new one is done, they swap. That is the old idea of double buffering, and a swapchain is its modern, explicit form.

The images belong to the presentation engine, not to the program. The program asks for one, may draw into it until it gives it back, and must not touch it after that. The engine decides which image comes next, and when.

2The loop: acquire, render, present

  1. Acquire. Ask the swapchain for the next image. The answer is an index into its images. It may block when every image is in use.
  2. Render. Record commands that draw into that image, and submit them.
  3. Present. Give the image back, with a request to show it.

There is a catch in step 1. Acquire returns as soon as the swapchain knows which image comes next, which can be before the display has stopped reading it. So the index alone does not make it safe to draw. The image becomes free at some later moment, and only the GPU timeline knows when. Two semaphores handle this. A semaphore is a GPU-side signal: one submission signals it, and another one waits for it. The CPU never waits on it.

Before present, the image must also be in the layout the display can read (in Vulkan: PRESENT_SRC). Its old contents do not matter at acquire, so the first barrier of the frame can discard them. See GPU synchronization for layouts and barriers.

When may a semaphore be used again?

A binary semaphore must be waited on once before it is signaled again. That makes reuse the most common swapchain bug:

SemaphoreFree again whenSo keep
Acquirethe submission that waited on it has finished, which a fence tells the CPUone per frame in flight, reused after that frame's fence wait
Presentthe present has waited on it. The program cannot observe that directly (without an extension that gives present a fence).one per swapchain image. An image is acquired again only after its last present finished, so by then its semaphore is free.

Keeping one present semaphore per frame in flight looks right and works on many machines, but the present of frame n may still hold it when frame n + 2 signals it again. Validation layers now report this.

Worked example: when the GPU is too slow for FIFO

A 60 Hz display refreshes every 16.7 ms. With FIFO, a frame can only appear at a refresh. These numbers come from stepping the rules above with a fixed GPU time per frame:

GPU per frameImagesFrames shown per secondTime each frame stays on screen
10 ms2 or 36016.7 ms, every time
20 ms23033.3 ms, every time
20 ms3about 50mostly 16.7 ms, every fifth frame 33.3 ms

With 2 images and 20 ms frames, a finished frame waits for the next refresh, and the GPU has no free image during that wait. It loses the rest of each refresh, so it drops all the way to 30. A third image lets the GPU start the next frame during the wait. The average is close to the GPU's own 50, but the timing is uneven, which the eye notices as judder.

4When the swapchain no longer fits

A swapchain is built for one window size and one surface. When the window changes, acquire and present report it:

ResultMeaningWhat to do
SuboptimalThe image was acquired or presented, but the swapchain no longer matches the surface exactly (for example, its size).Finish and present this frame. Rebuild before the next one.
Out of dateThe swapchain cannot be used any more. From acquire: no image was acquired.Skip this frame. Rebuild.
Surface size 0 × 0The window is minimized. No swapchain can be built for it.Skip frames, ideally sleeping until a window event, until the size is back.

Most programs also listen to the window system's own resize event, because not every platform reports out of date in time. Rebuilding works like this:

  1. Wait for the GPU. The old images may still be in use by frames in flight. The simple way is to wait until the device is idle; resize is rare, so the stall does not matter.
  2. Build the new swapchain with the new size, passing the old one as "old swapchain". That lets the system hand over smoothly, and retires the old one even if the build fails.
  3. Destroy the old swapchain and its image views.
  4. Rebuild what has the screen's size: depth buffers, full-screen render targets, the viewport, and the camera's aspect ratio.
  5. Use the swapchain's size, not the window's. The surface picks the final size, and on high-DPI screens it is in pixels, while the window size may be in points.
Signaled semaphores across a rebuild

A rebuild can happen between acquire and present. Then an acquire semaphore may be signaled and never waited on, and a binary semaphore in that state cannot be signaled again. A robust rebuild first makes sure every signaled semaphore is waited on (for example, with an empty submission that only waits), or destroys and recreates the semaphores.

5Format and color space

The swapchain also fixes the pixel format and the color space the display expects. A common choice is an 8-bit BGRA or RGBA format with an sRGB encoding. With an sRGB format, the hardware converts the shader's linear output into sRGB when it writes. HDR displays need other color spaces and wider formats. See color spaces: sRGB and linear.

7In RASM

VulkanSwapchain builds the swapchain with vk-bootstrap and owns all of its sync objects. No semaphore crosses the RHI: a submit only names the swapchain (SubmitDesc::swapchain), and the swapchain fills in the waits and signals. The engine's frame loop handles skipped frames and resize.

The frame loop around it

Resize, step by step

  1. Ask the surface. VulkanSwapchain::resize reads the surface size. A 0 × 0 surface returns OUT_OF_DATE and keeps the old swapchain (B5). A failed query returns FAILURE and keeps it too.
  2. Consume pending signals. releasePendingSemaphores submits a wait-only batch for an image that was acquired but not submitted, and for one submitted but not presented.
  3. Go idle and rebuild. The device waits idle, the old image views go, and the new swapchain is built with the old one as oldSwapchain. The old one is destroyed either way. If the build fails, there is no swapchain, and acquire reports OUT_OF_DATE until a rebuild works.
  4. New handles. RenderContext::recreateSwapchain registers the new images under new texture handles.
  5. Screen-sized resources. Engine::createSwapchainResources recreates the depth texture of each frame slot at the new size, keeps its bindless slot, and sets the camera aspect ratio from the swapchain's extent.

Keep these true
  • Swapchain calls handle VK_SUBOPTIMAL_KHR and VK_ERROR_OUT_OF_DATE_KHR explicitly, and return a SwapchainStatus the engine acts on.
  • No semaphore crosses the RHI. The acquire → submit → present order lives inside VulkanSwapchain.
  • Everything sized like the screen comes from the swapchain's extent in pixels, not from the window's logical size.
  • Swapchain images belong to the swapchain: RenderContext::destroyTexture refuses them.
