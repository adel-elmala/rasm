The GPU scene tables

The scene lives on the GPU as a few tables of fixed-size rows. A draw names an instance row, and the instance row names a geometry row and a material row. The CPU changes a row only when something changed, and syncGpuScene uploads the changed rows once per frame.

This is stop 3 of the engine tour, after the big picture and one frame. It shows RASM's tables and how the objects you create get into them. Why a renderer keeps its scene on the GPU like this is in GPU-driven rendering and indirect draws.

CPU work GPU work / drawn GPU buffer

In short

  • Engine-wide tables: geometry (one row per sub-mesh), material (one row per material), instance (one row per entity × sub-mesh). Per scene: a draw list of DrawInfo.
  • An entity gets its instance rows once its mesh is loaded. It joins the draw lists once every texture it uses is loaded. Nothing is drawn half-loaded.
  • syncGpuScene runs once per frame, after the fence wait. It gives rows to new entities, rebuilds the draw lists that changed, and uploads this frame slot's dirty rows.
  • A draw list is sorted into up to 3 runs by cull mode, because cull mode is set per indirect draw.
  • A row's cull mode comes from its material (doubleSided) and the sign of its matrix's determinant.

How a GpuTable uploads only its dirty rows, per frame slot, is in GPU memory and uploads.

How a shader finds the tables

No table is bound. The push constant points to this scene view's SceneData, and SceneData points to every table of this frame slot. So a shader follows two pointers to reach any row (Buffer device addresses).

3syncGpuScene, step by step

It runs in beginFrame: finishLoads → fence wait for this slot → updateFrameStats → updateStatsOverlay → syncGpuScene. Here is one call, in a scene with four entities. Click through (or use the arrow keys).

1. Before: what is waiting

finishLoads made the meshes of e1 and e2 READY and set texturesFinished, at the start of beginFrame.

2. Entities whose mesh is ready get rows

Rows are a bump allocation: firstInstance = instanceCount, then instanceCount grows by the sub-mesh count. If the table has no room, the entity logs an error and leaves the list without rows.

3. A texture finished: check the waiting entities

The rows of e4 do not change here. Only its draw-list membership does.

4. Rebuild the dirty draw lists

The whole list is rebuilt, not patched. Its cost grows with the number of entities in the scene (P7). Only scenes with the rebuild flag do it.

5. Upload this frame slot

The upload runs after the fence wait for this slot, so no GPU work still reads these buffers. A change made after beginFrame (for example updateTransform while recording) reaches the GPU in the next frame.

4Draw lists and cull-mode runs

A run is a DrawRun {cullMode, first, count}. There are at most MAX_DRAW_RUNS = 3 runs, one per cull mode (a static_assert ties the two together). A draw is skipped, with a warning when the entity gets its rows, if its sub-mesh has no vertices or no indices.

When a draw list is rebuilt

SceneDrawList::rebuild is set in two places:

  • addEntityToDrawList, from addEntityToScene: only if the entity already has rows and does not wait for textures. Otherwise it joins later, when it becomes drawable.
  • markDrawListsDirty: the entity becomes drawable, starts waiting for a texture again, or one of its rows changes cull mode. It marks only the scenes in the entity's scenes bits.

How a draw list reaches the GPU

  1. Rebuild sets staleSlots to both bits. The CPU list in draws is now newer than both slot buffers.
  2. Each slot uploads in its own frame. uploadDrawList writes draws into buffers[frame] and clears that slot's bit. If the buffer is too small, it destroys it and creates one with max(drawCount, capacity × 2) rows. Only this slot's last frame used the old buffer, and the fence wait covered it.
  3. prepareSceneView skips a list that is not ready. If the list is empty, or this slot's bit is still set (the upload failed), the scene passes record nothing this frame and the target keeps its clear color.

5The cull mode of a row

Each instance row gets one of the three cull modes. Why a mirrored object must cull its front faces is in Face culling and winding order. Here is how RASM picks the mode:

The determinant needs no matrix multiply: the entity's Transform is translate × rotate × scale (Transform::toMatrix), and a rotation has determinant 1. The cull mode is kept per row on the CPU in instanceCullModes; the GPU never sees it. updateCullModes recomputes it when the transform or the material changes, and marks the draw lists dirty only if some row's mode changed.

8Rules when you change it

Keep these true
  • Change table rows only through GpuTable::setRow (or set a draw list's rebuild). Slot buffers are written only in syncGpuScene, after that slot's fence wait.
  • Only gpuScene.cpp touches GpuScene. Other files call the Engine methods (queueInstanceRows, writeInstanceRows, writeMaterialRow, addEntityToDrawList, refreshEntitiesAfterMaterialChange).
  • An entity joins a draw list only with rows and all textures loaded. Keep that check in both addEntityToDrawList and rebuildDrawList.
  • EntityDrawState::scenes has one bit per scene, so MAX_SCENES must stay at most 16 (a static_assert checks it).
  • The run order is the order of CullMode, and MAX_DRAW_RUNS must equal the number of cull modes.
  • Changing InstanceData, MaterialData, GeometryData or DrawInfo is a CPU↔GPU struct change: follow the struct contract.
Known limits

Rows, geometry and materials are never freed, and entities and meshes cannot be destroyed (D4). A scene with a changed entity rebuilds its whole draw list (P7). Scene handles start at 1, so 15 of the MAX_SCENES scenes are usable.
