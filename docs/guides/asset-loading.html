Loading assets in the background

loadMesh, loadGLTF and loadTexture return a handle at once. A worker thread reads and decodes the file. The main thread picks up the result at the start of a later frame, uploads it, and frees the CPU copy.

CPU work (main thread or worker) GPU work GPU buffer

In short

  • One std::async task per load, no thread pool. The worker never touches the engine.
  • finishLoads runs at the start of beginFrame. It finishes the loads that are ready, and stops after 4 ms (LOAD_BUDGET). waitForLoads finishes all of them, without a budget.
  • glTF: a node walk with an explicit stack, and one checked accessor reader (strides, sparse, quantized). OBJ: one sub-mesh, one vertex per index.
  • With EngineConfig::meshLods on, the worker also builds coarser LODs of each sub-mesh (buildMeshLods).
  • Paths are cached: loading the same file twice gives the same handle. A mesh that failed can be loaded again on the same handle.
  • A mesh must fit the geometry pool as a whole before anything is created. After upload, the vertex arrays, the glTF model and the pixels are freed.

1Main thread and worker, step by step

A glTF file loads while the app keeps drawing frames. Click through (or use the arrow keys).

1. loadMesh returns at once

The handle is usable at once: createEntity can take it. The entity waits for the mesh in entitiesWaitingForMesh (see The GPU scene tables).

2. The worker decodes; frames go on

Frames keep their normal speed while a big file decodes. A scene that uses the mesh simply draws without it.

3. The result is ready

The worker is done, but nothing in the engine changes yet. The result waits in the std::future of the PendingMeshLoad.

4. Frame 4: finishLoads uploads it

GeometryPool::upload calls fillBuffer. Without ReBAR the data goes to the staging ring and reaches the pool at this frame's submit (see How data reaches the GPU).

5. The same frame draws it

A texture loaded with loadTexture takes the same path, with decodeTexture on the worker and finishTextureLoad on the main thread. An entity whose material uses it waits until it is in.

finishLoads runs before the minimized-window check in beginFrame, so loads still finish while the window is minimized.

2The time budget

waitForLoads calls finishLoads(true): no budget, and it blocks on each future until every pending load is done. Use it to show a fully loaded scene in the first frame.

3What the worker does

importMeshFile picks the importer from the file extension: .gltf and .glb go to tinygltf, everything else to tinyobjloader.

When every accessor is read, the worker clears model->buffers. Materials only need the decoded images, so the raw file bytes go early.

OBJ

One sub-mesh

All shapes go into one SubGLTFRaw with an identity transform and no material (index −1). The entity's material is used. OBJ materials are not read.

One vertex per index

Every face corner becomes its own vertex; vertices are not shared (buildMeshLods merges them before it makes LODs). V is flipped (1.0 - v), because OBJ puts the UV origin at the bottom-left. A missing normal or UV stays zero.

LODs

When EngineConfig::meshLods is on (the default), the worker calls buildMeshLods on each sub-mesh right after importMeshFile. createMesh calls it on the main thread. It makes coarser versions of the sub-mesh, its LODs, with meshoptimizer. Culling picks one per draw (see GPU culling).

Each step also locks the sub-mesh's open border (meshopt_SimplifyLockBorder): its border vertices and edges stay in every LOD. Culling picks a LOD for each sub-mesh on its own, so two sub-meshes that share an edge, like the parts of a glTF mesh split by material, can draw different LODs. With the border kept they still meet.

Each step simplifies with meshopt_SimplifySparse, so a coarse level costs work for its own indices, not for all the vertices. Then meshopt_optimizeVertexCache reorders the level's triangles so the GPU's vertex cache reuses more vertices. createMesh checks your indices before any of this: their count must be a multiple of 3 and each one below the vertex count.

A LOD costs only its indices, up to as many again as LOD 0 in total. The numbers for an example are in How data reaches the GPU.

4Path caching and failures

Both loaders first call resolveAssetPath: a relative path is joined to EngineConfig::assetRoot, so a relative and an absolute path to one file give the same key. Meshes are cached by that path in loadedMeshes. Textures are cached by path and format in loadedTextures, so one file can be loaded once as sRGB and once as UNORM.

Every error before the worker starts returns an invalid handle and caches nothing. isLoaded(mesh) is true only for MeshState::READY. isLoaded(texture) is true once the handle is no longer in pendingTextures, also for a texture that was filled white.

Known limit: B13

MAX_MESHES is 8 and mesh handles start at 1, so only 7 meshes can exist, counting createMesh. Handles are never reused.

5The geometry pool fit check

When it fits, finishMeshLoad goes over the sub-meshes in order. For each one it calls loadMaterial (glTF only) and then GeometryPool::upload, which appends the vertices, then LOD 0's indices followed by each coarser LOD's, computes a bounding sphere and writes one geometry row. The pool size is set by EngineConfig; the defaults and the upload path are in How data reaches the GPU. createMesh skips all of this background work: it builds the LODs, uploads at once and returns a READY mesh.

6Textures: two ways in

loadTexture

The main thread reads only the image header (stbi_info) and creates the texture at once, so it can go into a material before its pixels exist. The worker runs decodeTexture (stbi_load to 4 channels). finishTextureLoad calls fillTexture, and finishLoads sets texturesFinished, so waiting entities are checked.

glTF images

tinygltf decodes them on the worker, as part of the file. loadMaterial creates and fills each texture on the main thread inside finishMeshLoad, so they are ready when the mesh is. Each image is uploaded once per import, per sampler and color space (GltfImportCache).

fillTexture builds the whole mip chain on the main thread, inside the load budget. Color textures are sRGB, data maps are UNORM. See Materials and bindless textures.

9Rules when you change it

Keep these true
  • Worker code (importMeshFile, buildMeshLods, decodeTexture) must not touch the engine. It gets a path and returns a plain result.
  • Anything that creates GPU objects, writes the registry or calls fillBuffer for a load runs in finishLoads, on the main thread, before anything binds the bindless set or the geometry pool.
  • Check that the whole mesh fits (GeometryPool::fits) before creating anything for it. Nothing is freed (D4).
  • Free the CPU copy after upload (P6). Do not keep vertex arrays, the glTF model or pixels in the registry.
  • A texture that a material may already use must always be filled, even when its decode fails.
  • Normal, metallic-roughness and AO textures are R8G8B8A8_UNORM; color and emissive are R8G8B8A8_SRGB.
  • Changes to import behaviour need a test in tests/gltfImportTests.cpp, and changes to LOD building one in tests/meshLodTests.cpp (no GPU needed).
Not done yet

There is no thread pool and no cancel. Mips are built on the main thread (P2), so a big glTF can make one long frame. Meshes and textures cannot be unloaded (D4).
