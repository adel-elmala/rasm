Foundations

The RHI and the Vulkan backend

src/rhi/device.h is the line between the engine and a graphics API. Above it, code sees only neutral types. Below it, a backend turns them into native objects. Vulkan is the only backend today.

CPU work GPU work GPU memory / sync object shader entry point

In short

  • rhi::createDevice picks the backend. VULKAN works; DX12, METAL and WEBGPU log an error and return null.
  • Resources are plain structs that keep their descriptor. The backend derives from each one (VulkanBuffer from Buffer) and adds native members.
  • CommandBuffer, Queue, Swapchain and Device are interfaces with virtual functions.
  • Fences are timelines: a submit signals a 64-bit value, and waits block until the GPU reaches it.
  • The swapchain owns its semaphores. No semaphore crosses the interface; the order acquire → submit → present is enforced inside.
  • There is one queue, the graphics queue. Frames and uploads both use it.

1Resource structs and the backend's derived types

An object passed to a device always came from that device. So the backend casts it back with static_cast, with no check and no lookup. Here is one buffer, from creation to use:

create*

Logs the failure and returns null. RenderContext then returns an invalid handle. Every Vulkan object gets a debug name through setObjectName, which does nothing when debug utils is missing.

destroy*

Releases at once. The caller must know the GPU is done with the object: today that means the device is idle, or a fence wait covered its last use. Swapchain images belong to the swapchain; RenderContext::destroyTexture refuses them.

A PipelineDesc with computeShader set is a compute pipeline; otherwise it needs vertexShader and fragmentShader. RenderContext::createPipeline calls createComputePipeline or createGraphicsPipeline, and refuses a desc that sets both kinds. Every pipeline layout is the bindless set plus one PUSH_CONSTANTS_SIZE (16 bytes) push-constant range.

The engine creates the bindless set layout for ShaderType::ALL (VK_SHADER_STAGE_ALL), so compute shaders can sample textures too. Bind the set to the compute pipeline with bindDescriptorSet, as the Hi-Z build does. Compute writes buffers only: there are no storage images.

2Command buffers

On Vulkan each command buffer owns its own command pool (VK_COMMAND_POOL_CREATE_TRANSIENT_BIT). begin resets the whole pool and begins with VK_COMMAND_BUFFER_USAGE_ONE_TIME_SUBMIT_BIT. So the GPU must have finished the buffer's last submission before begin; a fence wait makes sure of that.

Depth is stored only with storeDepth (VK_ATTACHMENT_STORE_OP_DONT_CARE otherwise); beginPass sets it when EngineConfig::occlusionCulling is on, because drawScene then reads depth in the middle of a pass.

pushConstants must name COMPUTE for a compute pipeline and VERTEX_FRAGMENT for a graphics one, and fit in PUSH_CONSTANTS_SIZE. Binding a compute pipeline leaves the pass's graphics pipeline bound.

3Barriers: memoryBarrier and PipelineStage

Shaders reach buffers through device addresses, so the barrier is global (VkMemoryBarrier2), not per buffer. Its first scope includes earlier submissions on the same queue, so a GRAPHICS → COMPUTE barrier at the start of a frame also waits for the previous frame's draws.

PipelineStageVulkan stagesReads (as after)Writes

GRAPHICSdraw indirect, index input, vertex shader, fragment shaderindirect command, index, storage, uniformstorage

Source scope: the before stages and their writes. Destination scope: the after stages and their reads and writes. Reads before a barrier only have to finish, which the stage mask covers.

transitionImageLayout records one image barrier. Its source scope comes from the old usage only, and its destination scope from the new usage only.

The attachment usages include reads, for a beginRendering with load. A transition to the same layout (COLOR_ATTACHMENT → COLOR_ATTACHMENT) therefore orders earlier color writes before the load; drawScene does this in its pause.

Waiting at color output from UNKNOWN also chains the barrier to the swapchain's acquire semaphore, which the submit waits for at the same stage. Any other usage has no scope: the call logs an error, records nothing and returns false.

4Timestamps

createTimestampQueryPool returns null when the graphics queue has no timestamps (timestampValidBits is 0). That is not an error; the stats just have no GPU times. writeTimestamp writes once all earlier commands are done, so two timestamps bracket the commands between them. resetQueries resets the whole pool from the CPU, so the GPU must be done with it.

getTimestamps returns nanoseconds since the earliest query, and false while any query is unwritten. The counter can wrap, so each value becomes a signed distance from the first one, modulo the valid bits. A worked example with an 8-bit counter (real GPUs have up to 64):

A distance above half the range (here 127) counts as negative, so a query written before query 0 still comes out right. This holds while the queries span less than half the counter's range.

6The swapchain: acquire → submit → present

The swapchain owns everything that syncs it with the queue. A SubmitDesc with swapchain set waits for the image of the last acquire, and makes the next present wait for that submit.

SemaphoreKindHow manyWhy that many
acquireSemaphoresbinaryMAX_FRAMES_IN_FLIGHT (2), used in turnbefore reuse, acquire waits on the CPU until the submit that waited on it has finished (acquireReleaseValues), so it works at any frame pacing
presentSemaphoresbinaryone per swapchain imagean image is acquired again only after its present finished. They survive a resize; a bigger swapchain only adds more
releaseTimelinetimeline1tells acquire when an acquire semaphore is free again

The order is enforced

"Acquire again" happens after a failed submit: the image is still acquired and its semaphore still signaled, so acquire hands it out again instead of taking another one.

Resize

  1. A 0 × 0 surface returns OUT_OF_DATE and keeps the old swapchain. A failed surface query returns FAILURE and also keeps it.
  2. Pending signals are consumed. releasePendingSemaphores submits a wait-only batch for an acquired-but-unsubmitted image and for a submitted-but-unpresented one. A binary semaphore that is signaled and never waited on cannot be signaled again.
  3. The device goes idle, the old images are dropped, and the new swapchain is built with the old one as oldSwapchain. The present mode is always VK_PRESENT_MODE_FIFO_KHR (B21).
  4. If the build fails there is no swapchain, and acquire reports OUT_OF_DATE until a resize works.

7The one queue

QueueType has only GRAPHICS. All submits go to it, in order. That is why the upload copies need no semaphore: the barriers inside copyBuffers order them after earlier submissions and before later ones on the same queue. A SubmitDesc takes at most MAX_SUBMIT_COMMAND_BUFFERS (8) command buffers, which run in the given order. A failed submit leaves every semaphore as it was.

Known issues

D13: there is no transfer or async-compute queue yet.

D4: there is no deferred destruction. destroy* is immediate, so it is only safe when the device is idle or a fence covered the object.

P8: there is no pipeline cache, and every pipeline makes its own pipeline layout although they are all the same.

8How to add a backend

  1. Implement the interfaces under src/rhi/<backend>/: Device, CommandBuffer, Queue, Swapchain, and a derived struct for each resource. Follow the Vulkan files: one .h/.cpp pair each, native types in one types header like vulkanTypes.h.
  2. Register it. Add a case to the switch in rhi::createDevice (src/rhi/device.cpp), the sources to RASM_SRC, the libraries to src/CMakeLists.txt, and a find_dependency line to cmake/rasmConfig.cmake.in.
  3. Pick the shader target. getShaderCompilerTarget in src/engine.cpp maps the backend to MSL, HLSL or WGSL. The shaders still use device addresses and spirv_asm, so D3D12 and WebGPU need the binding work of D12 first.
  4. Give it a window hook. createWindowSurface in src/platform/ takes a VkInstance, so it is Vulkan-only. A new backend needs its own platform hook until D7 puts native window handles in DeviceDesc.
  5. Keep the contracts. Fences as growing 64-bit values, the swapchain's acquire → submit → present order with its own sync objects, global memory barriers between PipelineStage sets, timestamps in nanoseconds.

10Rules when you change it

Keep these true
  • All Vulkan calls live under src/rhi/vulkan/. Only the backend and src/rhi/device.cpp include its headers; the one exception is the surface hook in src/platform/.
  • New GPU features go into src/rhi/device.h in terms every planned backend (Vulkan, D3D12, Metal, WebGPU) can implement, never as a Vulkan-only path above the RHI.
  • Use synchronization2 (vkCmdPipelineBarrier2) and dynamic rendering. No render passes or framebuffers.
  • Check every VkResult, and pass it through toVkResultString in messages. Swapchain calls handle VK_SUBOPTIMAL_KHR and VK_ERROR_OUT_OF_DATE_KHR explicitly.
  • Every created object gets a debug name.
  • Public API misuse is checked in RenderContext with checkArgument; inside the backend, use plain assert.
  • Test with enableValidation on. A change that adds validation messages is not done.
