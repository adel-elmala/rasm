Culling and the frame

History buffers: last frame's image

Some effects need to know what the screen looked like a moment ago: a fading trail, temporal anti-aliasing, a denoiser, auto exposure. They keep a history buffer, an image that survives from one frame to the next. This page explains why it takes two images, how they swap, how to blend the past with the present, and when the past must be thrown away. The last part shows how RASM does it.

In short

  • A temporal effect reads last frame's result and writes this frame's result.
  • A pass cannot sample an image while it draws into the same image. That is a feedback loop, and the result is undefined.
  • So keep two copies and swap them every frame: draw one, read the other. This is ping-pong.
  • With frames in flight, the slot index already alternates, so it can pick the copy. Barriers on the one queue keep the copies safe; the fence alone does not.
  • Blending is a running average: mix(previous, current, α), or a decaying trail: max(current, previous × k). With k = 0.85, a trail falls to 10% in about 14 frames.
  • History is invalid on the first frame, after a resize and after a camera cut. Clear it, rebuild it, or ignore it for one frame.
  • It costs a second full-screen image and one more full-screen read per frame.

1Effects that need the past

Most passes only need this frame: the scene, the lights, the camera. A temporal effect also needs its own output from the frame before. It takes that output, mixes in what is new, and writes the result. Next frame, the result is the input again. The simplest example is a trail behind a moving object:

2One image cannot be read and drawn at once

The obvious idea is one image: read the old value at a pixel, and write the new value back to the same image. In a draw, this does not work. The GPU shades many pixels at once, in an order you do not control. A pixel shader that samples the image may get the old value, the new value, or a value that is half written. Worse, the image is in a layout for drawing, not for sampling, and caches for the two are not kept in step. This is a feedback loop, and graphics APIs call its result undefined. Validation layers report it.

A compute shader is a special case. If every thread reads and writes only its own pixel of a storage image, one image is enough, since no other thread touches that pixel. But as soon as a thread reads a neighbour (a blur, a reprojection, a filtered sample), it needs two images again.

3Ping-pong: two images that swap

Keep two copies of the image, A and B. Frame 0 draws A. Frame 1 reads A and draws B. Frame 2 reads B and draws A. Each frame, the copy that was "new" becomes "old". The data does not move; only the names swap. This is called ping-pong, or double buffering.

The code that picks the copies is two lines. The important part: both indices change every frame, so anything that refers to "the current copy" or "the previous copy" must be looked up again every frame.

// frame n draws history[n % 2] and reads history[(n + 1) % 2]
const uint32_t drawIndex = frameIndex % 2;
const uint32_t readIndex = (frameIndex + 1) % 2;

5History and frames in flight

With frames in flight, the CPU records frame n + 1 while the GPU still runs frame n. Each frame has a slot, and with two slots the slot index goes 0, 1, 0, 1. That is exactly the ping-pong pattern, so many engines give each slot its own history copy and let the slot index pick it. With N slots and N copies, slot i draws copy i and reads copy (i − 1) mod N.

Is it safe? The CPU waits on a fence before it reuses a slot, but that fence only says the frame two frames ago is done. The frame in between may still be reading the copy that the new frame will draw. What keeps the copy safe is the queue order and two barriers:

Two consequences follow:

  • Two copies are enough for any number of slots, because the GPU runs the frames one after the other. A copy per slot is a convenience: the index is already there. With exactly two slots, the two ideas are the same.
  • The copies are written by the GPU only. Data the CPU writes every frame needs a copy per slot for another reason (the CPU must not overwrite what the GPU still reads). History needs its copies because one pass reads and draws it.

6Mixing the past with the present

The pass has two inputs at every pixel: c, this frame's new value, and h, the history from last frame. It writes the new history h'. Two formulas cover most effects.

Running average

h' = mix(h, c, α)
= (1 − α) · h + α · c

Each frame, the new value gets weight α, and everything older shrinks by (1 − α). The frame i frames ago has weight α·(1 − α)i. This is an exponential moving average. It is used by TAA, denoisers and auto exposure. A small α is smooth but slow; with α = 0.1 the average covers about 1/α = 10 frames.

Decaying trail

h' = max(c, h · k)

The old image gets a bit darker every frame (k < 1), and anything new that is brighter wins at once. A pixel that was lit once and then left alone fades as kn. It is not an average: a bright object stays at full brightness, and only its trail fades.

Both fade the same way once the input goes dark: if c = 0, both give h' = h × (1 − α) or h × k. They differ in how fast they follow a new value. Here is one pixel that an object covers for 10 frames and then leaves, with k = 0.85 and α = 0.15:

How long does a trail last?

After n frames, a pixel keeps kn of its brightness. The half-life, the number of frames to reach 0.5, is ln 0.5 / ln k. For k = 0.85 that is 4.3 frames.

The same k gives a trail less than half as long at 144 fps as at 60 fps. The effect depends on the frame rate. To fix that, choose k for a reference rate and raise it to the frame time: with the frame time dt in seconds, use kdt × 60. At 144 fps that gives 0.8560/144 = 0.93 per frame, and the trail lasts the same 0.23 s to reach 10%. For a running average, use 1 − (1 − α)dt × 60 the same way.

float4 trail(float4 current, float4 previous, float dt)
{
    float k = pow(0.85, dt * 60.0);
    return max(current, previous * k);
}

Precision

History is fed back into itself many times, so small errors add up. In an 8-bit image, a value of 3/255 times 0.85 is 2.55/255, which rounds back to 3/255 on hardware that rounds to the nearest step. Dark trails then never quite reach 0. A running average with a small α has the same problem: a change smaller than one step is lost. A 16-bit float format avoids both; it costs twice the memory.

7When the history is wrong

The formulas trust that h really is "this pixel, last frame". Sometimes it is not:

  • First frame. A new image holds whatever was in that memory. Reading it can show noise or an old frame from another program. Clear every new copy to a known value before any frame reads it, or pass a flag that says "no history yet" and use c alone.
  • Resize. Images that follow the window size are made again. The new copies are new images, so the first-frame rule applies to them too. Keeping the old copy and sampling it with the new size would blend pixels that are no longer at the same place.
  • Camera cut, teleport, a new level. The image has nothing to do with last frame. Without a reset, the old place fades out over the next frames, like a ghost. The CPU knows when this happens, so it tells the shader to ignore h for one frame.

Reprojection: when the camera or objects move

A trail wants the old pixels to stay. TAA and denoisers do not: they want the same surface point, not the same pixel. When the camera moves, that point was at another place on the screen last frame. A motion vector per pixel says how far it moved, and the pass samples the history there:

Reprojection is not perfect. A point that was hidden last frame (behind an object that moved away) has no history at all; this is called a disocclusion. Shading changes too. So TAA also checks the history value: it looks at the 3 × 3 pixels around p in this frame and clamps the history colour into their range (minimum to maximum). A history value far outside that range is surely wrong, and is pulled in. Denoisers instead reject the history when depth or normal differ too much, and start that pixel over. These checks remove most ghosting, at the cost of some flicker.

10In RASM

RASM has history for render targets. A render target created with RenderTargetDesc::history set to true has one set of attachments per frame slot (MAX_FRAMES_IN_FLIGHT = 2). That is ping-pong, picked by the slot index frameCount. New copies are cleared before any frame reads them.

examples/01_render_graph draws a fading trail of the bunny this way. The Trail pass creates trail_rt with history, declares that it reads the previous copy, and draws the current one:

graph.addPass(
    "Trail",
    [&rtHandle, &trailHandle, colorFormat](rasm::PassBuilder &builder)
    {
        trailHandle = builder.createRenderTarget({
            .name = "trail_rt",
            .swapchainScale = 1.0f,
            .colorFormats = {colorFormat},
            .depthFormat = rasm::Format::D32_SFLOAT,
            .clearColor = glm::vec4(0.0f),
            .history = true,
        });
        builder.read(rtHandle);
        builder.readPrevious(trailHandle);
        builder.write(trailHandle);
    },

    [&engine, &drawFullScreen, &trailPipeline, &rtHandle, &trailHandle](rasm::RenderContext &ctx)
    {
        drawFullScreen(ctx, trailPipeline, engine.getBindlessTextureIndex(engine.getRenderTargetTexture(rtHandle)),
                       engine.getBindlessTextureIndex(engine.getPreviousRenderTargetTexture(trailHandle)));
    });

Its fragment shader is the decaying trail from section 6, with k = 0.85 per frame:

float4 fragMain(VSOutput input) : SV_TARGET
{
    float4 current = gTextures[pc.indices[0]].Sample(input.UV);
    float4 previous = gTextures[pc.indices[1]].Sample(input.UV);
    return max(current, previous * 0.85);
}

Keep these true
  • Look up getRenderTargetTexture, getPreviousRenderTargetTexture and their bindless indices every frame, inside execute. Fetched once, they point at the wrong copy every second frame.
  • Never read the target a pass draws to. Read last frame's copy with readPrevious.
  • Every new history copy must be cleared before a frame reads it. A new way to make copies goes through createAttachments, which queues the HistoryClear; destroying a copy must drop it.
  • clearNewHistory runs in beginFrame, before any pass. A frame that is not submitted gives its clears back (discardRecording).
  • endPass leaves every color SAMPLED. readPrevious records no barrier because it relies on that.
  • A history target is never transient: its memory must survive to the next frame.
