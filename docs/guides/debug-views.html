Culling and the frame

Debug views

A shaded image hides why it looks the way it does, and why it is slow. A debug view draws the same scene, but each pixel shows one value of the work behind it: a normal, a UV, how many fragments were shaded, which LOD, what culling did, how many lights. This page explains how each view is made and how to read it. The last part shows how RASM does it.

In short

  • A debug view is the scene's own shader with the shading swapped for one value. Everything else stays: the same draws, depth test, culling and cut-outs.
  • Values (normals, UVs, LOD tints, culling colors) are written as colors and shown as they are, without exposure or a tone curve.
  • Counts (overdraw, lights) are numbers. Overdraw adds 1 per fragment with additive blending; the display turns each count into a heat color.
  • The culling view also draws what culling left out, as see-through ghosts: the bounding box of each culled object. Freezing culling keeps one frame's results while the camera moves, so you can look at them from outside.
  • A view is a shader variant compiled with a define the first time it is chosen. While it is off, the normal shaders have no extra branch: it costs nothing.

1Six views, six questions

Each view answers one question. Pick the view by the question you have.

Normals

Which way does the surface face? Shows a broken normal map, flipped faces, missing tangents.

UVs

Where does the texture go? Shows seams, stretching, mirrored or missing UVs.

Overdraw

How many fragments were shaded at each pixel? Shows wasted shading work.

LODs

Which level of detail does each draw use? Shows LODs that switch too early or too late.

Culling

What was drawn, when, and what was left out? Shows culling that keeps too much or too little.

Light count

How many lights does each pixel shade? Shows lights whose range is too large.

2Swap the shading, keep the rest

A debug view must show the frame as it really is. So it does not draw the scene some other way: it runs the same draws, with the same vertex shader, depth test and culling, and changes only what the fragment shader writes. A cut-out leaf still cuts, a skinned arm is still where the skin pass put it.

normal view = n × 0.5 + 0.5

UV view = (fract(u), fract(v), 0) × checker

checker = 1 or 0.7, 8 squares per unit

n
The shading normal in world space, after the normal map, turned around on a back face. Each part is −1 to 1, so it is moved to 0 to 1: a surface facing +y is (0.5, 1, 0.5), light green.
fract
The part after the point. A UV of 2.3 shows as 0.3: a texture that repeats shows the same ramp again. The checker shows how big a texel is and where UVs are stretched.

3Count with additive blending

Overdraw is how many fragments were shaded at one pixel. Only one of them is seen; the others were work for nothing. To count them, every fragment writes 1 and the target adds what it gets: additive blending, result = source + target.

With the depth test on, the order of the draws matters. Front to back, the first surface writes its depth and the GPU rejects the ones behind it before they are shaded. Back to front, each nearer surface passes again. A see-through surface does not write depth, so everything behind it still counts.

The count is shown as a heat color, one step for each doubling, because overdraw from 1 to 4 is normal and 30 is a problem:

4Count the lights of a pixel

With clustered lighting, a pixel shades only the lights of its cluster: the box of the view, a screen tile times a depth slice, that it falls in. The light count view writes that number, plus the lights that reach every pixel (a sun), and shows it with the same heat ramp.

5Tint by LOD

A mesh with levels of detail is drawn with one of its index ranges. The LOD view tints each draw by the level it uses, 0 to 7, and keeps a little light from the camera so the shapes stay readable. Distant objects should change color in rings around the camera. A pop you see in the shaded image shows here as a draw that changes color.

The view does not need a new input: the draw already holds the first index of its range, and the mesh lists where each level's range starts. The level whose range starts there is the one drawn.

6Show what culling did

Two-pass occlusion culling draws in two passes. The early pass draws what was visible last frame. A Hi-Z is built from that depth, and the late pass draws what the early one missed and is visible now. The culling view colors each drawn object by its pass, and draws every culled object as a see-through ghost: a box around the bounding sphere that culling tested.

drawn early: seen last frame drawn late: seen only after the Hi-Z ghost: in the frustum, occluded ghost: outside the frustum

A ghost is a box, not the object's mesh. Drawing every culled mesh again would cost as much as drawing the whole scene without culling: in a city of 200 million triangles, about as much as 30 ms. The box is 12 triangles per object, and it is the shape culling really tested.

Ghost boxes

A box around each draw's bounding sphere, after the last pass. The vertex shader drops the ones culling kept.

Added, not tested

No depth test and additive blending: a ghost shows through walls, and more ghosts make a brighter color.

Freeze

Keep one frame's frustum, LOD camera and visibility. The early pass then culls with them; the late pass stops.

7Show the values as they are

A tone curve and exposure would change a value: a normal of 0.5 would not show as 0.5. So while a debug view is on, the tone map pass binds a debug display instead. It shows a value as the color it is, or a count as its heat color, and the bloom adds nothing.

  1. Scene passes write a value, or add 1, into the HDR target.
  2. MSAA resolve or TAA runs as usual.
  3. Debug display shows the value, or round(count) as heat.
  4. UI draws over the image.
Anti-aliasing stays on

Inside a surface every sample holds the same value, so the resolve and TAA give it back exactly. Only at edges do two values mix: a normal there is a blend of two normals, and a count is rounded to the nearer one. The image stays smooth and the inside of each surface stays exact.

8Free while it is off

A debug tool must not slow down the frames it is meant to measure. A switch in the shader would cost every frame a branch, and its code would make the shader bigger even when it never runs.

A branch

One shader for both. The normal frame carries the debug code.

A variant

One file, compiled twice. The debug one is made the first time a view is chosen.

9Pitfalls

The overdraw view is blue where nothing was drawn
Something is drawn there: a sky box, a ground plane far away. The view counts every fragment, even of a mesh you think of as background.
Overdraw is high on a flat wall
The draws behind it came first: back-to-front order, or a mesh drawn before the one in front. Sort opaque draws front to back, or draw a depth pre-pass.
A green object also has a red ghost
The early pass drew it, because it was seen last frame, and this frame's late test found it hidden. It is drawn now and will be culled next frame.
Ghost stripes over a green surface look yellow or white
A ghost adds its red to what is under it, and many ghosts add up. Read the stripes as "culled here", and their brightness as how many; the color of a stripe on black is its kind.
Everything is a ghost after freezing
Culling froze on a frame that had seen nothing yet, like the first frame, or the object appeared after the freeze. Frozen visibility never sees anything new. Freeze after a few frames, once the scene is loaded.
A see-through object looks wrong while frozen
Without a late pass its draws are not sorted back to front any more. The culling is right; only the order of the see-through draws changed.
Normals look right but the light is wrong
The view shows the normal the shading uses. Check the light count and the light itself next.

10In RASM

An application calls Engine::setDebugView with a DebugView, and Engine::setCullingFrozen. The RASM window (F1, with EngineConfig::ui) has both under Debug views, with a color key for the view. examples/15_debug_ui and examples/05_city take --debug-view overdraw and --freeze-culling.

Keep these true
  • The normal shaders get no debug branch: debug code lives inside #if defined(RASM_DEBUG_VIEW).
  • DebugView's numbers match the DEBUG_VIEW_* constants of debugViews.slang (a static_assert in gpuScene.cpp), and the RASM window's color keys match the shaders' colors.
  • No time and no random numbers in a view, so a view's image is the same in every run.
  • A new value a view needs goes into the variant or into SceneData's existing words, through gpu-struct-sync; never into the normal path.
