Rendering

Camera, coordinates and depth

A camera is a pose and a projection. Each frame the engine turns mouse and key input into a new pose, eases toward it, and builds two matrices from it. This page shows which way the axes point, how depth is stored (reversed-Z), and which triangle faces are culled.

CPU work GPU work GPU buffer

In short

  • The world is right-handed and Y-up, like glTF. A camera looks down its local −Z.
  • Clip space is Y-up. The Vulkan backend flips Y with a negative-height viewport, inside setViewport.
  • Input goes SDL → pollEvents → CameraInput → controller → targetTransform → easing → transform.
  • Depth is reversed-Z: the near plane is depth 1, the far plane is depth 0. Depth is cleared to 0 and the test is GREATER_OR_EQUAL.
  • A perspective farZ of 0 or infinity means an infinite far plane: depth = nearZ / distance.
  • Front faces are counter-clockwise. A mirroring transform flips the cull mode from BACK to FRONT.

1The axes

Shaders work in the Y-up clip space on every backend. So a full-screen pass computes y = 1 − 2 · v to put UV row 0 at the top, as examples/01_render_graph and statsOverlay.slang do. Mouse positions also reach the controllers Y-up (section 3).

4The two controllers

Trackball, step by step

Both mouse points are put on a unit sphere (projectOnSphere). The rotation axis is cross(p0, p1), the angle is the angle between them times orbitSensitivity. The camera rotates by minus that angle in its own frame. Then the position is put back on the sphere. A frame with no drag and no wheel leaves the target as it is.

Free-fly, step by step

yaw −= dx · lookSensitivity, pitch += dy · lookSensitivity (radians per NDC unit). The rotation is angleAxis(yaw, +Y) · angleAxis(pitch, +X). The pressed keys add up to one direction, which is normalized, so diagonal moves are not faster.

setCameraController starts the new controller from the current rendered pose. When it switches to free-fly, it computes yaw and pitch from the current view direction, so the view does not jump. A roll is dropped.

5Easing

The trackball does not mix positions in a straight line. A straight line would cut across the orbit and move the camera closer to the center. It eases the rotation, then puts the camera at center + radius · (rotation · +Z) with an eased radius.

6The view matrix

  1. Move the world so the camera is at the origintranslate(−position)
  2. Turn the world so the camera looks down −Zmat4_cast(conjugate(rotation)). For a unit quaternion the conjugate is the inverse rotation.
  3. Resultview = conjugate(rotation) · translate(−position), from getViewMatrix. The camera's scale is not used.

The vertex shader (rasm.slang) computes projection · view · world · position. drawScene writes view, projection and cameraWorldPosition into the call's SceneData.

7Reversed-Z projection

toProjectionMatrix in camera.cpp builds the matrix. glm builds the normal (not reversed) matrices in the [0, 1] depth range (GLM_FORCE_DEPTH_ZERO_TO_ONE, set in CMake, B2). Passing far as glm's near and near as glm's far reverses them.

clip z = nearZ, clip w = −viewZ = distance. So depth = z / w = nearZ / distance. fovY is in degrees in CameraProjection.

What is rejected

isValidProjection logs an error and refuses:

  • perspective: nearZ not finite or not > 0;
  • perspective: a finite farZ that is not > nearZ (0 and infinity are fine);
  • orthographic: nearZ or farZ not finite, or farZ not > nearZ. Orthographic has no infinite form.

createCamera then returns an invalid handle. setCameraProjection keeps the old projection. NaN fails every check.

An omitted farZ in a designated initializer is 0, so .perspective{.fovY = 45.0f, .aspect = ..., .nearZ = 0.1f}, as in the examples, gives an infinite far plane. For culling, the infinite far plane comes out of getFrustumPlanes as (0, 0, 0, nearZ), which every sphere passes. See GPU frustum culling.

A custom pass that writes its own depth must use the same rule. A skybox at the far plane writes depth 0 (z = 0), not z = w. The stats overlay writes depth 1 (z = w = 1), the near plane, so it passes over everything the pass drew.

9Front faces and mirrored transforms

getCullMode in gpuScene.cpp picks the mode per entity and sub-mesh, from scale.x · scale.y · scale.z · det(meshTransform). Draws are grouped into runs by mode, and drawScene calls setCullMode per run. The cull mode is dynamic pipeline state, so one pipeline serves all three (the GPU scene tables).

For lighting, fragMain in rasm.slang also needs to know the side. It sets backFace = isFrontFace == (handedness < 0), where handedness is the sign of the world matrix's determinant. Only double-sided draws show back faces, and those are lit with the reversed normal.

10One camera, any pass shape

Two things change the aspect ratio:

  • Per pass, for one draw: getProjectionMatrix(camera, aspect) fits a copy of the projection. drawScene does this for every call, so a render target of any shape renders without stretching.
  • Stored, for every camera: updateCameraAspectRatio runs after the swapchain is created or recreated, with the swapchain's pixel size, and rewrites each camera's projection.

12Rules when you change it

Keep these true
  • The depth clear (0.0 in beginRendering) and the compare (GREATER_OR_EQUAL in createGraphicsPipeline) are a pair. Change one, change the other, and the projection.
  • A pass that writes its own depth follows reversed-Z: far is 0, near is 1.
  • Pass a normal, Y-down pixel rectangle to setViewport. The backend flips it; do not flip it again.
  • GLM_FORCE_DEPTH_ZERO_TO_ONE is set in CMake. Do not define glm config macros in a .cpp (B2, CLAUDE.md).
  • Swapchain-sized things (depth textures, viewport, stored aspect) use the swapchain's pixel size, not Window::width/height (B17).
  • Camera math is CPU-only and is covered by tests/cameraTests.cpp. Run ctest --preset x64-debug after a change.
Not done yet

The engine owns the event loop: pollEvents runs inside beginFrame, and the app cannot drive the controllers itself or see input events (D7). There is no camera-relative rendering for large worlds yet (development plan, phase 5).
