Culling and the frame

Image tests: golden images

A unit test checks a number. A renderer's result is a picture, and most of its bugs show only there: a shadow in the wrong place, a black material, a missing mesh. An image test renders a fixed scene, reads the frame back, and compares it with a stored image that a person once checked: the golden image. This page is about the compare: when two pictures count as "the same", and how to keep that answer honest.

In short

  • Render a fixed scene headless, read the frame back, compare it with the golden. On a failure, save the new image and a difference image that shows where it changed.
  • Exact equality is too strict: the same code gives slightly different pixels on another GPU, driver or CPU. A test needs a tolerance.
  • A simple, strong rule: a pixel differs when a channel is off by more than T; the test fails when more than F of the pixels differ. Set T and F from the noise you measure, not by guess.
  • Perceptual metrics such as FLIP say how visible a difference is. They answer "would a person notice?", which is a different question from "did the code change?".
  • Goldens belong to one driver. A software rasterizer gives the same pixels on every machine and needs no GPU, so continuous integration can run it.
  • A golden changes only on purpose: the change that moves it says why, with the image before and after.

1One image test

The test is the same four steps for every scene. Only the last step needs a decision: same or not.

Everything before the compare must give the same frame on every run: all loads done before the first frame, a fixed frame count, animation at fixed times, no on-screen statistics. Headless rendering and readback explains why each of these matters.

2Why exact equality fails

Rendering is floating-point math, done in parallel, by code you do not own: the driver compiles your shaders, and the hardware rounds. The same scene, with the same code, can come out a little different:

Another GPU or driver

Each compiles the shaders its own way and rounds differently: a·b + c fused or not, faster sin and exp, another texture filter.

Another order

A parallel sum, blending or a reduction that runs in another order rounds differently. A wider SIMD unit or more threads changes the order.

Ties

A sample exactly on an edge or a depth exactly equal to another: tiny changes in math flip which side wins, and one pixel jumps by a lot.

So a good test has two parts: the noise it accepts, measured, and the bugs it must catch. A test that fails on noise teaches people to ignore it. A test so loose that it passes a real bug is worse than none.

3A threshold and a share of pixels

The rule this page uses has two numbers. The first, T, asks "is this pixel different?". The second, F, asks "are enough pixels different to fail?".

diff(p) = max over r, g, b, a of | actual(p) − golden(p) |

p differs ⇔ diff(p) > T

fail ⇔ (pixels that differ) / (all pixels) > F

T
the largest change of one 8-bit channel that is still noise, in steps of 1/255
F
the largest share of pixels allowed over T: the rare ties and edge pixels

T alone fails on a single tie pixel. F alone ignores how big a change is. Together they let through many tiny changes, or a few big ones, but not many big ones. Try it on a small image: three versions of a new render, one with noise only and two with a bug.

Set both numbers from a measurement: run the same code twice (and on two machines, if the test runs on more than one), compare, and read the largest difference and the share over each T. Choose T a little above the noise, and F a little above the share of outliers. Write the numbers down next to the test, so the next person knows why they are what they are.

Never raise T or F to make a red test green

If a test fails on noise, first find where the noise comes from: a timer, a thread count, a random seed. A tolerance hides a problem only until a real bug hides behind it.

4Other ways to compare

There are many metrics. They differ in the question they answer:

Exact match (hash)

Cheapest and strictest. Works when the whole chain is the same and nothing is parallel in an unknown order. Breaks on the first rounding change.

RMSE, PSNR

The mean of the squared differences. One wrong object in a corner hides in the mean of a large, correct image.

SSIM

Compares local brightness, contrast and structure in small windows. Good for compression and filtering; hard to turn into a pass or fail you can explain.

FLIP

NVIDIA's metric models how a person sees two images flipped back and forth: color, edges, viewing distance. It gives a map of how visible each change is.

FLIP answers "how much would a person notice?". That is the right question when two different renderers must agree, or when you tune a denoiser. A regression test asks "did my change move these pixels?". A change that nobody would notice, like a shadow one pixel off, is still a change the author should know about. So a regression test wants the strict, simple rule, with a tolerance only for noise. FLIP stays useful to judge a failure: is the difference big, or only real?

5Goldens belong to one driver

Section 2's noise is small on one machine and large across machines: two GPU vendors can differ on thousands of pixels and still both be right. A golden is therefore stored per driver, and the tests run on that driver.

A software rasterizer is a Vulkan driver that runs on the CPU: Mesa's lavapipe is one, and SwiftShader and WARP (for Direct3D) are others. It is slow, but it gives the same result on any CPU with the same build and settings, and continuous integration machines have no GPU anyway. Three things decide its pixels, so a test pins them, or measures that they do not matter:

Vector width

The shader compiler inside the driver picks its SIMD width from the CPU. Pin it, so a CPU with wider vectors compiles the same code.

Thread count

Tiles are spread over threads. When each pixel is computed by one thread, the count changes only the speed; measure that it does, or pin it.

The build itself

A new driver version changes its code, so the test fetches one exact build and checks its hash before it runs it.

Real GPUs are still worth testing: they are what users run. Compare those against a baseline taken on the same machine just before the change, which answers "did my change move pixels here?" without any stored file.

6Changing a golden

Goldens must change sometimes: a better shadow filter is a different picture. The danger is the change nobody looked at. So the rule is about people, not code:

  1. Test failsafter a change that should move pixels
  2. Look at diff.pngonly the expected places are red?
  3. Render new goldensonly the tests that changed
  4. Say why in the changewith before and after
The review rule

A change that changes a golden says why in its description, and shows the old and new image side by side. A reviewer who sees a golden change without that asks for it. Never update every golden at once to make the tests pass.

7Pitfalls

The test fails on one run and passes on the next
Something depends on time: a load that is not awaited, the wall clock, a thread race. Fix the cause; a larger tolerance only hides it.
Every test fails on a developer's machine
It ran on the local GPU, not on the driver of the goldens. Check which device the log names.
A golden shows a bug
It was captured without being looked at. Look at every golden before you store it: it must be a correct picture, or the test guards the bug.
The repository grows with each update
Keep goldens small (a few hundred pixels wide) and few. A small image still shows a wrong shadow or a black material.
An asset can't be stored with the tests
Its license may not allow it. Fetch it at test time from a fixed version and check its hash, like the driver.
Two tests in one process disagree with two processes
State leaks from one test to the next. Render one scene twice in one process and require a difference of 0.

8In RASM

RASM's image tests are one executable, rasm_image_tests (tests/image/imageTests.cpp), and one script that runs it on lavapipe, tools/image_tests.py. Each test renders a scene headless at 512 × 288 and compares the frame with its golden in tests/golden/lavapipe/.

Rules to keep

A golden changes only in a change that says why, with the old and new image. Look at every new golden before you store it. Set T or F per test only from measured noise, and write the reason next to it. A new test that would need an eighth mesh in an engine goes into another group.
