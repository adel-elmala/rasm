Foundations

Graphics APIs and the RHI

A graphics API is how a program talks to the GPU. The modern ones (Vulkan, Direct3D 12, Metal, WebGPU) share one model, with different names and different details. An engine that wants to run on several of them puts its own thin layer on top: a render hardware interface, or RHI. This page explains the shared model, the differences, and the choices an RHI has to make. The last part shows RASM's RHI.

In short

  • Explicit APIs move work from the driver to the application: memory, synchronization, pipeline creation and command recording.
  • All four have the same pieces: a device, queues, command buffers, pipelines, resources, a binding model, sync objects and a swapchain.
  • They differ most in binding, barriers, shader language and the platforms they run on.
  • An RHI is one interface above all of them. The engine is written once, against it. Each API gets a backend below it.
  • The main choices: how thin the layer is, virtual interfaces or a compile-time backend, how resources are named (handles or pointers), and who places the barriers.
  • A good RHI exposes what every planned backend can do, and never lets native types leak above it.

1What a graphics API does

A GPU is a separate processor with its own memory and its own command stream. A program cannot call it like a function. It writes commands into memory, hands them to the driver, and the GPU runs them later. The graphics API is the contract for this: how to create objects on the GPU, how to record commands, and how to know when they are done.

An older driver has to guess. When a texture is drawn into and then sampled, it must notice that, and flush caches in between. It does not know which shader combinations will be used, so it compiles them on the first draw, and the frame stutters. Explicit APIs remove the guessing: the application says what it needs, when it needs it. That makes the driver smaller and faster, and it makes the application longer. An engine absorbs that extra code once, so games and tools built on it do not have to.

One frame, in any of them

  1. At load time. Create resources, upload data, and build pipelines from shaders.
  2. Wait. Each frame, wait until the GPU is done with the memory this frame will reuse (see frames in flight).
  3. Get an image. Take one from the swapchain to draw into (see the swapchain).
  4. Record. Fill a command buffer: begin a render pass, bind a pipeline and its resources, draw, end. Put barriers between uses of the same memory (see GPU synchronization).
  5. Submit and present. Hand the command buffer to a queue, with a fence to signal. Then present the image.

4Why put a layer on top

An engine could call Vulkan directly everywhere. Then every renderer feature, every pass and every upload is written in Vulkan terms, and a second API means rewriting all of them. An RHI puts a line through the engine instead. Above the line, code knows only neutral types: a buffer, a texture, a pipeline, a command buffer. Below it, one backend per API turns them into native objects.

What an RHI gives

  • Portability: one engine, several APIs.
  • One place for the API's rules, so passes do not each get them slightly wrong.
  • A smaller surface: only the features the engine uses.
  • Tests: a fake backend can stand in for the GPU.

What it costs

  • A feature can only be used once every backend can implement it, or behind a "supported?" check.
  • Each backend is real code to write, test and keep in step.
  • A bad split (Vulkan ideas in the interface) makes the next backend hard.
  • A small cost per call, usually much less than the driver's.

5Design choices

How thin?

The first choice is the level of the interface. It ranges from "the same objects as the APIs" to "draw this mesh with this material".

A common mix: a thin RHI with explicit barriers, and above it a render graph that turns "reads" and "writes" into those barriers. The RHI stays simple, and passes still do not write barriers by hand.

Virtual interfaces or a compile-time backend?

Describing and naming resources

Almost every RHI creates objects from a plain descriptor struct: a list of fields such as size, format and usage. It is easy to read, easy to hash (for caches) and easy to store for debugging. The object it creates can be named in two ways:

Pointera pointer to the RHI objectno lookup, simplea stale pointer crashes, or worse, works on a new object

Recording commands

Direct

Each RHI call records the native command at once: draw becomes the API's draw. Simple and fast. The RHI's command buffer is a thin wrapper around the native one.

Deferred

RHI calls write a compact list of the engine's own commands. Later, often on another thread, the backend translates the list. Costs a second pass, but the list can be sorted, merged, or replayed, and the engine does not depend on the API's threading rules.

Who places the barriers?

ChoiceHowTrade-off
The callerThe RHI has a barrier call, close to Vulkan's.Fast and flexible. Every caller must know the rules from GPU synchronization.
The RHI tracks stateEach resource remembers its last use. Each use records a barrier if needed.Hard to get wrong. Costs a lookup per use, and knows only the past, not the future.
A render graphPasses declare reads and writes up front. The graph places barriers for the whole frame.Sees the whole frame, so it can batch and move barriers. Needs a graph. See render graphs.

6How to add a backend

  1. Check the shaders first. Can the shader compiler target the new API, and does the shader code use only features it has (pointers, bindless arrays, subgroup operations)? This is usually the biggest job.
  2. Implement each interface. Device, command buffer, queue, swapchain, and one derived struct per resource. Keep native types in the backend's own files.
  3. Map the enums. Formats, usages, stages, filter modes: one function per enum, in one file, with an error for values the API does not have.
  4. Keep the contracts. The interface promises things the native API may not: for example "a fence is a growing 64-bit value". Build that from what the API has.
  5. Hook up the window. Each API connects to a window in its own way (a surface, a swap chain, a layer).
  6. Register it. Add it to the place that picks the backend, and to the build.
  7. Compare images. Render the same frames on the old and the new backend and diff them. Run each API's validation layer.

Keep these true
  • Vulkan calls and types stay under src/rhi/vulkan/. From outside, only src/rhi/device.cpp, the surface hook in src/platform/ and src/thirdparty_impl.cpp (the VMA implementation) include them.
  • A new GPU feature goes into src/rhi/device.h in terms that Vulkan, D3D12, Metal and WebGPU can all implement, never as a Vulkan-only path above the RHI.
  • Public API misuse is checked in RenderContext with checkArgument. Inside the backend, use plain assert.
  • Check every VkResult and log it with toVkResultString. Every Vulkan object gets a debug name (setObjectName).
  • Test with enableValidation on. A change that adds validation messages is not done.
Not done yet

A second backend needs, in this order: shaders without raw pointers and spirv_asm (D12), a window hook that takes native handles (D7), and more queue types (D13). Objects are destroyed at once, so only when the GPU is idle or a fence covered their last use; there is no deferred destruction (D4). There is no pipeline cache (P8).
