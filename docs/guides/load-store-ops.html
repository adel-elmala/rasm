Culling and the frame

Load and store ops

A render pass draws into images called attachments. At the start of the pass, the GPU must know what to do with the old contents of each attachment. At the end, it must know what to do with the new contents. These two choices are the load op and the store op. They are two small flags, but on many GPUs they decide how many bytes a pass moves. The last part shows how RASM picks them.

In short

  • Load op, at the start: LOAD keeps the old contents, CLEAR fills the image with one value, DONT_CARE starts with anything.
  • Store op, at the end: STORE keeps the new contents, DONT_CARE may throw them away, NONE does not write at all.
  • On a tile-based GPU (phones, Apple) the image lives in small on-chip memory while the pass runs. LOAD is a copy in and STORE is a copy out. CLEAR and DONT_CARE are free.
  • Rule: load only what an earlier pass drew and you still need. Store only what someone reads later.
  • Depth is the classic win: most frames never read depth after the last pass, so it does not need to be stored.
  • A render graph knows who drew an attachment before and who reads it after, so it can pick the ops by itself.

1Two questions per attachment

A render pass draws into one or more attachments: color images, and often one depth image. Before the first triangle, the GPU asks "what is in this image now?". After the last triangle, it asks "do you need what I drew?". The program answers both questions, once per attachment, when it begins the pass.

2Why it matters: tile-based GPUs

There are two kinds of GPU. An immediate-mode GPU (most desktop GPUs) draws each triangle as it comes. Its pixels can land anywhere on the screen, so the color and depth images stay in video memory (VRAM), and a cache sits in between. A tile-based GPU (phones, Apple GPUs, many others) first sorts all the triangles of the pass into small screen tiles, for example 32×32 pixels. Then it draws one tile at a time, completely, in a small and very fast memory on the chip.

So on a tile-based GPU, the load and store ops are not details. A LOAD reads the whole image from memory, and a STORE writes the whole image. Memory traffic costs time and, on a phone, battery and heat. CLEAR costs nothing: the tile memory is filled with the clear value on the chip.

Desktop GPUs care too

An immediate-mode GPU has no copy in or out, but the ops still help it:

  • Fast clears. Many desktop GPUs keep images compressed in blocks, with a little metadata per block. A CLEAR can just mark every block as "clear" in the metadata, without writing the pixels.
  • No decompression. DONT_CARE at the start lets the driver skip work on the old contents, such as decompressing them.
  • Depth. A depth image that is not stored may never need to be written out of the GPU's compressed form.

The gain on desktop is smaller and depends on the GPU and the driver. But the right ops never cost anything, so set them right everywhere.

4Choosing the ops

Two questions decide everything. For the load op: "do I need what is already there?". For the store op: "will anybody read what I drew?".

SituationLoadStore
Main 3D pass, first on its imagesCLEAR color and depthSTORE color; depth only if a later pass needs it
A pass that draws on top (transparent objects, decals, UI)LOADSTORE color; depth as above
Full-screen post effect into a new imageDONT_CARESTORE
Shadow mapCLEAR depthSTORE depth: the lighting pass samples it
Depth that only the last 3D pass usesCLEAR or LOADDONT_CARE
The swapchain imageCLEAR, or DONT_CARE if every pixel is drawnSTORE: the screen reads it

5The same idea in other places

Discard in a barrier

An image barrier can change the layout from UNDEFINED. That also says "I do not need the old contents", like DONT_CARE. A pass that clears or does not care can use it: the driver may skip decompressing the old data. A pass that loads must not: the barrier would throw away what it wants to load. See GPU synchronization.

Merging passes

Two passes in a row on the same images pay a STORE and a LOAD in between. If they are one pass, the images stay on the chip and both copies go away (the last bar in section 3). Vulkan subpasses and tile-local reads let a pass even read the previous step's pixel while it is still on the chip, for example for deferred lighting.

Multisampling (MSAA) shows the store op at its best. A 4× MSAA image has 4 samples per pixel, but the screen needs only one. At the end of the pass, the GPU resolves the samples to one value, and stores only that.

The same works for depth that is cleared at the start and not stored at the end: it can be memoryless too, as long as no other pass needs it.

6How a render graph picks the ops

A render graph knows every pass, in the order they run, and what each pass writes and reads. That is exactly what the two questions need. Here is a frame with four passes, and the ops the graph finds for each image:

After sorting the passes, the graph walks them in order:

  1. Load op. For each attachment of the pass, look at the last earlier pass that drew it. If there is one, and the pass draws on top, LOAD. If there is none, CLEAR, or DONT_CARE when the pass says it covers every pixel.
  2. Store op. Look forward: is there a later pass that loads the image or samples it? Is it the swapchain, or an image kept for the next frame? Then STORE. Otherwise DONT_CARE.
  3. Barriers. A pass that does not LOAD can use the UNDEFINED layout in its barrier (section 5). A pass that loads keeps the layout.
  4. Optional: merge. Neighbouring passes on the same images, with nothing in between that samples them, can become one pass, so the LOAD and STORE between them go away.

The store op needs to know the future, so it is set after the whole order is known: either in a second walk backwards, or by fixing the previous writer when a later pass loads.

Bugs that hide on desktop

A wrong DONT_CARE often "works" on a desktop GPU, because the image in VRAM happens to keep its old data. The same code shows garbage on a phone or a Mac. The Vulkan validation layers do not catch it, because DONT_CARE is legal. Test on a tile-based GPU, or look at the image in a frame debugger.

8In RASM

RASM uses Vulkan dynamic rendering, so the ops go into VulkanCommandBuffer::beginRendering. A pass describes them with three flags, AttachmentOps: loadColor, loadDepth and storeDepth. The render graph sets them for each pass in RenderGraph::assignAttachmentOps, when it compiles. A frame written by hand passes them to Engine::beginPass.

Passes that draw to one target already run in the order they were added: compile adds an edge from each writer of a target to the next one. So assignAttachmentOps only walks the sorted order once and remembers the last writer of each target (the swapchain counts as one target). When a pass finds an earlier writer, it loads color and depth, and it sets storeDepth on that earlier pass. A pass that reads a target's depth (readDepth, readSwapchainDepth) sets storeDepth on the target's last writer before it, too. RenderGraph::execute then passes Pass::attachmentOps to beginPass unchanged.

beginPass also does the barrier from section 5. It calls transitionImageLayout with discard for each attachment that it clears, so the old layout is VK_IMAGE_LAYOUT_UNDEFINED. An attachment that it loads keeps its layout, and the barrier orders the earlier pass's writes before the load.

// A hand-written frame: a world pass, then a UI pass on top of it
engine.beginPass("World", {.storeDepth = true});
// ... draw the world
engine.endPass();
engine.beginPass("UI", {.loadColor = true, .loadDepth = true});
// ... draw the UI
engine.endPass();

Keep these true
  • Passes that draw to one target must keep running in add order. assignAttachmentOps depends on the edges that compile adds between them.
  • A pass that loads depth needs the pass before it to store depth. A pass that samples a depth declares readDepth or readSwapchainDepth, so the pass that drew it stores it.
  • Clear only with discard, load only without it. A discard before a load drops the contents.
  • Color stays stored: later passes sample render targets without telling the pass that drew them.
  • The depth clear value 0 pairs with the VK_COMPARE_OP_GREATER_OR_EQUAL depth test (reversed-Z). Change both or neither.
  • The first pass on a transient target must draw it: its memory held another target before.
