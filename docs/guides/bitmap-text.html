Culling and the frame

Text from a bitmap font

An engine often needs to show a few lines of text before it has any UI: frame times, counters, a warning. The smallest way to do it needs no font file, no texture and no text layout library: a tiny font stored as bits inside the shader, a buffer of character codes, and one rectangle whose pixels look up their own bit. This page explains how that works, and what the bigger alternatives do. The last part shows how RASM does it.

In short

  • A bitmap font stores each character (a glyph) as a small grid of on/off pixels. An 8×8 glyph is 64 bits: one byte per row.
  • Two 32-bit integers hold one glyph. The 94 printable ASCII characters fit in 752 bytes, small enough to live as a constant array in the shader.
  • The CPU writes the text as a grid of character codes, row by row, into a small buffer, 4 characters per integer.
  • One quad covers the text area. For each pixel, the fragment shader finds the cell (which character), the glyph pixel inside it, and the bit: on gives the text color, off the background.
  • An integer scale keeps the pixels sharp on big screens.
  • Font atlases and SDF fonts give nicer, proportional, scalable text, at the price of textures, per-glyph quads and a layout step.

1The problem

Normal text rendering is a large system: load a font file (TrueType, OpenType), turn the outlines of each glyph into pixels, pack them into a texture, lay out the string with the right spacing and kerning, then draw one textured quad per character. That is the right tool for game UI. It is too much for a debug overlay that must work on the first day of a new engine, with nothing else in place.

The minimal version gives up a lot on purpose: one fixed size, one fixed width per character, plain ASCII, no smoothing. In return it needs a short shader, a little C++, no assets, and one draw call.

2A font as bits

A bitmap font stores each glyph as a grid of pixels that are either on or off. Old computers worked this way: the IBM PC's VGA text mode drew every character from an 8×8 or 8×16 grid stored in ROM. An 8×8 grid has 8 rows of 8 pixels. One row is 8 bits, exactly one byte.

A font only needs the characters it will show. The printable ASCII characters go from ! (code 33) to ~ (code 126): 94 glyphs. The space (code 32) needs no glyph: it is all background.

3Packing glyphs into integers

Shaders work best with 32-bit integers. Four rows fit in one, so a glyph is two integers: rows 0 to 3 in the first, rows 4 to 7 in the second. The first row goes in the lowest byte:

word 0 = row0 | row1 << 8 | row2 << 16 | row3 << 24
word 1 = row4 | row5 << 8 | row6 << 16 | row7 << 24

'A':  word 0 = 0x33 << 24 | 0x33 << 16 | 0x1E << 8 | 0x0C = 0x33331E0C
      word 1 = 0x00 << 24 | 0x33 << 16 | 0x33 << 8 | 0x3F = 0x0033333F

The whole font is an array of 94 × 2 = 188 integers, 752 bytes. That is small enough to be a constant array in the shader source. No texture, no upload, no sampler. To read pixel (x, y) of the glyph for character c:

word = font[(c − 33) · 2 + y / 4]       the integer: rows 0–3 or 4–7
row  = (word >> ((y % 4) · 8)) & 0xFF    the byte: the row
lit  = (row >> x) & 1                   the bit: the pixel

A 64-bit integer would hold a whole glyph, but 64-bit integers in shaders are optional on some hardware. Two 32-bit words work everywhere.

4The text as a grid

With every glyph the same width, text layout is trivial: character i of line j goes in column i, row j of a grid. The CPU builds the grid as one string, row by row. Each line is padded with spaces to the width of the longest one, so every row has the same length, and the position of a cell is simple arithmetic:

Shaders often cannot read single bytes from a buffer, so the grid is read as 32-bit words and the byte is picked out: word i / 4, then shift by (i % 4) · 8 and mask with 0xFF. A space, or any code outside the font's range, is drawn as background.

5One quad, and a lookup per pixel

The draw itself is the simplest possible: one rectangle (two triangles, 6 vertices) over the area where the text goes. It needs no vertex buffer: the vertex shader makes the 4 corners from the vertex index and the panel's size. All the work happens in the fragment shader, once per pixel of the rectangle.

From a pixel to its bit

Let the text start at pixel o (the panel's corner plus a margin), each font pixel be s × s screen pixels, and glyphs be 8 × 8. For a fragment at pixel p:

t    = p − o              pixel, from the text's corner
if t.x < 0 or t.y < 0:   background (the padding)
f    = t / s              font pixel (integer division)
cell = f / 8              character cell (column, row)
if cell.x ≥ columns or cell.y ≥ rows:   background
g    = f % 8              pixel inside the glyph
code = byte number (cell.y · columns + cell.x) of the text
if code is outside the font:   background
lit  = bit g.x of row g.y of the glyph of code

Every step is integer math. Division drops the remainder, and % keeps it. Because the scale is a whole number, each font pixel covers exactly s × s screen pixels, and the edges stay sharp.

6Worked example

The two lines from section 4 (14 columns, 2 rows) on a 3840 × 2160 screen, with scale s = 2 and the text starting at o = (16, 16). Which color does the fragment at pixel (34, 42) get?

1. The panel

Drawn at 1 SVG unit per screen pixel. The panel is the text grid plus padding on all four sides, times the scale.

2. Pixel → font pixel → cell

The pixel is in cell (1, 1), at column 1, row 5 of that cell's glyph.

3. Cell → character

Rows are not aligned to words: a word can hold the end of one row and the start of the next. The index arithmetic does not care.

4. Character → bit

One array read, two shifts and two masks. The pixel is part of the stem of the P.

8Alternatives, and what they cost

The per-pixel bitmap font is the simplest end of a range. Each step up the range solves a limit of the one before:

MethodHowGoodLimits

Signed distance field (SDF) atlasthe atlas stores the distance to the glyph's edge instead of coverage; the shader thresholds it (Green, 2007)one atlas for many sizes; cheap outlines, shadows and glowround corners at large sizes; MSDF (multi-channel) keeps corners sharp

A UI libraryDear ImGui and similar: an atlas, plus widgetswindows, buttons, graphs, inputa dependency, its own render pass

One big quad

6 vertices for any amount of text. Cost: the fragment shader runs on every pixel of the box, including empty space and padding. For a small box that is a few hundred thousand pixels at most: tiny for a GPU.

One quad per character

6 vertices per character, built on the CPU or expanded by a shader. Only glyph areas are shaded, and each character can have its own size and position. This is how most text renderers work.

9In RASM

RASM uses exactly the method of sections 2 to 6 for its stats overlay, the panel that shows the numbers from GPU timing and frame statistics. The font, the lookup and the panel layout are in one shader, shaders/passes/statsOverlay.slang. The text is built on the CPU in src/renderer/statsOverlay.cpp. F1 turns it on and off (showStats).

Keep these true
