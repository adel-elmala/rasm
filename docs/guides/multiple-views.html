Culling and the frame

Many views of one scene

A game shows one camera in one window. Many programs need more: an editor with four viewports, a map application with a small map in the corner, a racing game in split screen, a security monitor in the scene that shows another camera. Each picture is a view: one camera's image of the scene, drawn into one place. This page explains how to draw several views in one frame: where each view goes, how a view becomes a texture, what each view must keep from frame to frame, and what an extra view costs. The last part shows how RASM does it.

In short

  • A view is a scene, a camera and an output: a part of the window (a viewport), or a texture.
  • Give a viewport as fractions of the window, and round each edge to a pixel. Views that touch then share their edge: no gap, no overlap.
  • Draw each view into a target of its own size, then copy it into its viewport in the last pass. Its post effects (bloom, TAA) stay inside it.
  • Views draw in list order: a later view goes over an earlier one. That is a picture-in-picture.
  • A view texture is a normal image: a material or the UI samples it. A pass after its writer sees this frame's picture, a pass before it sees the last frame's. A camera that sees its own screen gets the last frame: no cycle.
  • A view's history (last frame's depth and visibility, TAA) belongs to the view. Find it by what the view is (its camera and output), not by its place in the list.
  • An extra view costs a fixed part (culling, depth pyramid, small passes) and a part per pixel. Split one window in two and the pixel part stays about the same.

So a view needs three things: the scene, the camera and the output. The rest of this page is about the output and about what a view keeps.

2Viewports: a rect of the window

A viewport says where a view goes in the window. Give it as fractions of the window, not in pixels: (0.5, 0, 0.5, 1) is the right half of any window. A resize then needs no new numbers.

Two more rules keep a viewport safe. Clamp the edges to the window, and keep at least one pixel, so a rect that is too small or partly outside still draws something defined.

3One target per view

There are two ways to put two views in one window. You can draw both straight into the window's image, each with its own viewport. Or you can draw each view into a target of its own size and copy it into its viewport at the end, in the tone-map pass.

Views share one image

Blurs (bloom) read across the edge, so light from one view glows into the next. A depth pyramid and a TAA history cover both views, so one view's culling and history read the other's pixels.

A target per view

Every effect stays inside its view. The target has the view's own size, so a pixel of it is a pixel of the screen. The cost is the memory of one more target per view.

The last pass, the tone map, reads the view's target and writes its rect of the window. It sets the viewport (where the picture goes) and the scissor (where pixels may change) to that rect.

4Draw order: a later view goes on top

Views that write the same window draw one after the other. The first one clears the whole image; each later one keeps what is there and draws only its rect. So the list order is the stacking order, as in a painting.

  1. clear the window to the background
  2. view A draws its rect: the whole window
  3. view B draws its rect: the corner, over A
  4. the UI draws over both

Part of view A is drawn and then covered by view B. For a small map in a corner that is cheap. For two big views that overlap a lot, it is better to make view A's rect smaller.

5Render to texture

A view's output can also be a texture: a view texture. It is a normal color image. A material samples it like a photo (a TV, a mirror, a portal), and the UI shows it (an editor's viewport panel). Two questions follow: which frame does a reader see, and what happens when the camera sees its own screen.

Two rules make this safe. The texture must live across frames: memory that another target reuses during the frame (transient memory) would hold garbage when a later frame reads it. And the texture must hold something defined before the first frame draws it: clear it when it is made.

6What a view keeps from frame to frame

A view is not drawn from nothing each frame. Occlusion culling reads the depth pyramid and the visibility of the last frame, and TAA blends this frame into last frame's image. That history belongs to one view: another camera's history is a different picture.

Kept by place in the list

Adding, removing or moving one view hands every later view the wrong history: ghosts for a frame, and culling that draws too much or too little.

Kept by what the view is

The key is the camera and the output. A view keeps its targets and history while it is in the list, wherever it is. A new key starts with an empty history.

A view whose rect changes size keeps its key, but its targets change size. The textures are made again, and their old contents are gone, so its history starts over for one frame. The GPU may still read the old textures in the frames in flight, so making them again waits for those frames: the same short wait a window resize has.

7What an extra view costs

Each view runs the whole scene pipeline: culling, the depth pyramid, the draws, the transparent pass, its post effects and the tone map. Part of that cost is fixed per view. The rest grows with the view's pixels, so cutting one window into parts moves pixels around but adds only the fixed part.

1.50 ms4 views: split screen in two halves, the map and the view texturelayout 2

Measured in RASM's example below, 1920 × 1080, Release, on an RTX 3060, with TAA and bloom on the big views and neither on the map. Four quarters cost less than two halves here: one quarter is the map, without TAA and bloom, so fewer pixels go through them. A small view (a map, a mirror) is cheap: skip its bloom and TAA, and it costs mostly the fixed part.

8Input per view

Each view's camera listens to its own rect of the window. A press inside the rect starts a drag that belongs to that view until the release, even when the mouse leaves the rect. The wheel goes to the view under the pointer. The rect in window points is the viewport's fractions times the window's size in points. The camera controllers guide draws it: two views, two inputs, one window.

9Pitfalls

A line of the background color between two views
The viewports were rounded by width, not by edge. Round each edge, so touching views share it.
The glow of a lamp in one view shows in the next
Both views share one HDR image, and the blur reads across the edge. Give each view its own target.
Ghosts for one frame when a view is added
The histories are kept by list place. Key them by the view's camera and output.
A stretched picture in a narrow view
The projection used the window's aspect ratio. Fit it to the view's target instead.
The TV shows garbage, or a validation error about an image layout
The view texture was transient, or never cleared, so a reader found undefined data. Keep it across frames and clear it when it is made.
Dragging in one view turns another view's camera
Both cameras read the whole window's input. Give each camera the input of its own rect.

10In RASM

Engine::render(views, count) draws a list of Views in one frame: each is a scene, a camera and a ViewOutput, which is a ViewRect of the window or of a target. Engine::render(scene, camera) is the same with one view. examples/20_views shows split screen, a map, four views and a TV in the scene.

the application and the engine graph passes targets 
const rasm::ViewRect leftHalf = {.x = 0.0f, .y = 0.0f, .width = 0.5f, .height = 1.0f};
const rasm::ViewRect rightHalf = {.x = 0.5f, .y = 0.0f, .width = 0.5f, .height = 1.0f};
const rasm::ViewRect corner = {.x = 0.75f, .y = 0.0f, .width = 0.25f, .height = 0.4f};
const rasm::View views[] = {
    {.scene = scene, .camera = security, .output = {.target = tv}},
    {.scene = scene, .camera = left, .output = {.rect = leftHalf}},
    {.scene = scene, .camera = right, .output = {.rect = rightHalf}},
    {.scene = scene, .camera = map, .output = {.rect = corner}, .bloom = rasm::ViewToggle::OFF},
};
engine.render(views, 4);

Keep these true
  • A view's kept state is found by its camera and output target, never by its place in the list.
  • A frame with the same list and sizes compares and runs: no graph build, no heap allocation (the views image test counts them).
  • A view texture is not transient and starts cleared: any pass may sample it at any point of the frame.
  • Resizing a target waits only for the frames in flight, and only when its size in pixels changes.
