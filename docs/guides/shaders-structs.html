Shaders and the CPU↔GPU struct contract

RASM compiles its Slang shaders from source while the engine runs, every time a pipeline is built. The shaders read C++ structs straight from GPU memory. So the C++ side and the Slang side must agree on every byte, and two checks help keep them equal.

CPU work / C++ side GPU buffer / bytes Slang side

In short

  • ShaderCompiler holds one Slang global session and one session. compileFromString turns source text plus an entry point name into SPIR-V bytes. Nothing is cached on disk.
  • Shaders come from EngineConfig::shaderDir; lib/ is the include path. Examples use the repo's shaders/, so a shader edit needs no build.
  • Structs are laid out with scalar layout: no padding except for 8-byte alignment of 64-bit fields. glm's default packing gives the same bytes in C++.
  • src/renderer/uberMaterialTypes.h and shaders/lib/core.slang must match. Checks: static_asserts (C++ only), validateRasmStructs (debug builds only, B23). Neither checks field types (C11).
  • The push constant is 16 bytes (PUSH_CONSTANTS_SIZE) for every pipeline.
  • To change a struct, follow the gpu-struct-sync skill.

1From a .slang file to a pipeline

The session settings

ShaderCompiler::initialize makes the session once, at engine start. Every compile uses these settings.

Module names carry a hash

The session keeps every module it ever loaded, and it rejects a second module with the same name but different source. So compileFromString loads the module under the name outputPath + "." + hash(source), for example rasm.vert.slang plus the hash. A shader edited on disk gets a new name and compiles as a new module. Callers can reuse a name freely.

Where the shaders come from

  1. The setting. EngineConfig::shaderDir names the folder. When it is empty, the engine uses RASM_SHADER_DIR, a CMake cache value that defaults to shaders.
  2. Resolved against the executable's folder. resolveFromExecutableDir does this. An absolute path stays as it is. So by default the shaders are a shaders/ folder beside the executable.
  3. Checked once. initialize fails with "Shaders not found in …" unless lib/ and passes/rasm.slang exist there.
  4. Examples. They set shaderDir = RASM_EXAMPLE_SHADER_DIR, which is the repo's shaders/ (cmake/RasmExample.cmake). Edit a shader, restart the example, and the edit is live.
No cache (P8)

Every launch compiles every shader from source. There is no SPIR-V cache on disk and no Vulkan pipeline cache. Each pipeline also gets its own pipeline layout, although all of them are the same (the bindless set and a 16-byte push-constant range).

3Scalar layout: one struct, byte by byte

GPU languages have several layout rules. The usual one for storage buffers, std430, aligns a float3 to 16 bytes. RASM uses scalar layout instead: every type aligns to its largest scalar, so a float3 aligns to 4. That is exactly how glm packs glm::vec3 in C++. Here is GeometryData under both rules.

StructScalar (used)std430 would giveWhere the difference comes from
GeometryData120 bytes144 bytesboundsCenter (a float3) aligned to 16, and the struct rounds up to 16
InstanceData108 bytes128 bytesnormalMatrix (float3x3) is 36 bytes, not 48 (each column padded to 16), and the struct rounds up to 16

The rules of scalar layout

C++SlangSizeAlign
float, uint32_t, int32_t, enum class : uint32_tthe same44
glm::vec2 / vec3 / vec4float2 / float3 / float48 / 12 / 164
glm::mat3 / mat4float3x3 / float4x436 / 644
uint64_t (device address)uint64_t or T*88
T a[N]T a[N] or T[N] aN × sizealign of T
  • 64-bit fields align to 8 on both sides. Both add the same hidden padding, and a struct with one rounds its size up to 8. In SceneData, lights ends at 528 (144 + 8 × 48), which is already a multiple of 8, so vertsPtr sits right there at 528. Keep 64-bit fields at 8-aligned offsets so no padding hides.
  • Never use bool (1 byte in C++, 4 in Slang), size_t, int/long, double, or glm's aligned types in a shared struct.

4The two checks, and what they miss

How validateRasmStructs finds the Slang layout

  1. Start at pc. It finds the push-constant parameter named pc in the linked program.
  2. Follow scene. If pc.scene is not a SceneData, the shader is a custom pass with its own push constants (for example the stats overlay), and the check returns true.
  3. Walk the pointers. From SceneData it reaches each struct through a field: lights, vertsPtr, drawInfoPtr, instancesPtr, geometryPtr → lods, materialsPtr → material → its four parts (fieldStruct).
  4. Compare. For each struct, validateStruct compares the size and every listed field offset with sizeof/offsetof of the C++ struct, and logs each mismatch.

Why the walk? ProgramLayout::getTypeLayout has no layout rule for data behind a pointer, so it reports std140/std430 padding. Only the path through pc reports the scalar layout that the shader really reads.

A missed side fails at start-up with exact numbers (debug build):

[error] Size mismatch for SceneData: C++ 552, shader 560
[error] Offset mismatch for SceneData.lights: C++ 144, shader 148
[error] Offset mismatch for SceneData.vertsPtr: C++ 528, shader 536
Assertion failed: validateRasmStructs(...)

(From the gpu-struct-sync skill's test, which added a float to the Slang side only. The sizes are from that time.)

5The 16-byte push constant

  • argument is for compute only. In countMain and writeMain it is the cull phase (0 early, 1 late). In hizMain it is the Hi-Z level to build. Draws do not read it.
  • static_assert(sizeof(PushConstants) == PUSH_CONSTANTS_SIZE) ties the C++ struct to the constant, and validateRasmStructs checks the Slang side.
  • A custom pass brings its own push-constant struct of at most 16 bytes. The stats overlay's OverlayPushConstants has its own static_assert against PUSH_CONSTANTS_SIZE. See the render graph.
  • Growing the push constant means raising PUSH_CONSTANTS_SIZE, which changes every pipeline layout.

6How to change a struct safely

The full procedure is the gpu-struct-sync skill in .claude/skills/gpu-struct-sync/SKILL.md. Every place below must change in the same commit.

  1. The C++ struct. It is in src/renderer/uberMaterialTypes.h, with hand-aligned header columns.
  2. The Slang mirror. It is in shaders/lib/core.slang: same field order, matching types.
  3. The static_asserts. At the end of uberMaterialTypes.h: the size, and every offset after the change that matters (arrays, pointers, the last field). Compute the new numbers yourself; do not copy them from the compiler error.
  4. The validateRasmStructs table. In src/renderer/shaderCompiler.cpp: one row per field, {"slangName", offsetof(gfx::X, cppName)}. A new struct needs its own validateStruct call, reached through fieldStruct.
  5. Shared constants and enums: MAX_LIGHTS (include/rasm/light.h), MAX_VERTEX_UV_SETS and MAX_MESH_LODS (include/rasm/mesh.h), MaterialId, LightType.
  6. VertexFull only: rasm::Vertex in include/rasm/mesh.h and the static_asserts in src/renderer/geometryPool.cpp.
  7. PushConstants only: Keep it at PUSH_CONSTANTS_SIZE.
  8. The CPU writers. Fill the new field in drawScene, writeInstanceRows, rebuildDrawList, convertToGfxMaterial (all in src/renderer/gpuScene.cpp), GeometryPool::upload. Zero-init ({}) hides a forgotten field.
  9. The GPU readers: shaders/passes/rasm.slang, shaders/passes/cull.slang, shaders/passes/hiz.slang, shaders/lib/pbr.slang, shaders/lib/unlit.slang, shaders/lib/frustumCulling.slang, shaders/lib/occlusionCulling.slang, shaders/lib/lodSelection.slang.
  10. Docs that quote numbers: docs/architecture.md, the frame-debug skill, and these guides.

Then verify in a debug build

Build x64-debug. Only debug builds run validateRasmStructs. A failed static_assert means your expected offsets are wrong.

Then run the examples

Use the verify-change skill, or run each example with enableValidation = true. A mismatch stops the app at start-up with the log above.

7tools/compile-shaders.bat

An offline compile check with slangc, run from the repository root. It compiles every pass shader with its entry points: rasm.slang and statsOverlay.slang (vertMain, fragMain), cull.slang (countMain, writeMain) and hiz.slang (hizMain). The engine does not use its output (it writes into shaders/build/). Its flags mirror the session settings:

A new pass shader goes in the script too

Add one slangc line with its -entry names. The script only checks that the shaders compile. The struct check (validateRasmStructs) runs only in the engine, so still run an example.

9Rules when you change it

Keep these true
  • C++ structs in uberMaterialTypes.h match core.slang byte for byte under scalar layout. Update both sides, the static_asserts and the validateRasmStructs tables together.
  • Verify struct changes in a debug build: release builds skip validateRasmStructs (B23).
  • Compare field types by eye: the checks only see sizes and offsets (C11).
  • No bool, size_t or double in a shared struct. Keep 64-bit fields at 8-aligned offsets.
  • The push constant stays PUSH_CONSTANTS_SIZE (16) bytes in every pipeline.
  • Shared GPU structs go through core.slang; new pass entry points go in shaders/passes/, shared modules in shaders/lib/.
  • A shader change is done only when the examples run with enableValidation = true and no new validation messages.
