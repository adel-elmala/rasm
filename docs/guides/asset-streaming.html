GPU data

Streaming assets in the background

Reading a model or a texture from disk can take hundreds of milliseconds. A frame has about 16. So an engine loads assets on other threads, while it keeps drawing, and brings each one in when it is ready. This page explains how that works: workers, the hand-off to the main thread, a time budget per frame, what to show until the data arrives, caching, failures, and when to free memory. The last part shows how RASM does it.

CPU work (main thread or worker) GPU work memory: buffers, results, caches

In short

  • A load call returns a handle at once. The object is in the loading state until its data is in.
  • Worker threads read and decode the file. They work on their own memory and never touch the engine's state.
  • The main thread picks up finished results at one fixed point in the frame. Only it creates GPU objects and makes the asset visible.
  • A budget per frame (time or bytes) limits how much it picks up, so many loads that finish together do not make one long frame.
  • Until the data is in, the engine shows nothing, a placeholder, or a low-detail version.
  • Loads are cached by path, so one file is loaded once. A failure is a state, not a crash.
  • After the upload, the CPU copy is usually not needed. Free it.

1Why not load on the main thread

The main thread runs the frame loop: input, game logic, and recording the GPU's work. If it stops to load a file, no new frame is made until the load is done. The picture freezes.

Not every part of a load can move to another thread, though. To see which parts can, split the load into its steps.

2What a load is made of

StepBottleneckWhy it can or cannot move
Readthe diskOnly a file name and a byte array. Any thread can do it.
Parse, decodethe CPUA pure function of the bytes. Any thread can do it, if the library has no global state.
Processthe CPUSame as decode: plain data in, plain data out.
Uploadthe bus to the GPUIt creates GPU objects and records copies. Graphics APIs let several threads do this, but each command buffer and pool belongs to one thread at a time. Many engines keep it on the main thread, which is simpler.
PublishnothingIt changes the engine's tables, which the main thread reads all the time. Doing it at one fixed point avoids locks.

3Worker threads and job queues

A worker is a thread that runs jobs given to it by another thread. A job here is "load this file": it gets a path and returns the decoded data. There are three common ways to run them.

WayHowGoodBad
One task per loadStart a new task (a thread, or a library task like a future) for each load. The task's result is the hand-off.Very little code. No queue to write.100 loads at once start up to 100 threads, which fight for the CPU and the disk. No order, no priorities, hard to cancel.
Fixed thread pool with a job queueA few threads (often the core count minus one or two) take jobs from a shared queue.The CPU is never oversubscribed. The queue can be sorted by priority (near objects first), and a job can be removed before it starts.More code: the queue, its lock, and shutting the threads down.
Asynchronous I/O plus a poolThe OS reads the file in the background (overlapped I/O, io_uring); only decoding uses a worker.No thread waits on the disk.Platform-specific code.

4The hand-off between threads

The worker and the main thread run at the same time. If both touch the same data, the result depends on timing: a data race. The safe pattern is that data moves between threads and is never shared. The worker gets a copy of what it needs (a path, some options), builds its result in its own memory, and hands the whole result over in one step. Click through one load (or use the arrow keys).

1. The request returns at once

The caller can use the handle right away, for example to place the object in the scene. The renderer knows the object is not ready and skips it.

2. The worker decodes; frames go on

Each frame asks "is it done?" without waiting. That check must be cheap and must never block.

3. The result waits

Once it has handed over its result, the worker forgets it. Nothing in the engine has changed yet, so there is no race.

4. The main thread picks it up

This happens at one fixed point, usually the start of the frame, before anything reads the engine's tables. So the new asset is either fully in for the whole frame, or not at all.

5. The GPU copies it, then draws it

The copies are recorded before the draws that use them, with a barrier between, so the same frame can already draw the asset. See GPU memory and GPU synchronization.

What the worker may touch

Its inputs (copied in), its own memory, and thread-safe libraries. Not the engine's tables, not the graphics device, not anything the main thread may change. Careful with libraries that keep global settings: an image loader with a global "flip vertically" switch gives different results depending on which thread set it last.

Shutting down

When the program exits while a load runs, the worker still writes into memory that the program is about to free. So shutdown must first wait for (or cancel) every running job, and then free what the finished ones returned.

5A budget per frame

Workers finish at random times. Often many finish together, for example when a level starts. If the main thread picked them all up in one frame, that frame would be long again: the freeze from section 1, only shorter. So the main thread works under a budget: it picks up results until the budget is used, and leaves the rest for the next frame.

Budget inHowTrade-off
TimeStop when the clock passes the limit.Follows the real cost. One big item can still go over, because work is not split.
BytesStop after N MiB of uploads.Predictable for the bus and the staging memory. Ignores CPU work such as building mips.
CountStop after N items.Simplest. A large and a small texture count the same.
No budgetTake everything that is ready, and wait for the rest.For a loading screen: the first frame shows the full scene.

Worked example

30 textures finish at the same moment. Finishing one on the main thread (creating it, copying it, building its mips) takes 3 ms. The frame rate is 60 Hz, so a frame is 16.7 ms.

PolicyMain-thread work per frameResult
No budget30 × 3 = 90 ms, in one frameOne frame takes over 100 ms: a visible hitch of about 5 frames.
4 ms, checked before each texturestarts at 0 ms and 3 ms, so 2 textures = 6 msEvery frame stays smooth. All 30 are in after 15 frames, 0.25 s.

A smaller budget gives smoother frames, but the scene fills in more slowly. A big item that cannot be split, such as one huge texture, needs to be split into pieces (one mip level or one tile at a time) to stay under the budget.

6What to show until the data arrives

One more choice matters: what is one unit. An object often needs a mesh and several textures. If each part appears on its own, the object can show up with a wrong surface for a few frames, for example without its normal map. Waiting until all parts of an object are in avoids that half-loaded look, at the cost of a little more delay.

A placeholder must also be ready before anything can use the asset. When a material points at a texture whose pixels are not there yet, and the renderer may sample it, the texture must hold something defined: a plain color, not uninitialized memory.

7Caching by path, and failures

The same file is often requested many times: a tree model used by a thousand trees, a texture shared by many materials. The loader keeps a cache: a map from the file's path to its handle. A second request returns the first handle, also while the first load still runs.

Errors come in two kinds, and they reach the caller in different ways:

KindExamplesFoundHow the caller learns it
Earlythe file does not exist, the file type is not supported, bad argumentsin the load call, before any job startsan invalid handle, at once
Latethe file is corrupt, the decoder fails, there is no GPU memory left for iton the worker, or when the main thread picks it upthe handle's state becomes failed; the caller can ask for it

Should a failed path stay in the cache? If it stays as "failed", every later request fails fast, which is cheap. If a request may retry, a file that was fixed on disk loads on the next try. Either way, a failure must never leave a half-made asset behind: check that everything fits (memory, table slots) before creating the first part, or undo the parts on failure.

8Freeing the CPU copy

During a load the same data exists several times. Most copies are only needed for a short time.

The decoded data is the big one. A 2048 × 2048 RGBA texture is 16 MiB, and 21.3 MiB with all its mips. A program that keeps every decoded texture after the upload uses twice the memory for nothing. Keep a CPU copy only when the CPU really reads it later:

KeepBecause
positions and indices, as a separate copyphysics, ray picking, CPU culling of individual triangles
small metadata: sizes, bounds, ranges in the GPU buffersthe renderer needs them every frame
nothing elseif the GPU copy is lost, load the file again

9File formats, just enough

Two common mesh formats need different work before the data is GPU-ready:

PitfallWhat happens
glTF data is not alignedA float may start at any byte. Read it with a byte copy, not a pointer cast.
A glTF buffer view has a strideAttributes can be interleaved. Element i starts at offset + i × stride, not i × element size.
OBJ and glTF put the UV origin in different cornersOBJ's v runs up from the bottom; images and glTF start at the top. Flip one of them (v' = 1 − v).
Paths with non-ASCII charactersSome C libraries open files in the system's code page. Open the file yourself (as UTF-8 or wide characters) and pass the bytes or a stream.

10In RASM

RASM loads meshes and textures with one worker task per load. The main thread picks up the finished results at the start of each frame, inside a 4 ms budget. An entity is drawn only when its mesh and all its textures are in.

Textures: two ways in

loadTexture

The main thread reads only the image header (stbi_info) and creates the texture at full size at once, so a material can use the handle before the pixels exist. The worker runs decodeTexture (stbi_load, always 4 channels). finishTextureLoad fills it and sets texturesFinished, so syncGpuScene checks the waiting entities.

Images inside a glTF file

tinygltf decodes them on the worker, as part of the file. loadMaterial creates and fills each one on the main thread, inside finishMeshLoad, so they are ready in the same frame as the mesh. An image with fewer than 4 channels is expanded to RGBA first.

Keep these true
  • Worker code gets a path and returns a plain result. It must not touch the engine, the registry or the device.
  • Anything that creates GPU objects, writes the registry or fills a buffer for a load runs in finishLoads, on the main thread.
  • Check that the whole mesh fits (GeometryPool::fits) before creating any part of it.
  • A texture a material may already use is always filled, even when its decode fails.
  • Free the CPU copy after the upload (P6). Do not keep vertex arrays, the glTF model or pixels in the registry.
  • Shutdown waits for every pending load. The engine's destructor takes each pending texture result and frees its pixels.
Not done yet

No thread pool, no priorities, no cancel. Mips are built on the main thread (P2), so a big glTF file can make one long frame. Nothing can be unloaded (D4), and only 7 meshes can ever be created, because MAX_MESHES is 8 and handles start at 1 and are never reused (B13).
