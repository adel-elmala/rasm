Culling and the frame

GPU timing and frame statistics

To make a renderer faster, you first need to know where the time goes and how much work the GPU really did. That is harder than it sounds: the GPU runs later than the CPU, on its own clock, and its results come back frames later. This page explains how engines measure GPU time and count GPU work without slowing the frame down. The last part shows how RASM does it.

In short

  • The CPU records commands; the GPU runs them later. A CPU timer around a draw call measures the recording, not the drawing.
  • A timestamp query asks the GPU to write its own clock into a query pool when it reaches a point in the command stream. Two timestamps give the time of the work between them.
  • Ticks become nanoseconds with the timestamp period. Only the low valid bits count, so the difference must be taken modulo 2bits.
  • Results are read after the frame's fence, so they arrive N frames late (N = frames in flight), and the CPU never waits for them.
  • Shaders can count their own work (objects culled, triangles kept) with atomics into a small buffer that the CPU reads the same way. A 64-bit count can be built from 32-bit atomics with a carry.
  • Single-frame numbers are noisy: average them, or refresh the text slowly, so that people can read them.

1Two clocks: CPU time and GPU time

A frame has two kinds of time. CPU time is how long the CPU works on the frame: game logic, culling, recording command buffers. GPU time is how long the GPU works on it: running the shaders, writing pixels. The two run at the same time, on different frames.

The time from one frame start to the next is the frame time. It is easy to measure on the CPU, and it is what the player feels. But it is neither the CPU time nor the GPU time: it is the larger of the two, plus any waiting. With vertical sync on, it is also rounded up to the display's refresh interval (16.7 ms at 60 Hz), even if both sides finish in 3 ms.

2Why the CPU cannot time GPU work

The obvious idea fails: start a CPU timer before a draw call and stop it after. The draw call only writes a command into a command buffer. It returns in microseconds, long before the GPU starts it. Waiting for the GPU does not work either:

CPU-side attemptWhat it really measures
Timer around the draw callthe cost of recording the command
Timer from submit to "the fence is signalled"the GPU work plus the queue wait (earlier frames still running), the driver's delay, and the moment the CPU noticed the fence
Submit each pass alone and wait for itthe pass, but the GPU now idles between passes and cannot overlap them. The frame becomes much slower, and the numbers describe that slower frame.

The only reliable clock for GPU work is the GPU's own clock. The GPU must write it down at the right moments, while it runs the frame as usual.

3Timestamp queries

A query is a small slot that the GPU fills with an answer. A query pool is an array of them. A timestamp query is filled with the value of the GPU's clock. The command that fills it goes into the command buffer, between other commands, like a bookmark:

What the API tells you about the clock

Value (Vulkan name)MeaningUse
Timestamp period (timestampPeriod)nanoseconds per tick, a float. Often 1, but it can be 10, 41.7, 52.1, … depending on the GPU.ns = ticks × period
Valid bits (timestampValidBits, per queue family)how many low bits of the 64-bit value are real. 0 means the queue has no timestamps.take differences modulo 2bits (below)

Wrap-around

With fewer than 64 valid bits, the counter wraps back to 0 now and then. A pass that straddles the wrap has an end timestamp smaller than its begin. Plain subtraction then gives a huge number. The fix is to subtract and keep only the valid bits; that is subtraction modulo 2bits:

mask  = 2^bits − 1                      bits = 32 → mask = 0xFFFFFFFF
ticks = (end − begin) & mask

begin = 0xFFFFF000   end = 0x00001000   (the counter wrapped in between)
ticks = 0x00001000 − 0xFFFFF000 = 0x2000 (mod 2^32) = 8192 ticks
      → 8192 × 40 ns = 0.328 ms

This works as long as the measured work is shorter than one full turn of the counter. Even with 32 bits and a 1 ns tick, a turn is 4.3 seconds.

Rules of query pools

  1. Reset before use.A query must be reset before the GPU writes it again, either by a command in a command buffer or, where supported, from the CPU (Vulkan 1.2 "host query reset").
  2. Read after the GPU is done.Reading earlier either fails ("not ready") or, with a "wait" flag, blocks the CPU until the GPU gets there.
  3. Do not reuse while in flight.A pool that the GPU is still writing cannot be reset by the CPU. With several frames in flight, each frame needs its own pool (section 4).

4Reading results without stalling

The timestamps of frame N are written while the GPU runs frame N, which is after the CPU has moved on. If the CPU waited for them right away, it would lose the overlap of section 1. Instead, each frame-in-flight slot gets its own query pool. The CPU reads a slot's pool at the moment it must wait for that slot anyway: after the slot's fence, just before it records the slot's next frame.

The same pattern works for anything the GPU writes for the CPU: counters (section 7), readback of pixels, GPU-generated lists. A frame that was recorded but never submitted wrote nothing, so the reader must notice that (for example, by checking that the fence value moved) and skip the slot.

5Per-pass timers

A timer is a pair of timestamps: one before a piece of work, one after it. Put a pair around the whole frame and one around each pass, and you have a profile of the frame. A pool with 2k queries holds k timers: timer i uses query 2i for its begin and 2i + 1 for its end.

Thing to knowWhy it matters
Pass times do not add up to the frame timeA GPU overlaps work: the next pass may start before the previous one has fully drained. Nested timers are counted twice if added.
Timestamps are cheap, not freeA timestamp waits for earlier work to reach its stage. Many timers inside a pass can reduce overlap a little. A few per pass are fine.
Tile-based GPUs (most phones)Inside a render pass, the GPU works tile by tile, not draw by draw. Timestamps between draws in one pass are not meaningful there; time whole passes.
Clock speed changesA GPU with little work lowers its clock. A light frame can then show longer times than expected. Profile with a stable workload, or ask the driver for a stable clock.
Fixed pool sizeA pool holds a fixed number of timers. When a frame wants more, the extra ones must be dropped, ideally with one warning, not one per frame.

6Pipeline statistics, and other counters

Timestamps say how long. Other questions are "how much": how many vertices, triangles or pixels did the GPU really process? APIs have query types for that too:

Query typeCounts
Pipeline statisticsper pipeline stage: input vertices and primitives, vertex shader runs, primitives after clipping, fragment shader runs, compute shader runs. Chosen by flags when the pool is made.
Occlusionsamples that passed the depth test between begin and end. Used for occlusion tests and lens flares.
Vendor counterscache hits, memory traffic, occupancy. Seen in tools like Nsight, Radeon GPU Profiler or PIX, not usually inside the engine.

Pipeline statistics have the same timing as timestamps (begin, end, read frames later). They are optional on some hardware and have a small cost. They cannot answer questions about the engine's own work, such as "how many objects did culling keep?". For that, the shaders count by themselves.

7Counting in shaders, with atomics

In a GPU-driven renderer the GPU decides what to draw, so the CPU does not know how many objects survived culling or how many triangles were drawn. The shader that decides can count. Thousands of threads add to the same counter, so the add must be an atomic operation: a read-modify-write that no other thread can interrupt.

64-bit counts from 32-bit atomics

A 32-bit counter overflows at 4,294,967,295. A big scene can draw more triangles than that per frame. 64-bit atomics would fix it, but not every GPU and API has them: WebGPU has none, and Metal has them only on some GPUs and only for some operations. The trick: keep two 32-bit words, low and high, and carry by hand.

1. Add up a group's numbers in 64 bits

Unsigned 32-bit math wraps around, it does not fail. So "the result went down" means "it passed 232".

2. Add the group's total to the buffer

The atomic returns the value from just before this group's add. Only this group's add can have caused the wrap it sees, so each carry is counted exactly once.

3. Read it on the CPU

Reading in the middle of the frame could see a low word that has wrapped and a high word that has not been incremented yet. Reading after the fence avoids that.

8Turning numbers into something readable

A frame time changes every frame by a little, and sometimes by a lot (a spike). Printing every frame's value makes an unreadable blur. Common fixes:

MethodHowGood for
Sample and holdshow the latest value, but update the text only a few times per secondthe simplest; readable; hides spikes between updates
Mean over a windowkeep the last n values in a ring, show their averagesteady numbers; needs memory for n values
Exponential moving averageavg = avg + α · (value − avg), with α = 0.05 to 0.2one number of state; reacts in about 1/α frames
Max, or percentilesthe worst frame of the last second; the 99th percentile ("1% low" fps)stutter: the average hides it, the max shows it
A grapha strip of the last few hundred frame timesseeing spikes and patterns at a glance

An example with α = 0.1. Frames take 16.7 ms, then one takes 40 ms, then 16.7 ms again. The average moves from 16.7 to 16.7 + 0.1 · (40 − 16.7) = 19.0, then to 19.0 + 0.1 · (16.7 − 19.0) = 18.8, and slowly back. The spike is visible, but it does not take over the display. The max of the last second would show 40.

Average times, not frames per second

Frame rate is 1000 / ms, which is not linear. Two frames of 10 ms and 30 ms average 20 ms, which is 50 fps. Averaging their rates (100 fps and 33 fps) gives 67 fps, which is wrong. Average the times, then convert.

9Measure only when someone looks

Timers, counters and readback are cheap but not free: a few commands per pass, some atomics in the shaders, a buffer read and a text update per frame. A common rule is to measure only while an overlay is shown or a tool asks for the numbers. Two details follow:

  • The first values arrive N frames after measuring starts (section 4). Until then, show zeros or nothing.
  • A counter that the shaders always add to (because skipping the atomics would need a shader branch) must be zeroed before the first measured frame, or it shows garbage from earlier frames.

10Memory numbers

The other number people ask for is "how much video memory do we use?". The API can tell, per memory heap:

NumberMeaning
Budgethow much of this heap the process can use now without trouble. It changes with what other programs use. Going over it makes the driver move memory around, which is slow.
Usagehow much of this heap the process uses now, counting everything: buffers, textures, the swapchain, the driver's own allocations.
Heap sizethe total. It never changes, and it is not what you can really use.

In Vulkan these come from the VK_EXT_memory_budget extension. A heap marked device-local is video memory on a discrete GPU. On an integrated GPU, or with resizable BAR, device-local memory can also be visible to the CPU, so "device-local" and "video memory" are not exactly the same thing. See GPU memory.

11In RASM

RASM collects one set of numbers per frame into a public FrameStats. The application reads it with Engine::getFrameStats; the stats overlay draws it on screen. Everything follows sections 3 to 9: timestamp pairs per pass, one query pool and one counter buffer per frame slot, read after the slot's fence.

The timers

Each slot has a pool of 2 × MAX_GPU_TIMERS = 32 timestamps, so 16 timers. Timer i writes queries 2i and 2i + 1, both with vkCmdWriteTimestamp2 at the "all commands" stage.

TimerStarted byName
The frame's command bufferbeginFrame, ended in endFrame"Frame" (always timer 0, not listed)
Each graphics passbeginPass / endPassthe pass name: "Scene 1" and "Scene 2" of the scene passes ("Scene" without occlusion culling), "Clear" for the empty swapchain pass, or your graph pass's name
Each render graph compute passRenderGraph::executethe pass name: "Cull 1", "Hi-Z" and "Cull 2" of the scene passes ("Cull" without occlusion culling), or your graph pass's name
The application's own workEngine::beginGpuTimer / Engine::endGpuTimerits own name

Every timer is in the frame's one command buffer, around one pass. As in section 5, gpuFrameMs runs from the earliest timestamp to the latest end, and gpuTimers are sorted by start time, so they list the passes in the order they ran: "Cull 1", "Scene 1", "Hi-Z", "Cull 2", "Scene 2". VulkanDevice::getTimestamps turns the raw values into nanoseconds: each value becomes its signed distance from the first one, masked to timestampValidBits (the wrap rule of section 3), then the earliest is subtracted and the result multiplied by timestampPeriod. It reads without the wait flag, so a pool that is not ready returns nothing instead of stalling.

The counters

The cull shader counts what it keeps. Each slot has a Cull Stats Buffer of CULL_STATS_WORDS = 13 words, host-visible and host-readable. The STATS_* constants in cull.slang and the CULL_STATS_* ones in gpuScene.h name them:

WordsHoldsBecomes
[0]visible drawsdrawsVisible
[1] low, [2] highvisible triangles at the LOD culling pickedtrianglesVisible
[3] low, [4] highthe same draws' triangles at LOD 0trianglesVisibleLod0
[5] … [12]visible draws at LOD 0 … 7drawsPerLod

countMain does what section 7 describes. Each thread writes its result to shared memory; the group's last thread adds the 64 triangle counts in two words with a carry, then calls InterlockedAdd once for the draw count and addCount64 for each triangle count. Threads 0 to 7 each count the group's draws at their LOD and add that. The early and the late culling (see occlusion culling) both count, and a draw is still counted once, because the late pass only keeps draws the early one did not draw. Draws of a scene view drawn without culling are not seen by the shader, so the CPU adds them from DrawTotals (unculledDraws, unculledTriangles), counted at LOD 0.

Keep these true
  • The STATS_* words in cull.slang match the CULL_STATS_* words in gpuScene.h.
  • A slot's pool and counter buffer are read and reset only after that slot's fence wait (the frame order in beginFrame).
  • endFrame records a COMPUTE → HOST barrier after the last pass; without it the CPU may read stale counters.
  • beginGpuTimer may return UINT32_MAX; endGpuTimer must accept it and do nothing.
