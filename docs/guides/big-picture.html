Engine tour

The big picture

RASM is a stack of a few layers. The application talks to one class, Engine, and gets small handles back. Under it, RenderContext turns handles into GPU objects, and rhi::Device hides the graphics API. Vulkan is the only backend today.

This is the first stop of a three-page tour of the engine. It shows the parts and how they fit together. Each idea behind a part (handles, bindless, culling, ...) has its own guide, linked where it comes up.

CPU work GPU work GPU buffer / memory

In short

  • Layers: application → Engine → RenderContext → rhi::Device → VulkanDevice → GPU.
  • Applications include only include/rasm/. Everything in src/ is private.
  • Every object is a handle: Handle with an index and a generation. One HandleManager in Engine makes them all.
  • CPU objects (entities, meshes, materials, cameras, lights, scenes) live in Engine's registry. GPU objects (buffers, textures, pipelines, ...) live in RenderContext's tables.
  • Shaders, pipelines and descriptor set layouts are deduplicated by their descriptor. Buffers and textures are always new.

3Public and private headers

Engine holds GeometryPool, ShaderCompiler, GpuScene, FrameStatsCollector and StatsOverlay this way. RenderContext keeps its rhi::Device and all its tables in RenderContext::Impl. Private code includes private headers relative to src/, for example "rhi/vulkan/vulkanDevice.h".

The tests are the exception

rasm_tests links rasm::rasm like an application, but it also has src/ on its include path, to test private classes against a fake rhi::Device.

4Handles and the two kinds of owner

The application never holds a pointer. It holds a handle: Handle, an index and a generation. A default handle has generation == 0 and is invalid (isValid). Its tag makes each handle its own C++ type, so a MeshHandle cannot go where a TextureHandle is expected. Why handles, and what the generation is for, is in Generational handles. This section shows who owns what in RASM.

CPU object: createEntity

1. getNextEntityHandle gives {3, 1}.
2. index >= MAX_ENTITIES? Then warn and return an invalid handle.
3. registry.entities.resize(4), then entities[3] = the new Entity.
4. With a mesh: queueInstanceRows, so the GPU scene gives it rows later.

GPU object: createBuffer

1. device->createBuffer(desc) returns an rhi::Buffer pointer, or null on failure (then an invalid handle).
2. getNextBufferHandle gives {5, 1}.
3. buffers[{5, 1}] = that pointer.
4. Every later call looks the handle up, and logs an error if it is not found.

OwnerTypeLimitWhere the limit is

Indices start at 1 and the check is index >= MAX_*, so slot 0 is never used. That is why only 7 meshes fit.

Known issues

D4: nothing can be destroyed before shutdown, and generation is always 1, so a stale handle cannot be detected. Registry slots and bindless slots are never reused. Generational handles shows what is missing.

B13: a handle index is taken before validation, so a failed create still uses up an index.

5Descriptors and creation dedup

Each GPU resource has its own creation descriptor in rasm/render/resource.h: BufferDesc, TextureDesc, ShaderDesc, PipelineDesc, RenderTargetDesc, BindlessDescriptorSetLayoutDesc, DescriptorPoolDesc. Each has a name, default values for every field, and a defaulted operator==. You fill them with designated initializers.

An entity without a valid material, or a sub-mesh without one, draws with the default material: getMaterial resolves an invalid handle to it. On the GPU each entity becomes one instance row per sub-mesh, and a material becomes one row that names its textures by bindless slot. The GPU scene tables (stop 3) show how these objects reach the GPU. Streaming assets in the background shows how meshes and textures load, and Mesh simplification how a mesh gets its LODs.

9Rules when you change it

Keep these true
  • A public header never includes a private header or a backend or third-party header (except glm). Forward-declare, or use a private Impl.
  • A new field in ShaderDesc, PipelineDesc or BindlessDescriptorSetLayoutDesc must also be folded into its hash in src/rhi/resource.cpp.
  • createBuffer and createTexture always make a new resource. Cache at the asset level if you want sharing, and destroy what you replace.
  • A new part gets its own .h/.cpp pair in its layer's folder, and its .cpp goes into target_sources(rasm ...) in src/CMakeLists.txt. A header in include/rasm/ needs no list entry: it is found and installed by itself.
  • A new dependency linked to rasm also needs a find_dependency line in cmake/rasmConfig.cmake.in, because rasm is a static library.
  • No templates in RASM code. Handle in rasm/handle.h is the only exception.
