Sorting on the GPU

A GPU-driven renderer decides on the GPU what to draw, so when the draws must be in an order (see-through surfaces back to front, for example), the GPU has to sort them too. A CPU sort compares and moves one pair at a time. A GPU sort needs a plan where thousands of threads each compare one pair, all at the same time, with no thread waiting for another. This page explains the bitonic sort, the classic such plan, and how it maps to compute dispatches. The last part shows how RASM sorts its see-through draws.

In short

  • Sort small keys: a number that gives the order, plus the item's index so equal numbers keep a fixed order.
  • A sorting network is a fixed list of compare-and-swap steps. It does not depend on the data, so every step can run one thread per pair.
  • The bitonic network sorts n = 2m keys in m(m + 1) / 2 steps of n / 2 compares each.
  • Steps that compare keys close together run inside one workgroup, in shared memory; steps with a long distance need a dispatch of their own and a barrier.
  • When only the GPU knows how many items there are, sort a fixed power of two and give the missing items the largest key: they end up last.
  • For very many keys a radix sort does less work; for a few thousand, bitonic is simple and fast.

1What to sort: keys

Moving whole items around is slow, so sort keys: one small value per item that says where it goes, and the item's index. After the sort, one more pass copies the items to their new places.

A float as a sortable integer

For a float that is 0 or more, its bits read as an unsigned integer grow with the float. So asuint(depth) sorts like the depth. To sort far first with an ascending sort, use the complement, ~asuint(depth).

2Sorting networks

A compare-and-swap looks at two places and swaps them if they are out of order. A sorting network is a fixed list of such compares, grouped into steps; the compares of one step touch different places, so they can all run at once. Whatever the input, after the last step the list is sorted.

The bitonic network builds bigger and bigger sorted pieces. A merge of size k (2, 4, 8, …) takes two sorted halves that run in opposite directions, a bitonic sequence, and turns it into one sorted piece, in steps of distance j = k/2, k/4, …, 1. In each step, place i is compared with place i + j; the piece sorts up when bit k of i is 0 and down when it is 1, so the next merge again gets two halves in opposite directions.

3Steps as dispatches

Every step must see the result of the step before it, everywhere in the list. On a GPU that means a barrier between steps. Inside one workgroup a barrier is cheap: the group's threads sync on shared memory. Across workgroups it means ending the dispatch, a memory barrier, and a new dispatch.

Short steps: in a group

When the distance j is below the block size, both keys of every pair are in the same block. One dispatch runs all such steps of a merge in shared memory.

Long steps: one dispatch each

A distance of a block or more crosses blocks. Each such step is a dispatch over the whole list, reading and writing memory, then a barrier.

The count

With blocks of B keys, the first log B merges are one dispatch. Each larger merge of size k takes log(k/B) long steps and one short-step dispatch.

When only the GPU knows the count

In a GPU-driven frame the number of items to sort comes from an earlier GPU pass, and the CPU records the dispatches before that pass runs. So the CPU sizes the sort for the most items there can be, rounded up to a power of two, and the threads past the real count write the largest key. Those keys sort to the end, and the copy pass stops at the count.

Pad with the largest key, index included

A padding key with the largest order value but a small index could tie with a real item at that value and land in front of it. Make the padding key the largest in every part, (max, max), and give real items indices below the padding's.

4Other GPU sorts

Bitonic

Simple, no atomics, fixed work. Best for up to some tens of thousands of keys.

n log² n compares.

Radix

Sorts by a few bits at a time with histograms and prefix sums. The fastest for millions of keys.

n × (bits / digit size) passes.

Sort per tile only

Particles or a tiled renderer may only need each tile in order: one shared-memory sort per group and no global steps.

One dispatch.

5In RASM

RASM sorts the see-through (BLEND) draws of each shaded view back to front, after culling has packed the visible ones (see transparency and stream compaction). The plan is made on the CPU from the size of the blend run, which the CPU knows; the count of visible draws is read on the GPU.
