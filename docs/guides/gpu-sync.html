Foundations

GPU synchronization: barriers, stages, layouts

A GPU runs the commands of a command buffer in order, but not one after the other: they overlap, and their results sit in caches for a while. When one command reads what another wrote, the program has to say so, with a barrier. This page explains what a barrier does, how to write one well, and how images add layouts on top. The last part shows RASM's barriers.

In short

  • Two uses of the same memory, where at least one writes, form a hazard: read after write, write after read, or write after write.
  • A barrier is an execution dependency (later work waits for earlier work) plus, for writes, a memory dependency (the write is flushed from caches and made visible to the reader).
  • Both halves are scoped by pipeline stages and access types: "wait for these stages, and make these writes visible to those reads".
  • Narrow scopes keep the GPU busy. Too wide is slow but correct; too narrow is a bug that may only show on another GPU.
  • Images also have a layout, the way their memory is arranged for one kind of use. A barrier changes it, and the old contents can be discarded at the same time.
  • Across submissions and queues, semaphores order GPU work and fences tell the CPU. A render graph can write all of this from declared reads and writes.

1Why the GPU needs to be told

Commands in one command buffer start in the order they were recorded. But a GPU is a pipeline with many cores: the next command starts as soon as there is room, long before the last one is done. Without a barrier, a command that reads a buffer can run at the same time as the command that writes it.

Older APIs found these cases themselves. Vulkan and Direct3D 12 do not: the program says where they are. A missing barrier is not an error the driver reports. It is a race, and it may only show up on another GPU, another driver, or under more load.

3Two halves: execution and memory

"Wait for A" is only half of the job. The other half is caches. A GPU has a small cache next to each group of cores, a larger shared one, and then memory. A write first lands in a cache near the core that made it. Another core may hold an old copy of the same bytes in its own cache.

Execution dependency

"Work after the barrier, in these stages, does not start before work before the barrier, in those stages, has finished." Enough for write after read.

Memory dependency

"Writes of these kinds, before the barrier, are made available, and then visible to accesses of those kinds after it." Needed for read after write and write after write.

5Access types: what to flush and make visible

Stages say when. Access types say which memory traffic the memory dependency covers. Each access type belongs to certain stages:

The access rule
  • Source access: only the writes before the barrier. A read leaves nothing to flush, so naming it does nothing.
  • Destination access: every read and write after the barrier that must see the earlier writes (or come after them).
  • Write after read: source access is empty. The stages alone are enough.

6Writing a barrier: Vulkan synchronization2

Vulkan 1.3 made synchronization2 core. It packs stage and access together for each side of each barrier, which is easier to read than the original call. One call, vkCmdPipelineBarrier2, takes a list of barriers of three kinds:

KindCoversUse it for
Memory barrierall memorybuffers. Drivers rarely do better with a per-buffer barrier, and a global one also covers memory read through GPU pointers.
Buffer barrierone range of one bufferpassing a buffer between queue families (section 9).
Image barriersome mips and layers of one imageimages: it is the only kind that can change a layout.

A memory barrier for the example on this page's first picture, where a compute shader writes the draw commands of a later indirect draw:

// A compute pass wrote draw commands; the next draw reads them as indirect arguments.
VkMemoryBarrier2 barrier = {.sType = VK_STRUCTURE_TYPE_MEMORY_BARRIER_2,
                            .srcStageMask = VK_PIPELINE_STAGE_2_COMPUTE_SHADER_BIT,
                            .srcAccessMask = VK_ACCESS_2_SHADER_STORAGE_WRITE_BIT,
                            .dstStageMask = VK_PIPELINE_STAGE_2_DRAW_INDIRECT_BIT,
                            .dstAccessMask = VK_ACCESS_2_INDIRECT_COMMAND_READ_BIT};
VkDependencyInfo dependency = {.sType = VK_STRUCTURE_TYPE_DEPENDENCY_INFO, .memoryBarrierCount = 1, .pMemoryBarriers = &barrier};
vkCmdPipelineBarrier2(commandBuffer, &dependency);

Put several barriers into one call when they sit at the same point: the driver can then do one wait instead of several. And never put a barrier between two draws "just in case": every barrier drains part of the pipeline.

7Image layouts

GPUs store images in different arrangements for different uses: tiled and compressed for drawing into, a different tiling for sampling, plain lines for the display. Vulkan calls the arrangement a layout, and it is part of the image's state. An image barrier changes it, between the source and the destination scopes.

Layout (Vulkan)For
UNDEFINED"I do not care about the contents". Only valid as the old layout: changing from it may throw the contents away.
COLOR_ATTACHMENT_OPTIMALdrawing into the image
DEPTH_STENCIL_ATTACHMENT_OPTIMALdepth testing and writing
SHADER_READ_ONLY_OPTIMALsampling in shaders
TRANSFER_SRC / TRANSFER_DST_OPTIMALcopies and blits
GENERALanything, including storage writes; possibly slower
PRESENT_SRChanding a swapchain image to the display

Two details catch people out. First, an image barrier is a full barrier: even a "discard" must still wait for the last use of the image (a write after read), so its source stages are not empty. Second, the layout belongs to each mip level and array layer. A barrier can change only some of them, and the program must then track each one.

11Automating it, and pitfalls

Writing every barrier by hand does not scale. Two common helpers:

Track the state of each resource

Each image remembers its current layout and last use. A call like "make this texture readable" records the right barrier, or none. Simple, but each call only knows the past.

A render graph

Passes declare what they read and write before anything is recorded. The graph knows the whole frame, so it can place, merge and move barriers. See render graphs.

PitfallWhat happens
Read access in the source maskDoes nothing. The intended write is not flushed if it was left out.
Forgetting write after readA pass overwrites a texture while the previous pass still samples it.
ALL_COMMANDS on both sides, everywhereCorrect but slow: the GPU drains at every barrier.
Wrong old layoutUndefined contents, or a validation error. UNDEFINED as old layout when the contents are needed loses them.
A barrier inside a render passNot allowed in Vulkan's dynamic rendering, except for special self-dependencies. End the pass first.
Testing on one GPUSome GPUs flush caches anyway, and hide the missing barrier. Use the validation layer's synchronization validation.

12In RASM

RASM uses synchronization2 and one queue. The RHI offers two barrier calls, deliberately coarse: a global memoryBarrier between sets of PipelineStage, and an image transition between two TextureUsage values. RenderContext remembers each texture's usage, and the RenderGraph derives barriers from what passes declare.

The three stage sets

PipelineStageVulkan stagesAccesses as before (writes only)Accesses as after
COMPUTEcompute shadershader storage writeshader storage read and write, uniform read
GRAPHICSdraw indirect, index input, vertex shader, fragment shadershader storage writeindirect command, index, shader storage and uniform read; shader storage write
HOSThosthost writehost read and write

PipelineStage is a set of flags, so one barrier can name several with |. Culling ends with COMPUTE → GRAPHICS | HOST: the draws read the lists, and the CPU reads the cull stats after the fence.

Any other usage has no scope: the transition logs an error, records nothing and returns false. The source scope comes only from the old usage and the destination only from the new one, so each table row is written once. UNKNOWN as the old usage is the "discard" of section 7: it waits for every stage that could have used the image, because the last use is not known. Its color output stage also chains the barrier to the swapchain's acquire semaphore.

The barriers of one frame

The render graph's part

Before each pass, RenderGraph::execute records at most one memoryBarrier and moves the textures the pass reads to SAMPLED. bufferBarrier keeps, per buffer, the stages of the last write and of the reads since. Its rules are the hazards of section 2: a read after a write waits for the write (once per reading stage), and a write waits for every use since the last write. The state carries over to the next frame. See render graphs.

Keep these true
  • Use synchronization2 (vkCmdPipelineBarrier2) and dynamic rendering; no render pass objects.
  • No barrier, dispatch or layout change between beginRendering and endRendering; RenderContext checks it.
  • A texture's layout changes only through transitionImageLayout, so Texture::state stays true. A frame that is not submitted calls discardRecording.
  • A new TextureUsage that textures move into needs a source and a destination scope in getSrcScope and getDstScope.
  • A graph pass declares every buffer and texture it uses, or the graph cannot place its barriers.
  • Test with enableValidation and enableSyncValidation on (or verify.py --sync); a change that adds validation messages is not done.
