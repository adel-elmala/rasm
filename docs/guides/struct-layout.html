GPU data

Struct layout rules

The CPU writes a struct into a buffer, and a shader reads it. Two different compilers decide where each field goes, and they must agree on every byte. This page explains the rules each side uses, where they differ, and how to check that they match. The last part shows how RASM does it.

In short

  • Every type has a size and an alignment. A field goes at the next offset that is a multiple of its alignment; the gap before it is padding.
  • C++ aligns each type to its own size (a float to 4, a double to 8). A vec3 of floats is 12 bytes, aligned to 4.
  • GPU languages have several rule sets. std140 aligns a vec3 to 16 and pads arrays to 16. std430 drops the array padding. scalar aligns everything to its scalar, like C++.
  • The same struct can be 112, 96 or 72 bytes depending on the rules. A mismatch does not crash; the shader just reads the wrong bytes.
  • Check it: static_assert the C++ offsets, and compare them with the shader compiler's reflection at startup.

1The problem: two compilers, one buffer

A C++ compiler lays out the CPU struct. A shader compiler lays out the GPU struct. Nothing connects the two. The bytes in the buffer are whatever the CPU wrote; the shader reads each field at the offset its compiler chose.

2Size, alignment and offset

Every layout rule set, CPU or GPU, uses the same algorithm. Only the numbers in it differ.

WordMeaning
sizehow many bytes the value takes
alignmentits offset must be a multiple of this number
offsetwhere the field starts, from the start of the struct
paddingunused bytes added so the next field is aligned, or so the struct size is
stridethe distance from one array element to the next
offset = 0
maxAlign = 1
for each field:
    offset = roundUp(offset, align(field))      // padding goes here
    field.offset = offset
    offset = offset + size(field)
    maxAlign = max(maxAlign, align(field))
structSize  = roundUp(offset, maxAlign)          // padding at the end
structAlign = maxAlign

roundUp(x, a) is the smallest multiple of a that is ≥ x. The padding at the end makes the size a multiple of the alignment, so that in an array every element is aligned too: the array stride is the struct size.

3C++ layout

On every desktop platform, C++ aligns each scalar to its size: int32_t and float to 4, double, int64_t and pointers to 8. A struct aligns to its largest member. Order matters: the same fields can need more or less padding.

Math libraries follow the same rules. In glm (by default), a vec3 is three floats: 12 bytes, aligned to 4. A mat3 is three vec3 columns: 36 bytes. A vec4 is 16 bytes but also aligned to only 4. Some libraries (and glm with special options) align vec4, or even vec3, to 16 for SIMD; that changes every offset after them.

The C++ side can be pinned with checks the compiler runs:

struct Light
{
    glm::vec3 position;
    float intensity;
};

static_assert(sizeof(Light) == 16);
static_assert(offsetof(Light, intensity) == 12);

4GPU layouts: std140, std430, scalar

Vulkan GLSL and SPIR-V know three rule sets for buffer memory. They differ in two places: how a three-component vector aligns, and whether arrays and structs are rounded up to 16 bytes.

5One struct, three layouts

Here is one struct, laid out under all three rule sets. d is an array of two vec2; m is a 3 × 3 matrix stored as three columns (c0, c1, c2).

struct Example
{
    float a;
    float3 b;
    float c;
    float2 d[2];
    float3x3 m;
};

Click through the std430 row, field by field, with the algorithm of section 2.

1. a: float

The first field always starts at 0.

2. b: float3

The only padding between fields in this struct: 12 bytes before b.

3. c: float

No padding: a scalar fits right after a float3.

4. d: float2[2]

In std140, each float2 would take 16 bytes, and d would end at 64.

5. m: float3x3

Each column of a float3x3 wastes 4 bytes in std430 and std140, but not in scalar layout.

6. The end: size and alignment

The size is 96. The C++ struct is 72, so the two sides disagree from b on.

8Push constants

Push constants are a few bytes written straight into the command buffer, the fastest way to give a draw small per-draw values. Their layout follows the same rules (std430 by default in Vulkan GLSL). Two extra limits apply:

LimitValue
Total size (maxPushConstantsSize)at least 128 bytes in Vulkan 1.0 to 1.3, at least 256 in Vulkan 1.4. Many desktop GPUs allow 256.
RangesThe pipeline layout declares which byte ranges each shader stage sees. A push must stay inside a declared range.
Offsets and sizesmultiples of 4
Direct3D 12 equivalentroot constants: the whole root signature is 64 DWORDs (256 bytes), shared with root descriptors and tables

Because the space is small, a common design puts just one pointer (8 bytes) and a couple of indices there, and everything else in buffers. See Buffer device addresses.

9Making sure both sides agree

A layout mismatch gives no error by itself. So each project picks one or more ways to catch it:

10In RASM

RASM uses scalar layout for everything, so its C++ structs (with glm's default packing) and its Slang structs follow the same rules. The structs live twice: in src/renderer/uberMaterialTypes.h (namespace rasm::gfx) and in shaders/lib/core.slang. Two checks hold them together.

A mismatch shows up at startup, in a debug build, with messages in this form (from validateStruct):

Size mismatch for <struct>: C++ <bytes>, shader <bytes>
Offset mismatch for <struct>.<field>: C++ <offset>, shader <offset>

Shaders are compiled at startup

RASM compiles its Slang shaders when the engine starts, from EngineConfig::shaderDir. So the check runs on every start of a debug build, and a shader edit needs no build step. tools/compile-shaders.bat compiles every pass offline with the same flags (-force-glsl-scalar-layout, -matrix-layout-column-major), only as a syntax check; the engine does not use its output.

Keep these true
  • Change a shared struct on both sides in the same change: the C++ struct, the Slang struct, the static_asserts, and the table in validateRasmStructs. The gpu-struct-sync skill lists every place.
  • Run a debug build after the change: only it runs the reflection check.
  • Never use bool, size_t, int or glm's aligned types in a shared struct.
  • Keep 64-bit fields at offsets that are multiples of 8, and the struct size a multiple of 8.
  • Compare the two definitions field by field by eye: types are not checked.
