Culling and the frame

Multiple render targets

Often one pass must produce several images for the same pixels: a color, a normal, a material, a mask. Multiple render targets (MRT) let one draw write all of them at once. The fragment shader returns several values, and each one goes to its own texture. This page explains how that works, what it costs, and where it goes wrong. The last part shows how RASM does it.

In short

  • A pass can have N color attachments. The fragment shader returns N values; output i goes to attachment i.
  • The geometry is drawn once: vertex work, rasterization and the depth test happen one time for all N images.
  • All attachments have the same size. Each one has its own format, and can have its own blend state and write mask. There is one depth attachment for all of them.
  • The pipeline is built for the exact list of formats, in order. A pass with other formats cannot use it.
  • APIs allow 4 to 8 color attachments. The real limit is bytes per pixel: every byte is written and later read, for every pixel, every frame.
  • The classic use is deferred shading: a G-buffer pass writes surface data, a lighting pass reads it.

1The problem: several images per pixel

Many techniques need more than one value per pixel. Deferred shading needs the surface color, the normal and the material of every pixel. Motion blur and temporal anti-aliasing need a velocity per pixel. Object picking needs an object ID per pixel. Post effects often need a mask that says which pixels belong to what.

A pass with one output can only write one of these images. To get three, you draw the scene three times, with three shaders. Every draw reads the vertices again, runs the vertex shader again, builds the triangles again and runs the depth test again. Only the last step, the fragment shader, does different work.

There is a second problem with the top way. The three passes must agree exactly on which surface is in front at each pixel. With the same depth test and the same vertices they usually do, but it is easy to break: a shader that moves vertices a little differently, or a different depth state, and the normal image shows a different surface than the albedo image.

2The idea: one pass, N outputs

A render pass does not have to draw into one image. It can have a list of color attachments: textures numbered 0, 1, 2 and so on. The fragment shader then returns one value per attachment. The GPU writes output 0 to attachment 0, output 1 to attachment 1, and so on, all for the same pixel.

In the shader, each output is marked with its attachment number. In Slang and HLSL the fragment shader returns a struct, and each field has a semantic with the number. (In Slang, fragMain also gets the [shader("fragment")] attribute; it is left out here.)

struct GBufferOutput
{
    float4 albedo : SV_TARGET0;
    float4 normal : SV_TARGET1;
    float4 material : SV_TARGET2;
};

GBufferOutput fragMain(VSOutput input)
{
    GBufferOutput output;
    output.albedo = float4(baseColor, ambientOcclusion);
    output.normal = float4(normalize(input.normal) * 0.5 + 0.5, 0.0);
    output.material = float4(metallic, roughness, 0.0, 0.0);
    return output;
}

Other shading languages spell the number differently, but the idea is the same:

LanguageOutput 1 is written as
Slang, HLSLfloat4 normal : SV_Target1; (the case of the semantic does not matter)
GLSLlayout(location = 1) out vec4 normal;
Metal (MSL)float4 normal [[color(1)]];
WGSL@location(1) normal: vec4f

Everything before the fragment shader is shared. The rasterizer finds the pixels once. The depth test runs once, and if it fails, none of the outputs are written. If it passes, all of them are. So the images can never disagree about which surface is visible.

3The rules

The attachments of one pass are not fully free. They share some things and keep others apart:

Size (width, height)shared: all the sameOne pixel position (x, y) must mean the same place in every texture.
Sample count (MSAA)sharedThe rasterizer makes one set of samples for all of them.
Formatper attachmentA color can be 8-bit sRGB, a normal 10-bit, a velocity 16-bit float, an ID a 32-bit integer.
Blend stateper attachment, if the GPU supports independent blendWithout it, all attachments must use the same blend state (Vulkan: the independentBlend feature; D3D12: IndependentBlendEnable). Desktop GPUs all support it.

Load and store, clear valueper attachmentOne attachment can be cleared and another kept; see Load and store ops.

The pipeline is built for exact formats

A graphics pipeline is compiled for a fixed list of attachment formats: how many there are, in which order, and which format each one has. The driver bakes the conversion from the shader's output (a float4) to each format into the pipeline. So a pipeline can only draw in a pass whose attachments have exactly those formats.

So one shader often needs several pipelines: one per list of formats it draws into. A material shader that draws both into a G-buffer and into a forward HDR target is two pipelines.

4The cost: bytes per pixel

Every attachment is written for every pixel the pass covers, and some later pass reads it back. So the cost of MRT is simple to estimate: add up the bytes per pixel of all attachments, and multiply by the number of pixels.

Worked example: a G-buffer at 1080p

A 1920 × 1080 image has 2,073,600 pixels. Take the packed layout: four 4-byte color attachments and a 4-byte depth, 20 bytes per pixel.

memory      20 B × 2,073,600 px = 41,472,000 B ≈ 39.6 MiB
write       41.5 MB per frame   × 60 frames/s ≈ 2.5 GB/s
write+read  83 MB per frame     × 60 frames/s ≈ 5.0 GB/s
LayoutB/pixelMemory at 1080pWrite + read, 60 fps, 1080pMemory at 4KWrite + read, 60 fps, 4K
packed2039.6 MiB5.0 GB/s158.2 MiB19.9 GB/s
fat3671.2 MiB9.0 GB/s284.8 MiB35.8 GB/s

These are lower bounds. A pixel covered by several triangles is written several times (overdraw), the depth test also reads depth, and later passes may read the images more than once. A mid-range GPU has a few hundred GB/s in total, so a fat G-buffer at 4K takes a real part of the frame.

Packing: fewer bytes for the same data

DataNaivePackedHow

Tile-based GPUs

Most mobile GPUs, Apple's included, draw the screen in small tiles and keep the tile's attachments in fast on-chip memory. Writing many attachments is cheap there, as long as they fit in that memory and the pass does not store the ones nobody reads later. If all attachments together are too big for a tile, the GPU uses smaller tiles, which costs more. See Load and store ops.

5The classic use: deferred shading

In forward shading, every triangle computes its lighting while it is drawn. A pixel that is covered five times is lit five times, and every object's shader must loop over every light. Deferred shading splits this in two passes. The first pass, the geometry pass, uses MRT to store what is needed for lighting: the G-buffer (geometry buffer). The second pass, the lighting pass, runs once per pixel, reads the G-buffer as textures, and computes the lighting only for the surface that is really visible.

What it gives

  • Lighting runs once per visible pixel, not once per covered triangle.
  • Many lights are cheap: each light only touches the pixels it reaches.
  • Other screen effects (ambient occlusion, reflections, decals) can read the same normals and depth.

What it costs

  • The G-buffer memory and bandwidth from section 4, every frame.
  • One surface per pixel: transparent objects need a forward pass after.
  • MSAA is hard: every attachment would need all its samples.
  • All materials must fit the same G-buffer layout.

MRT is not only for deferred shading. A forward pass can also write a velocity image for temporal effects (see History buffers), an object ID for picking, or a mask for a later post effect, next to its color.

7Pitfalls

ProblemWhat you seeFix
Output number and attachment order differNormals show up in the color image, or masks in the albedo. Nothing crashes: all are float4.Keep one list of the attachments and build both the pass and the shader struct from it.
An output is not written on some pathGarbage in that image at some pixels. A missing output (or a missing channel) is undefined, not 0.Write every output in every branch. Use a write mask if the image should keep its old value.
Data in an sRGB formatNormals and masks come back bent: the GPU applied the sRGB curve on write.Use UNORM or float formats for data. Only colors get sRGB. See Color spaces.
Blending on a format that cannot blendValidation error, or the pipeline fails. Integer formats never blend, and 32-bit float often cannot.Turn blending off for that attachment (needs independent blend), or pick another format.
Blending on with data in alphaA mask or roughness stored in alpha also changes how the color mixes.Keep blending off on data attachments, or move the data out of alpha.
A mask read with a linear filterAt edges the mask is 0.3 or 0.7, not 0 or 1, when the reader's size or position differs.Compare against 0.5, or sample with a nearest filter.
Too many bytesThe pass is bandwidth-bound; on tile-based GPUs it is slower than expected.Pack (section 4), and do not store attachments that no later pass reads.

8In RASM

A RASM render target has up to MAX_COLOR_ATTACHMENTS (4) color textures and one depth texture. Its formats are listed in RenderTargetDesc::colorFormats. A pipeline that draws into it takes its formats from the target, and every color is a bindless texture that later passes can sample. examples/01_render_graph uses two colors.

The fragment shader of the Background pass, as in the example (where fragMain also has the [shader("fragment")] attribute):

struct Targets
{
    float4 color : SV_TARGET0;
    float4 mask : SV_TARGET1;
};

Targets fragMain(VSOutput input)
{
    Targets targets;
    targets.color = gTextures[pc.indices[0]].Sample(input.UV);
    targets.mask = float4(targets.color.a < 0.5 ? 0.0 : 1.0);
    return targets;
}

The target lists the two formats in the same order, and the pipeline is made from the target, so the formats always match:

compositeHandle = builder.createRenderTarget({
    .name = "composite_rt",
    .swapchainScale = 1.0f,
    .colorFormats = {colorFormat, rasm::Format::R8G8B8A8_UNORM},
    .depthFormat = rasm::Format::D32_SFLOAT,
});

// later: a pipeline with the target's formats
auto pipeline = engine.createPipeline("background", source, compositeHandle);

Keep these true
  • The shader's SV_TARGET0, SV_TARGET1, … follow the order of the target's colorFormats. Make the pipeline with createPipeline(name, source, renderTarget), so its formats come from the target.
  • A render target desc has at least one color, no gap in colorFormats, and a depth format. checkRenderTargetDesc rejects anything else.
  • Data attachments (masks, normals, IDs) use a UNORM or float format, never sRGB.
  • Write every output on every path. Blending is off, so an output the shader skips leaves undefined values.
  • drawScene draws only into a target with one color in the swapchain format.
  • A new per-attachment field in PipelineDesc (a blend state, a write mask) must also go into its hash in src/rhi/resource.cpp, or two different pipelines are merged.
