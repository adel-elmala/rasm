Culling and the frame

Async compute and multiple queues

A GPU can take work from more than one queue at a time. Async compute sends some compute work to a second queue, so it runs next to the graphics work instead of after it. This page explains when that makes a frame shorter, how the two queues stay in order, and why it often does not help. The last part shows how RASM does it.

In short

  • One queue runs its work in order. Parts of the GPU sit idle while a pass is limited by something else, or while a barrier drains the pipeline.
  • A compute queue from a separate queue family can fill those gaps with compute work.
  • It only helps when there is independent work to overlap. A chain where each step needs the last one gets nothing, and pays for the handoffs.
  • A barrier works inside one queue only. Between queues you need a semaphore, and a semaphore can only be waited for at the start of a submit. So the frame is split into batches.
  • A resource used on both queues needs concurrent sharing or an ownership transfer.
  • Timestamps of two queues may not share a clock: time each pass on its own queue. Measure before you keep it.

1Idle parts of a busy GPU

A GPU has many parts: shader cores, the rasterizer, the depth test, blending, the memory bus. A pass rarely uses all of them fully. A shadow map pass writes only depth, so it is limited by the rasterizer and the depth test, and most shader cores have little to do. A small compute dispatch may fill only a few cores. And at a barrier, the GPU lets the work before it finish before it starts the work after it, so for a moment almost everything is idle.

With one queue, the GPU runs the passes in order, so these idle moments add up. With a second queue, the GPU can take compute work from it and run it in the idle parts.

2Queues and queue families

A GPU offers its queues in queue families. All queues of one family can run the same kinds of work. A typical desktop GPU has three kinds:

FamilyCan runUsed for
Graphicsdraws, compute, copies, presentthe main frame. Every GPU that can draw has one.
Compute onlycompute, copiesasync compute. No draws, no render passes, no graphics pipeline stages.
Transfer onlycopiesuploads and downloads next to rendering, often on a separate copy engine.

Async compute means a queue from the compute-only family. That family is what usually maps to separate hardware that takes work in parallel. Two queues of the graphics family may or may not run side by side: the API does not promise it. A GPU without a compute-only family has no async compute, and the compute work stays on the graphics queue.

Not every GPU overlaps well

Having a compute family only means the API lets you submit to it. How much the hardware really overlaps differs between vendors and generations, and between kinds of work. Integrated and mobile GPUs often gain little.

3Overlap needs independent work

Two passes can run at the same time only when neither needs the other's result. If pass B reads what pass A wrote, B must wait for A, whatever queue each one is on. So the first question is not "is this compute work?" but "what can run next to it?".

A chain can still gain at its edges. The first step of the next frame may not need anything from the end of this frame. Then it can run next to the last steps of this frame, as long as the two frames use different copies of the buffers they write.

4Crossing queues: semaphores and batches

A pipeline barrier orders commands on one queue, across all submissions to it (see GPU synchronization). It cannot see another queue. Between queues the tool is a semaphore: one submit signals it when all its work is done, and another submit waits for it before it starts. The signal also makes the first submit's writes available, and the wait makes them visible, so no extra barrier is needed for memory.

A timeline semaphore holds a number that only grows. Each submit to a queue signals the next value, and a wait names the value it needs. One timeline per queue is enough: "wait until the compute queue reaches 41" means "wait for the compute queue's 41st submit".

The catch: a submit waits only at its start. There is no "wait here" inside a command buffer for another queue. So each place where a queue needs the other queue's result starts a new submit. Call the commands between two such places a batch: one command buffer and one submit on one queue.

Two rules keep the batches safe:

  • Submit the signal before the wait. Timeline semaphores allow a wait to be submitted first, but then nothing may stop the signal from coming. Submitting batches in the order they were cut is simplest: every wait names a submit that already went out.
  • A failed submit signals nothing. A later wait for its value would block forever. Stop the frame there, or lower the wait to a value that was really signaled.

A render graph knows every pass's reads and writes, so it can place these waits itself. Where it would put a barrier on one queue, it puts a semaphore wait between two.

5Sharing resources between queues

Each buffer and image is created for some queue families. There are two ways to use one on two families:

Sharing modeHowCost
Exclusive + ownership transferThe resource belongs to one family at a time. Passing it is a release barrier on the old queue and an acquire barrier on the new one, around the semaphore (GPU synchronization, section on queue families).More code, and a pair of barriers per handoff. The image keeps its best memory layout and compression.
ConcurrentThe resource is created for both families and either queue may use it at any time. The semaphores still order the work.No transfers. Some GPUs compress concurrent images less, so they can be slower to read and write.

Layout transitions still happen in both modes. A compute queue can only name compute stages in its barriers: it has no vertex, fragment or attachment stages. A transition there of an image that the graphics queue last used as a depth attachment waits for "all commands" instead, which chains to the semaphore wait at the start of the batch.

6Timing work on two queues

Each queue writes timestamps into a query pool, so you can time each pass: a timestamp before and one after, on the same queue. But a timestamp from one queue and one from another may count from different origins. So "latest end minus earliest start" across both queues can be wrong by milliseconds. Keep a frame's total on one queue, and treat the other queue's timers as durations only. The sum of all pass times can now be more than the frame time, because some passes ran at the same time.

The honest measure of async compute is the frame time itself, with the GPU as the limit: turn off vsync (or measure on the GPU), and compare the same scene with and without it, more than once.

7When it pays off

Good candidates

  • Compute next to depth-only or raster-heavy passes: culling or light binning next to shadow maps.
  • Post-processing of one frame while the next frame's geometry is drawn.
  • Simulation (particles, cloth) whose result is needed only later in the frame.
  • Work for a second view while the first view draws.

Poor candidates

  • A strict chain, where each step waits for the last.
  • Tiny dispatches: the handoffs cost more than the work.
  • Two passes that both need the same unit, like memory bandwidth: they only slow each other down.
  • A frame limited by the CPU: the GPU is idle anyway.

8Pitfalls

  • Hazards across frames. Next frame's compute may start while this frame's graphics still reads a buffer. A buffer with one copy needs a wait across frames too. One copy per frame slot avoids it.
  • Graphics stages on a compute queue. A barrier there may not name fragment, vertex or attachment stages or accesses. Code shared by both queues must fit its barriers to the queue.
  • The swapchain's binary semaphore. The acquire semaphore may be waited for once. A frame of several graphics submits waits for it in the first one only.
  • Uploads on one queue, readers on the other. A copy's barriers order it only on its own queue. A reader on the other queue must wait for the copy's submit, and the copy must wait for the other queue's earlier reads of what it overwrites.
  • The handoff cost. Each semaphore wait leaves the waiting queue idle until the signal. Many small batches can make a frame slower than one queue.

9A worked example

Say a frame has three passes, timed alone on the GPU: culling 0.4 ms (compute), a shadow map 1.2 ms (graphics) and the main draw 2.0 ms (graphics). The main draw needs the culling; the shadow map needs nothing.

SetupWhat runs whenFrame
One queueculling, then shadow map, then main draw0.4 + 1.2 + 2.0 = 3.6 ms
Two queues, perfect overlapculling next to the shadow map, then main drawmax(0.4, 1.2) + 2.0 = 3.2 ms
Two queues, realthe shadow map runs a little slower while culling shares its cores, and the main draw waits for one handoffabout 3.3 ms
Two queues, chain only (no shadow map)culling, handoff, main draw0.4 + 2.0 + a handoff: a little more than one queue's 0.4 + 2.0 = 2.4 ms

The saving is at most the time of the work that overlaps, here 0.4 ms. Without anything to overlap, the second queue only adds handoffs.

10In RASM

RASM has an optional compute queue. With EngineConfig::asyncCompute on, and a GPU with a compute family that has no graphics, the scene view's culling and Hi-Z passes run on it. They are added with RenderGraph::addAsyncComputePass, and the graph places the semaphore waits. With the option off (the default), or without such a family, every pass runs on the graphics queue in one submit, as before.

Is it faster?

Not yet. On 05_city (an RTX 3060, Release, vsync off for the test, two runs each), a frame took 1.68 to 1.69 ms without async compute and 1.71 to 1.72 ms with it. The scene passes are the chain from section 3, so the handoffs cost a little more than the one overlap saves. That is why asyncCompute is off by default. It should pay off once a frame has graphics work that does not need the culling, like shadow maps or a second view. examples/03_instances turns it on, so the path runs under validation.

Keep these true
  • An async compute pass must declare every resource it uses. An undeclared one gets neither a barrier nor a wait, and the two queues can then race.
  • A buffer that each frame writes for itself should be declared per frame slot, or the next frame's compute waits for this frame's graphics.
  • Code that records through FrameResources::commandBuffer may be on either queue. Only compute work belongs in an async pass.
  • Keep the batches in the order they were closed when submitting, and never wait for a value that a failed submit did not signal.
  • A frame that fails partway through its submits cannot put its texture states back (B30).
