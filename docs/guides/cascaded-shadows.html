Cascaded shadow maps

One shadow map over a big outdoor view has the same texel size everywhere: too coarse next to the camera, and wasted far away. Cascaded shadow maps cut the camera's view into slices by distance and give each slice its own map. This page explains where to cut, how to fit a map around a slice so shadows stay still, and how a pixel picks its map. It builds on Shadow mapping. The last part shows how RASM does it.

In short

  • Split the camera's view depth into 2 to 4 slices. Each slice gets its own shadow map, a cascade, with the same number of texels.
  • Near slices are small, so their texels are small: sharp shadows next to the camera, and still shadows far away.
  • The split depths mix an even split and a logarithmic one, with one number, lambda.
  • Each cascade's box surrounds a sphere around its slice, so its size does not change when the camera turns, and it moves in whole texels, so shadow edges do not crawl.
  • The pixel shader picks the cascade by the pixel's view depth, and fades the shadow out at the end of the last one.

1The problem: one map for a big view

A shadow map texel covers box width / map size world units, the same everywhere in the box. A screen pixel is different: it covers a small area near the camera and a large area far away. Compare the two at both ends of the view.

what the camera sees (from above) the shadow map's box and texels

Making the map bigger helps a little and costs a lot: twice the resolution is four times the memory and the drawing. What helps is spending the texels where the pixels are small.

2The idea: one map per slice of the view

Cut the camera's view into slices by distance. Give each slice its own shadow map with the same number of texels. The near slice is short and narrow, so its map covers a small area and its texels are small.

  1. Split the view depth from near to the shadow distance into slices.
  2. Fit a box along the light around each slice, and snap it to whole texels.
  3. Draw the scene's depth once per box, into that cascade's map.
  4. Pick the cascade per pixel by its view depth, and test it like one shadow map.

3Where to split

The split depths decide how big each slice is. Two simple rules, and a mix of them:

Even

Same length for every slice. The first slice is long, so near texels stay big.

Logarithmic

Each slice is the same ratio longer: texels on screen stay the same size. The first slice is tiny.

Mix (lambda 0.7)

Mostly logarithmic, with some even split so the first slice is long enough to matter.

spliti = λ · logi + (1 − λ) · eveni, i = 1 … N

logi = n · (f / n)i / N

eveni = n + (f − n) · i / N

n
the camera's near plane
f
the shadow distance: the last split. Past it there is no shadow.
N
the number of cascades
λ
the mix: 0 is even, 1 is logarithmic. 0.5 to 0.8 is common.

4Fitting a box around a slice

A slice is a frustum piece with 8 corners. Its map needs a box along the light that holds all 8. The tightest box changes shape whenever the camera turns, and so does the texel size. Shadows then swim. A sphere around the slice does not change when the camera turns, so a box around the sphere keeps its size.

Tight box

The camera turns, the box changes size. Texels grow and shrink: edges shimmer.

Box around a sphere

The sphere does not turn, so the box keeps its size. It wastes some texels in the corners.

The smallest sphere whose centre is on the view axis has a simple formula. In view space, the slice's near corners are at depth zn, at distance rn from the axis; its far corners are at zf, at rf. The centre at depth c is as far from the near corners as from the far ones:

c = (zf² + rf² − zn² − rn²) / (2 (zf − zn))

c = clamp(c, zn, zf)

r = max( √((c − zn)² + rn²), √((zf − c)² + rf²) )

c
the centre's depth on the view axis. It moves to the far end when the far corners are wide: then the sphere is just the far corners' circle.
r
the radius. It depends only on the projection and the two depths, never on where the camera looks.

The box is an orthographic camera that looks along the light, with a square side of 2r. Its depth range must also hold the casters: a tree or a wall outside the slice, between the slice and the sun, still throws its shadow into the slice. So the box starts well before the sphere, toward the light.

5Stable shadows: move in whole texels

The box follows the camera every frame. If it moves by part of a texel, the texel grid slides over the world, and every shadow edge is sampled at new places: edges crawl and flicker while the camera walks. Moving the box only in whole texels, along the light's own x and y, keeps the grid fixed in the world.

Free move

The grid slides over the world. Edge texels change every frame: crawling edges.

Whole texels

The grid stays on the same world lines. The same texels are dark: still edges.

t = 2 r / size

x′ = ⌊x / t⌋ · t, y′ = ⌊y / t⌋ · t

t
one texel in world units
x, y
the sphere's centre in the light's frame (its right and up axes)
x′, y′
the box's centre: on the texel grid of a frame that never moves
Both halves are needed The snap keeps the grid's position fixed; the sphere keeps the texel's size fixed. A snapped tight box still shimmers when the camera turns, because its texels change size.

6Picking the cascade in the shader

The main pass knows every cascade's matrix and split depth. For each pixel:

  1. Depth the pixel's distance along the camera's axis.
  2. Choose the first cascade whose split is beyond it.
  3. Test in that map: normal offset, bias, PCF.
  4. Off the edge? Use the next, bigger cascade.
  5. Fade out near the shadow distance.
Neighbouring pixels can pick different cascades So the shader cannot read "the cascade's texture" through one index that differs per pixel, unless it marks the index as non-uniform (NonUniformResourceIndex in HLSL and Slang), which some compilers turn into extra requirements. A loop over the cascades with a constant count, unrolled, avoids it: each copy of the loop body reads one fixed cascade, whose texture index is the same for every pixel of the draw.

8Pitfalls

Shadow edges crawl when the camera moves
The box is not snapped to whole texels.
Shadow edges shimmer when the camera turns
The box is fitted tightly to the slice, so its size changes. Fit it around a sphere.
A shadow is cut off, or a caster's shadow is missing
The box starts at the sphere, so casters between the slice and the light are clipped. Extend it toward the light.
A visible line where the shadow changes sharpness
The seam between two cascades. A higher resolution, a lambda closer to even, or blending the two cascades over a short band hides it.
The shadow ends in a hard line far away
No fade at the shadow distance.
Blocky shadows next to the camera even with cascades
Lambda too low (cascade 0 is too long), or too high (cascade 0 ends before anything visible, and cascade 1 does the work).
Acne in the far cascades only
A bias in world units. Bias in texels of the cascade that is read: its texels are bigger.
Shadows flicker between frames for no reason
The pass that draws a cascade and the pass that reads it use different matrices, for example one frame apart. Compute both from the same camera in the same frame.

9In RASM

RASM has cascaded shadows for one directional light per shaded view. Engine::addShadowPasses makes the cascades: one depth-only render target and one set of scene passes per cascade, all drawn from the application's camera. It returns a SceneShadow, which addScenePasses takes for the view that is shaded with it. No light camera exists: every view of the shadow fits the cascades again each frame, with the same function, so the maps are drawn and read with the same matrices. examples/06_shadows shows it.

const rasm::SceneShadow shadow = engine.addShadowPasses(graph, scene, camera, rasm::ShadowDesc{.light = sun, .cascadeCount = CASCADE_COUNT, .size = 2048, .distance = 60.0f, .splitLambda = 0.7f});
if (shadow.cascadeCount == 0 || !engine.addScenePasses(graph, scene, camera, sceneTarget, shadow))
    return 1;

Keep these true
  • The views that draw the cascades and the view that reads them must fit with the same inputs in the same frame: the same camera, the same aspect ratio, the same SceneShadow. addScenePasses rejects a shadow that addShadowPasses did not make for the same scene and camera in the same graph, and a second view that reads the same shadow.
  • The sphere's radius must not depend on the camera's direction, and the box must move in whole texels, or shadows shimmer and crawl.
  • MAX_SHADOW_CASCADES in include/rasm/scene.h and in shaders/lib/core.slang must match.
  • The cascade loop in sampleShadow stays unrolled, so each texture index is uniform over the draw.
  • The offsets read a texel's size from rows 0 and 2 of a cascade's matrix, which holds because the box is orthographic.
