Foundations

Generational handles

An engine has many objects: meshes, textures, entities, buffers. Code outside the engine needs a way to name one of them, and to find out when the object it names is gone. A generational handle does both with two small numbers. This page explains how it works. The last part shows how RASM does it.

In short

  • A raw pointer breaks when the object moves or is freed. A plain index breaks when its slot is reused for a new object.
  • A handle is an index into a table of slots plus a generation: a counter that goes up each time the slot is freed.
  • A lookup checks that the handle's generation equals the slot's generation. If not, the handle is stale and the lookup fails safely.
  • Freed slots go on a free list and are reused, so the table does not grow forever.
  • A tag type makes a mesh handle and a texture handle different types, so the compiler stops you from mixing them.
  • A handle does not own its object. The table does. Destroying an object the GPU still uses must wait until the GPU is done.

1The problem: naming an object

An application asks the engine to load a mesh. The engine must give back something the application can keep and pass back later: "draw this mesh". There are three common choices.

ChoiceGoodBreaks when
PointerFastest: no lookup at all.The object moves (an array grows, a level is compacted) or is freed. Using it then is undefined behaviour: a crash, or worse, wrong data.
IndexSmall (4 bytes), survives moves, easy to send to the GPU.The slot is reused. The old index now names a different object, and nothing notices. This is called the ABA problem.

2The idea: index plus generation

The engine keeps each kind of object in a table of slots. Each slot stores the object and a generation number. A handle stores two numbers: the slot's index, and the generation the slot had when the handle was made.

The lookup in pseudo-code:

lookup(handle):
    if handle.index >= slots.size:
        return null                  // never made
    slot = slots[handle.index]
    if slot.generation != handle.generation:
        return null                  // stale: freed, maybe reused
    return slot.object

Two more rules make this complete:

  • Destroying an object adds 1 to its slot's generation. Every handle made before is now stale, at once, without finding them.
  • Generation 0 means "no object". Slots start at generation 1. So a handle that is all zeros, which is what a default-constructed handle is, never matches a slot. It is the handle version of a null pointer.

3Reusing slots: the free list

Without reuse, the table grows by one slot for every object ever made. A game that spawns and removes bullets would grow it forever. So a destroyed slot goes on a free list, and the next create takes a slot from it. The generation is what makes this reuse safe. Click through an example (or use the arrow keys).

1. Create A, B and C

Each handle copies its slot's current generation.

2. Destroy B

The object is destroyed, the generation goes up, the index goes on the free list.

3. Create D: it reuses slot 1

Create pops an index from the free list and uses the slot's current generation.

4. Look up B and D

The stale lookup fails in a defined way. The caller can log it, skip the work, or treat it as a bug.

Where the free list lives

A free slot holds no object, so its memory can store the index of the next free slot. The free list then needs no extra memory: one "first free" index, and a chain through the free slots. This is an intrusive free list.

Which slot to reuse first

A stack (last freed, first reused) is simplest and keeps memory warm in the cache. A queue (first freed, first reused) spreads reuse over all free slots, so each generation grows more slowly. That delays the wrap-around of section 4.

4How many bits

Handles are often packed into one 32-bit or 64-bit integer, so they are cheap to copy, hash and store in GPU buffers. The bits are split between the index and the generation. The index bits limit how many objects can live at once. The generation bits limit how many times one slot can be reused before its generation wraps back to an old value.

SplitObjects alive at onceReuses of one slot before a wrapWorst case: one slot reused every frame at 60 fps

A wrap only causes a bug if old code still holds a handle from exactly one full cycle ago, and uses it. That is rare, but a small generation makes it possible. Two common fixes:

  • Retire the slot. When its generation reaches the maximum, do not put it on the free list again. It is lost, but no handle can ever alias.
  • Spread the reuse. A queue-ordered free list (section 3) reuses each slot less often.

5Dense storage for fast loops

A table with holes is slow to loop over: the loop must skip the free slots, and the live objects are spread out in memory. Systems that loop over every object each frame (all entities, all particles) often add one more layer. This is usually called a slot map.

6Type-safe handles

A mesh handle and a texture handle are both "two integers". If they are the same C++ type, nothing stops code from passing a mesh handle to a function that wants a texture. The lookup then reads the wrong table, and may even pass the generation check by luck.

The fix is a tag type: an empty type that is never defined and never used at runtime. It is only there to make each kind of handle a different type.

struct MeshTag;
struct TextureTag;

template <typename Tag>
struct Handle
{
    uint32_t index = 0;
    uint32_t generation = 0;
};

using MeshHandle = Handle<MeshTag>;
using TextureHandle = Handle<TextureTag>;

void bindTexture(TextureHandle texture);

Now bindTexture(mesh) is a compile error. The tag costs nothing: both types have the same two fields and the same size. This pattern is also called a phantom type or a strong typedef.

7Who owns the object

A handle is a weak reference. Holding it does not keep the object alive. The object belongs to its table, and it lives until someone calls destroy. This is different from a reference-counted pointer.

8Handles for things made from a description

Some objects are fully described by their creation settings, and never change after. A compiled shader, a pipeline, a sampler and a descriptor layout are like this. If two parts of the program ask for the same one, they can share it. The table then keeps a second map: from the description to the handle. This is called interning or a dedup cache.

Dedup is right for immutable objects

Shaders, pipelines, samplers, layouts. Nobody writes into them after creation, so sharing one is the same as having two. It saves memory and creation time; a pipeline can take milliseconds to compile.

Dedup is wrong for mutable objects

Buffers and textures. Two users that ask for "a 1 MiB storage buffer" want two buffers, because each will write its own data. Sharing one would make them overwrite each other.

Every field must take part in both the equality and the hash. A field that is left out of the compare makes two different descriptions look equal, and one user silently gets the other's object. A field left out of only the hash is still correct, just slower (more collisions).

Asset loading often uses the same idea one level up: a map from the file path to the handle. Loading the same file twice then gives the same mesh, and the file is read once.

10In RASM

RASM uses one handle type for every object, Handle in include/rasm/handle.h, with an index and a generation. It has the type-safe tags of section 6. It does not have the free list or the generation bump yet: indices only grow, and the generation is always 1.

Two kinds of owner

CPU objects: Engine's registry

createEntity: getNextEntityHandle gives {3, 1}. If index >= MAX_ENTITIES, it warns and returns an invalid handle. Otherwise registry.entities grows to hold index 3. The handle is the position in a vector, as in section 2, but without the generation check.

GPU objects: RenderContext's maps

createBuffer: rhi::Device::createBuffer makes the object first (null on failure: an invalid handle). Then getNextBufferHandle gives a handle, and the map stores it. destroyBuffer and destroyTexture erase the map entry.

The dedup caches

Every creation descriptor in include/rasm/render/resource.h (ShaderDesc, PipelineDesc, BindlessDescriptorSetLayoutDesc, ...) has a defaulted operator==, so equality always compares every field. The hashes are written by hand in src/rhi/resource.cpp. ShaderDescHash hashes the name, the type, the entry point and the SPIR-V bytes; PipelineDescHash hashes the name, the four handles (with HandleHash), the topology and both attachment formats.

Because a pipeline's description holds shader handles, and equal shader descriptions give the same shader handle, two equal pipeline descriptions find each other too.

Two more details

  • A texture handle can come before its pixels. loadTexture creates the texture and returns its handle at once; the file is decoded in the background. isLoaded says when it is ready. See Streaming assets in the background.
  • Swapchain images are texture handles too. registerSwapchainImages gives each image a handle, and destroyTexture refuses them: they belong to the swapchain.

Keep these true
  • A new field in ShaderDesc, PipelineDesc or BindlessDescriptorSetLayoutDesc is compared by the defaulted operator== on its own, but must also be added to its hash in src/rhi/resource.cpp.
  • Never add dedup to createBuffer or createTexture (B1). Cache at the asset level, and destroy what you replace.
  • Destroy a buffer or texture only when no frame in flight can still use it: there is no delete queue yet.
  • A default handle ({}) means "none". Check isValid before using a handle that a create may have failed to fill.
Not done yet

D4: CPU objects (entities, meshes, materials, ...) cannot be destroyed, the generation is always 1, and registry slots are never reused. Bindless slots are reused in one place only: a depth texture that is replaced on resize keeps its slot. Streaming worlds will need the full design of this page: a generation bump, free lists, and deferred destruction tied to the frame fences.

B13: a handle index is taken before the create is checked, so a failed load still uses up an index. With only 7 mesh slots, this matters.
