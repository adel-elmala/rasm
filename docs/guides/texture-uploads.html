GPU data

Texture uploads

A PNG on disk is a few megabytes. In video memory the same texture is a chain of mip levels, in a tiled order only the GPU knows. This page follows a texture through the four steps that get it there: decode, make the mips, reorder the texels, place them in memory. It compares the two ways to do the copy (a staging buffer, or host image copy), the places a program can make the mips, and how many textures share memory. The last part shows how RASM does it.

In short

  • Four steps: decode the file, make the mips, reorder the texels into the GPU's tiling, put them in video memory. Only the last two need the GPU or its driver.
  • Staging: the CPU writes rows into a buffer, and a GPU copy command tiles them into the image. It works everywhere.
  • Host image copy (Vulkan 1.4): the driver tiles on the CPU, with no command buffer. It is good only where the image can live in the same memory as any other texture, and keeps the GPU's best layout. Ask the device both.
  • Mips can come from the file, a CPU worker, GPU blits or a GPU compute pass. Filter color in linear light, weight it by alpha, and make normals unit length again.
  • Thousands of textures should share a few large memory blocks (sub-allocation): a separate allocation per texture is slow to make and slow to free.
  • A model's textures are many megabytes: copy them a few per frame, not all in one frame.

1Four steps from file to GPU

Follow one 2048 × 2048 color texture. Two steps are plain CPU work on bytes; two need to know the GPU.

2Two ways to reorder and place

The CPU cannot write the tiled order itself: it is the vendor's secret. Two paths hand the rows to someone who knows it.

Staging copy

Works on every GPU and every format. Costs a command buffer, barriers, a fence before the buffer is reused, and a little GPU copy time.

Host image copy

Vulkan 1.4 (VK_EXT_host_image_copy before). No staging memory, no commands. The CPU must be able to write the image's memory, which is the catch (next section).

3Where a host-copied image may live

The CPU writes a host-copied image directly. So the driver may allow such an image only in memory the CPU can reach. Each image asks for a set of memory types (a bit mask). Compare the set of an image filled by a copy with the set of the same image made for host copy. This is a real discrete GPU with resizable BAR:

So a program should ask the device, per format, before it picks host copy:

  1. Featurethe device has host image copy
  2. Formatit lists host image transfer
  3. Best layoutthe GPU reads it as fast as any image
  4. Copy layoutthe shader-read layout is allowed
  5. Memorya device-local type both sets share

If any answer is no, the format uses staging. A device without the feature then still starts and draws: it only loses a shortcut. In Vulkan the checks are the hostImageCopy feature, the format's host-image-transfer feature bit, optimalDeviceAccess in VkHostImageCopyDevicePerformanceQuery, pCopyDstLayouts, and the memory type bits.

4Where to make the mips

A full mip chain adds a third to the texture. Each level is the one above, half the size, filtered. Four places can make it:

In the file

KTX2 and DDS store the levels, already block-compressed. Best quality and no load-time work.

Needs an offline tool step.

A CPU worker

Same code on every GPU and API. Any filter: linear light, alpha weighting, renormalized normals.

About 10 ms of CPU per 2048² texture; a third more bytes to copy.

GPU blits

A few commands, almost no GPU time. The filter is a fixed box; colors are not weighted by alpha, and normals are not renormalized.

Vulkan and Metal have blits; D3D12 and WebGPU do not.

GPU compute

Fast and any filter. The image needs storage usage, and an sRGB image a second, UNORM view.

Storage usage can turn off the GPU's texture compression (AFBC, DCC): slower reads for the texture's life.

Filter what the numbers mean

A mip is an average. What to average depends on the texture:

Color: linear light

Decode sRGB to light, average, encode again. Averaging the stored numbers darkens every edge.

Cut-outs: weight by alpha

A transparent texel's color is never seen, so it must not count. Without the weight, leaves get dark rims far away.

Normal maps: renormalize

Average the directions, then make each unit length again, so every level stores a direction. A two-channel map (z rebuilt from x and y) needs it most.

5Many textures, few allocations

A scene has hundreds of textures; a streaming map has thousands over its life. Giving each its own device allocation is simple, but each allocation is an OS call, drivers limit how many exist, and freeing one can take milliseconds.

One allocation per texture

Sub-allocated

Keep a dedicated allocation for the few large render targets that a driver asks to have one. The block size also changes what "memory in use" means: the OS counts whole blocks, so count the bytes of the textures inside them too.

6Pitfalls

Far textures look too dark, edges have dark lines
The mips averaged sRGB numbers, not light. Filter sRGB textures in linear light.
Leaves and fences get dark or bright rims in the distance
The mips averaged the hidden color of transparent texels. Weight color by alpha.
Bumps look flat or bright far away
Averaged normals are shorter than 1; a two-channel map rebuilds a wrong z from them. Renormalize each mip.
Loading a level freezes one frame for 200 ms
Mips are made on the main thread, or all of a model's textures are copied in one frame. Make mips on a worker, and copy a few textures per frame.
Frames drop while textures load, the CPU is idle
The GPU stalls on host-copied images in special memory. Use host copy only where the image can use the same memory types as a copied one.
A GPU without host image copy cannot start the program
The feature was required. Make it optional: the staging path serves every device.
Destroying a big model makes one long frame
Each texture had its own allocation, and each free is an OS call. Sub-allocate.

7In RASM

The worker decodes and makes every level; the main thread only creates the texture and copies the levels, in parts of 4 MiB under a budget per frame; the device copies through the staging ring, on the transfer queue where there is one, unless host copy is safe for the format. The texture counts as loaded once its copies are done (transfer queues).

Rules to keep
  • No image asks VMA for host access: a host-copied image uses only the memory types queryFormatSupport found.
  • The main thread never makes mips for a load. A worker hands over every level.
  • Every texture fill of a load goes through pendingTextures, so the budget sees it.
  • The worker's level count is the texture's mip count (getFullMipCount), or fillTexture refuses the levels.
