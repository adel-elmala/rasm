Culling and the frame

Immediate-mode UI

Debug windows, sliders and tool panels are code that runs every frame. An immediate-mode UI library, like Dear ImGui, turns that code into a few buffers of triangles, and the engine draws them over its image. This page explains how the UI becomes triangles, how they are drawn, and what input and color need. The last part shows how RASM does it.

In short

  • In an immediate-mode UI, the program calls Button("Save") every frame. The call draws the button and returns true on the frame it is clicked. There are no widget objects to keep in sync.
  • Each window appends triangles to a draw list: a vertex buffer (position, UV, color), an index buffer, and draw commands.
  • A draw command is a range of indices with a clip rectangle and a texture. The renderer draws each range with the rectangle as its scissor.
  • One atlas texture holds the font and a white pixel, so most of the UI is a few draws.
  • The UI reads input first and says whether it wants the mouse or the keyboard, so a click on a window does not also turn the camera.
  • UI colors are sRGB numbers and are meant to be blended as numbers. Blending them in linear light makes light text on a dark window look bolder.

1Two ways to build a UI

A retained-mode UI keeps a tree of widget objects. The program creates them once, keeps them up to date, and reacts to their events. An immediate-mode UI keeps no widgets for the program: the program describes the UI again in every frame, and the library draws it at once.

Retained mode

Widgets live between frames. The program creates them, updates them and handles their events.

Immediate mode

The program's code is the UI. It runs every frame and works on the program's own values.

The library still keeps a little state inside, keyed by each widget's label: which window is open, where it is, which slider is being dragged. The program does not see it. Immediate mode is the usual choice for engine tools and debug windows, because a new value on screen is one line of code.

2One UI frame

The UI is rebuilt between reading the input and drawing the frame:

  1. Input. Mouse, keys and text go to the library.
  2. New frame. It takes the display size and the time step.
  3. Build. Each widget checks the input and adds its triangles.
  4. Render. The draw data: every window's draw list.
  5. Draw. Copied to GPU buffers, drawn last in the frame.

A click is handled in the same frame it arrives: the button sees the press in step 3 and returns true. The program changes its values right there, before the frame is drawn.

3From widgets to triangles

Everything a UI shows is made of triangles: a window is a rectangle, a button is a rectangle with text, a letter is a small rectangle cut out of the font texture. A rectangle is 4 vertices and 6 indices.

4Draw commands and clip rectangles

A draw list is one vertex buffer, one index buffer, and a list of draw commands. A command says: draw these indices, with this texture, only inside this rectangle. A new command starts when the texture or the clip rectangle changes, for example when a scrolling child area begins.

The clip rectangle is in display points. On a high-DPI screen a point is several pixels, so the renderer scales it by the framebuffer scale, rounds it outward to whole pixels (a pixel that is partly inside stays), and clamps it to the framebuffer. A rectangle with nothing left is not drawn at all.

x₀ = floor(max((clip.left − display.x) · s, 0))

x₁ = ceil(min((clip.right − display.x) · s, width))

s
the framebuffer scale: pixels per point (1 on a normal screen, 2 on most high-DPI laptops)
display.x
where the UI's display starts, usually 0
x₀, x₁
the scissor's left and right edge in pixels; y works the same way with the top and bottom

5One texture for nearly everything

Switching textures needs a new draw command, so the library puts all its images into one atlas: every glyph of the font at the sizes in use, the mouse cursors, and one white texel. A flat rectangle samples the white texel, so its color is just the vertex color. Text samples its glyph. Then a whole window is usually one command.

The atlas

Packed by the library. It grows when text needs a new size, and the renderer uploads it again.

Glyphs as coverage

A glyph's texels are white, and the alpha says how much of each one the letter covers. Edges are partly covered: that is the anti-aliasing.

Images

A widget can show any texture of the program. The library only passes its texture ID through; what the ID means is up to the renderer.

6Colors are sRGB numbers

The UI's colors are the numbers the designer picked on screen: sRGB numbers (see Color spaces). Its anti-aliasing mixes them by coverage, and the look was tuned for mixing the numbers themselves. Mixed in linear light instead, an edge pixel comes out brighter. So light text on a dark window looks bolder and softer.

Mixed in linear light

The edge is almost white. The strokes look thicker than designed.

Mixed as numbers

The edge is half way, as the font and the style were designed.

0.55white over 0.10 at half coverage, mixed as numbers0.5 · 1 + 0.5 · 0.10; byte 140
0.74the same mixed in linear lightencode(0.5 · 1 + 0.5 · 0.010); byte 188
+48bytes brighter on every half-covered edge pixelabout a third of the way to white

The scene, on the other hand, must blend in linear light. So a renderer that draws the UI into an sRGB target has two ways out. The clean one: draw the UI through a second, UNORM view of the same image, where the hardware stores and blends the numbers as they are; the swapchain must allow a mutable format for that. The fallback: decode the UI's colors in the shader, and accept the bolder look.

7Who gets the input

The UI and the program share one mouse and one keyboard. After each frame the library says what it wants: the mouse (the pointer is over a window, or drags one), the keyboard (a window has the focus), or text (a text field takes typing). The program then keeps that input away from the rest:

Mouse

Presses and the wheel over a window go to the UI only.

Keyboard

Keys for the camera are ignored while a window has the focus.

Text

Even Escape and the function keys belong to the text field.

The flags come from the last built frame, so they are one frame old. That is fine for input: a pointer that just entered a window is caught on the next event.

8Pitfalls

Light text looks bold and soft
The UI is blended in linear light. Draw it through a UNORM view of the target, so its colors blend as numbers.
Dragging a slider also turns the camera
The program ignores the library's capture flags. Check them before the camera takes the mouse.
The UI flickers or shows garbage after the font grows
The atlas was changed in place while the GPU still drew the last frame with it. Upload a new texture, and free the old one only when no frame in flight uses it.
Large lists draw wrong vertices
The renderer ignores a command's vertex offset, which the library uses to pass 65,536 vertices with 16-bit indices. On APIs where the vertex index does not include the base vertex, pass the offset to the shader yourself.
The UI is tiny on a 4K laptop
Sizes and fonts are in points, but were not scaled by the display's scale. Scale the style and the font by it.
Scene colors look washed out in an image widget
The texture is sampled as linear light but drawn as numbers, or the other way round. Convert by the texture's format, so the image shows its stored colors.

9In RASM

RASM uses Dear ImGui for the UI part, and draws its draw data with a small renderer of its own, through the RHI and the render graph. ImGui's own SDL3 platform backend feeds it the input. Turn it on with EngineConfig::ui; F1 shows the RASM window, and Engine::setUiCallback adds the application's windows. The API: UI with Dear ImGui.
