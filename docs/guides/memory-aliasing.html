Culling and the frame

Transient memory and aliasing

Most render targets are needed for only a few passes of the frame. If each one gets its own memory, most of that memory sits idle. Memory aliasing lets resources that are never alive at the same time use the same bytes. This page explains lifetimes, heaps, how to pack the resources, and the barrier that every takeover needs. The last part shows how RASM does it.

In short

  • A transient resource lives only inside one frame, from the first pass that uses it to the last. Its lifetime is an interval of passes.
  • Two resources whose lifetimes do not overlap can use the same bytes. This is aliasing. The memory needed is at least the peak: the most bytes alive in any one pass.
  • The device tells you a resource's size, alignment and memory types before it exists. You allocate one big heap and create each resource at an offset in it.
  • Choosing the offsets is a packing problem (NP-hard in general). The usual greedy method: biggest first, each at the lowest aligned offset that no overlapping resource uses.
  • Memory that changes owner holds garbage. The new resource's first use must overwrite it, after a global barrier, because an image barrier covers only its own image. Last frame's users count too.

1The problem: memory that sits idle

A modern frame draws into many textures that nobody sees: a G-buffer, an HDR color target, bloom, a tone-mapped image, an anti-aliased image. Each one is read by the next pass or two, and then it is not needed any more. But if each one has its own memory, that memory stays reserved for the whole frame, and for every frame after it.

Full-screen textures are big. One pixel of an RGBA8 or D32 texture is 4 bytes, so at 1920 × 1080:

2Lifetimes are intervals

Put the passes in the order they run and number them. A transient resource's lifetime is the interval from the first pass that uses it to the last one. Before its first pass nothing is in it yet; after its last pass nobody reads it again. A render graph knows the order and every pass's reads and writes, so it can compute every lifetime (see render graphs).

Both ends count

A pass that reads one texture and draws another uses both at the same time. In the example, pass 3 (Tonemap) reads HDR and draws LDR. HDR ends in pass 3 and LDR starts in pass 3, so they overlap and must not share. So the two ends of a lifetime are inclusive: lifetimes [a, b] and [c, d] overlap when

a ≤ d  and  c ≤ b

The lower bound

Add up the sizes of the resources alive in each pass. The largest sum is the peak. Any layout needs at least that much memory, because all those bytes are in use at the same moment. Without aliasing, the frame needs the sum of all sizes. With good aliasing, it needs close to the peak: here 48 MiB instead of 68 MiB.

3Memory requirements, heaps and placed resources

Usually a resource and its memory are made together: create the texture, and the allocator gives it memory of its own. That is a dedicated (or committed) allocation. To share memory, the two steps must be split: first get one big block of memory, a heap, then create each resource at an offset inside it. Such a resource is placed. It does not own its memory: destroying it leaves the heap alone, and the heap must outlive every resource in it. For heaps and memory types in general, see GPU memory.

Asking before creating

To pack resources into a heap, we must know their needs before we place them. Every API can tell the needs of a resource from its description alone (size, format, usage), without creating it:

4Packing: where each resource goes

Now each resource is a rectangle. Its width is its lifetime, which is fixed. Its height is its size. We choose only its offset: how high it sits. Rectangles must not overlap, and the goal is the lowest total height, the heap size. In computer science this is dynamic storage allocation. Finding the best answer is NP-hard, so engines use a fast heuristic instead.

The common heuristic is greedy first fit, biggest first:

  1. Sort by size, biggest first. Big pieces are the hardest to fit. Small pieces placed later can fill the gaps between them.
  2. For each resource, collect the blockers. These are the resources already placed whose lifetimes overlap its own. Sort them by offset.
  3. Walk up from offset 0. If the resource fits below the next blocker (after rounding up to its alignment), stop. If not, jump past the end of that blocker and try again.
  4. Place it. It goes at that offset. The heap size is the highest end of any resource.

Here are the five textures, sorted: G-buffer 32, HDR 16, LDR 8, AA 8, Bloom 4. LDR and AA are the same size, so they keep their order. Step through it:

That is not always so: when many resources start and end at different times, the greedy result can be above the peak. In practice it is close, and it is fast: n resources need about n² overlap tests, which is nothing for a few dozen render targets.

struct Request
{
    uint64_t size = 0;
    uint64_t alignment = 1;
    uint32_t first = 0; // first pass that uses it
    uint32_t last = 0;  // last pass that uses it, included
};

uint64_t alignUp(uint64_t value, uint64_t alignment)
{
    return (value + alignment - 1) / alignment * alignment;
}

bool overlap(const Request &a, const Request &b)
{
    return a.first <= b.last && b.first <= a.last;
}

// Writes each request's offset and returns the heap size.
uint64_t pack(const Request *req, uint32_t count, uint64_t *offsets)
{
    std::vector<uint32_t> order(count);
    std::iota(order.begin(), order.end(), 0u);
    auto bigFirst = [req](uint32_t a, uint32_t b)
    { return req[a].size > req[b].size; };
    std::stable_sort(order.begin(), order.end(), bigFirst);

    uint64_t heapSize = 0;
    std::vector<uint32_t> placed;
    for (uint32_t i : order)
    {
        // The placed ones alive at the same time, lowest offset first.
        std::vector<uint32_t> blockers;
        for (uint32_t j : placed)
        {
            if (overlap(req[i], req[j]))
                blockers.push_back(j);
        }
        auto lowFirst = [offsets](uint32_t a, uint32_t b)
        { return offsets[a] < offsets[b]; };
        std::sort(blockers.begin(), blockers.end(), lowFirst);

        // Stop at the first gap that is big enough, else jump past.
        uint64_t offset = 0;
        for (uint32_t j : blockers)
        {
            if (alignUp(offset, req[i].alignment) + req[i].size <= offsets[j])
                break;
            offset = std::max(offset, offsets[j] + req[j].size);
        }
        offsets[i] = alignUp(offset, req[i].alignment);
        heapSize = std::max(heapSize, offsets[i] + req[i].size);
        placed.push_back(i);
    }
    return heapSize;
}

Alignment

An offset must be a multiple of the resource's alignment. So the free offset found by the walk is rounded up: alignUp(x, a) = ⌈x / a⌉ · a. The bytes skipped by the rounding are lost. The heap itself must start at an address that suits every resource in it, so its alignment is the largest one.

Memory types

A heap is one allocation, so it has one memory type. A resource may go into a heap only if the resource's memory-type mask has the heap's type in it. Color and depth textures, or buffers and textures, can report different masks. So resources are split into groups, and each group gets its own heap and its own packing.

GroupingHowResult
Same maskResources with exactly the same mask share a heap.Simple. Can make more heaps than needed.
Shared typeResources whose masks have a common bit share a heap of that type.Fewer heaps, more sharing. A little more code.

On most desktop GPUs, all render targets accept the same device-local memory, so one heap is the usual result.

5Taking over memory

When a resource starts to use bytes that another resource used before, three rules apply.

1. The contents are garbage

The bytes still hold the old resource's data, which means nothing to the new one. Even worse, GPUs keep hidden compression data next to many render targets, and that data is wrong too. So the new resource's first use must write all of it: a clear, or a "discard" followed by a pass that writes every pixel. A transient resource must never be read first. In Vulkan, the first use also starts from the UNDEFINED layout, which tells the driver to throw the old contents away, compression data included.

2. A barrier between the old owner and the new one

The GPU runs passes in parallel unless a barrier tells it to wait (see GPU synchronization). Without a barrier, the new resource's writes can land while a pass still reads the old resource, or the old resource's writes, still in a cache, can reach memory after the new ones:

The natural barrier is the one that moves Y into its first layout. But an image barrier only covers its own image: its memory part flushes and waits for writes to Y, not to X. So aliasing needs a barrier that covers all memory:

APIThe barrier for a takeover
VulkanA global memory barrier (VkMemoryBarrier2): wait for the stages that used the old resources, flush their writes, before the stages of the new one. Then the image barrier from UNDEFINED as usual.
Direct3D 12An aliasing barrier, D3D12_RESOURCE_BARRIER_TYPE_ALIASING, naming the resource before and the resource after (or none, meaning "any").
MetalResources from a heap are usually not tracked. A MTLFence, updated after the old resource's last pass and waited for before the new one's first pass.

3. Last frame counts too

The layout is the same every frame. So the first owner of some bytes in frame N+1 takes them over from their last owner in frame N. A new frame is not a barrier: commands from two submissions on one queue may overlap on the GPU.

Direct3D 12

CreateHeap, then CreatePlacedResource at an offset. On resource heap tier 1 hardware, a heap holds only one kind of resource: buffers, render-target and depth textures, or other textures. Tier 2 allows a mix. The first use of an aliased render target must be a clear, a DiscardResource or a full copy.

Metal

A MTLHeap of the automatic type places resources itself: makeAliasable on a resource lets later resources from the heap take its memory. A placement heap takes explicit offsets, as on this page. Either way, fences order the takeover.

No memory at all: memoryless attachments

Tile-based GPUs (most phones, and Apple GPUs) draw a render pass one small tile at a time, in on-chip memory. An attachment that is cleared at the start of the pass and not stored at the end, like a depth buffer used only inside one pass, never needs to reach main memory. It can be memoryless: MTLStorageMode.memoryless in Metal, or a lazily allocated memory type (VK_MEMORY_PROPERTY_LAZILY_ALLOCATED_BIT) with a transient attachment in Vulkan. That is aliasing taken to the end: zero bytes. It depends on the pass's load and store ops; see load and store ops. Desktop GPUs usually have no such memory type.

7Pitfalls

  • Reading before the first write. The first use reads the previous owner's data. Nothing fails; the image just shows garbage, often only on some GPUs. A graph should reject a transient whose first use is a read.
  • Forgetting the last frame. The barrier at a resource's first use must also cover the previous frame's last users of the same bytes. A barrier that only looks at earlier passes of the same frame misses them.
  • An undeclared use. A pass that samples a texture without declaring it is outside the lifetime. By then another resource may own the bytes. Every read and write must be declared.
  • Keeping a handle after the last pass. A texture handle or descriptor still points at the old bytes, but a different resource writes them now. Reading it shows that resource's data, with no error.
  • Resize. New sizes mean a new layout and new heaps. The GPU must be done with the old heaps before they are freed. For a moment, both may exist.
  • Debugging. Capture tools show an aliased texture's bytes even outside its lifetime, so it seems to hold another texture's image. That is expected.
  • Fragmentation. Alignment gaps and greedy choices can leave a heap above the peak. Compare the heap size with the peak to see how much.

8In RASM

RASM aliases the render targets of a render graph. A render target that RenderGraph::createRenderTarget or PassBuilder::createRenderTarget makes without history is transient: its handle exists at once, but its textures are made only after the graph is compiled, inside heaps shared with the graph's other transient targets. The packing is the greedy method of section 4, in rhi::packAliased.

examples/01_render_graph has two transient targets. offscreen_rt (one color and depth) lives in passes 1 to 5: Scene 1 draws it, Hi-Z reads its depth, Scene 2 draws it again, and Trail reads it. composite_rt (two colors and depth) lives in passes 6 and 7. Their lifetimes do not overlap, so they share one heap. trail_rt has history, so it has memory of its own.

Lifetime of the memory

The graph owns its transient targets. RenderGraph::~RenderGraph calls RenderContext::destroyTransientRenderTargets, which waits for the GPU, destroys the textures, and frees a group's heaps once none of its targets is left. A RenderGraph is move-only, so two graphs never free the same targets. Placing a layout again first waits for the GPU to be idle, then builds the new heaps and textures, then frees the old heaps.

Keep these true
  • A transient target's first pass draws it. Declare every read with PassBuilder::read, so the lifetime covers it. A texture or bindless index used outside the declared passes reads another target's bytes, with no error.
  • Lifetimes are inclusive at both ends. A pass that reads one target and draws another uses both.
  • If transient targets get a new kind of use (compute writes, copies), add its stages and accesses to VulkanCommandBuffer::aliasingBarrier. Today it covers attachment writes and fragment and compute reads only.
  • Placed textures do not own their memory. Destroy them before their heap (destroyHeap), and wait for the GPU before a heap is freed.
  • A change to rhi::packAliased comes with a test in tests/memoryAliasingTests.cpp, and the test that no two overlapping lifetimes share a byte must still pass.
