Camera controllers and easing

A camera controller turns mouse moves, the wheel and held keys into a camera position and rotation, once per frame. This page explains the two common kinds, the fly camera and the orbit camera, and how to smooth their motion so it looks the same at any frame rate. The last part shows how RASM does it.

In short

  • A controller keeps its own state (angles, a center, a distance) and writes a target pose. Smoothing then moves the rendered pose toward it.
  • A fly camera stores yaw and pitch. Yaw turns around the world's up axis, pitch around the camera's right axis. Pitch is clamped short of ±90°.
  • An orbit camera turns around a center point. A turntable uses yaw and pitch; an arcball maps the mouse onto a sphere.
  • Mouse moves are distances: never multiply them by the frame time. Held keys are speeds: always multiply them by it.
  • Exponential easing with t = 1 − e−k·dt gives the same motion at 30 or 144 frames per second. A fixed factor per frame does not.

1What a controller does

Each frame, the controller reads the input of that frame and updates a pose: a position and a rotation. The view matrix is then built from the pose (see the view matrix). Good controllers split this into two poses:

  1. Inputmouse move, wheel, held keys, frame time
  2. Controllerstate: yaw, pitch, center, distance
  3. Target posewhere the camera should be
  4. Smoothinga part of the way each frame
  5. Current poseused to render: the view matrix is built from it
target pose current pose, one dot per frame
Two poses, two jobs
  • The controller never touches the current pose.
  • The rendered camera is always a little behind the target.
  • To jump without smoothing (a cut, a teleport), set both poses.

2Reading the input

Mouse positions in units that do not depend on the window

A mouse move arrives in pixels. A move of 100 pixels is a big part of a small window and a small part of a big one. So controllers first map pixels to a resolution-independent range, often −1..1 like NDC. Windows report y growing down, so y is flipped at the same time.

s   = min(width, height)
x_n = (2 · x_px − width) / s
y_n = (height − 2 · y_px) / s          (flipped: up is positive)

Mouse moves are distances, keys are speeds

This is the most common mistake in camera code. The same half second of input, cut into frames at 36 and at 144 frames per second:

A mouse move is a distance

A mouse move of 0.2 units is a distance the hand moved. At a high frame rate, the same hand motion is split into more, smaller moves; the sum is the same. So the turn angle is Δ · sensitivity, with no frame time in it.

A held key is a speed

A held key says "move while I am down", which is a speed. One frame at 144 fps is a quarter as long as one frame at 36 fps, so it must move a quarter as far: distance = speed · dt.

InputKindPer frameWrong version
Mouse movedistanceangle = Δ · sensitivity× dt: looking gets slower as the frame rate rises
Wheeldistance (notches)zoom by notches · step× dt: the same
Held keyspeedmove = speed · dtno dt: moving gets faster as the frame rate rises

Frame time, and held keys

Cap the frame time

Frame time dt is the time since the previous frame, from a monotonic clock. A debugger stop or a window drag can make one frame last seconds, so engines cap dt (for example to 0.1 s). Otherwise the camera jumps far on the next frame.

Read the physical key

Held keys are read as a state ("is W down now?"), not as events. Read the physical key (a scancode), not the letter: WASD then sits in the same place on an AZERTY keyboard.

Reset on focus loss

When the window loses focus, it misses the key-up event. Reset the key state then, or the camera keeps flying.

3The fly camera

A fly camera (also called FPS or free camera) turns where the mouse goes and moves with the keys. Its state is two angles, yaw and pitch, plus a position. There is no roll: the horizon stays level.

Why pitch is clamped

Pitch at ±90°

The view direction is parallel to the up axis. Then yaw and roll turn around the same line, and one degree of freedom is lost: this is gimbal lock. In practice the view flips over or spins when the mouse crosses the pole, and a lookAt built from this direction gets a zero cross product (lookAt).

Pitch clamped

Clamping to a value a little below 90° avoids all of it.

Moving with the keys

The forward and right directions come from the rotation: forward = R · (0, 0, −1), right = R · (1, 0, 0). Each held key adds or subtracts one of them.

move = 0
if W: move += forward      if S: move −= forward
if D: move += right        if A: move −= right
if |move| > 0:  position += normalize(move) · speed · dt

The plain sum

Two keys at once (W and D) give a diagonal of length √2 ≈ 1.41: diagonal moves are 41% faster.

The normalized sum

The sum is normalized first, so every direction moves at the same speed.

Fly or walk

With forward taken from the full rotation, looking down and pressing W moves down: a fly camera. A walking camera uses the yaw alone for movement, so it stays on the ground, and adds separate keys for up and down.

Drag or capture

Games capture the mouse: it is hidden, and every move turns the view. Tools and viewers usually turn only while a button is held, so the mouse stays free for the rest of the user interface.

4The orbit camera

An orbit camera looks at a center point (a model, a map location) from a distance. Dragging turns the camera around the center; the wheel changes the distance. There are two classic ways to map the drag to a rotation.

How an arcball maps the mouse to a sphere

Imagine a glass ball of radius 1 under the screen, centered in the window. Each mouse point is lifted straight up onto the ball. Two points p0 (where the drag started this frame) and p1 (where it is now) give a rotation: around the axis p0 × p1, by the angle between them.

The details that differ between orbit cameras:

The angle

Shoemake's arcball turns by twice the angle between the points (it uses the quaternion p1 · p0*). Many simple trackballs use the angle itself, times a sensitivity.

Turn the object or the camera

"Grab" feel: the scene follows the cursor. For a camera, that means turning the camera the opposite way: by −angle, in its own frame.

Roll

Small circles with the mouse add up to a roll. A turntable cannot roll; an arcball can.

Zoom

Additive (distance −= notches · step) feels slow far away and too fast up close. Multiplicative (distance ×= 0.9 per notch) feels the same at any distance. Clamp at a minimum either way.

Position

Always center + distance · (R · (0, 0, 1)): the camera's +Z points away from what it looks at.

5Smoothing: exponential easing

Raw input is jumpy: a mouse reports whole pixels, and frames are not evenly spaced. Smoothing moves the current pose a fraction t of the remaining way to the target each frame:

current = current + (target − current) · t

The question is how to choose t. A fixed number (say 0.1) looks right at one frame rate and wrong at all others: at 144 fps it runs 144 times a second, at 30 fps only 30 times. The fix comes from asking what the smoothing should do in time, not in frames: the remaining distance should shrink by the same factor every second.

remaining(time) = remaining(0) · e^(−k · time)

one frame of length dt:   remaining ← remaining · e^(−k · dt)
so                         t = 1 − e^(−k · dt)

Many frames multiply: e−k·dt1 · e−k·dt2 · … = e−k·(dt1 + dt2 + …). Only the total time matters, not how it was cut into frames. k is the speed: half the distance is gone after ln 2 / k seconds (0.12 s for k = 6).

Rotations and orbits

Positions blend with a straight mix. Rotations should not: mixing two quaternions number by number and normalizing moves at an uneven speed. Slerp (spherical linear interpolation) moves along the arc at a constant speed, and takes the same t.

An orbit camera needs one more step. For a 120° turn around the center:

Straight mix of positions

Halfway, a straight mix of positions is only half the distance from the center: the view zooms in and out during every turn.

Eased rotation, eased distance

Along the arc the camera keeps its distance.

  1. 1. Rotationslerp the rotation by t
  2. 2. Distancemix the distance by t
  3. 3. Positioncenter + distance · (R · +Z)

Try other angles. The picture blends one turn both ways, and plots the distance to the center on the right.

current and target straight mix of the positions blend of the rotation: along the arc

Stop when close enough

Exponential easing never reaches the target exactly. Worse, mixing two nearly equal values still rounds a little, by an amount that depends on dt, so a camera "at rest" moves by float noise. Snap to the target once the difference is below a tiny threshold.

A smoother option: a spring

Exponential easing starts at full speed and then slows down. A critically damped spring also keeps a velocity, so the camera speeds up gently too. It costs a few more lines and one more state variable per value.

7Who runs the controller

A small program is happy when the renderer reads the input and moves the camera for it. An editor, a game or a map application wants more: its own keys, two views with a camera each, a scripted camera path that the user can take over. Then the controller works better as a helper: a plain value the application keeps, and one function it calls each frame. The renderer only gets the pose.

The renderer runs it

No code in the application. But one controller for one camera, with the renderer's input only.

The application runs it

A few lines per frame. Any number of cameras, any input, and the application can change the input or the pose in between.

The helper is one value with everything a controller keeps: its state (angles, center, distance) and the two poses of section 1. Its function takes one frame's input and moves both poses. With no controller it still eases, so a pose the application sets as the target is smoothed too. To switch controllers, make the new one from the current pose: a fly camera takes its yaw and pitch from the rotation, so the view does not jump.

One input per view

With two views in one window, each camera needs its own input. Each view's input reads the same events, but only inside its own rectangle, and its mouse units are taken from that rectangle:

Which view gets the input
  • A press starts a drag only in its own view, and not on a UI window.
  • The drag stays with that view until the button goes up, even over another view.
  • The wheel goes to the view under the pointer.
  • Held keys go to the view the application picks: the one under the pointer, or the last one clicked.

8Pitfalls

Looking around is slower at a high frame rate
Mouse moves multiplied by dt.
Walking is faster at a high frame rate
Key movement not multiplied by dt.
Smoothing feels different on another machine
A fixed smoothing factor per frame instead of 1 − e−k·dt.
The camera jumps after a breakpoint or a window drag
dt not capped.
The view flips at the top or bottom
Pitch not clamped below 90°.
The horizon slowly tilts in a fly camera
Small turns added to the last rotation instead of rebuilding it from yaw and pitch.
The camera keeps moving after alt-tab
The key-up event was lost; the key state was not reset on focus loss.
The orbit zooms in and out while turning
The position eased in a straight line instead of along the sphere.
A drag in one view also turns the other camera
Both cameras read the whole window's input. Give each view its own input, limited to its rectangle.
The view jumps when the controller changes
The new controller kept its old angles. Make it from the current pose.

9In RASM

RASM has both kinds of controller: FREE_FLY (a fly camera, turned while a mouse button is held) and TRACK_BALL (an arcball-style orbit camera). Easing is the exponential kind of section 5. The controllers are helpers, as in section 7: a CameraRig holds the controller, the rendered transform and the targetTransform, and updateCameraRig moves it by one CameraInput. They need no Engine. The engine runs the same function for the camera given to beginFrame, unless that camera's controller is CameraController::Type::NONE.

An application that drives a camera itself turns the engine's controller off and keeps its own rig. pollEvents before the frame makes this frame's input readable at once; beginFrame then polls no more. examples/05_city does this with the input the engine read, and examples/19_embedding with its own CameraInputState:

engine.setCameraController(camera, rasm::CameraController{.type = rasm::CameraController::Type::NONE});
rasm::CameraRig rig = rasm::createCameraRig(freeFly, start);

while (engine.running())
{
    engine.pollEvents();
    rasm::updateCameraRig(rig, engine.getCameraInput());
    engine.setCameraTransform(camera, rig.transform);
    engine.render(scene, camera);
}

How events become a CameraInput: a CameraInputState takes them one by one (addCameraInputEvent), then gives the frame's input (takeCameraInput). The engine keeps one for the main window, and applies to it every event, from the SDL platform or from Engine::addInputEvent (The platform layer). An application can keep one per view:

  • mouseStart is last frame's drag position, mouseEnd the newest one, both from toInputNdc in the InputArea: a rectangle in window points, the units of InputEvent mouse positions.
  • A press starts a drag only inside the area and not on the UI (UiInputCapture, from Engine::getUiInputCapture). The drag goes on outside the area until the release.
  • wheelDelta is summed over the frame while the pointer is in the area. A wheel event has no position, so before the first move it counts in every area.
  • W, A, S, D are held keys by position (InputEvent::physicalKey), so they stay in the same place on an AZERTY keyboard.
  • deltaTime comes from steady_clock: 0 on the first frame, at most 0.1 s. With EngineConfig::fixedDeltaTime it is that step instead, so the easing is the same in every run. Engine::getDeltaTime returns it.
  • A FOCUS event that loses the focus lets go of every key and ends the drag, so no key stays held.

Keep these true
  • Controllers write targetTransform only. transform is written by easing and by setCameraTransform.
  • The engine's path and an application's call the same updateCameraRig: no controller math in Engine.
  • Mouse deltas are never multiplied by deltaTime; key movement always is.
  • The easing factor comes from 1 - exp(-easingSpeed * deltaTime), never a fixed number per frame.
  • A camera at rest must stay bit-for-bit still: keep the snap in the easing of updateCameraRig (B24).
  • Run ctest --preset x64-debug after a change; tests/cameraTests.cpp covers the controllers.
Not done yet

Views are not first-class yet: the engine draws one window, and its own input covers all of it. An application with several views keeps one CameraInputState per view (development plan, phase 5: multiple views and windows). There is no turntable or walk mode, and a fly camera has no keys for up, down or a faster speed.
