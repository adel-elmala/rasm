GPU data

Bindless resources

In the classic model, the CPU tells the GPU which textures a draw may use, before each draw. In the bindless model, all textures sit in one big array that is bound once, and the shader picks a texture by its number. This page explains how that works, which GPU features it needs, and how to manage the numbers safely. The last part shows how RASM does it.

In short

  • A descriptor is a small GPU record that says "this image, read with this sampler". Shaders reach textures only through descriptors.
  • Classic binding changes the bound descriptors before each draw. Bindless puts every descriptor in one array, binds it once, and stores slot numbers in the data the shader reads.
  • It needs descriptor indexing: an array with no fixed size, empty slots allowed (partially bound), writes while the array is bound (update after bind), and indexing that may differ per pixel (non-uniform).
  • Slots are handed out by a small allocator, usually a counter plus a free list.
  • A freed slot can be reused only after every frame that may still read it has finished on the GPU.
  • Bindless makes GPU-driven rendering possible: the GPU can choose the draws, because no draw needs the CPU to bind anything.

1The problem: binding per draw

A shader cannot read "texture number 7" by itself. It reads textures through descriptors: small records, prepared by the CPU, that hold an image view, a sampler and the layout the image is in. In the classic model, each draw gets its own small group of descriptors, and the CPU binds that group right before the draw.

Binding per draw has three costs:

CostWhy
CPU timeEach bind is a driver call, and the driver checks and copies state. With 10,000 draws this adds up to milliseconds.
Many small setsEvery material needs its own set, allocated from a pool and kept alive. Changing a material means writing a new set.
No GPU-driven drawsIf a compute shader decides which objects to draw (after culling, for example), the CPU does not know the draws. It cannot bind a set "before draw 517", because it never sees draw 517.

2The idea: one array, and numbers in the data

Bindless turns the problem around. All textures go into one big descriptor array, created once and bound once. Each texture gets a fixed slot in it: a number from 0 to the array size minus 1. The data that the shader reads anyway (a material record, an instance record) stores slot numbers instead of textures. The shader reads the number and indexes the array.

Now a draw needs nothing bound of its own. Two draws with different materials differ only in which record they read, and that is data. Data can be written by the GPU too, so a compute shader can build the whole list of draws.

4The GPU features it needs

The first versions of Vulkan and Direct3D had fixed-size arrays that had to be fully valid, and could not change while a command buffer used them. Bindless needs a few relaxations. In Vulkan they are called descriptor indexing (an extension first, core since Vulkan 1.2):

Each feature also has a limit. The important one is the size of the array: how many sampled images one set and one shader stage may see with update after bind. On current desktop GPUs this is hundreds of thousands to millions, so the array size is a choice, not a hard wall.

Non-uniform indexing

A GPU runs threads in groups of 32 or 64, called waves (or warps). A wave runs one instruction for all its threads at once. A descriptor is often loaded into scalar registers that the whole wave shares. That only works when every thread in the wave uses the same index. An index with this property is called dynamically uniform.

In HLSL and Slang the mark is NonUniformResourceIndex(i); in GLSL it is nonuniformEXT(i). When do you need it?

5Handing out slots

A slot number is a small resource of its own. Something must decide which slot a new texture gets, and remember which slots are free. The usual allocator is a counter and a free list:

allocate():
    if freeList is not empty: return freeList.pop()
    if counter == capacity:   fail ("array full")
    counter = counter + 1
    return counter - 1

free(slot):
    freeList.push(slot)       // only when no GPU work can still read it

Some engines also reserve the first slots for fixed textures: slot 0 for a white texture, slot 1 for a flat normal map, and so on. Then "slot 0" can mean "no texture", and the shader needs no special case (see section 7).

6When a slot can be reused

The CPU runs ahead of the GPU by one or more frames (see frames in flight). When the program frees a texture during frame N, the GPU may still be running frame N − 1, and frame N is not even submitted yet. Both may read that slot. If a new texture takes the slot now, those frames draw the new texture on the old objects, or read an image that no longer exists.

The fix is a retire list: a freed slot first waits, tagged with the frame that freed it. Once the GPU has finished that frame (its fence has signaled), the slot moves to the free list. The image memory waits in the same way. Here is one slot, with 2 frames in flight:

Frame 10: the app frees texture T

"Free" only records the wish. The descriptor and the image stay as they are.

Frame 11 starts: wait for frame 9

Each frame start checks the retire list against the newest finished frame.

Frame 12 starts: frame 10 is done

This last condition is the program's job: every material that used T must have been changed before the free.

Frame 12: a new texture U takes slot 4

The wait is F frames for F frames in flight. With 2 frames, a slot is reused at the earliest two frame starts after its free.

The two rules of slot lifetime
  • Never write a slot that work on the GPU may still read. Update after bind allows writes to a bound set, not writes under a running read.
  • Never let a record keep a stale slot number. If material M still says "4" after slot 4 went to U, M draws with U. This is the same problem that generational handles solve for CPU handles.

7A material without a texture

Most materials do not use every texture slot. A rock may have a color and a normal map, but no emissive map. The shader must still produce the right result. There are two common ways:

A "none" number and a branch

Store a special value, such as 0xFFFFFFFF, for "no texture". The shader checks it and skips the sample, using the material's factor alone. No extra textures are needed. The cost is a branch per texture, and the special value must never reach the array.

Default textures

Reserve slots for tiny 1×1 textures that change nothing, and point empty slots at them. The shader always samples: no branch, one code path. The cost is a few slots and a sample that reads the same texel every time (it stays in the cache).

TextureDefault texelWhy that value changes nothing
Base colorwhite (1, 1, 1, 1)factor × 1 = factor
Metallic-roughnesswhitefactor × 1 = factor
Occlusionwhite1 means "not occluded"
Emissivewhitefactor × 1 = factor; the emissive factor is 0 when the material does not glow
Normal map(0.5, 0.5, 1.0)decodes to (0, 0, 1): the surface normal itself (see normal mapping)

A third value is a placeholder: a gray or checker texture shown while the real one is still loading. A slot can also be pointed at the placeholder first and rewritten when the real texture is ready, because the slot number does not change.

A sampler holds how to read a texture: the filter (nearest, linear), the mip filter and the wrap mode (see mipmaps and sampling). A bindless design has to decide where samplers live.

Descriptor buffers make the memory explicit: descriptors become bytes the app manages like any other buffer data, with the same frame-in-flight rules. That makes them a natural fit for engines that already manage GPU buffers by hand. They are newer, so their support is narrower than descriptor indexing.

10Trade-offs and pitfalls

What it gives

  • Very little CPU work per draw, and none between GPU-chosen draws.
  • One pipeline layout for every shader that reads textures.
  • Materials become plain data, easy to change and to upload.
  • Shaders can read any texture: decals, terrain splat maps, a visibility buffer that shades any material.

What it costs

  • The driver no longer checks which textures a draw uses. A wrong index reads the wrong texture or crashes the GPU, with no error.
  • Lifetime is the app's job: slots, retire lists and stale numbers.
  • The driver no longer knows which images a draw reads, so the app must put every image in the right layout itself (see GPU synchronization).
  • Debuggers show "an array of 1000 textures" instead of "this draw's 4 textures".

11In RASM

RASM has one bindless set for the whole engine: an array of 1024 combined image samplers. A material row on the GPU stores slot numbers, and a texture handle becomes a slot number the first time a material or a pass needs it. Slots are only handed out, never freed.

A material that waits for its texture

The slot is written at once, but the texture may still be decoding on a worker thread (see streaming assets). The engine therefore keeps every entity that uses it out of the draw lists until the pixels arrive. Here is what happens when the app gives material M of entity E a new texture T that is still loading:

1. updateMaterial(M, values)

updateMaterial copies the new values over the record, keeps the handle, and calls writeMaterialRow. The row index does not change, so no instance row changes.

2. refreshEntitiesAfterMaterialChange

E disappears from the image until T is ready. No frame ever samples slot 8 before T has pixels.

3. finishLoads: T is decoded

The flag tells syncGpuScene that it is worth checking the waiting entities again.

4. syncGpuScene: E comes back

From this frame on, E draws with T. Changing only factors (colors, roughness) never makes an entity wait.

Keep these true
  • "No texture" is INVALID_TEXTURE_INDEX in the row, never 0: slot 0 is a real texture. The shader must check hasTexture before it indexes gTextures.
  • An image must be in the shader-read layout whenever a draw may sample its slot: the descriptor promises VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL. That is why endPass moves a render target's color attachment there (B10).
  • Do not rewrite a slot that a frame in flight may read. Today only the depth slots are rewritten, with the device idle.
  • A new texture field in gfx::Material is a CPU↔GPU struct change: see struct layout.
  • If an index ever comes from per-pixel data (a G-buffer, a decal list), mark it non-uniform.
Not done yet

No material destruction, and no free list or retire list for slots (D4). RenderContext::destroyTexture exists, but it does not touch the slot or bindlessTextureIndexMap: a texture that a material still uses must not be destroyed. The array size and the 256 materials are fixed at compile time (D15). No default textures. See also the bindless API.
