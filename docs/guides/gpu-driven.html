Drawing

GPU-driven rendering and indirect draws

A classic renderer walks over its objects on the CPU and records one draw call for each. A GPU-driven renderer keeps the scene in GPU memory and lets the GPU itself decide what to draw and how. The tool that makes this possible is the indirect draw: a draw call whose arguments live in a GPU buffer. This page explains the idea from the start. The last part shows how RASM does it.

In short

  • A CPU draw loop costs CPU time per object: state changes, bindings and one draw call each. With many objects, the CPU becomes the limit.
  • GPU-driven rendering moves the scene into GPU tables (objects, meshes, materials). The CPU only updates rows that changed.
  • An indirect draw reads its 5 arguments from a buffer. A compute shader can write them, so the CPU does not need to know them.
  • Multi-draw indirect runs many draw records with one call. A draw count buffer lets the GPU also choose how many.
  • firstInstance, or a draw-index built-in, tells the shader which object a draw belongs to.
  • One call uses one pipeline state. So draws are sorted into runs that share their state, with one call per run.

1The CPU draw loop

The simplest renderer draws one object at a time. For each object, the CPU sets up the GPU state the object needs, then asks for a draw:

for each object in the scene:
    if the object is not visible: skip it
    bind the pipeline        (only if it is not the one bound already)
    bind the vertex and index buffers of the object's mesh
    bind the descriptor set of the object's material
    set constants:           the object's world matrix
    drawIndexed(indexCount, 1, firstIndex, vertexOffset, 0)

Each line is a command that the graphics driver must check and turn into GPU commands. This happens on the CPU, every frame, for every object.

This is called a CPU-driven renderer. The CPU decides everything: which objects are visible, in which order they are drawn, and with which arguments. It works well for hundreds of objects. With tens of thousands, recording the commands can take longer than the GPU needs to draw them.

2Not all commands cost the same

Changing some state is much more expensive than changing other state. A new pipeline means new shaders and new fixed-function settings for the GPU. New push constants are only a few bytes. Most engines know this rough order:

So the first fix for a CPU-driven renderer is to sort the draws. Each draw gets a number, a sort key, built from its state, with the most expensive state in the highest bits. After sorting, draws with the same expensive state are neighbours, and that state changes once per group instead of once per draw.

Sorting reduces the state changes, but the CPU still records one draw per object and still decides what is visible. GPU-driven rendering removes the loop itself.

3The idea: give the scene to the GPU

The GPU is very good at doing the same small job for many items in parallel. Culling and building draw arguments are such jobs. So a GPU-driven renderer moves the scene into GPU buffers and lets a compute shader do the work of the CPU loop.

This needs two things from the API. First, a draw call that takes its arguments from GPU memory. Second, a way for the shader to find its object's data without per-draw bindings. The next sections cover both. The second also needs bindless textures and vertex pulling, because there is no chance to bind a mesh's buffers or a material's textures between draws.

4Indirect draw arguments

An indexed draw needs 5 numbers. A direct draw call passes them as function arguments, from the CPU. An indirect draw call passes only a buffer and an offset. The GPU reads the 5 numbers from that buffer when it runs the call. We call these 5 numbers a draw record.

Every modern API has this record, with the same fields in the same order. Only the names differ:

Because the record is plain memory, anyone who can write a buffer can write it: the CPU through an upload, or a compute shader on the GPU. That is the whole point. The CPU only says "draw what is written there", and the GPU fills in what "there" means.

5firstInstance as an object id

A draw record says which triangles to draw. It does not say which object they belong to: where it is, which material it has. In a CPU-driven renderer, the CPU binds that data before each draw. In a GPU-driven renderer, nothing is bound between draws, so the shader must find the object's data itself. It needs a number that is different for each draw: an object id.

The usual trick uses firstInstance. Instancing draws the same mesh instanceCount times, and each copy gets an instance index. Copy i gets firstInstance + i. When the draw has one copy, its instance index is just firstInstance. So the renderer writes the object's row number into firstInstance, and the vertex shader uses the instance index to read that row.

There is a second way. Some APIs give the shader a draw-index built-in: the number of the record inside the current multi-draw call (next section). The shader can read the record itself with it, and any extra per-draw data stored next to it. Both ways are common. Watch out for the API differences:

6Multi-draw indirect

One indirect draw that reads one record saves little: the CPU still makes one call per object. Multi-draw indirect fixes that. One call reads N records, one after another, and runs N draws. The records are stride bytes apart, usually exactly the record size.

The GPU still runs N separate draws. Its command processor, the front part of the GPU that reads commands, walks the records itself. That is cheap, but not free: a draw of a few triangles still has a fixed cost on the GPU. GPU-driven rendering removes the CPU cost of a draw, not the GPU cost.

7Draw count buffers

Multi-draw indirect still has one number from the CPU: N, the record count. But after GPU culling, only the GPU knows how many draws are left. One answer is to keep N fixed and make culled records draw nothing (set their indexCount or instanceCount to 0). That works, but the command processor still reads every empty record.

The better answer is a draw count buffer. The call takes a second buffer, and the GPU reads the record count from it at run time. The CPU passes only an upper limit, maxDrawCount. The GPU draws min(count, maxDrawCount) records.

Packing the visible records tightly at the start of the buffer, in a stable order, is a job of its own: stream compaction. In Vulkan the call is vkCmdDrawIndexedIndirectCount, core since Vulkan 1.2 with the drawIndirectCount feature. Direct3D 12 has the same count buffer in ExecuteIndirect.

Order matters for the GPU too

Culling runs in parallel, so the easy way to pack is an atomic counter: each kept record takes the next free slot. Then the order of the records changes from frame to frame. The picture stays the same, but depth-test efficiency and debugging captures do not. A prefix sum keeps the original order. See stream compaction.

8Grouping draws by state: runs

One indirect call uses the state that is bound when it is recorded: one pipeline, one set of bindings, one value of every dynamic state. All its draws share it. So draws that need different state cannot be in the same call.

The fix is the sort from section 2, done once: sort the draw records by their state, so each state's records are one contiguous range, a run. Then record one indirect call per run, each with its own offset, its own maxDrawCount and its own count.

This is why GPU-driven renderers work hard to reduce the number of states:

What would split the runsHow engines avoid it
A pipeline per materialOne shader for all materials, with the material as data: uber shaders.
Textures bound per materialAll textures in one big array, picked by index: bindless resources.
Vertex and index buffers per meshAll meshes in one big buffer: vertex pulling and mega-buffers.
Fixed-function state, such as face cullingDynamic state: the value is set in the command buffer, not baked into the pipeline. It still splits runs, but not pipelines.
Blending (transparent objects)Cannot be avoided. Transparent objects need their own pipeline, and usually a sorted order, so they get their own pass.

9What the CPU still does

GPU-driven does not mean the CPU does nothing. It means the CPU's work no longer grows with the number of objects drawn each frame.

WhenCPU work
Once, at loadUpload meshes, textures and materials. Create the pipelines.
When something changesWrite the changed rows of the scene tables: a moved object, a new material. Rebuild the draw list when objects are added or change state.
Every frameWrite the camera and the per-frame constants. Record the culling dispatches, a few binds and one indirect call per run. Submit.
NeverLoop over all objects to test, sort or draw them.

The CPU also loses something: it no longer knows what was drawn. How many objects were visible, or how many triangles, is only in GPU memory. To show it, the CPU must read it back a frame or two later, after the GPU has finished (see GPU timing and frame statistics).

10Worked example

A scene with 8 draws in two states. Click through what happens in one frame.

1. The draw list, sorted by state

All 8 records are in a GPU buffer. Nothing in this step happens per frame.

2. Culling tests every record

5 of the 8 records are visible: 3 in run A, 2 in run B.

3. Pack each run, write its count

Each run's records start where the run starts, so the CPU already knew the offsets when it recorded the calls.

4. Two indirect calls draw them

The CPU recorded 2 state changes and 2 calls. It did not know that 5 draws would be visible, nor which ones.

12In RASM

RASM is GPU-driven from the start. Engine::drawScene draws a whole scene with one pipeline, a few binds and one drawIndexedIndirectCount per cull-mode run: at most 3 calls, or 6 with occlusion culling. The tables it reads are in the GPU scene tour.

Keep these true
  • DrawInfo has the layout of the Vulkan indexed indirect record, on both sides. A field added to it changes the stride of every indirect call and of the culling buffers.
  • The draw list is sorted by cull mode, each run is contiguous, and culling packs a run's visible draws at the start of that run's range. drawScene and cull.slang both rely on runFirst.
  • Every call pushes firstDraw = the run's first slot. Without it, every run would read run 0's draws.
  • A new state that differs between draws must be dynamic state and a new run, or it cannot be in this pass. Raising the number of runs means changing MAX_DRAW_RUNS on both sides and the static_assert next to it.
  • drawScene sets the cull mode back to NONE after its runs: beginPass sets it for every other pipeline.
Not done yet
  • P3: no real instancing. Each entity's sub-mesh is its own draw, even when the mesh is shared.
  • D4: nothing can be removed, so draw lists only grow and instance rows are never freed.
  • D18: the culling runs before every other GPU work of the frame, from its own command buffer. GPU work that changes what culling reads would need it to become a graph pass.
  • D12: getDrawIndex uses spirv_asm, so this path is Vulkan-only today.
  • No transparent objects: the scene pipeline has blending off.
