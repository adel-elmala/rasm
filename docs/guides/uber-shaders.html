Uber shaders and shader permutations

Materials differ: one has a normal map, one does not; one is lit, one is unlit. A renderer can compile a separate shader for every combination, or write one big shader, an uber shader, that handles all of them with branches at run time. This page explains both ways, what a branch really costs on a GPU, and why GPU-driven renderers lean towards one shader. The last part shows how RASM does it.

In short

  • Every on/off feature doubles the number of shader combinations, the permutations. A few features give hundreds of shaders.
  • Compile-time variants (#if) give the fastest code per combination, but cost compile time, memory, pipeline-creation stalls and draw-call splits.
  • An uber shader branches at run time on material data. One shader, one pipeline, slightly slower code.
  • A branch that is the same for all threads of a wave is cheap. A branch that differs inside a wave (divergence) runs both sides.
  • The real cost of an uber shader is often registers: the worst path decides how many waves fit on the GPU.
  • Specialization constants sit in between: one compiled shader, with constants fixed when the pipeline is made.

1The permutation explosion

Take a typical material model, like glTF's. A texture can be there or not. The surface can be opaque, cut out, or blended. It can be lit or unlit, single- or double-sided. Each choice changes the shader code, so each combination of choices is, in the simplest design, its own shader.

Not every combination is used by a real scene, so engines only compile the ones they meet. But they do not know which ones until the content is loaded, and the set changes with every new asset.

2Way 1: compile-time variants

The classic answer writes the shader once, with preprocessor switches, and compiles it once per combination with different #defines:

float3 n = input.normal;
#if HAS_NORMAL_MAP
    n = sampleNormalMap(material.normalTexture, input.uv, n);
#endif
// compiled twice: with HAS_NORMAL_MAP = 1, and with HAS_NORMAL_MAP = 0

Good

  • The fastest code for each combination. Unused features cost nothing.
  • Each binary uses only the registers its own path needs.
  • Simple to reason about: one shader does one thing.

Bad

  • Compile time grows with the number of combinations.
  • Each binary needs a pipeline. Creating a pipeline the first time it is needed causes a visible stall: the well-known shader stutter.
  • More pipelines mean more state changes, and more splits of a GPU-driven draw list.

3Way 2: one uber shader with runtime branches

The other answer compiles one shader that contains every feature, and decides at run time, from the material's data, which parts to run. The material stores flags, or uses a special value such as "no texture" for a missing texture index:

float3 n = input.normal;
if (material.normalTexture != NO_TEXTURE)
    n = sampleNormalMap(material.normalTexture, input.uv, n);
// compiled once; the branch is decided per material, at run time

Whether this is fast depends on how GPUs run branches. That is the next section.

4How a GPU runs a branch

A GPU does not run each pixel's shader on its own. It runs them in groups of 32 or 64 threads, called a wave (or warp). All threads of a wave share one instruction stream: at each step, they all run the same instruction, each on its own data. Each thread is a lane of the wave.

So what happens at an if? If all lanes agree, the wave simply runs the side they chose. If they disagree, the wave runs both sides, one after the other, and switches off the lanes that did not choose the side being run. This is called divergence.

So the question is not "does the shader branch?" but "is the branch the same for all lanes of a wave?". There are three kinds of values a branch can test:

The value is…ExampleCost of the branch
known when compilinga #define, a specialization constantnone: the compiler removes the side not taken
the same for the whole draw (uniform)a material flag, when the draw has one materialsmall: every wave takes one side; only the test itself costs
different per pixel or vertex (varying)a texture value, the light's distancecan be both sides, when neighbouring pixels disagree

A material branch is the good, middle case: all pixels of one draw share one material. Whether one wave can hold pixels of two draws depends on the GPU. When it can, the branch may diverge in that wave, at draw edges only. In Vulkan, the specification treats each draw of a multi-draw as its own group for this purpose, so a value that is the same for the whole draw still counts as uniform.

5The hidden cost: registers

Divergence is easy to see. A bigger cost of uber shaders is easy to miss. A GPU keeps many waves in flight on each compute unit at once. When one wave waits for memory, for example for a texture, the unit switches to another one. More waves in flight hide more waiting. The number of waves that fit is called occupancy.

Waves share the unit's register file. A shader that needs more registers per thread leaves room for fewer waves. And the compiler must give the shader enough registers for its worst path, even if most materials never take it. One rare, heavy feature in an uber shader can lower the occupancy of every material.

On GCN, each SIMD has 256 vector registers per lane, and holds at most 10 waves, so waves = min(10, ⌊256 / registers⌋). Other GPUs have other numbers, but the same shape: more registers, fewer waves. A branch that raises the count from 40 to 64 turns 6 waves into 4, for every pixel the shader runs, taken or not.

Keep the heavy path small

Do not copy big structs or arrays into local variables at the top of an uber shader "just in case": the compiler may keep them in registers for the whole shader. Read data when a path needs it, through a pointer or an index.

6Way 3: specialization constants

Vulkan offers a middle way. A specialization constant is a constant in the compiled shader (SPIR-V) whose value is given only when a pipeline is created. The driver then compiles the pipeline with that value, and removes the branches it decides. Metal has the same idea as function constants.

// Slang
[SpecializationConstant] const bool hasNormalMap = false;

// GLSL
layout(constant_id = 0) const bool HAS_NORMAL_MAP = false;

7The material type switch

Some differences are not small features but whole shading models: lit and unlit, skin, hair, cloth, clear coat. An uber shader handles them with a small integer per material, the material type (or shading model id), and a switch at the top of the pixel shader:

switch (material.type)
{
case UNLIT:      return shadeUnlit(material, input);
case CLEAR_COAT: return shadeClearCoat(material, input);
default:         return shadeStandard(material, input);
}

The type is uniform per material, so this is the cheap kind of branch. The register cost from section 5 still applies: the heaviest model sets the register count for all. Deferred renderers use the same idea one step later: they write the shading model id into the G-buffer, and the lighting pass switches on it per pixel. There, neighbouring pixels can have different ids, so divergence is real at the edges between materials.

8Why GPU-driven renderers want one pipeline

In a GPU-driven renderer, one indirect call draws many objects, but with one pipeline. Every extra pipeline splits the draw list into another run: another range to cull and pack, another count, another call.

This is why GPU-driven renderers usually combine three ideas: an uber shader for the shading, bindless textures picked by index from the material row, and vertex pulling from one mega-buffer. Together they remove every reason to bind anything between draws.

10In RASM

RASM draws every scene object with one uber shader, shaders/passes/rasm.slang: one vertMain, one fragMain, compiled once into one pipeline. Materials are rows in the material table, and fragMain branches on them at run time.

How to add a shading path

  1. The public type. Add a value to MaterialType in include/rasm/material.h, before COUNT, and a case for it in the switch in Engine::createMaterial (src/assets/material.cpp).
  2. The GPU id. Add the same value to gfx::MaterialId in src/renderer/uberMaterialTypes.h and to MaterialId in shaders/lib/core.slang, in the same order.
  3. The mapping. Return it from getGfxMaterialId in src/renderer/gpuScene.cpp.
  4. The shading. Write a shade function in a new file in shaders/lib/, include it in rasm.slang, and branch to it in fragMain before the PBR path, like the unlit path. Read only the fields you need through the MaterialData pointer.
  5. New material data. If the path needs any: new fields in Material on both sides, filled in convertToGfxMaterial. That is a CPU↔GPU struct change: follow the struct rules.
  6. Check. Run the examples with enableValidation on. A shader-only change needs no rebuild; the enum changes do.

Keep these true
  • Every scene draw goes through the one pipeline. A material feature is a field and a branch, not a new pipeline: a new pipeline would split every draw list.
  • MaterialId has the same values in the same order in C++ and Slang.
  • The material branch must stay uniform per draw. If one draw ever covers several materials (real instancing), the texture indices need a non-uniform marker.
  • Shaders output linear color; the swapchain encodes it (see color spaces).
