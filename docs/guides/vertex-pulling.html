Vertex pulling and mega-buffers

Normally the GPU's fixed-function hardware reads vertices from vertex buffers and hands them to the vertex shader. With vertex pulling, the vertex shader gets only a number, and reads the vertex from memory itself. Together with one big buffer for all meshes, a mega-buffer, this removes all per-mesh bindings, which GPU-driven rendering needs. This page explains both. The last part shows how RASM does it.

In short

  • The classic path: the pipeline describes the vertex layout, the CPU binds vertex buffers, and fixed-function hardware fetches and converts each vertex.
  • Vertex pulling: the pipeline has no vertex input. The shader gets the vertex index and reads a struct from a storage buffer.
  • The index buffer stays. It still decides which vertex each corner uses, and lets the GPU reuse shaded vertices.
  • A mega-buffer holds every mesh. A mesh is a range in it; a draw finds it with firstIndex and vertexOffset.
  • The shader decides the vertex format, so any packing or compression is possible, decoded in a few instructions.
  • Speed is about the same on most desktop GPUs. The real gain is flexibility, and no bindings between draws.

1How the GPU usually gets its vertices

A vertex is a small record: a position, a normal, texture coordinates, maybe more. A mesh stores its vertices in a vertex buffer. In the classic path, the application tells the pipeline what one vertex looks like, with a vertex input layout: how many bytes per vertex (the stride), and for each attribute, its format and its byte offset. Then, before each draw, it binds the vertex buffer.

The fetch hardware also converts. An attribute stored as 4 bytes of 0 to 255 can arrive in the shader as a float4 from 0 to 1. The shader does not know how the data was stored.

What the classic path costs you

LimitWhy it hurts
The layout is part of the pipelineMeshes with different vertex formats need different pipelines, even with the same shaders. Each one splits a draw list (see runs).
Vertex buffers are bound per drawEach mesh in its own buffer means a bind between draws. One indirect call over many meshes cannot do that.

2Vertex pulling: the shader reads its own vertex

The idea is simple. Give the pipeline an empty vertex input layout. The vertex shader still runs once per vertex, and it still gets one built-in input: the vertex index, the number of the vertex it must produce. It uses that number to read the vertex from a storage buffer, like any other array.

In Slang or HLSL, a minimal vertex shader looks like this:

struct Vertex
{
    float3 position;
    float3 normal;
    float2 uv;
};

StructuredBuffer<Vertex> vertices;

float4 vertexMain(uint vertexIndex : SV_VertexID) : SV_Position
{
    Vertex v = vertices[vertexIndex];
    return mul(viewProjection, float4(v.position, 1.0));
}

The struct is now a contract between the code that writes the buffer and the shader that reads it. Both sides must agree on every byte: see struct layout rules. The buffer can be a descriptor binding, as here, or a raw GPU address (see buffer device addresses).

3The index buffer still does its job

Vertex pulling replaces the reading of vertex data. It does not replace the index buffer. Indexed drawing works as before: the hardware reads one index per triangle corner, and that index becomes the vertex index the shader receives.

This matters for speed. A vertex is usually shared by several triangles. The GPU keeps the results of recent vertex shader runs in a small cache, keyed by the index. When the same index comes again soon, it reuses the result instead of running the shader again. With pulling, the cache still works, because the hardware still sees the index.

Which number the shader receives

Indexed draws add vertexOffset (also called base vertex) to every index value. Whether the vertex-index built-in includes it depends on the API, and on how the shading language maps its built-in. Check before you index a buffer with it:

API, built-inValue for an indexed draw
Vulkan, VertexIndexindex value + vertexOffset
Direct3D, SV_VertexIDindex value only: the base vertex is not added
A shading language that targets bothpicks one meaning, and may subtract the base vertex on Vulkan to match Direct3D

Non-indexed draws are simpler: the vertex index counts from firstVertex upward, one per vertex.

4One buffer for every mesh

Vertex pulling removes the vertex layout from the pipeline. The second half of the job is to remove the bind between draws. The usual answer is a mega-buffer: one big vertex buffer and one big index buffer for all meshes. Each mesh is a range in each of them. The buffers are bound once, and every draw finds its mesh with two numbers from its draw record.

Local or global indices

Mesh B's indices can be stored in two ways. Local: as the mesh was made, 0 to 3, and the draw adds vertexOffset = 24. Global: already moved, 24 to 27, with vertexOffset = 0. Local is the usual choice:

Local indices + vertexOffsetGlobal indices

Sharing out the space

A mega-buffer is created once, with a fixed size. Giving a mesh a range of it is sub-allocation, the same problem as a memory allocator:

StrategyHowGood forProblem
Bump (linear)Each mesh goes right after the last one. Nothing is freed.Content loaded once: a level, a model viewerThe buffer only fills up.
Free listFreed ranges go into a list; a new mesh takes the first range that fits.Meshes that come and goHoles: the free space splits into pieces too small to use (fragmentation).

Freeing a range is also a timing problem: the GPU may still be drawing from it in a frame that is in flight. See frames in flight.

7Smaller vertices

Vertex data is read for every vertex of every draw. Smaller vertices mean less memory, and less memory traffic each frame. With pulling, the shader can decode any packing it likes, so engines often store far less than full 32-bit floats:

AttributeFullPackedHow it is decoded
Position3 × float32 = 12 B3 × 16-bit + 2 B padding = 8 BQuantized inside the mesh's bounding box: p = min + q / 65535 × (max − min). The box is stored once per mesh.
Normal3 × float32 = 12 B2 × 16-bit = 4 BOctahedral encoding: the unit sphere is folded onto a square, so 2 numbers are enough.
Tangent + sign4 × float32 = 16 B2 × 8-bit + sign, 4 BOctahedral too, with the bitangent sign in a spare byte.
Texture coordinate2 × float32 = 8 B2 × 16-bit = 4 BUnsigned normalized 16-bit for UVs in 0 to 1; half floats for UVs that repeat.

1,000,000 vertices64,000,000 B ≈ 61.0 MiB20,000,000 B ≈ 19.1 MiB

A trap: half-float UVs

A 16-bit half float has 10 bits of fraction. Between 0.5 and 1.0, its step is 2−11 ≈ 0.00049. On a 4096-texel texture, that is 4096 × 0.00049 = 2 texels: visible as wobbly, swimming textures. Unsigned normalized 16-bit has the same step everywhere, 1 / 65,535, which is 0.06 texels on the same texture.

8Performance notes

TopicWhat to know
Fetch hardware vs shader loadsOn many desktop GPUs, vertex fetch already runs as ordinary shader loads, so pulling costs about the same. Some GPUs, often mobile ones, still have fast fixed-function fetch. Measure before you depend on either.
AlignmentA struct whose size is a multiple of 16 bytes lets the compiler use wide 16-byte loads. A 12-byte float3 at an odd offset may turn into several small loads.
Cache linesMemory moves in lines of 64 or 128 bytes. A 64-byte vertex that starts on a line boundary costs one line; a 20-byte vertex costs a third of one.
Index orderReorder the triangles so that shared vertices come close together. The vertex cache then hits more often (Forsyth's algorithm, meshoptimizer).
Vertex orderReorder the vertices into the order the indices first use them. Reads then walk the buffer forward, line by line.
RobustnessA wrong vertex index in a pulled read is just a read of the wrong memory: another mesh, or past the end of the buffer. Debug builds can check the index against the mesh's range.

9In RASM

RASM uses vertex pulling for every graphics pipeline: no pipeline has a vertex input layout. All meshes live in one geometry pool: one vertex buffer, one index buffer and one table of sub-mesh rows, created at startup and sized by EngineConfig.

Keep these true
  • Vertex, gfx::VertexFull and the Slang VertexFull have the same 64 bytes. A change to one changes all three and the static_asserts (see struct layout).
  • vertMain adds draw->vertexOffset to SV_VertexID. Removing it makes every mesh read the first mesh's vertices.
  • Indices are local to their sub-mesh. Every LOD of a sub-mesh uses the same vertexOffset.
  • The index buffer is bound as U32_UINT. 16-bit indices would need a second index buffer and their own draws.
