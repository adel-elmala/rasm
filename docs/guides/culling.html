Rendering

GPU culling

Before the scene is drawn, a compute shader tests every draw against the camera view. Draws that are fully outside are removed, and so are draws hidden behind what is already drawn (occlusion culling). Each draw that stays gets the coarsest level of detail that still looks the same. The CPU never sees which draws survive. The GPU writes the list and the count, and the draw call reads them.

CPU work GPU work GPU buffer shader entry point

In short

  • Input: the scene's draw list (one DrawInfo per sub-mesh of each entity). Output: the visible draws, packed, and one count per run.
  • Two dispatches per drawScene call: countMain tests and counts, writeMain copies the visible draws to their final place.
  • Test: a bounding sphere that is fully behind one of the 6 frustum planes is culled.
  • The visible draws keep the draw list's order, every frame. No count needs to be cleared.
  • The culling is recorded after the frame, in its own command buffer, but it runs before the frame on the GPU.
  • Occlusion culling runs the same two dispatches twice: early (what was visible last time) before the frame, and late (the rest, tested against a Hi-Z of the early draws' depth) in the middle of the pass.
  • Level of detail: the draw list holds LOD 0. For each visible draw, selectLod swaps in the index range of the coarsest LOD whose error on screen stays under EngineConfig::lodErrorPixels.

1Where culling sits in a frame

drawScene records its draws inside a render pass. Vulkan does not allow dispatches inside a render pass. So the dispatches go into a second command buffer, the cull command buffer. It is recorded last, in endFrame, but it is submitted first.

This works because drawScene does not need the results while recording. It only records "draw from this buffer, with the count in that buffer". The buffers are filled later on the GPU, before the draws run.

2The data flow

All these buffers are found through SceneData, which the push constant points to. Each drawScene call has its own SceneData, its own visible-draw buffer and its own counts. That is why two passes can draw the same scene with two cameras in one frame.

3The test: sphere against plane

Every sub-mesh has a bounding sphere in the geometry table, in mesh space. countMain moves it to world space with the instance's world matrix, then tests it against the 6 planes of the camera frustum.

Two details that keep the test correct

The radius under scale

A scaled mesh has a bigger sphere. countMain multiplies the radius by the largest stretch of the world matrix. It gets an upper bound of it cheaply (Gershgorin's theorem on transpose(M) × M). The bound is exact for normal rotate + scale matrices, and never too small for odd ones.

The far plane

RASM uses reversed-Z with an infinite far plane by default. The far plane then comes out as (0, 0, 0, nearZ), so d = nearZ for every sphere and it always passes. See Camera, coordinates and depth.

4Runs and groups

The draw list is stable-sorted by cull mode into runs (NONE, then FRONT, then BACK, the order of the enum), because cull mode is set per indirect call. Culling splits each run into groups of 64 draws, one compute workgroup each. A group never crosses into the next run.

The CPU counts the groups of each call in drawScene (cullGroupCounts). recordCulling dispatches that many groups for both entry points, and so does recordOcclusionCulling for the late cull.

6Occlusion culling

A draw inside the frustum can still be hidden behind a wall. Occlusion culling removes it. RASM uses the two-pass Hi-Z scheme. It is on by default; EngineConfig::occlusionCulling turns it off.

Why it stays correct

History only saves work

The visibility flags are a guess from last time. Whatever the early cull skips, the late cull tests against the depth that is really there, and draws it if it is visible. A wrong guess costs time, never pixels.

Flags per call

Each drawScene call of a frame has its own flags (GpuScene::visibility), one per instance row (EngineConfig::maxInstances rows), made the first time the call culls. Both frame slots share them, because the GPU runs the frames in order. Rows start at 0, so a new instance is drawn by the late cull first. A call should keep its camera from frame to frame; if two cameras swap call order, they read each other's flags: slower, still correct.

The cost of the pause

The pass ends after the early draws and begins again with load, so with occlusion culling on, beginPass stores depth (storeDepth) and the depth textures can be sampled. The Hi-Z build and the late cull get their own GPU timer, "Hi-Z", in the stats overlay.

7Level of detail

A far object covers few pixels, so it does not need all its triangles. When a mesh loads, RASM builds coarser versions of each sub-mesh, its LODs (see Asset loading). Culling picks one LOD for each visible draw, every frame.

Which LOD

pixels   = lods[i].error × sphere.scale × |projection[1][1]| × viewportHeight / 2 / distance
distance = |sphere center − camera| − sphere radius     (≤ 0: the camera is inside, LOD 0)
PartMeaning
lods[i].errorhow far LOD i's surface may be from LOD 0, in the mesh's own units. It adds up the errors of the steps, so it never gets smaller. LOD 0 has 0.
sphere.scalethe world matrix's largest stretch, the same bound the frustum test uses for the radius. It turns mesh units into world units.
the restpixels per world unit at that distance. An orthographic camera (projection[3][3] == 1) skips the division by distance.
distanceto the sphere's nearest point, so the error is never too small.

Where it runs

countMain calls selectLod to count the visible triangles for the stats overlay. writeMain calls it and writes the LOD's firstIndex and indexCount into the visible draw. The draw list on the CPU always holds LOD 0.

Settings

EngineConfig::meshLods (on) builds the LODs as meshes load. EngineConfig::lodErrorPixels (1 pixel) is the limit; 0 always draws LOD 0. An unculled drawScene call draws LOD 0.

8When culling is off

If cull.slang (or a module it includes) fails to compile, drawScene does not leave the screen black. It draws the whole draw list with plain drawIndexedIndirect and logs the error. It tries to build the culling pipelines again next frame, so a fixed shader on disk is picked up while the app runs.

Culled call

drawInfoPtr → visible-draw buffer
draw: drawIndexedIndirectCount
stats: visible counts come from the GPU

Unculled call (fallback)

drawInfoPtr → the draw list itself
draw: drawIndexedIndirect, all draws
stats: all draws count as visible

Occlusion culling falls back to frustum culling alone (hizLevelCount = 0, no late pass) when EngineConfig::occlusionCulling is false, when hiz.slang fails to compile, when the depth texture has no bindless slot, when the visibility or Hi-Z buffer cannot be created, or when the viewport is not the whole pass with depth range 0 to 1 (RenderContext::getViewport): the Hi-Z covers the whole attachment, and the test maps NDC onto it. The image is the same either way; only the number of draws changes.

10Rules when you change it

Keep these true
  • CULL_GROUP_SIZE, CULL_EARLY and CULL_LATE are in cull.slang and gpuScene.cpp; HIZ_GROUP_SIZE is in hiz.slang and gpuScene.cpp. Change both sides. So are the Hi-Z level sizes (getHizLevelCount, getHizLevel).
  • Both tests must stay conservative. Removing a draw that is partly visible makes objects pop. Compare the image with EngineConfig::occlusionCulling on and off: it must not change.
  • Do not record a dispatch inside a render pass. RenderContext::dispatch refuses it.
  • selectLod changes only firstIndex and indexCount. All LODs share the sub-mesh's vertices, so vertexOffset stays.
  • A new pointer in SceneData is a CPU↔GPU struct change: follow the struct contract.
