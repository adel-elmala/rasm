Texture compression: blocks, KTX2 and Basis

Textures take most of a scene's video memory. A GPU can read textures that stay compressed in memory, but only in its own block formats, and each kind of GPU reads different ones. This page explains how block compression works, why a PNG does not save any video memory, and how a Basis Universal file in a KTX2 container is turned, at load time, into whatever the GPU reads. The last part shows how RASM loads KTX2 files.

In short

  • A block format stores each 4 × 4 tile of texels in 8 or 16 bytes, where plain RGBA8 needs 64. The GPU decodes a block when it samples it, so the texture stays small in video memory.
  • PNG and JPEG are small on disk only: the GPU can't sample them, so they are decoded to RGBA8 before the upload.
  • Desktop GPUs read BC formats, mobile GPUs ASTC and ETC2. A Basis file (ETC1S or UASTC) is none of them, but it transcodes fast to any of them.
  • Pick the format per GPU and per use: color in BC7, a two-channel normal map in BC5, one channel in BC4, RGBA8 when the GPU has none of them.
  • A block format can't make its own mips cheaply, so the file brings them. Color space is a matter of how the same blocks are read: an sRGB or a UNORM view.

1Textures are most of the memory

A 2048 × 2048 color texture in RGBA8 is 16 MiB, and its mips add a third. A model with a base color, a normal map and an occlusion-roughness-metal map per material soon needs hundreds of megabytes.

2Blocks of 4 × 4 texels

Texels next to each other are often close in color. A block format cuts the texture into tiles of 4 × 4 texels. Each tile stores a few endpoint colors and, per texel, a short index that says where between the endpoints the texel lies. Every tile has the same size, so the GPU finds the tile of any texel with one multiply: it can sample at random, which a PNG's variable-length stream can't do.

The real formats add tricks on top of this picture: several pairs of endpoints for tiles with two regions, more index bits, a separate line for alpha. The families that matter today:

3Small on disk is not small on the GPU

A PNG or a JPEG packs the image with a method made for files: a stream that must be decoded from the start. The GPU can't sample that, so the loader decodes it to RGBA8, and that is what reaches video memory. A block-compressed file is already in the shape the GPU reads.

PNG or JPEG

Small file, full-size texture. The decode and the mips also cost CPU time at load.

Block-compressed (KTX2)

The file brings its mips; loading copies the blocks.

4One file for every GPU: Basis Universal

An engine that ships BC7 files can't run them on a phone, and ASTC files can't run on most desktop GPUs. Basis Universal stores a texture in an in-between format that no GPU samples, but that turns into any of them quickly, without the slow search a real encoder does. This step is called transcoding, and it runs on the CPU at load time.

ETC1S

Tiles share palettes of endpoints and index patterns, so files are tiny. Quality is lower: fine for base colors seen from afar, weak for normal maps.

About 1 to 2 bits per texel on disk.

UASTC

One 16-byte block per tile, a subset of ASTC, so it maps almost one to one onto BC7 and ASTC. Near BC7 quality; files are larger, so they are usually zstd-compressed.

8 bits per texel before zstd.

5The KTX2 container

KTX2 (Khronos texture, version 2) is the file around the data. It names the format with Vulkan's format numbers, stores every mip, and says what the channels mean and how the color is encoded. glTF reads it through the KHR_texture_basisu extension.

6Picking the format

Two things decide the target: what the GPU can sample, and what the texture is used for. Color is read as RGB and alpha. A normal map needs only x and y. Occlusion or a height map needs one channel. Each use has a list of formats, best first, and the loader takes the first one the GPU has.

7Normal maps in two channels

A tangent-space normal is a unit vector that points out of the surface, so z is never negative and follows from x and y. Storing only x and y lets a two-channel format spend all its bits on them: BC5 keeps each in its own BC4 half, with two 8-bit endpoints and a 3-bit index per texel, where BC7 shares its bits among three or four channels.

Basis keeps x in RGB and y in alpha (ktx create --normal-mode); its BC5 and EAC RG11 targets read those two, so the GPU format has x in R and y in G.

8Mips and color space

Mips come from the file

Making a mip of a block texture means averaging texels and encoding the result again, which takes an encoder and time. So the tool that makes the file makes the mips (ktx create --generate-mipmap). Without them, a texture shimmers when it is minified.

Color space is the view

BC7, ASTC and ETC2 have an sRGB and a UNORM format with the same bits. Pick it by the texture's use, as for any texture (color spaces): color is sRGB, data is linear.

9Pitfalls

Bumps look flat or lit from inside
A two-channel normal map read as three channels: z comes back as 0 (or −1). Rebuild z in the shader, or let the loader do it for an RGBA8 fallback.
Normal maps look blocky
ETC1S on a normal map. Use UASTC for normal maps and other data, ETC1S for colors.
Distant surfaces sparkle
A block texture without mips. The file needs them.
Colors too dark or washed out
A color texture read through a UNORM view, or a data texture through sRGB.
Odd sizes break the upload
A 30 × 30 texture still takes 8 × 8 whole blocks. Sizes and copies count blocks, not texels: a level is ⌈w / 4⌉ × ⌈h / 4⌉ × block bytes.

10In RASM

RASM reads KTX2 files with libktx (the KTX::ktx target of the vcpkg port ktx, built without its ETC software decoder: cmake/triplets/x64-windows.cmake). A .ktx2 passed to loadTexture and the images of glTF's KHR_texture_basisu go the same way: the format is picked from the header, the transcode runs on the load's worker thread, and the main thread only copies the levels.
