Culling and the frame

Render graphs

A frame is many passes: shadows, a G-buffer, lighting, post effects, UI. Each one reads what earlier ones wrote. A render graph (or frame graph) lets every pass declare what it reads and writes, and works out the rest: the order of the passes, which passes are not needed, the barriers between them and, in bigger engines, where in memory each texture lives. This page explains how. The last part shows what RASM's graph does.

In short

  • Each pass declares the resources it reads and writes. Passes never name each other.
  • "B reads what A writes" becomes an edge A → B. The passes and edges form a directed acyclic graph (DAG).
  • A topological sort (for example Kahn's algorithm) gives an order where every writer runs before its readers. A cycle means the frame cannot be ordered.
  • Passes whose results nobody reads can be culled.
  • Knowing every use of every resource, the graph emits the barriers and layout transitions itself.
  • Knowing every resource's lifetime, it can place short-lived (transient) textures in the same memory, one after another: aliasing.

1The problem

Without a graph, a frame is a hand-written list of passes. Each pass also carries the synchronization it needs, written by hand: "wait for the shadow map to be written, then move it to a layout for sampling". This works for three passes. With twenty, it breaks in quiet ways.

By hand, you mustWhat goes wrong
order the passesa pass reads a texture before it is written: last frame's data, or garbage

2The idea: declare, compile, execute

The frame graph was presented by Yuriy O'Donnell for Frostbite at GDC 2017, and most engines now have one. It splits the frame into three phases.

During setup, resources are only virtual: a handle and a description (size, format), no memory yet. A pass can create one (it lives only inside this frame: a transient resource), or import one from outside (the swapchain image, or last frame's color for temporal effects). Only compile decides where each transient resource really lives.

Here is a small frame used in the rest of the page. Passes are green, resources amber. An arrow into a resource is a write, an arrow out of it a read.

Versions: writing the same resource twice

Sometimes two passes write the same texture: transparent objects are drawn on top of the lit image. If both writes go to "HDR", the graph cannot tell whether Post wants the image before or after the transparent pass. So each write makes a new version of the resource, and a read names the version it wants.

4From declarations to edges

Two passes must be ordered when they touch the same resource and at least one of them writes it. These are the classic hazards:

5Sorting: Kahn's algorithm

A topological sort lists the nodes of a DAG so that every edge points forward. Kahn's algorithm (1962) does it by counting. A pass's in-degree is the number of edges into it: how many writers it still waits for. A pass with in-degree 0 can run now.

for each pass p:  inDegree[p] = number of edges into p
queue = every pass with inDegree 0, in the order they were added
while queue is not empty:
    p = queue.popFront()
    order.append(p)
    for each edge p → s:
        inDegree[s] -= 1
        if inDegree[s] == 0: queue.pushBack(s)
if order has fewer passes than the graph: there is a cycle

The five passes were added in the order Post, Lighting, Shadow, GBuffer, Debug (#0 to #4), on purpose: the order of adding does not matter, only the edges. Click through the sort.

1. Count the incoming edges

Shadow and GBuffer wait for nobody. They enter the queue in the order they were added: Shadow (#2) before GBuffer (#3).

2. Take Shadow

Each successor of the taken pass loses one incoming edge. Lighting still waits for GBuffer.

3. Take GBuffer

Two passes become ready at once. Either order is correct; this one keeps the order of the edges.

4. Take Lighting

Post becomes ready, behind Debug in the queue.

5. Take Debug, then Post

All 5 passes are in the order, so the graph has no cycle. The work is one visit per pass and one per edge: O(passes + edges).

6. When there is a cycle

No pass can start. A graph should report this as an error with the pass names, because it is always a mistake in the declarations.

Which order, among the valid ones

A DAG usually has many valid orders. Here, Debug could also run right after GBuffer. Kahn's algorithm with a FIFO queue in "order added" gives a stable, predictable answer. Engines that care pick on purpose:

Short lifetimes

Run a reader soon after its writer. The texture between them dies sooner, and its memory can be reused sooner (section 8).

Fewer stalls

Put independent work between a writer and its reader, so the barrier between them waits for work that is already done.

6Culling unused passes

A pass whose outputs nobody reads does not change the image. The graph can skip it. Start from the passes that write something that leaves the graph (an imported resource such as the backbuffer), and walk the edges backwards. Every pass that is never reached is culled.

This is what makes debug views free when they are off: the pass is still declared, but nothing reads its output. A pass with effects the graph cannot see, such as a readback to the CPU, must be marked so that it is never culled.

7Barriers and layout transitions

The GPU runs commands in parallel and keeps data in caches. A barrier makes later work wait for earlier work and makes its writes visible (see GPU synchronization). An image also has a layout: how its memory is arranged for one kind of use. The graph knows, for each pass in order, how it uses each resource, so it can work out both:

Declared useVulkan layoutStage and access to wait for or block
render into (color)COLOR_ATTACHMENT_OPTIMALcolor attachment output · color attachment write
render into (depth)DEPTH_ATTACHMENT_OPTIMALearly and late fragment tests · depth write
sample in a shaderSHADER_READ_ONLY_OPTIMALthe shader stages that read · shader read
write in a compute shaderGENERAL (images) · buffers have no layoutcompute shader · shader write
presentPRESENT_SRC_KHRnothing after it: the present engine waits on a semaphore

Two refinements are common. Split barriers signal at the end of the writer and wait just before the reader, so the GPU can work in between. And a pass is either all graphics or all compute, so the graph only needs to know the stage of the pass, not of every draw inside it.

8Transient resources and memory aliasing

After sorting, the graph knows each transient resource's lifetime: from the first pass that uses it to the last. Two resources whose lifetimes do not overlap can share the same memory. This is aliasing. Here is another small frame, a post-processing chain, with made-up but typical sizes:

Pass (sorted)0 GBuffer1 Lighting2 DoF3 MotionBlur4 Tonemap
G-buffer, 32 MiBwritereadread (depth)
HDR, 16 MiBwriteread
DoF, 16 MiBwriteread
MB, 16 MiBwriteread

Placing the resources is an interval packing problem. A simple greedy method works well: sort the resources by size, largest first, and put each one at the lowest offset where it overlaps no already-placed resource that is alive at the same time.

What aliasing needs

The resources come from one memory heap, with compatible memory types and alignment. Each one is created on that memory, not with its own allocation.

The catch

When a resource takes over memory, its old contents are garbage. Its first use must fully overwrite it (a clear, or a discard and a full write), and a barrier must separate the last use of the old resource from the first use of the new one.

9Async compute

Many GPUs can run a compute queue next to the graphics queue. Compute work that does not depend on the graphics work in flight can fill the gaps in it. The graph knows the dependencies, so it can move a compute pass to the other queue and put a semaphore on each edge that crosses between queues.

10Variants and pitfalls

  • Undeclared use is invisible. A pass that reads a texture without declaring it gets no edge and no barrier. Most graph bugs are missing declarations.
  • Persistent resources. Textures that live across frames (last frame's color for TAA, an exposure value) are imported, not transient. With frames in flight, they often need one copy per frame.
  • Rebuild or retain. Rebuilding the graph every frame makes dynamic frames easy (a pass is declared or not). Compiling once is cheaper, but every change needs a recompile.
  • Render pass merging. On tile-based mobile GPUs, passes that read the previous pass's output at the same pixel can be merged into one render pass with subpasses, keeping the data on chip.
  • One queue or many. Async compute adds cross-queue semaphores and makes resource ownership harder: a resource used on two queues needs a queue ownership transfer or concurrent sharing.

11In RASM

RASM's render graph is a small one. It sorts passes with Kahn's algorithm, and records the texture transitions and buffer barriers that their declarations need. It does not cull passes, does not manage memory, and runs on one queue. The graph is retained: you add the passes once, and RenderGraph::execute runs them every frame.

graph.addPass(
    "Forward",
    [&](rasm::PassBuilder &builder) // setup: runs once, inside addPass
    {
        rtHandle = builder.createRenderTarget({...});
        builder.write(rtHandle);
    },
    [&](rasm::RenderContext &) // execute: every frame
    {
        engine.drawScene(scene, camera);
    });

Texture state lives in RenderContext: rhi::TextureStates remembers each texture's last usage, so transitionImageLayout takes only the new one. If a recorded frame is never submitted, RenderContext::discardRecording puts the old states back. Buffers are reached through device addresses, so the graph cannot see them; it trusts the declarations. For each declared buffer it keeps a BufferAccess: the stage of the last write and the stages that read since. All of a pass's buffers fold into one global memoryBarrier. Render targets: one set per frame slot

RASM has no transient textures. A render target from PassBuilder::createRenderTarget is a normal, permanent resource, and it holds two sets of attachments, one per frame slot, so the CPU can record frame N+1 into one while the GPU still reads the other. Each color texture is in the bindless set; Engine::getRenderTargetTexture returns the current slot's. A reading pass looks it up in execute, every frame:

auto commandBuffer = engine.getCurrentFrameResources().commandBuffer;

Keep these true
  • Declare every resource a pass reads or writes with PassBuilder. An undeclared use is not sorted and gets no barrier.
  • Look up getRenderTargetTexture and its bindless index inside execute, every frame. They differ per frame slot.
  • No dispatch or memoryBarrier inside a graphics pass: RenderContext refuses both. Use addComputePass.
  • Change a texture's layout only through transitionImageLayout, which keeps the remembered state right. Recorded commands that are not submitted must be followed by discardRecording, as endFrame does.
  • Sorting, the compile checks and buffer barriers run on the CPU only. Add a test in tests/renderGraphTests.cpp when you change compile or bufferBarrier.
