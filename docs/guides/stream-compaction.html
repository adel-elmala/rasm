Culling and the frame

Stream compaction

Stream compaction takes a long list, keeps only the items that pass a test, and writes them into a new list with no gaps. On one CPU thread this is a simple loop. On a GPU, thousands of threads test at the same time, and each kept item must find its place without waiting for the others. This page explains the two answers: an atomic counter, and the prefix sum. The last part shows how RASM packs its visible draws.

In short

  • The goal: the kept items, packed (no gaps) and often in order (the same order as the input), plus their count.
  • Atomic append: every kept item takes the next slot from a shared counter. Simple and fast, but the order changes from run to run.
  • Prefix sum (scan): the place of an item is the number of kept items before it. It keeps the order, and needs no atomics.
  • Inside a workgroup the scan runs in shared memory (Hillis–Steele or Blelloch), or with one wave instruction per wave.
  • Across workgroups it needs a second level: scan the group counts, then add each group's base. Or one pass with decoupled look-back.
  • The count goes into a buffer that an indirect draw reads, so the CPU never waits for it.

1The problem

A GPU culling pass tests every object and keeps the visible ones. A particle system removes dead particles. A ray tracer keeps the rays that still bounce. Each time, the input is an array, the test gives a yes or no per item, and the next step wants only the yes items, side by side, so it can work on them without checking again.

On one thread, compaction is a loop with a write index that grows by one for each kept item. On a GPU each item has its own thread, and all of them run at once. Thread 6 (item g) cannot know that it goes to place 3 without knowing how many of threads 0 to 5 kept their item. That is the whole problem.

PropertyMeaningWhy it can matter
Packedno gaps between kept itemsThe next step runs one thread per kept item, or one draw per kept item, with no wasted work.
Stable (in order)kept items keep their input orderThe same input gives the same output every time. For draws, order decides which of two surfaces at equal depth wins, and how blending adds up.
Countedthe number of kept items is written somewhereThe next step must know where the list ends.

2The simple way: an atomic counter

Put one counter in memory, set to 0. Every thread whose item passes does an atomic add of 1 on it. The atomic returns the old value, which is a slot nobody else got. The thread writes its item there.

Good

One pass, a few lines, and fast when few items pass. The counter is the count, ready for the next step.

Not so good

The output order is not stable. When many threads hit one counter, the atomics are serialized, which costs time. The counter must be cleared before each use, which is one more command and one more barrier.

A common fix for the contention is to do one atomic per wave instead of one per thread (see section 5). The order is then stable inside each wave, but the waves still race. When order does not matter, for example for particles that are drawn with additive blending, atomic append is the right choice. When it does, use a prefix sum.

3Prefix sums

A prefix sum, also called a scan, replaces each item of an array with the sum of the items before it. There are two kinds. The exclusive scan does not count the item itself; the inclusive scan does.

Compaction is a scan of the flags

Give each item a flag: 1 if it passes, 0 if not. The exclusive scan of the flags tells each kept item how many kept items come before it. That number is its place in the output. The count is the last scan value plus the last flag.

Steps 1 and 3 are trivially parallel: each thread works alone. All the difficulty is in step 2, computing a scan with many threads. The next two sections do that, first inside one workgroup, then across many.

4A scan inside one workgroup

The threads of one workgroup share a small, fast shared memory (groupshared in HLSL and Slang) and can wait for each other with a barrier. Each thread puts its value into an array in shared memory, and the group then computes the scan in place, in a few steps with a barrier after each one.

The naive way

Each thread loops over the items before it and adds them up. Thread i does i additions, so the last thread of a 64-thread group does 63, and the whole group waits for it. The total work is n(n − 1) / 2. This is fine for small groups and very simple, but it does not scale.

Hillis–Steele: few steps, more work

In step k (k = 0, 1, 2, …), every item adds the item 2k places to its left, if there is one. After log2 n steps each item holds the sum of everything up to it: the inclusive scan.

Blelloch: two sweeps, less work

Blelloch's scan works like a tree. The up-sweep adds pairs, then pairs of pairs, and so on, until the last item holds the total. Then it sets the last item to 0 and the down-sweep walks back down the tree: at each node, the left child gets the parent's value, and the right child gets the parent's value plus the old left child. The result is the exclusive scan.

For 64 items: the naive loop does 2016 additions, Hillis–Steele 321 in 6 steps, Blelloch 126 in 12 steps. On a GPU, the number of barriers often matters more than the number of additions, which is why the next idea wins.

5Wave intrinsics

A GPU runs threads in fixed bundles called waves (AMD), warps (NVIDIA) or subgroups (Vulkan): usually 32 or 64 threads, called lanes, that run the same instruction together. Modern APIs let the lanes of a wave share values directly, with no shared memory and no barrier. Two of these instructions are made for compaction.

A workgroup of 256 threads holds several waves. Each wave scans itself with one instruction and writes its total to shared memory. After a barrier, one wave scans those few totals, and after a second barrier, each lane adds its wave's base:

Here is a compaction kernel in Slang that is in order inside each wave and uses one atomic per wave. It is the common "good enough" version when the order of the waves does not matter:

// One thread per item. In order inside a wave; the waves
// take their places in the order they reach the atomic.
void compactMain(uint3 id : SV_DispatchThreadID)
{
    bool keep = id.x < itemCount && passes(items[id.x]);
    // Kept lanes below this one, and kept lanes in the whole wave.
    uint slot = WavePrefixCountBits(keep);
    uint count = WaveActiveCountBits(keep);
    uint base = 0;
    if (WaveIsFirstLane())
        InterlockedAdd(counter[0], count, base);
    base = WaveReadLaneFirst(base);
    if (keep)
        output[base + slot] = items[id.x];
}

A thread past the end of the array gets keep = false instead of returning early. Here an early return would be harmless, because wave instructions skip inactive lanes, but a kernel with a group barrier must keep every thread running until the barrier.

6More than one workgroup

A workgroup can only see its own shared memory. To scan a million items, the groups must also learn how many items all earlier groups kept. The classic way is three passes, or two when the last pass also scans the block totals itself:

One pass: decoupled look-back

Merrill and Garland (2016) showed how to do it in one pass. Each block posts a small status record for the blocks after it. To find its base, a block reads the records of earlier blocks, from right to left, adding as it goes, and stops at the first one that already knows its full prefix.

1. The input

Nothing is known about the output yet, not even its size.

2. Test and flag

Each thread runs the test on its own item and writes a flag into shared memory.

3. Scan inside each group

After a barrier, each thread knows its local slot (its place among its group's kept items), and the group knows its count. The groups still do not know about each other.

4. Scan the group counts

This is a second, much smaller scan: one value per group. With a few groups it is one more workgroup; with many, it is the multi-level scheme of section 6.

5. Scatter

For example l: group 2 has base 4, and l has local slot 2, so it goes to place 6.

6. Write the count

The last group knows the total without any extra work: its base plus its own count. The rest of the output buffer keeps whatever it held before.

8Writing a count for an indirect draw

In GPU-driven rendering the compacted items are draw commands, and the count tells the draw how many there are. An indirect count draw (vkCmdDrawIndexedIndirectCount in Vulkan, ExecuteIndirect with a count buffer in Direct3D 12) reads both from buffers when it runs, so the CPU records the call before the GPU has even culled.

Who writes the countNeeds a clear first?Notes
Atomic append: the counter itselfyes, every frameThe clear must finish before the culling starts.
Ordered scan: the last group writes base + its countnoWritten fresh every time, so a stale value never survives.
No compaction: keep every draw, set its instance count to 0no count at allSimplest, but the GPU still reads and skips every culled command.

9Choosing a method, and pitfalls

MethodOrderDispatchesCost
Atomic per threadrandom1 (+ clear)contention when many pass
Atomic per wave, wave prefix insidestable inside a wave only1 (+ clear)low; the usual choice when order is free
Group scan + atomic per groupstable inside a group only1 (+ clear)low
Two or three passes (scan, then propagate)fully stable2 to 3reads the data twice
Decoupled look-backfully stable1the least traffic, the most code
  • Threads past the end must still run the group's barriers and wave instructions, with a flag of 0. An early return before a barrier is undefined behaviour.
  • Barriers between dispatches. The pass that reads the group counts must wait for the pass that wrote them. The draw that reads the count must wait for the pass that wrote it.
  • Capacity. The output buffer must hold the worst case: every item kept.
  • Segments. When the input is several lists back to back (one per material, say), each list needs its own count. Either make groups that never cross a list boundary, or use a segmented scan, which restarts the sum at each boundary.

10In RASM

RASM uses ordered compaction to pack the draws that survive culling (see frustum culling and occlusion culling). The input is a scene's draw list, one DrawInfo per sub-mesh, split into up to MAX_DRAW_RUNS runs of one cull mode each, because the cull mode is set once per indirect call. Each run is compacted on its own, and drawn with one drawIndexedIndirectCount. The scheme is two dispatches over groups of CULL_GROUP_SIZE = 64 draws, with no atomics for the positions.

countMain: one thread per draw

Each thread tests its draw and writes 1 or 0 to visibleFlags in shared memory. After GroupMemoryBarrierWithGroupSync, each thread adds up the flags of the threads below it: the naive loop of section 4. It stores its slot, with the chosen LOD above it (slot | lod << CULL_LOD_SHIFT), or CULLED, in cullSlotsPtr. The group's last thread writes the group's count to groupCountsPtr.

writeMain: one thread per draw again

Each group finds its base by adding the counts of all earlier groups of its run: thread t adds groups t, t + 64, …, into partialSums, and after a barrier every thread adds the 64 partial sums. A visible draw goes to drawInfoPtr[runFirst + base + slot], with its LOD's index range. Thread 0 of the run's last group writes drawCountsPtr[run] = base + its count.

When it runs

The culling is a compute pass of the render graph, Cull, before the pass that draws, Scene. Engine::addScenePasses adds both. Cull declares that it writes the visible draws and the draw counts, and Scene that it reads them, so the graph records one barrier between them. Inside Cull, Engine::recordSceneCulling records countMain, a COMPUTE → COMPUTE barrier and writeMain.

Keep these true
  • CULL_GROUP_SIZE is defined in cull.slang and in gpuScene.cpp. Change both, and the scratch size in getVisibleDrawBufferSize (one count per group, at most one group per 64 draws plus one per run).
  • A group must never cross a run. getCullGroup and the CPU's group count in Engine::prepareSceneView must agree.
  • Threads past the end of a run still reach every barrier, with visible = false. Do not return early in countMain or writeMain.
  • The count must be written every time the culling runs, by the run's last group. Nothing clears it.
  • A new pointer in SceneData is a CPU↔GPU struct change: follow the struct layout rules.
