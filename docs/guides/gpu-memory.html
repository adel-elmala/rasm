How data reaches the GPU

The CPU puts data into GPU buffers in two ways. A mapped buffer gets a plain memcpy at once. Any other buffer gets its data through a staging ring, and a GPU copy moves it at the next submit. Textures are different again: the CPU writes them directly with host image copy.

CPU work / CPU memory GPU work GPU buffer / memory

In short

  • Three kinds of buffer: hostVisible (the CPU rewrites it), hostReadable (the CPU reads it back) and the default, device-local.
  • RenderContext::fillBuffer asks one question: is the buffer mapped? Yes: memcpy now. No: UploadManager::upload, and the data arrives with the next submit.
  • The staging ring is 64 MiB (RING_SIZE). Writes are split into chunks of at most 16 MiB (MAX_CHUNK_SIZE). The upload fence tells when ring space is free again.
  • A GpuTable keeps a CPU copy of its rows and one buffer per frame slot. Each slot uploads only its dirty rows, merged into ranges.
  • Shaders find every buffer through its device address. Textures are filled on the CPU with vkCopyMemoryToImage, mips included.

1Three kinds of buffer

A buffer's kind is set by two flags in BufferDesc. VulkanDevice::createBuffer turns them into VMA flags, and VMA picks the memory type.

After creation, Buffer::mapped says which case you got. It is true when VMA returned a mapped pointer (pMappedData). The engine's own buffers are:

2Which path does fillBuffer take?

Mapped: a direct write

VulkanDevice::fillBuffer copies into mappedData and calls vmaFlushAllocation (a no-op on coherent memory). The bytes are there when the call returns. Nothing orders this write with the GPU. If a frame in flight reads that range, it can see half old and half new data.

Not mapped: a staged copy

The bytes go into the staging ring, and a BufferCopy is queued. The GPU copy runs at the next RenderContext::submit, before the frame. Its barriers wait for all earlier work on the queue, so it never overwrites data that an earlier frame still reads.

The safe rule for both paths: only write a range that no frame in flight reads. The engine does that in two ways. GPU tables have one buffer per frame slot (section 5). The geometry pool only writes new ranges that no frame has used yet (section 7).

3The staging ring

UploadManager owns one hostVisible buffer of RING_SIZE = 64 MiB. Two counters, head and tail, count bytes since the start and never wrap. head - tail bytes are in use, and head % RING_SIZE is where the next chunk goes. Click through a worked example (or use the arrow keys).

1. An empty ring

UploadManager::initialize creates the ring, an upload fence (a timeline, value 0) and two command buffers.

2. upload: 40 MiB into the vertex pool

Nothing has reached the GPU yet. The copy waits in pendingCopies, and pendingRanges remembers which bytes of the vertex pool this batch writes.

3. submit: the batch goes to the GPU

The batch stores fenceValue = 1 and ringEnd = head. Those two numbers are all the ring needs to free the space later.

4. Next frame: space comes back, a chunk skips to the start

reclaim never blocks: getFenceValue only reads the fence. A and B are separate copies, because B's source does not continue A's.

5. If the GPU is late: the ring is full

This wait stalls the CPU. It happens only when more than about 64 MiB are uploaded in one go, for example a big glTF in one frame.

Same dst, and the new copy's srcOffset and dstOffset both start where the last copy ends. The usual case: one big upload in chunks, or rows written in ascending order.

Starts a new batch

The new range overlaps the span of everything written to that dst in this batch (WrittenRange: lowest begin to highest end). The span is exact for ascending writes. For other orders it can cause a spare flush, never a missed one.

4Batches on the one queue

  1. Two command buffers take turns. batches[2] each hold a command buffer, the fence value of their last submit, the ring end and the buffers they wrote. Before flush reuses one, it waits until the fence reaches that batch's fenceValue.
  2. Each submit signals the next value. submittedValue + 1. Values only grow.
  3. A failed submit keeps its copies. They stay in pendingCopies and go out with the next flush. Their ring bytes are safe, because only a completed batch frees ring space.
  4. Destroying a buffer cancels its copies. RenderContext::destroyBuffer calls cancelUploads: pending copies to it are dropped, and it waits for a submitted batch that wrote it.

5GPU tables: one copy per frame slot

Two frames can be in flight (MAX_FRAMES_IN_FLIGHT = 2). A GpuTable has one buffer per frame slot, so the CPU can rewrite slot 0 while the GPU still reads slot 1. It also keeps a CPU copy of every row (shadow), and a dirty bit per row and slot (dirtySlots). The instance table and the material table are GpuTables. Here is one with 8 rows.

1. setRow(5), setRow(6), setRow(2)

setRow only touches CPU memory. It copies the row into shadow and, for each slot whose bit was clear, adds the row to that slot's dirtyRows list.

2. Frame in slot 0: upload(ctx, 0)

mergeRows sorts the rows and joins neighbours into RowRanges. Each range is one fillBuffer call from shadow. Slot 1 is still read by the GPU, so it is not touched.

3. setRow(6) again, before slot 1's frame

A row that changes ten times between two uploads is still sent once per slot. The upload always reads the newest value from shadow.

4. Frame in slot 1: upload(ctx, 1)

If a fillBuffer fails, upload keeps the rows dirty, and that slot sends them all again in its next frame.

upload runs in syncGpuScene, after the fence wait for the frame's slot (frameCount). So the GPU is done with that slot's buffer, on both fillBuffer paths. See The GPU scene tables for what fills the rows.

6Device addresses: how shaders find the buffers

VulkanDevice::createBuffer asks for the address once (vkGetBufferDeviceAddress) and stores it in Buffer::deviceAddress. RenderContext::getBufferDeviceAddress returns it, or logs an error and returns 0. The address of a slot buffer is different from the other slot's, so drawScene writes this slot's addresses each call. The full chain is in Drawing with the uber shader.

7The geometry pool

All meshes share these three default (device-local) buffers. They have one copy, not one per frame slot. That is safe because GeometryPool::upload only writes a new range at the end, which no frame has read yet. Their size is fixed when the engine starts:

8Textures: host image copy and CPU mips

  1. Create. VulkanDevice::createTexture gives a full mip chain only to TextureUsage::SAMPLED images in R8G8B8A8_UNORM, R8G8B8A8_SRGB or B8G8R8A8_SRGB. Render targets and other formats get one level. Sampled images use VK_IMAGE_USAGE_HOST_TRANSFER_BIT and a dedicated allocation.
  2. Change the layout on the CPU. vkTransitionImageLayout moves every level from VK_IMAGE_LAYOUT_UNDEFINED to VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL.
  3. Build the mips on the CPU. Level 0 is the input; each next level is half the size of the one before.
  4. Copy. vkCopyMemoryToImage with one VkMemoryToImageCopy per level. This needs VK_EXT_host_image_copy (core in Vulkan 1.4) and the hostImageCopy feature.

The input must be RGBA8 and exactly width × height × 4 bytes. Color and emissive textures are R8G8B8A8_SRGB; normal, metallic-roughness and occlusion maps are R8G8B8A8_UNORM. More in Materials and bindless textures.

Known issue: P2

Sampled images ask for host-access memory flags, which can push them out of the fastest memory. The mip chain is built on the main thread, inside finishLoads. There is no staging fallback for GPUs without the hostImageCopy feature.

9Reading a buffer back

  1. Create it hostReadable. RenderContext::readBuffer refuses any other buffer.
  2. On the GPU: a barrier to the host. memoryBarrier(..., PipelineStage::HOST) after the shader writes. Culling ends with COMPUTE → GRAPHICS | HOST for this.
  3. On the CPU: wait for the fence of the submit that wrote it.
  4. Read. VulkanDevice::readBuffer calls vmaInvalidateAllocation, then copies out.

The engine does this for the cull stats: updateFrameStats reads the slot's cullStats buffer right after beginFrame waited for that slot's fence. See Frame stats and the overlay.

11Rules when you change it

Keep these true
  • Never fillBuffer a range that a frame in flight reads. On a mapped buffer the write lands at once, with no ordering. Use one buffer per frame slot, or a new range.
  • GPU scene tables are written only in syncGpuScene, after that slot's fence wait. Change rows through GpuTable::setRow, never by writing a slot's buffer.
  • Staged data arrives with the next submit, not when fillBuffer returns. Do not read it back earlier.
  • Read only hostReadable buffers, and only after a barrier to PipelineStage::HOST and a fence wait.
  • createBuffer always makes a new buffer (B1). Destroy the one you replace, and only when no frame in flight uses it. There is no deferred destruction (D4).
  • A chunk must never wrap in the ring. Keep MAX_CHUNK_SIZE at most a quarter of RING_SIZE, so padding plus a chunk always fit in an empty ring.
  • Normal, metallic-roughness and AO textures are R8G8B8A8_UNORM; color and emissive are R8G8B8A8_SRGB.
