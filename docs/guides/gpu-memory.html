GPU data

GPU memory and uploads

A GPU reads its data fastest from its own memory, but the data starts on the CPU. This page explains the kinds of GPU memory, how the CPU writes into them, and the usual ways to move data across: mapped writes, staging copies, ring buffers and per-frame copies. The last part shows how RASM does it.

CPU work / CPU memory GPU work GPU buffer / memory

In short

  • A discrete GPU has its own fast memory (VRAM). The CPU reaches it only across the PCIe bus, if at all.
  • The API lists memory types with flags: device-local (fast for the GPU), host-visible (the CPU can map it), coherent, cached.
  • Memory the CPU cannot map is filled with a staging copy: the CPU writes a host-visible buffer, and the GPU copies it over.
  • A ring buffer reuses one staging buffer forever. A fence tells when the GPU has finished reading each part.
  • Many small copies go out in one batch. Barriers order them against the frames that read the data.
  • Data the GPU reads every frame and the CPU changes every frame needs one copy per frame in flight.
  • Engines sub-allocate: a few big memory blocks, with many buffers inside each.

1Two memories, one bus

A discrete GPU is a card with its own memory chips, called VRAM. VRAM is very fast for the GPU: hundreds of GB/s, sometimes more than 1 TB/s. The CPU's memory (system RAM) is on the other side of the PCIe bus, which is much slower: about 16 GB/s for PCIe 3.0 x16, about 32 GB/s for PCIe 4.0 x16. An integrated GPU (most laptops, phones, Apple silicon) has no VRAM: CPU and GPU share the same RAM.

2Heaps and memory types

Vulkan (and Direct3D 12 and Metal, with other names) describe the memory as heaps and memory types. A heap is a pool of physical memory with a size. A memory type is a way to use a heap, described by flags. Every allocation picks one memory type.

FlagMeaning
device-localFast for the GPU. On a discrete GPU this is VRAM.
host-visibleThe CPU can map it: get a normal pointer and write or read with memcpy.
host-coherentCPU writes become visible to the GPU without an extra call (and the other way round).
host-cachedCPU reads go through the CPU cache, so reading is fast. Without it, reads are very slow.

Write-combined memory

Host-visible memory that is not cached is usually write-combined: the CPU collects writes in a small buffer and sends them over the bus in big pieces. Writing it in order, once, with memcpy, is fast. Reading it, or writing scattered bytes, or doing x += 1 on it, is very slow, because each read crosses the bus. So treat mapped upload memory as write-only.

Coherent or not

Coherent

After the CPU writes, the bytes are visible to the GPU at the next submit. Nothing else is needed.

Not coherent

After writing, the CPU must flush the range (vkFlushMappedMemoryRanges). Before reading what the GPU wrote, it must invalidate the range. Ranges are rounded to nonCoherentAtomSize, a device limit of up to 256 bytes.

4The staging ring

Making a new staging buffer for every upload is slow, and freeing it needs to wait for the GPU copy. Instead, engines keep one big staging buffer and use it as a ring. Two counters describe it: head, where the next write goes, and tail, the oldest byte the GPU may still read. Bytes between them are in use. A fence (or a timeline value) per submitted batch tells when its bytes are free again.

This example uses a 64 MiB ring. A piece is never split across the end of the ring; a piece that does not fit before the end skips to the start. Click through it.

1. An empty ring

Counters that never wrap make the math simple: head − tail is the space in use, and head mod size is the next position.

2. Upload 40 MiB

Nothing has reached the GPU yet. The copy command waits in a list until the next submit.

3. Submit: the batch goes to the GPU

The CPU does not wait. It goes on recording the next frame.

4. Next frame: space comes back, a piece skips to the start

Checking a fence value does not block. The ring only learns about finished batches; it never waits for them here.

5. If the GPU is late: the ring is full

This wait stalls the CPU. It only happens when more than a ring's worth of data is uploaded before the GPU catches up, for example a big level loaded in one frame.

The ring size is a trade-off. Bigger means fewer stalls but more memory that sits idle most of the time. As a rough number: at about 25 GB/s over PCIe, copying 64 MiB takes about 2.7 ms, so a 64 MiB ring can move a lot per frame before the bus itself becomes the limit.

5Batching and ordering the copies

A copy command is cheap, but a submit is not. So uploads are collected and sent as one batch: one command buffer with many copies, submitted once per frame, before the frame's own work.

TopicWhat to know
MergingTwo copies whose source and destination ranges both continue each other become one bigger copy.
Overlapping writesCopies in one batch have no barrier between them, so their order is not defined. Two writes to the same bytes in one batch must go into two batches (or the second must replace the first on the CPU).
A transfer queueMany GPUs have a separate copy queue that runs next to the graphics queue. Copies there do not slow the frame, but they need a semaphore to order them, and buffers may need a queue ownership transfer. See GPU synchronization.
Destroying a buffer with pending copiesDrop its pending copies, and wait for submitted batches that write it. Otherwise the GPU copies into freed memory.

6Sub-allocation

Asking the driver for memory (vkAllocateMemory) is slow, and the number of live allocations is limited: the Vulkan spec only promises 4096 (maxMemoryAllocationCount). A scene can have far more buffers than that. So engines allocate a few big blocks and place many buffers inside each one: sub-allocation.

AllocatorHow it worksGood for
Linear (bump)One pointer that only moves forward. Free all at once by resetting it.Data that lives exactly one frame, or forever (load once, never free).
RingA linear allocator that wraps around, freed in the order it was used (section 4).Staging, per-frame constants.
Free list (or TLSF)Keeps a list of free ranges; finds one big enough; merges neighbours on free.General buffers and textures of mixed sizes and lifetimes.
PoolMany slots of one fixed size.Many objects of the same size.

Most Vulkan engines do not write this themselves. The Vulkan Memory Allocator (VMA) library from AMD picks memory types from usage hints, manages blocks with a free-list allocator, and handles alignment, dedicated allocations and memory budgets. Direct3D 12 has the same idea in D3D12MA.

7Changing data the GPU is reading

The CPU is usually a frame ahead of the GPU (see Frames in flight). If the CPU writes a buffer while the GPU still reads it for the previous frame, the GPU can see half old and half new data. A staging copy is safe (its barrier waits), but a direct mapped write is not ordered at all.

Per-frame copies

Simple and fast. Costs N times the memory. Every change must be sent N times, once to each copy.

Write only new ranges

For data that only grows (a mesh pool), write each new range once, in a part no frame has read yet. One copy is enough.

8Textures

A texture is not stored row by row in GPU memory. The GPU uses an optimal tiling: a hidden, vendor-specific order (blocks, swizzles) that makes nearby texels close in memory. The CPU cannot write that order itself. So textures need either a copy command or a special CPU path.

Mip levels add about a third: a 4096 × 4096 RGBA8 texture is 64 MiB, and 85 MiB with all its mips. Formats with block compression (BC7, ASTC) cut that by 4× or more, and are usually made offline. See Mipmaps and texture sampling.

9Reading data back

Sometimes the CPU needs a result the GPU computed: a count, a picked object, a timing. Reading back has its own steps, in this order:

  1. Use host-cached memory. Reading write-combined memory is very slow (section 2). Ask for host-visible and host-cached.
  2. On the GPU: a barrier to the host. After the shader or copy that writes the data, a barrier with the host as the destination stage makes the writes available to the CPU.
  3. On the CPU: wait for the fence. Wait for the fence of that submit. Until then the data may not be there yet.
  4. Invalidate, then copy. If the memory is not coherent, invalidate the range first. Then copy the bytes out.

Waiting for this frame's fence would stall the CPU until the GPU catches up. So engines read results a frame or two late: in frame N they read what frame N − 2 wrote, after the fence they already wait for anyway.

10In RASM

RASM uses VMA for all memory. A buffer is one of three kinds, set by two flags in BufferDesc. RenderContext::fillBuffer then picks path A or B of section 3 by itself: a mapped buffer gets a memcpy, any other buffer goes through the staging ring in UploadManager.

Keep these true
  • Never fillBuffer a range that a frame in flight reads. On a mapped buffer the write lands at once, with no ordering. Use one buffer per frame slot, or a new range.
  • GPU scene tables are written only in syncGpuScene, after that slot's fence wait, through GpuTable::setRow.
  • Staged data arrives with the next submit, not when fillBuffer returns.
  • Read only hostReadable buffers, and only after a barrier to the host stage and a fence wait.
  • createBuffer always makes a new buffer (B1). Destroy the one you replace, and only when no frame in flight uses it.
  • Keep MAX_CHUNK_SIZE at most a quarter of RING_SIZE, so a skipped end plus a chunk always fit in an empty ring.
  • Normal, metallic-roughness and AO textures are R8G8B8A8_UNORM; color and emissive are R8G8B8A8_SRGB.
