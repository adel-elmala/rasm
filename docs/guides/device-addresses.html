GPU data

Buffer device addresses

A shader usually finds its buffers through numbered binding slots. With buffer device addresses it gets a 64-bit pointer instead, and reads memory through it like C code does. This page explains how that works, what it costs, and what can go wrong. The last part shows how RASM does it.

In short

  • Every buffer lives at some GPU virtual address. The API can tell you that address as a plain 64-bit number.
  • A shader can treat the number as a pointer: p[i], p->field, p + n. No descriptor, no binding slot.
  • Pointers can be stored inside buffers, so data can link to other data: a tree of tables reached from one root pointer in a push constant.
  • The price: no bounds checks, no type checks, and the address dies with the buffer. A bad pointer reads garbage or loses the device.
  • Textures and samplers still need descriptors. Buffer addresses replace only the buffer bindings.

1How shaders usually find buffers

In the classic model, a shader declares buffers at fixed binding slots: "set 0, binding 2 is the material buffer". Before a draw, the CPU fills a descriptor for each slot (which buffer, which range) and binds the descriptor set.

2The idea: a GPU pointer

The GPU has a virtual address space, just like a CPU process. Every buffer is placed somewhere in it. A device address is the 64-bit number where the buffer starts. A shader that knows the number can read the buffer directly, with no descriptor in between.

3Getting an address in Vulkan

The feature is buffer device address. It started as the extension VK_KHR_buffer_device_address and is core since Vulkan 1.2. Four steps:

  1. Enable the feature. Turn on bufferDeviceAddress when the device is created. Shaders that use 64-bit pointers usually also need shaderInt64.
  2. Mark the buffer. Create it with the usage bit SHADER_DEVICE_ADDRESS.
  3. Mark the memory. Allocate its memory with the flag DEVICE_ADDRESS (a memory allocator library can do this for you).
  4. Ask. vkGetBufferDeviceAddress returns the 64-bit address. It does not change while the buffer lives, so ask once and keep it.

4Pointers in a shader

Here is a compute shader in Slang that moves particles. The push constant holds a pointer to the particle array and a count. There are no buffer bindings at all.

struct Particle
{
    float3 position;
    float3 velocity;
};

struct Params
{
    Particle *particles;
    uint count;
    float deltaTime;
};

[[vk::push_constant]]
ConstantBuffer<Params> params;

void update(uint index)
{
    if (index >= params.count)
        return;
    Particle *p = params.particles + index;
    p->position += p->velocity * params.deltaTime;
}

The pointer math is the same as in C. particles + index means "index elements further", so the byte address is the base plus index × the size of one Particle. The size comes from the struct layout the shader is compiled with; see Struct layout rules.

A worked example

A table of rows that are 108 bytes each, in a buffer at address 0x1_0020_0000. The shader wants field m of row 5. The field starts 64 bytes into the row.

Each arrow is a memory read that must finish before the next address is known. A deep chain adds latency. In practice the first two levels are the same for every thread of a draw, so they stay in the cache and cost little.

Sub-arrays in one buffer

Because a pointer can point anywhere inside a buffer, one allocation can hold several arrays one after another. Each gets its own pointer: the base plus the size of the arrays before it.

6Alignment

A load through a pointer must be aligned: the address of a value must be a multiple of that value's alignment. A float needs a multiple of 4, a 64-bit integer or pointer a multiple of 8. A misaligned access is undefined behaviour: on some GPUs it works, on others it reads the wrong bytes.

7Lifetime and safety

An address is just a number. Nothing ties it to the buffer it came from, so all the classic pointer bugs are possible:

BugWhat happensHow engines avoid it
Out of bounds: index past the endReads another buffer's bytes, or faults. The robust-access features do not cover pointer access.Pass counts next to pointers and check them; size tables from known limits.
Use after free: the buffer was destroyedThe address may now belong to another buffer, or to nothing: garbage, or a lost device.Destroy only after the frames that could use it are done (Frames in flight).
Stale address: the buffer was recreated (for example to grow it)The new buffer has a new address. Old copies of the old one point at freed memory.Write the addresses again every frame, from the current buffers.
Null: an unused pointer left at 0Reading address 0 faults, usually a lost device.A flag or count next to the pointer says whether it may be read.
Wrong typeThe shader reads the bytes as a different struct. No error.Keep CPU and GPU struct definitions in sync, and check them (Struct layout rules).

Tools help a little. The Vulkan validation layers have a GPU-assisted mode that can check some pointer accesses at run time. Capture tools such as RenderDoc need the bufferDeviceAddressCaptureReplay feature to replay a frame with the same addresses.

Modern GPU-driven renderers usually mix the two: device addresses for all buffers, and one big array of texture descriptors for all images (see Bindless resources).

9In RASM

RASM binds no buffer through a descriptor. Every buffer gets a device address at creation, and shaders reach all scene data from one root pointer in a 16-byte push constant: the pattern of section 5. Textures go through the bindless descriptor set.

The vertex shader in shaders/passes/rasm.slang follows the chain like this (spacing changed):

DrawInfo *draw = pc.scene->drawInfoPtr + getDrawIndex();
InstanceData *instance = pc.scene->instancesPtr + draw->firstInstance;
VertexFull vert = pc.scene->vertsPtr[input.vertexID + draw->vertexOffset];

And Engine::prepareSceneView in src/renderer/gpuScene.cpp does the CPU-side pointer math for the sub-arrays (line breaks added):

sceneData.cullSlotsPtr =
    sceneData.drawInfoPtr + static_cast<uint64_t>(visibleCapacity) * sizeof(gfx::DrawInfo);
sceneData.groupCountsPtr =
    sceneData.cullSlotsPtr + static_cast<uint64_t>(visibleCapacity) * sizeof(uint32_t);

Keep these true
  • Write every address in SceneData from the current buffers every frame; never cache an address across a buffer that can be recreated or resized.
  • Destroy a buffer only when no frame in flight can still read its address.
  • A pointer that is 0 must not be read. Guard it with a count or a flag, like hizLevelCount.
  • Keep 64-bit fields at 8-byte aligned offsets in every shared struct. SceneData and PushConstants are CPU↔GPU structs: follow the struct contract.
